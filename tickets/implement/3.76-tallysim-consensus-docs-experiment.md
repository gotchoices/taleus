## Design doc (primary deliverable)

Extend `packages/tallysim/docs/design.md`'s **Consensus simulation** section with:

- **The consensus metrics** (`sim/consensus-metrics.ts`): `pCommitGivenFound` headline (commit ÷ found,
  0-never-NaN), `timeToSettleMs` (over settled lifts = commit|void; omitted for pending),
  `messagesPerLift` (record-pushed counts), and the four-reason `voidReasons` tally
  (`refused-promise` / `voted-no-commit` / `stalled` / `expired`) with its **precedence** (outcome-driven:
  commit→none; pending→stalled always; void→expired>refused-promise>voted-no-commit). Note it's a
  compile-checked source of truth (`zeroVoidReasons()`), the `pruneReasons` pattern.
- **The failure-injection knobs + their dedicated seed streams**: the NEW `consensus.refuserFraction`
  (drawn from `consensusSeed`, an independent stream — "do not perturb the discovery streams"), and that
  the sleeper / dropped-push / slow-voter failures reuse the existing `conditions` block (they degrade
  BOTH discovery and consensus because `pushCondition` reuses the per-link conditions map). Include the
  **sleeping/dropped TARGET → stall** mechanism (discovery peer-matches the terminus without delivering,
  but the consensus push to it drops ⇒ the lift stalls on one build), and the v1 asymmetry note (a dropped
  push on a needed edge stalls; phase-2 "a refuser only hurts itself" is OUT of v1), cross-referencing
  `feat-tallynet-propagation-timeouts`.
- **The sequential-lift invariant**: consensus runs sequentially; a sequence of lifts mutates the one kept
  network in order, so balances between lifts are defined only under a fixed lift order; there is no
  concurrent consensus mode.
- **The metrics runner rebuilds the sim per query** (to see each committed lift's changed capacity) vs
  **the trace uses one sim with throwaway clones** (no depletion, monotonic clock, unique codes for the
  viewer join) — the deliberate, documented difference.
- **The v2 trace-header `lifts[]` extension**: the `TraceLiftEntry` shape, why it's needed (consensus
  events key by member pubkey, not entity id; the route isn't in the discovery stream), and the
  **"events no-bump / header bump"** distinction. Reader accepts versions {1, 2}; `lifts` optional.

Keep the prose timeless and readable for someone without this context (de-jargon per the workflow rules).

## Experiment (STRETCH — the seeded tests in the runner ticket are the primary proof; skip if time-boxed)

`experiments/commit-vs-found/` — a modest grid mirroring `experiments/found-vs-oracle/`: a small `N`, a few
seeds, ~50 queries, varying e.g. `consensus.refuserFraction` and/or `conditions.dropFraction`, with the
`consensus` block enabled. A `regenerate.sh` (copy the found-vs-oracle one; stream with `tee`, well under
~10 min, byte-identical reproduction) drives `node dist/cli/consensus.js` per spec into `out/*.{jsonl,csv}`
and concatenates a combined `commit-vs-found.jsonl`. **Keep latencies well under the code TTL** (600_000 ms;
`VirtualClock` starts at 0) or an expired code changes the outcome — document the ceiling in the README. A
short `README.md` states the headline question (how often does a found route actually commit, and why do
the rest fail) and what the data shows.

a non-existent experiment folder).
