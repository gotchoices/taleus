# tallysim — the oracle

Second of three chained implement tickets in the network-model tier (after `tallysim-model-generators`,
before `tallysim-runner`). The **oracle** is code that sees the *whole* graph and searches it directly —
the ground truth the later `tallysim-discovery` tier measures the real routing protocol against
("found vs. oracle"). Keeping the two apart is the point: when a lift fails, the oracle tells you whether
the **network** could ever have carried it, separating that from whether the **protocol** found it.

Depends on the network model + generators from `tallysim-model-generators` (the `Network`/`Tally` types,
the capacity model, the generators used to build test graphs). Stays **platform-neutral** (the viewer
runs the oracle live in a page): no Node globals, no `Math.random`, no result depending on unordered-key
iteration.

## Compiled graph view

The serialisable `Network` is convenient to build and store but slow to search. Compile it once into a
**directed capacity graph** for the oracle:

- Each tally becomes **two directed capacity edges**, `stock→foil` and `foil→stock`, with capacities from
  the model's `cap(S→F)` / `cap(F→S)` (see `tallysim-model-generators` § Capacity model).
- Store it CSR-style (compressed sparse row): per source entity, a contiguous slice of
  `(targetEntity, capacity)` pairs. Use **typed arrays** — `Int32Array` for targets/offsets, and a
  `Float64Array` for capacities so `Infinity` (unlimited) is representable directly.
- Build must be deterministic (edges emitted in tally order; neighbour slices in a defined order).

**Performance target** (parent plan's third design point): 10,000 entities × mean degree 10, and
~1,000 oracle route-existence queries, must run in **seconds, not minutes**. CSR + typed arrays + reused
scratch buffers (a visited array cleared per query, or a generation-stamp array to avoid re-allocation)
are the way to hit it. Route-existence/shortest-path (BFS) is cheap at this scale; max-flow is the
expensive metric — see its note below.

> NOTE (tripwire, record at the capacity array in code): capacities are `number` (`Float64Array`), so a
> simulated capacity above 2^53 would lose integer precision. Fine for all planned scenarios (simulated
> units stay small). *If* a scenario ever needs capacities beyond 2^53, switch the capacity store to
> `BigInt64Array` and the oracle arithmetic to `bigint`. Not work now — a conditional.

## Oracle queries

Name each algorithm in `docs/design.md`; keep each a small, separately-tested function.

- **Route existence + shortest length** — for a payment of amount `A` from `X` to `Y` with max depth `D`:
  **bounded breadth-first search (BFS)** from `X` over only the directed edges with `capacity ≥ A`,
  stopping at depth `D`. Returns `{ exists, shortestLength }` (`shortestLength` = the BFS level at which
  `Y` is first reached, `≤ D`). BFS gives the shortest hop count for free.
- **Self-payment / circular clearing (`X === Y`)** — a payment to oneself is a **cycle**, not a
  zero-length path: search for a directed cycle through `X` with every edge `capacity ≥ A`, bounded by
  depth `D`. Returns existence + shortest cycle length. (Do **not** report length 0.)
- **Max-flow `X → Y`** — maximum value payable, not just whether one unit is: **Edmonds–Karp**
  (BFS-augmenting-path Ford–Fulkerson) on the directed capacity graph. This answers "how much is payable"
  (the parent plan's "useful to see how much, not just whether"). Document that this metric is
  **not depth-bounded** (depth-bounded max-flow is a different, harder problem; out of scope) — it is the
  "ignoring depth, how much could flow" figure, complementary to the depth-aware route-existence query.
  > NOTE: Edmonds–Karp is `O(V·E²)`; on 10k-node graphs it is far costlier than BFS. The `tallysim-runner`
  > tier must compute max-flow on a **sampled subset** of queries (or only on request), never on every
  > query in a 10k sweep. Record this as guidance in design.md so the runner respects it.
- **Clearing-cycle availability** — for a node and amount `A` up to depth `D`: how many directed cycles
  with spare capacity (`min edge capacity ≥ A`) pass through the node. A bounded DFS from the node seeking
  returns to the start; **cap the count** (e.g. stop at a configurable maximum, since cycle counts explode)
  and also report the shortest such cycle's length. This feeds the clearing metric.

All amounts/capacities compared as the model's integers (represented in `Float64Array`; see the tripwire).
`A = 0` / `A ≤ 0` should be handled explicitly (document: treat `A ≤ 0` as "any edge qualifies" or reject —
pick one and test it).

## Brute-force verification harness

The oracle's correctness rests on cross-checking its bounded searches against an **independent exhaustive
enumeration** on small graphs (≤ 10 nodes): enumerate every simple path / cycle up to depth `D` directly
and compare existence, shortest length, and capacity/depth respect. For max-flow, verify against a second
independent computation on tiny graphs (e.g. a brute-force min-cut, or an alternative max-flow
implementation). Keep the brute-force code in the test tree (it is a test oracle, intentionally slow).

## Edge cases & interactions

- **Self-payment (`X === Y`)** is a cycle, never a zero-length path.
- **Disconnected graphs / isolated endpoints:** `X` or `Y` isolated ⇒ no route; `exists = false`,
  `shortestLength` undefined; max-flow 0.
- **Duplicate tallies between a pair** become two directed edges in each direction — capacities add along
  parallel edges for max-flow; route existence just needs one qualifying edge.
- **Zero-capacity directions** are pruned by the `capacity ≥ A` filter (and by `A > 0`).
- **Depth boundary:** a `Y` reachable only at depth `D+1` must report `exists = false` at depth `D`
  (off-by-one: a 1-hop path is length 1; `D` counts hops).
- **Capacity boundary:** an edge with `capacity === A` qualifies (`≥`, not `>`); `capacity === A-1` does not.
- **Complete / very dense graphs** at the perf target must not blow memory (CSR, not an adjacency matrix).
- **Determinism:** neighbour iteration order is the CSR order; no result depends on unordered-key iteration.

## Tests to plan

- **Oracle vs. brute force** on seeded random small graphs (≤ 10 nodes, generators from the previous
  ticket): route existence, shortest length, self-payment cycle, clearing-cycle count all match exhaustive
  enumeration; **capacity respected** (a route using an under-capacity edge is never reported);
  **depth respected** (nothing beyond `D`).
- **Max-flow** matches the independent computation on tiny graphs; parallel-edge capacities add; a
  min-cut equals the max-flow value.
- **Boundary tests:** `capacity === A`, depth `D` exactly, isolated endpoints, `X === Y`, `A ≤ 0`.
- **Performance smoke:** a 10,000-entity × mean-degree-10 graph with ~1,000 BFS route-existence queries
  completes in seconds (assert a generous wall-clock ceiling, not a tight one — CI machines vary).
- **Determinism:** same graph + same query ⇒ identical result, run twice.
