Today the viewer (sigma.js, 2D) pans by dragging and zooms by wheel or pinch, but nothing on screen says so,
and there are no buttons. A developer tried it and didn't find the controls.

This ticket is self-contained inside the graph tier: everything lives in `src/graph/render.ts` (the one
browser-only sigma module, already building the tooltip and WebGL-missing DOM the same way), plus new CSS
classes in `src/app/styles.ts`. **`src/app/shell.ts` does not need to change** — the `GraphView` interface
gains no new methods, because nothing outside `render.ts` needs to trigger a camera action. Keep
`src/core/`, `src/graph/model.ts` and `src/graph/layout.ts` untouched.

## Design (resolved)

sigma's `Camera` (`node_modules/sigma/dist/declarations/src/core/camera.d.ts`) exposes `x`, `y`, `angle`,
`ratio` getters, `animate(state, options)`, `zoomIn(options)`, `zoomOut(options)` and `reset(options)`.
`DEFAULT_CAMERA_STATE` is `{x: 0.5, y: 0.5, angle: 0, ratio: 1}` — sigma auto-rescales the graph's node
extent to fit exactly that normalized frame (`autoRescale`/`getGraphDimensions`), so **that default state
already *is* "whole graph, unrotated, fitted to the viewport."** Two consequences that remove the need for
any manual bounding-box math:

- **Fit to graph** = `camera.animate({x: 0.5, y: 0.5, ratio: 1}, {duration})` — re-frames the whole graph but
  **keeps the current rotation angle**. At a non-zero angle this still uses the axis-aligned extent/ratio, so
  a rotated non-square graph can have its corners clipped — acceptable for a dev tool; do not add rotated-bbox
  math to compensate (scope creep for an "easy" ticket).
- **Reset** = `camera.reset({duration})` — the full `DEFAULT_CAMERA_STATE`, i.e. Fit plus `angle: 0`. This is
  also exactly the camera's state right after a fresh `createGraphView` mount.
- **Zoom in / out** = `camera.zoomIn(options)` / `camera.zoomOut(options)` — reuse sigma's own
  `zoomingRatio`/`zoomDuration` settings, so button and keyboard shortcut behave identically to the existing
  wheel zoom.
- **Rotate left / right** = `camera.animate({angle: camera.angle ± ROTATE_STEP}, {duration})`. Programmatic
  `animate()` ignores `enabledRotation` (that flag only gates captor/mouse-driven rotation), so this works
  regardless of sigma's rotation settings.
- **Pan (arrow keys)** = `camera.animate({x: camera.x ± PAN_STEP_FRACTION * camera.ratio, y: ...})` — scaling
  the step by the current `ratio` keeps pan speed proportional to zoom level (a fixed-distance step would feel
  too fast when zoomed out, too slow when zoomed in).

Suggested constants (tune by feel during manual testing, these are starting points):
`ROTATE_STEP = Math.PI / 12` (15°), `PAN_STEP_FRACTION = 0.1`, a short `duration` (150–250ms) for all
button/key-triggered `animate()` calls so repeated presses feel snappy, not laggy.

### On-screen control cluster

A small `<div class="tsv-camera-controls">` of plain `<button type="button">`s, absolutely positioned inside
the graph `container` (which is already `position: relative` — the same pattern the tooltip and
WebGL-missing message already use), e.g. bottom-right corner. Six buttons: zoom in (`+`), zoom out (`−`),
Fit, Reset, rotate left (`↺`), rotate right (`↻`). Give each an `aria-label` (e.g. `"Zoom in"`) since the
glyphs alone aren't self-describing. Reuse the existing `#tsv-app button` styling (add a positioning/layout
class in `styles.ts`, not a whole new button skin).

### Keyboard shortcuts — scoped to the graph, not the document

Requirement: shortcuts fire "only while the graph has focus, never while typing in search or other inputs."
Resolve this the same way focus-scoping normally works in the DOM, not by tracking a boolean: give the graph
`container` `tabIndex = 0` and attach the `keydown` listener **to `container` itself**, not `document`. A
`keydown` on a container only fires when that element (or a descendant, e.g. one of the camera-control
buttons) has focus, so it is automatically inert while the search box, file input, or any panel control has
focus — no extra state needed. `preventDefault()` on every handled key so arrow keys never trigger page/panel
scrolling.

Mapping (`event.key`):
- `+` and `=` → zoom in (both, since `+` needs Shift on most layouts)
- `-` and `_` → zoom out
- `0` → **Reset** (the ticket's shortcut list has one slot for "fit/reset"; Reset is the more complete action
  — it subsumes Fit whenever the view isn't rotated, which is the common case — so it gets the key. Fit stays
  reachable via its on-screen button for the "I rotated, now just re-frame without un-rotating" case.)
- `ArrowUp` / `ArrowDown` / `ArrowLeft` / `ArrowRight` → pan
- `[` → rotate left, `]` → rotate right

A developer tabbing through the page can also reach the control-cluster buttons and the container itself via
normal Tab order — no `tabIndex="-1"` on the buttons.

### Dismissible mouse-gesture hint

A small overlay (e.g. `<div class="tsv-camera-hint">`), also a child of `container`, with the exact text
scope calls for: drag to pan, wheel/pinch to zoom — plus a `×` dismiss button. Persist the dismissal in
`localStorage` (mirrors `app/theme.ts`'s `storeTheme`/`safeGetStored` pattern — a small self-contained
try/catch pair inside `render.ts`, not a shared helper) under its own key, e.g.
`tallysim-viewer:camera-hint-dismissed`, so once dismissed it stays dismissed across reloads and future
network loads. Keyboard shortcuts are *not* named in this hint — the ticket only asks for the mouse gestures
here.

### Cleanup — the one real gotcha

`container` (the `graph` div in `shell.ts`) is **not** recreated between loads — `shell.ts`'s `teardown()`
calls `view.destroy()` and *then* `graph.textContent = ''`, which removes child DOM (so the button cluster,
hint and tooltip elements all disappear fine) but does **not** remove listeners attached to `container`
itself. Today's code never attaches a listener directly to `container`, only to `sigma` (cleaned by
`sigma.kill()`) and to children like the tooltip (removed via `tooltip.remove()`). This ticket is the first
to add `container`-level listeners (`keydown`, and `focus`/`blur` if used for any visual focus state), so
`destroy()` **must** explicitly `removeEventListener` each one it added — otherwise every repeated "Load
sample" / file load stacks another keydown listener on the same persistent element, and one keypress fires
N times after N loads. Keep references to the bound handlers in `createGraphView`'s closure so `destroy()`
can remove exactly them.

### Things that need no code change (verify manually instead)

- **Labels/hover at any rotation**: sigma draws labels on its own screen-space layer (not rotated text), and
  hover hit-testing already works in camera-transformed coordinates — this should already hold with no
  change. Confirm during the manual pass, don't add compensating code.
- **Hidden-tab focus**: when the Graph/Sweep mode toggle (`shell.ts`'s `applyMode`) hides `#tsv-graph` via
  `display: none`, the browser spec auto-blurs a focused element that stops being rendered, so a focused
  graph container won't keep eating keystrokes while the Sweep tab is shown. No explicit `.blur()` call
  needed in `shell.ts`; just confirm this with a manual check (focus the graph, switch to Sweep, press an
  arrow key, confirm nothing happens).
- **Empty / zero-node graph**: "Fit" and "Reset" are plain camera-state assignments (`{x:0.5,y:0.5,ratio:1[,angle:0]}`)
  that don't read the node extent at all, so an edgeless/nodeless graph (which `docs/design.md`'s "settled"
  signal already treats as a valid, immediately-settled case) can't make them throw or misbehave.
- **WebGL-unavailable stub**: `createGraphView` returns the inert `stubView` before any of this runs, so no
  control cluster, hint, or keyboard listener is ever created when there's no sigma/camera to control —
  matches the existing tooltip/WebGL-missing-message branching, no special-casing needed.

## Edge cases & interactions

- **Focus handoff between graph and panel inputs**: typing `[`/`]`/`0`/arrows in the search box, the file
  input, or any replay/live/sweep panel control must never pan/zoom/rotate the graph. Covered by scoping the
  listener to `container` itself (see Design) rather than `document` — verify explicitly, since a
  document-level listener with an "is an input focused?" check would have been the wrong, more fragile design
  and is NOT what to build.
- **Repeated network loads reusing the same container**: the cleanup gotcha above — a listener leak here is
  silent (no error, just N-fold repeated actions) and easy to miss in a quick manual pass, so test it
  explicitly (load sample twice, press `0` once, confirm one reset's worth of movement, not two).
- **In-flight camera animation interrupted by a new action**: `camera.animate()` replaces any animation
  already running (sigma's own behavior), so pressing zoom-in while a rotate animation is mid-flight, or
  triggering `search()`'s own `camera.animate({x,y,ratio:0.3})` while a keyboard pan is in flight, should not
  need special-casing — confirm nothing jumps or throws when actions are triggered back-to-back quickly.
- **Rotated view + Fit's axis-aligned clipping**: confirm this reads as "a reasonable re-frame, occasionally
  not pixel-perfect at odd angles" rather than "broken" — it's an accepted trade-off (see Design), not a bug
  to chase.
- **Mode switch while the graph has keyboard focus**: covered by the browser's own auto-blur-on-hide behavior
  (see Design) — verify it manually rather than adding a defensive `.blur()` call that would just be dead code
  if the browser already handles it.
- **WebGL-missing stub**: confirm no control cluster/hint/listener appears when `webglAvailable` is `false`
  (e.g. by forcing `webgl2Supported()` to return `false` temporarily while testing, or on a browser/profile
  that actually lacks WebGL2).
