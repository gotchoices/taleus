# tallysim — experiment runner, CLI, first experiment

Third and **final** ticket of the network-model tier (after `tallysim-model-generators` and
`tallysim-oracle`). It turns the generators + oracle into a usable experiment harness and produces the
tier's first checked-in result. This ticket is the **tail of the tier**: the downstream plan ticket
`tallysim-discovery` and the backlog item `feat-tallysim-trading-model` depend on it (it owns the sweep
runner they build on, and the "step the economy" seam the trading model plugs into).

## Scenario and sweep model

```ts
/** What to generate and how to query it. The network is given EITHER as (generator, params, seed) OR as
 *  a materialised Network — both are valid inputs; the runner materialises the former. (Parent plan's
 *  second design point, decided: store either; runner materialises.) */
interface ScenarioSpec {
	network:
		| { generator: string; params: Record<string, number>; seed: number }
		| { materialized: Network }
	workload: {
		kind: 'payment' | 'clearing'
		queries: number                 // how many random queries
		amount: { dist: string; params: Record<string, number> }  // query amount distribution
		depth: number                   // max depth D
		seed: number                    // workload PRNG seed (separate from the network seed)
		metrics?: string[]              // which metrics to compute (max-flow opt-in; see below)
	}
}

/** A sweep varies ONE OR TWO parameters over ranges and repeats over seeds. */
interface SweepSpec {
	base: ScenarioSpec
	vary: { path: string; values: number[] }[]   // 1 or 2 entries (e.g. network.params.k)
	seeds: number[]                               // repeat each cell over these seeds
}
```

> NOTE (resume): the landed implementation extends this — see "Deviations" above. The generator variant also
> carries `capacity: CapacityDistribution`; `vary` accepts any arity.

**Runner behaviour.** For each sweep cell (one combination of varied values) and each seed: materialise
the network, draw the workload (random `(X, Y)` pairs and amounts from the workload PRNG — reuse
`tallynet`'s `SeededRandom`), run the oracle per query, aggregate the metrics. Emit **one record per
run** (the resolved parameters + seed + metrics). The core runner **yields records as plain objects**
(an array or generator) — it does not touch the filesystem, so the browser viewer can drive it too.

**Max-flow is opt-in per run** (`workload.metrics` must include it), because Edmonds–Karp is costly on
large graphs — honour the sampling guidance from `tallysim-oracle` (sample a subset of query pairs for
max-flow, never all 1,000 on a 10k graph). Document the default (max-flow off unless requested).

## Metrics (oracle level)

Aggregated per run, over its workload:
- **P(route exists)** — fraction of payment queries with a route (the headline metric).
- **path-length distribution** — histogram / mean+quantiles of `shortestLength` over successful queries.
- **max-flow distribution** — when enabled, over the sampled pairs.
- **largest-connected-component fraction** — one per network (reuse `src/structure.ts`).
- **clearing-cycle availability** — for `kind: 'clearing'`, fraction of sampled nodes with ≥ 1 usable
  cycle, and the cycle-length distribution.

Keep metric aggregation a pure module (`src/metrics.ts`): records in, summary out.  *(DONE.)*
