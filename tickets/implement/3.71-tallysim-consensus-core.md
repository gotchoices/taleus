After discovery finds routes, the simulator today stops. This ticket adds the **consensus phase**: the
originator picks one found plan, the sim drives the real `tallynet` sign-and-settle protocol over that route
on the virtual clock, reads whether it **committed** or **voided**, and — on commit — moves each tally's
balance along the route in the network model so the next query sees the changed capacity.

This is the protocol-behaviour heart. Metrics, failure-injection scenarios and the trace-header extension are
the next ticket (`tallysim-consensus-metrics-trace`); the viewer animation is `tallysim-viewer-consensus`.
Build the mechanism and prove commit/void/conservation here.

## Background the implementer needs

Read `packages/tallynet/src/testing/consensus.test.ts` first — it is the **exemplar**. It wires a whole graph
of `ConsensusNode`s over one `InMemoryNetwork` + `VirtualClock` and drives a lift from `buildLift` → originator
`start(record)` → `clock.runUntilIdle()` → every node's `outcome(transactionCode)` agrees. The sim does exactly
this, on a tallysim-generated network, for the route discovery just found.

Key facts already in place (no need to rediscover):

- **The harness already supports consensus.** `InMemoryNetwork` builds `ConsensusNode`s **only when
  `signerFor` + `verifier` are passed** (so discovery-only runs pay no keygen). It exposes `buildLift(spec)`,
  `consensusNode(name)` (`.start` / `.update` / `.outcome`), `consensusStoreOf(name)`, `memberKey(name)`,
  `resourceFor(name)` injection, and `deliveryErrors` (receiver-side push throws). Per-link `conditions`
  (latency / drop) govern consensus pushes too (`pushCondition` → `resolveCondition`).
- **Member keys are not node names.** Consensus keys a node by its base64url ed25519 public key; discovery keys
  it by name (`entityName(id)`). The harness holds the name↔key bijection and every `buildLift`/`consensusNode`
  call takes the **name**. Consensus `TraceEvent`s carry the member **key** as `nodeId`/`to`/`from` — the next
  ticket's trace header must therefore record the key↔entity map; this ticket just needs the bijection to drive.
- **Deterministic ed25519 (load-bearing).** The exemplar's signer is `secret = sha256(seed ‖ name)`, ed25519
  signing is deterministic, so a `(seed, name)` pair always yields the same key pair, signatures, and trace
  stream. The sim MUST derive signer secrets this way from a **dedicated identity seed stream**, or member keys
  (and thus the whole trace) stop being byte-reproducible. `@noble/curves` is a tallynet **dev**dependency; the
  sim ships consensus wiring, so add `@noble/curves` to **`packages/tallysim`'s `dependencies`** (pure JS;
  passes the `no-node-globals` guard — verify with `yarn workspace tallysim test`).
- **Settlement is strict-majority over the referee (`R`) members** (`commitCount > R/2` / `noCommitCount >
  R/2`), counted by `tallynet` unchanged. "The referee" in the parent ticket is legacy single-referee wording:
  model it as a **voter set of `R`-role members**, whose default is a set of one — the **originator voting
  itself** (originator member gets roles `['P','R']`). A scenario option supplies a larger set. See the voter
  model note in the project memory (lifts are settled by a voter set, not "the referee").

## What to build

### 1. Consensus wiring on the sim network (`sim/harness.ts` or a new `sim/consensus-harness.ts`)

`buildSimNetwork` today omits `signerFor`/`verifier`, so consensus is off. Add an opt-in so a run that needs
consensus gets it, without disturbing the discovery-only path (the pinned byte-identical discovery sweep must
not change). Suggested shape — a sibling builder or an options flag:

```ts
buildSimNetwork(network, conditions, conditionsSeed, trace?, options?, consensus?: {
  identitySeed: number         // derives each node's ed25519 secret: sha256(identitySeed ‖ entityName(id))
})
```

When `consensus` is present, pass `signerFor`, `verifier`, and `resourceFor` (the sim resource port, below)
to `InMemoryNetwork`. Reuse the exemplar's `verifier` (ed25519, false-not-throw on malformed input).

### 2. Pick a plan (`sim/plan-select.ts`)

A documented, simple originator policy over `QueryOutcome.plans` (each carries `path: Link[]` of link nonces
and `members`). Decided default: **shortest path** (fewest hops), ties broken by **first found** (stable array
order) — deterministic. Expose the policy as a small enum/function so the next ticket can sweep it; ship
`shortest` as the only implementation for now. Empty plans → no lift (caller skips the consensus phase).

### 3. Reconstruct the exact route (`sim/route.ts`)

The chosen plan's `path` is a list of per-session link nonces. The sim holds the whole network, so it inverts
the hash exactly as the viewer's `deanonymise.ts` does: for the plan's `sessionCode`, build `nonce → tally
index` by recomputing `makeNonce(sessionCode, linkIdForTally(i))` for every tally `i`, then walk the path from
the originator (`query.from`) across each tally's two endpoints. Return **both**:

- `tallyPath: number[]` — the ordered tally indices the route crosses (one per hop), and
- `route: number[]` — the ordered entity ids `[from, …, to]` (the node path).

An unresolvable nonce or a non-contiguous walk is a bug for a self-generated network — surface it as a thrown
error (not a silent sentinel), since here the sim built the very network it is decoding.

### 4. Build and drive the lift (`sim/consensus-harness.ts`)

From `tallyPath` + `route` + the amount, assemble a `LiftSpec` and drive it:

- **Members:** every entity on `route` is a participant (`['P']`); the originator additionally gets `['R']`
  under the default single-voter policy. A circular lift (originator = payee, so `route[0] === route[last]`)
  lists the originator **once** in `members` but appears on two links — `buildLift` handles that via the route
  pairs.
- **Exact links — extend `buildLift`.** `buildLift` resolves each route pair to a graph edge by neighbour name
  via `.find(...)`, which picks the **first** tally between a pair and so mis-selects when **parallel tallies**
  exist. Add an optional `routeLinkIds?: string[]` (one link id per hop) to `LiftSpec` in
  `packages/tallynet/src/testing/network.ts`; when present, `addLiftLink` uses the specified link id instead of
  the first-neighbour match, disambiguating parallels. The sim passes `tallyPath.map(linkIdForTally)`. Keep the
  name-pair fallback for callers that don't supply it (the existing consensus tests).
- **Drive:** `net.consensusNode(entityName(from)).start(record)`, then `await net.clock.runUntilIdle()`.
- **Outcome:** read `consensusNode(name).outcome(transactionCode)` → `'commit' | 'void' | 'pending'`. A clean
  run has every node agreeing; assert `deliveryErrors` is `[]` unless a failure was injected. `pending` (a
  stalled lift — a dropped push or a tie that never settles; v1 has no timeout) is a real third outcome to
  surface, not an error.

Return a `LiftResult` the next ticket's metrics consume:

```ts
interface LiftResult {
  transactionCode: string
  sessionCode: string
  route: number[]
  tallyPath: number[]
  amount: number
  outcome: 'commit' | 'void' | 'pending'
}
```

### 5. Move money on commit (`sim/consensus-harness.ts` + `capacity.ts`/`model.ts`)

On `outcome === 'commit'`, mutate the network's `Tally.balance` along `tallyPath`. Payment flows from the
originator (payer) outward to the target (payee): for each hop `u → v` resolved to tally `t`, value flows
`u → v` (v better off), which per the capacity model (`capacity.ts`) means:

- if `u` is the **foil** and `v` is the **stock** of `t`: `b += amount` (rises toward `+stockCreditLimit`);
- if `u` is the **stock** and `v` is the **foil** of `t`: `b -= amount` (falls toward `-foilCreditLimit`).

Add a single documented helper (e.g. `applyLiftToBalance(tally, fromIsStock, amount)`) next to the capacity
helpers so the direction lives in exactly one place. Mutate a **clone** per run if the network came in
`materialized` by reference (mirror the `NOTE` in `runner.ts`); a sequence of lifts mutates the one kept
network in order. On `void`/`pending`, balances are unchanged.

The commit must never push a direction's capacity negative — the amount cleared each hop already satisfied
`capFwd ≥ amount` at discovery time, so a single lift over the found route stays within bounds; assert this
(a violated bound is a route-reconstruction or direction bug).

## Edge cases & interactions

- **Circular lift** (originator on two links): animates/settles as one closed loop; originator appears once in
  `members`, twice on links; `tallyPath` first and last tallies both touch the originator; settles once; the
  balance walk visits each tally once; conservation holds around the loop.
- **No plan found:** consensus phase skipped cleanly (no lift, no mutation).
- **Parallel tallies between a pair:** the exact-link `routeLinkIds` path selects the tally the discovery used,
  not the first — verify with a two-tally pair where only one direction has capacity.
- **Refuser** (a route participant whose `shouldPromise` is false or whose `promise` throws): the lift **voids
  everywhere**, every held resource releases (`release({success:false})` once per promising node), balances
  unchanged. Reuse the exemplar's `resourceSet({ [name]: { shouldPromise: false } })` pattern.
- **Voter votes no-commit** (`shouldCommit: false` on an `R` member): voids everywhere; balances unchanged.
- **Balance at a credit bound after a lift** (a now-zero-capacity direction): a subsequent query that needs
  that direction prunes it — the whole point of mutating the model. Cover with a two-lift sequence.
- **`Infinity` capacity edge on the route:** unlimited credit; `b` is finite, moves by `amount`, never serialised
  here (no CBOR `Infinity` path), capacity stays `Infinity` in the unbounded direction.
- **Determinism:** same `(network seed, identity seed, workload seed, conditions seed)` ⇒ identical member keys,
  outcome, and resulting balances. A non-deterministic signer secret (e.g. seeded from wall-clock or a shared
  RNG whose draw order shifts) would break this — the dedicated identity-seed stream is the guard.
- **Pending (stalled) lift:** a dropped push on a cut edge or a 2-voter tie leaves `outcome === 'pending'`;
  surface it, do not throw, do not mutate balances.
- **`from === to` / `< 2` entities:** discovery returns no usable plan; consensus phase is skipped.

## Tests to plan

- **All-cooperative commits.** A seeded small graph with a known route: the originator picks the shortest plan,
  the lift commits at every node (`outcome(txCode) === 'commit'` for all members), and the targeted tally
  balances moved by `amount` in the right direction.
- **One refuser voids.** The same route with one participant's `shouldPromise=false`: every node's outcome is
  `void`, every promising node released with `success:false`, balances unchanged.
- **Conservation.** Over any committed lift, each **intermediary** node's net position is unchanged — what it
  gains as creditor on its in-tally it gives as debtor on its out-tally (derive the exact invariant from
  `capacity.ts`: the signed change on the in-tally equals the signed change on the out-tally for that node).
  Only the payer and payee see a net change.
- **Capacity changes between lifts.** Two lifts in sequence over overlapping edges: the second sees the first's
  balance change (a route available before is pruned after, or an amount that fit before no longer fits),
  deterministically under one seed.
- **Determinism of the full discovery + consensus pass.** Running the same scenario twice yields identical
  `LiftResult`s and identical post-run balances (byte-compare the serialised network).
- **Parallel-tally disambiguation.** `routeLinkIds` drives the lift over the exact tally discovery chose.
- **Harness extension unit test.** `buildLift` with `routeLinkIds` builds the topology over the named links;
  without it, behaviour is unchanged (existing consensus tests still pass).
