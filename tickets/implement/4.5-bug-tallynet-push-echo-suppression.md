description: When a lift node receives a transaction record from a neighbour and has nothing new to add, it sends the same record straight back to that neighbour instead of staying quiet, which the original ChipNet code avoided. Harmless but wasteful; restore the suppression.
files: packages/tallynet/src/consensus/participant.ts, packages/tallynet/src/consensus/store.ts, packages/tallynet/src/consensus/participant.test.ts, packages/tallynet/docs/chipnet-review.md
difficulty: easy
----

A real (minor) regression found by the ChipNet regression check (`packages/tallynet/docs/chipnet-review.md` § Regression check, Consensus table row "Inbound peer-record save"). Not a correctness bug — the union merge is idempotent, so an echoed record changes no outcome — but a lost convergence/bandwidth optimisation that ChipNet had and TallyNet dropped with no stated reason.

## What ChipNet did

ChipNet's `TrxParticipant.update(record, fromAddress)` saved the record the peer just sent **before** doing anything else: `../chipnet/src/transaction/participant.ts:34`

```
if (fromAddress) {
    await this.state.savePeerRecord(fromAddress, record);
}
```

That primes the push skip-test. When this node then pushes to reachable peers, the skip-test (`pushModified` → `getPeerRecord(peer, tx)` equal? skip) finds the sender's last-known copy already equal to what we would send, so **we do not echo the record straight back to the peer we just got it from**. (ChipNet even flags a staleness subtlety in a `TODO` at `participant.ts:33` — the saved copy might be older than what we just sent it — but the suppression itself is deliberate.)

## What TallyNet does

`TrxParticipant.update(record, fromAddress)` (`packages/tallynet/src/consensus/participant.ts:144`) uses `fromAddress` **only** for the `record-received` trace event (`:225`). `savePeerRecord` is called **only after a successful outbound push** (`push`, `:627`). So on first receipt from peer X, the skip-test in `push` (`getPeerRecord(tx, X.key)`, `:618-620`) has no entry for X, and a node whose state does not change (a pure relay, or any node that has already signed) **pushes the record right back to X**. One redundant round-trip per receiving node per delivery.

## Fix — confirmed against the current code

Verified by directly implementing and testing against this branch's `packages/tallynet/src/consensus/participant.ts` (all 325 tallynet tests pass, including a new regression test — see below); the edit was reverted afterward so this ticket, not a fix-stage commit, carries it into `implement/`, per this repo's fix→implement separation.

In `validateAndMerge` (`packages/tallynet/src/consensus/participant.ts`), right after the existing persistence block:

```ts
await this.store.saveRecord(merged)
if (pending.length > 0 || hadPending) {
	await this.store.savePendingCommits(merged.transactionCode, pending)
}
```

add, before the `record-received` trace emit:

```ts
if (fromAddress) {
	await this.store.savePeerRecord(merged.transactionCode, fromAddress.key, snapshotRecord(merged))
}
```

`snapshotRecord` is the module-local helper already used by `push` (`:827`) — reuse it as-is (it is a function declaration, hoisted, already callable from anywhere in the module).

Subtlety to preserve, not reintroduce a bug:
- Save the **merged** record (what we now hold), not the raw incoming one — otherwise the skip-test compares our push against a *subset* of what we know and still echoes. (ChipNet saved the raw incoming record, which is why its own `TODO:33` worries about staleness; saving the merged record is strictly better and avoids that worry.)
- The snapshot must be a frozen copy (the live `merged` keeps mutating as we advance state through `advanceState`/`sign`, both of which run *after* `validateAndMerge` returns), exactly as `push` already snapshots before `savePeerRecord` (`:623-627`). `snapshotRecord` handles this.
- This must not suppress a push the peer genuinely needs: if our state advances (we add a promise/commit) **after** this save, `merged`/the live record differs from the saved snapshot, so `push`'s content compare (`sameSignatureSets`) correctly re-pushes. Only an unchanged record is suppressed.

No change needed in `store.ts` — `savePeerRecord` already has the right shape; this ticket's `files:` list includes it only because the docstring there (`:16-18`, `:32`) is what the ChipNet-comparison reasoning leans on, in case a sanity-check during implementation is wanted. The actual save call is unchanged.

## Edge cases & interactions

- **Relay node** (not in topology): merges and pushes without signing — this is the main case that currently echoes. After the fix it must stay silent toward the sender but still forward to its *other* reachable peers.
- **Circular lift / 2-cycle on a tally link**: both ends push to each other every delivery. Saving the sender's copy must not deadlock diffusion — the record still reaches the sender via its *own* advancing state (content differs ⇒ re-push). Assert the lift still settles everywhere.
- **Drop/sleeping links**: suppression keys off our stored peer-record, independent of delivery conditions; a dropped push never saved a peer-record, so nothing changes there.
- **Restart**: peer-records are durable; after a restart with no stored peer-record, the first receipt re-primes it (same as today, one echo then quiet).
- Do **not** regress the existing "push suppressed when peer copy equals" test (`participant.test.ts`, describe block `TrxParticipant — reachability and push`); add a test asserting a relay that receives an unchanged record issues **no** push back to the sender.

## Regression test (already written and verified passing; re-add during implement)

Add to the `describe('TrxParticipant — reachability and push', ...)` block in `packages/tallynet/src/consensus/participant.test.ts`, right before the `'logs once and emits ok:false when a push fails...'` test:

```ts
it('suppresses the echo back to the peer we just received from, but still forwards onward and re-pushes once content changes', async () => {
	// ChipNet primed the sender's peer-record on receipt so an unchanged record was never pushed
	// straight back to whoever just sent it (docs/chipnet-review.md § Regression check). A relay with
	// nothing new to add must stay quiet toward the sender while still forwarding to other peers, and
	// must resume pushing to the sender once our content actually changes.
	const alice = makeParty()
	const bob = makeParty()
	const relay = makeParty()
	const members = [
		member(alice, [MemberTypes.participant], { physical: 'addr-alice' }),
		member(bob, [MemberTypes.participant, MemberTypes.referee], { physical: 'addr-bob' }),
	]
	const record = makeRecord(members, { n1: link(alice, bob) })
	const { participant, pushes } = harness({ self: relay })
	const aliceP = await sign(alice, 'P', record)

	await participant.update({ ...record, promises: [aliceP] }, { key: alice.key })
	expect(pushes.map((p) => p.to)).toEqual([bob.key]) // forwarded to bob, not echoed back to alice

	const bobP = await sign(bob, 'P', record)
	await participant.update({ ...record, promises: [aliceP, bobP] }, { key: bob.key })
	// bob's own content is suppressed (we just received it from bob); alice's copy is now stale → re-pushed
	expect(pushes.map((p) => p.to)).toEqual([bob.key, alice.key])
})
```

This exercises both halves of the fix in one flow: the no-echo case (first `update`, `fromAddress: alice`) and the correctly-resumed-push case (second `update`, `fromAddress: bob`, where alice's stored copy is now stale because bob's promise was added).

With just this test added (fix not yet applied), `pushes` after the first `update` is `[alice.key, bob.key]` (echo present) — confirms the test reproduces the bug before the fix lands.
