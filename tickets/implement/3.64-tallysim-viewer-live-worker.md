**This is the engine half of the former single `3.64-tallysim-viewer-live-run` ticket.** That ticket was
split under a budget limit after its pure helper (`src/live/build-scenario.ts`) was already written and
type-checks clean (`yarn tsc --noEmit` green). The UI half is `tallysim-viewer-live-controls` (which has this
ticket as a `prereq`). Read the sibling ticket too — together they are the original "live run" feature.

The viewer's **replay tier** (prior ticket) animates a *recorded* trace file. The live-run feature adds the
**second source**: generate a network and run a live `tallynet` discovery simulation *in the page*, feeding its
trace events into the same replay view. `tallysim`'s core and `tallynet/testing` are platform-neutral (no
`node:` imports — verified across `packages/tallynet/src/{testing,discovery,consensus}/`, `crypto.ts`,
`nonce.ts`, and `packages/tallysim/src/{sim,generators}/`), so the real engine runs in-browser, no server. The
viewer already imports `tallysim` + `tallynet` in the browser; this adds the transitive `tallynet/testing`
import (via `buildSimNetwork`), which is a shipped subpath export (`tallynet/testing` → `dist/testing/index.js`)
and uses only `@noble/hashes` + the Web Crypto global.

## What `build-scenario.ts` already provides (DONE — do not rewrite, just test it)

Pure form-values → run-description translation, DOM-free and sigma-free:

- `LiveRunParams` — the form's values: `generator` (`'uniform' | 'scale-free' | 'clustered' | 'small-world'`),
  `entityCount`, `generatorParams` (generator-specific numerics only, **not** entityCount/capacity),
  `capacity: CapacityDistribution`, `seed`, optional `conditions: ConditionsSpec` / `conditionsSeed` / `budget`,
  `amount`, `depth`, and optional `from`/`to` (the click-picked payer/payee).
- `buildNetworkSource(params)` → `NetworkSource` (`params` folds `entityCount` in with `generatorParams`,
  matching `materializeNetwork`'s `{ ...params, capacity, seed }` spread).
- `buildWorkload(params)` → a **nominal** single-query `WorkloadSpec` (`kind:'payment'`, `queries:1`, constant
  amount). It is nominal because the header embeds a `SimScenario` (which must carry a workload) but the live
  path runs the one explicit click-picked query, **not** a drawn one. The reload path replays recorded events,
  never re-executes the workload, so the nominal workload never misleads.
- `buildScenario(params)` → `SimScenario` (network source + nominal workload + optional conditions/budget);
  independent of `from`/`to` so generation can happen before a query is picked.
- `buildQuery(params)` → `QuerySpec`; throws if `from`/`to` unset. `from === to` is a valid self-payment.
- `buildLiveRun(params)` → `{ scenario, query, runSeed: DEFAULT_RUN_SEED (0) }`.
- `generatorIdOf(id)` maps the form id to the canonical `tallysim` `*_ID` constant.

## TODO: `sim-protocol.ts` — the worker↔main message union (shared by worker + controls)

Keep it a type-only module so both sides agree. Suggested shape:

```ts
import type { TraceEvent } from 'tallynet'
import type { QuerySpec, SimScenario, TraceHeader, TraceNetworkSnapshot } from 'tallysim'
import type { RouteInput } from '../replay/routes.js'

export type MainToWorker =
  | { type: 'generate'; scenario: SimScenario; runSeed: number }
  | { type: 'run'; scenario: SimScenario; query: QuerySpec }

export type WorkerToMain =
  | { type: 'network'; snapshot: TraceNetworkSnapshot }
  | { type: 'header'; header: TraceHeader }
  | { type: 'event'; event: TraceEvent }
  | { type: 'done'; sessionCode: string; found: boolean; routes: RouteInput[] }
  | { type: 'error'; phase: 'generate' | 'run'; message: string }
```

`RouteInput` (`src/replay/routes.ts`) is `{ from, to, linkNonces: string[], terms?: unknown[] }` — exactly the
shape the replay's found-routes list consumes. This is how the live source finally lights up the **full**
found-routes list (with exact-path isolate-on-select) that a recorded trace cannot (`plan-found` is path-less).
`Infinity` in `terms` (unlimited `LiftTerms.capFwd`/`capBack`) survives `postMessage` structured clone fine.

## TODO: `sim-worker.ts` — generate in-worker, then run discovery and stream the trace envelope

Run generation **and** discovery off the main thread so a large network stays responsive. Key design points
discovered during investigation:

- **Worker-scope typing under the DOM lib.** The viewer's tsconfig uses `lib: [ES2022, DOM, DOM.Iterable]` and
  `types: [jest, node]` — it does **not** include the `WebWorker` lib (it conflicts with DOM). So do **not**
  reach for `DedicatedWorkerGlobalScope`. Instead cast `self` to a minimal typed shape:
  ```ts
  const ctx = self as unknown as {
    postMessage(message: WorkerToMain): void
    addEventListener(type: 'message', listener: (e: MessageEvent<MainToWorker>) => void): void
  }
  ```
  `self`, `MessageEvent`, `postMessage` all come from the DOM lib; this type-checks with no lib change.
- **Flow.** On `generate`: `network = materializeNetwork(scenario.network, runSeed)`, keep it, post
  `{ type:'network', snapshot: makeNetworkSnapshot(network) }`. On `run`: use the kept `network` +
  `scenario.conditions ?? {}` + `scenario.conditionsSeed ?? 0`, build a trace sink, call
  `buildSimNetwork(network, conditions, conditionsSeed, sink, scenario.budget)`, then
  `await runQuery(sim, query)`.
- **Header-from-first-event (the ticket's determinism subtlety).** A session code is minted *inside*
  `discover()` and is not knowable synchronously from the returned promise. The live path does **not** need
  `cli/trace.ts`'s two-pass trick (it animates the one real run it observes). Every `TraceEvent` carries
  `sessionCode`, so: the sink, on the **first** event, builds + posts the `header`
  (`buildTraceHeader({ ...VIEWER_VERSIONS, scenario, runSeed: 0, queries: [{ sessionCode, ...query }] })`), then
  posts that event and every subsequent one. **After** `runQuery` resolves, if no event ever fired (a
  zero-event degenerate run — see edge cases), post the header using `outcome.sessionCode` so the main thread
  can still build an index.
- **Routes for the found list.** `routes = outcome.plans.map(p => ({ from: query.from, to: query.to,
  linkNonces: p.path.map(l => l.nonce), terms: p.path.map(l => l.intents) }))`; post `{ type:'done', … }`.
- **Versions.** The header's `tallysimVersion`/`tallynetVersion` are provenance only (never validated on read —
  only `traceFormatVersion` is checked by `parseTrace`). Use a `VIEWER_VERSIONS` constant (e.g. both `'0.1.0'`,
  current package versions) with a NOTE that they are the viewer's bundled provenance strings.
- **Determinism / reuse decision (document in the handoff).** Investigation chose to rebuild `buildSimNetwork`
  per Run rather than reuse one `InMemoryNetwork` across queries (a slight departure from the original ticket's
  "one `InMemoryNetwork` serves many queries" phrasing). Rationale: a fresh `buildSimNetwork` starts the
  session-code RNG at the fixed `SESSION_CODE_SEED`, so **each** live run byte-matches a `tallysim trace`
  single-query trace of the same seeds — the cleanest reading of "same params + seed ⇒ byte-identical trace".
  The *expensive, user-visible* reuse (rendered graph + settled layout) is preserved on the main-thread side.
  Keep the generated `network` in the worker across runs (it is read-only; no balances move this tier). If a
  future reviewer prefers literal `InMemoryNetwork` reuse, swap in a mutable `currentSink` indirection instead.
- **Errors.** Wrap generate/run in try/catch and post `{ type:'error', phase, message }` — never let the worker
  die silently (surfaced by the controls as a clear message, per the "worker failure" edge case).

### Edge cases the worker must not throw on (the harness already tolerates them)
- `from === to` (self-payment / clearing loop): yields a circular or empty plan; the loop's path nonces ride in
  `routes` so the UI's found-list isolate can draw the closed loop.
- `< 2 entities` or a generator producing no edges: empty result, possibly **zero events** → post header from
  `outcome.sessionCode`, `routes: []` (or the loop), `found:false`.

## Key API reference (saves re-discovery)
- `buildSimNetwork(network, conditions: ConditionsSpec, conditionsSeed: number, trace?: TraceSink, options?)` —
  `options` is `Partial<OriginatorOptions & ParticipantOptions>`; `scenario.budget`
  (`{initialBudgetMs?, perHopBudgetMs?}`) slots straight in. (`sim/harness.ts`)
- `runQuery(sim, QuerySpec)` → `Promise<QueryOutcome>` where `QueryOutcome = { sessionCode, plans:
  Plan<LiftTerms,unknown>[], found }`; `plan.path` is `Link<LiftTerms>[]`, `Link = { nonce, intents }`.
- `materializeNetwork(source, runSeed)` (`workload.ts`); `makeNetworkSnapshot`, `buildTraceHeader`,
  `serializeTraceLine`, `TraceHeader`, `TraceNetworkSnapshot`, `TraceQueryEntry` (`sim/trace-format.ts`).
- Trace envelope order is header (line 1), network (line 2), events (3+) — the `makeTraceWriter` sequencing to
  mirror. The main thread (controls ticket) feeds header+network into `createTraceIndex(header, network)` then
  `.add(event)` per event (`src/core/trace-index.ts`).
