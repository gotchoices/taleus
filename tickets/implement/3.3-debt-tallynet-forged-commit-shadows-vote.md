## Summary

In TallyNet consensus a payment ("lift") settles in two phases: every **participant** on the
route signs a **promise** (`P`/`NP`), then every **referee** votes **commit** (`C`) or
**no-commit/void** (`NC`); a strict majority of referees one way settles the lift. Each vote is a
signature over a canonical preimage, and a referee's commit vote binds the *full promise set* into
that preimage (`consensus/digest.ts`) — so a commit can only be *verified* once a node holds the
complete promise set. To tolerate out-of-order delivery, the participant currently **stores an
incoming commit without verifying it** while the promise phase is still incomplete, and verifies it
later once the promise set fills.

The defect: the per-signer "first one wins" dedupe (`mergeSignature` in `consensus/participant.ts`)
runs **before** cryptographic verification. So while the promise phase is incomplete, any forwarding
node can inject a commit carrying a target referee's (public) address and **garbage signature bytes**.
It passes membership + role checks, no prior signature from that referee exists, and — because the
promise phase is incomplete — it is **stored unverified**, occupying that referee's commit slot. When
the referee's genuine vote later arrives it collides with the stored fake and is refused as `changed`
(same face, different bytes) or `equivocation` (opposite face). The fake never verifies either, so it
is never counted. Net effect: **the referee's real vote is permanently silenced at the victim node.**
Do it to enough referees and no commit majority can form; the lift stalls and (once
`feat-tallynet-propagation-timeouts` lands) is driven to void.

Scope: **liveness/outcome, not safety.** A forged vote never *counts* (it never verifies), so no false
commit can be manufactured — but genuine votes can be suppressed, enough to block or wrongly void a
lift. Promises are **not** affected: promise-phase signatures are verified immediately on merge (their
preimage does not depend on the promise set), so a forged promise is dropped as `forged` and can never
be stored to shadow a genuine one. Only the commit phase has the store-then-verify-later path.

## Reproduction (confirmed)

The exploit was reproduced end-to-end against the existing multi-node harness
(`src/testing/network.ts` + `VirtualClock`). An observer node X (a pure relay, non-member) was driven
with two `update()` calls:

1. First update: `{ ...record, promises: [], commits: [garbageC_for_R] }` — promise phase empty, so
   the garbage `C` for referee R is stored **unverified** in `commits`.
2. Second update: the complete promise set (`A`'s `P`, `B`'s `P`) plus **R's genuine `C`**.

Result: R's genuine commit is refused with reject reason **`changed`**, and `X.outcome(tx)` reads
**`pending`** — it should read **`commit`** (R is the sole referee; a majority of one). With a garbage
`NC` injected first, the genuine `C` is instead refused as `equivocation`; same silencing.

(The reproduction was a throwaway test, already removed; its exact shape is captured by "Tests to add"
below — fold it into `src/testing/consensus.test.ts`.)

## The fix (settled design — do NOT relitigate)

Settled 2026-11-25, **option 2 of the two the source ticket weighed**: unverified commit-phase
arrivals go into a **side pool** that never blocks anything. A commit enters the authoritative
`commits` set — and the `changed`/`equivocation` dedupe checks — **only once it verifies**.

Invariant to preserve both ways:
- **A referee's genuinely-signed vote can never be suppressed by a signature that does not verify.**
- A referee that verifiably signs *both* faces (`C` and `NC`, both checking out against the complete
  promise set) is still caught as **equivocation**, and the first (earlier-arrived) face stands.
- The honest out-of-order case keeps working: a genuine commit that arrives **before** the promise
  phase completes is retained and counted once the promise set fills.

### Where the pool lives (persistence is required)

The pool must survive **across** `update()` calls: a genuine early commit can arrive in one update and
only become verifiable in a later update that completes the promise set (the behaviour the current
store-in-`commits` path provides and that must not regress). So the pool is **durable, keyed by
`transactionCode`**, alongside the record — not kept only in memory and not folded into the pushed
record.

Add to `TrxStore` (`consensus/store.ts`) and implement in `MemoryTrxStore` (+ cover in
`store.test.ts`):

```ts
/** Unverified commit-phase signatures held out-of-band until the promise set completes (never pushed). */
getPendingCommits(transactionCode: string): Promise<Signature[]>
/** Persist the pending-commit side pool for transactionCode. */
savePendingCommits(transactionCode: string, commits: Signature[]): Promise<void>
```

The pool is **side state, never part of the wire record**: it is not digested, not pushed, not part of
`coreEqual`. Keeping it off `TrxRecord` keeps that type the pure merge/wire object it is documented to
be. (An implementer who would rather hang a non-wire field off the record may, provided it is excluded
from `snapshotRecord`/push, the digest, and `coreEqual` — but the store-backed pool is the
recommendation and the cleaner separation.)

### Merge logic (`mergeSignature` + a drain step)

For a **commit** signature, after the existing membership + role checks:

- **Promise phase NOT complete** → cannot verify. Route to the pending pool instead of `commits`:
  - identical `(address, value)` already pending → silent dedupe (idempotent);
  - else if the pool already holds `MAX_PENDING_COMMITS_PER_REFEREE` (a small constant, **4**) entries
    for this `address` → **drop and log** (`rejectSignature` with a new reason, see below), so a peer
    cannot grow the pool without bound;
  - else append to the pool.
  - Do **not** touch `merged.commits`. The authoritative `commits` set now only ever holds verified
    signatures, so the `changed`/`equivocation` dedupe can never be triggered by an unverified entry.
- **Promise phase complete** → verify immediately (as today). Fails → `rejectSignature('forged')`.
  Verifies → *then* apply the existing `changed`/`equivocation`/identical-dedupe check against
  `merged.commits` (now a verified-only set) and append on no collision.

**Drain** the pending pool whenever the promise phase is complete and the pool is non-empty — do this
in `validateAndMerge` **after** merging the incoming promises and **before** merging the incoming
commits, so earlier-arrived (pooled) votes are processed before same-update arrivals and the
"first face stands" ordering is deterministic. Draining = run each pooled commit through the
promise-phase-complete path: verify → `forged`-drop or promote-with-dedupe into `merged.commits`.
After a complete-phase drain the pool is emptied (every entry is either promoted or dropped). Persist
the emptied/updated pool via `savePendingCommits` alongside the existing `saveRecord`.

Promotion ordering within the pool: preserve insertion order, so the earliest genuine face of a true
equivocation is the one that stands.

`countVerifiedCommits` can stay as-is (it re-verifies defensively; harmless at lift scale and the
promise set is stable once the phase completes). Delete the now-obsolete "liveness edge" `NOTE:` block
in `mergeSignature` (lines ~271-278 today) — the stall it documents is exactly what this ticket
closes.

### Reject reason

Add a `SignatureRejectReason` member for the pool-cap drop (`consensus/types.ts`), e.g.
`'pool-full'` ("pending commit pool cap reached for this signer"), and document it in that union.
Pooled commits that fail verification on drain reject as the existing `'forged'` (consistent with a
complete-phase forged commit). Update any exhaustive switch/assertion over the reason union.

### Document the general rule

In `packages/tallynet/docs/design.md` § Protocol design (Consensus) add the invariant, stated plainly:
**no unverified input may change state that blocks a verified one.** Note concretely that unverified
commit-phase signatures are held in a durable side pool (capped per referee) and only promoted into the
counted `commits` set after they verify against the complete promise set; and that promise-phase
signatures need no pool because they are verified on arrival and an unverified promise is never stored.

### Audit (part of this ticket)

Audit discovery and consensus for any *other* place that dedupes or rejects on an **unauthenticated**
field in a way that lets unverified input shadow verified input, and fix any found here. Concrete
pointers:

- **Consensus / promises** (`mergeSignature`, promise branch): confirm — and note in the design doc —
  that the pre-verify dedupe is safe for promises because a forged promise with no prior entry is
  dropped as `forged` (verified immediately) and never stored, so it can never become the `existing`
  that blocks a genuine promise. No code change expected; document the reasoning.
- **Discovery** (`discovery/participant.ts`): `store.validateNewQuery` (duplicate-visit reject),
  `pruneCandidates`, and `foldPlans` (dedupe-by-path) operate on route-search state that v1 does not
  cryptographically authenticate at all (member-identity binding is a later feature), so the
  "unverified shadows verified" shape does not apply. Confirm this and record the conclusion in the
  ticket handoff / a one-line note; do **not** expand scope into discovery auth.

Out of scope (do not build here): detecting, attributing, or punishing misbehaving peers — backlog
`feat-tallynet-hostile-peers`. Propagation timeouts / void-on-timeout — `feat-tallynet-propagation-timeouts`.

## Tests to add (multi-node, in `src/testing/consensus.test.ts`)

Follow the existing adversarial-signature pattern there (the `makeSigner(seed, name)` doubles,
`corrupt`, an observer/relay node `X`, two-phase `update()` delivery). Add a `describe` block:

- **Garbage `C` injected pre-promise does not silence the genuine vote.** Inject a corrupted `C` for
  referee R while the promise phase is empty/incomplete; later deliver the complete promise set + R's
  genuine `C`. Assert R's vote is counted and the record reaches **commit** (sole referee, or a
  majority that needs R). This is the headline regression test; it currently fails (outcome `pending`,
  reject reason `changed`).
- **Garbage `NC` injected pre-promise** (collides as `equivocation` under the old code): same setup,
  garbage `NC` first; R's genuine `C` still counts → commit.
- **Honest out-of-order early commit still counts.** Deliver R's **genuine** `C` *before* the promise
  phase completes (pooled unverified), then deliver only the completing promise(s) in a **separate**
  update that does *not* re-carry the commit; assert the pooled genuine commit is drained, verified,
  and counted → commit. This guards the behaviour the side pool must not regress.
- **Genuine equivocation still refused.** A referee that signs two *verifying* opposite faces (both
  over the complete promise set) is still refused as `equivocation`; the first (earlier-arrived) face
  stands and the outcome matches it. (Keep/extend the existing post-commit equivocation test too.)
- **Pool cap.** Injecting more than `MAX_PENDING_COMMITS_PER_REFEREE` distinct pre-promise commits for
  one referee drops the overflow with the `pool-full` reject reason, and a genuine vote for that
  referee delivered afterward still verifies and counts (the cap must not lock out the real vote).

Also add/adjust a focused unit test in `consensus/participant.test.ts` if the single-participant
harness there can exercise the pool/drain transition directly (cheaper than the full network for the
dedupe-ordering cases).
