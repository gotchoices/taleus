## Why this ticket exists (continuation)

The source ticket (`3.3-debt-tallynet-forged-commit-shadows-vote`) ran into the runner's soft token
budget partway through implementation. The **code fix is done and compiles** (`yarn build` from
`packages/tallynet` is green). What remains is the **design-doc note, the tests, and the full
build/test/lint validation** — plus one *pre-existing* unit test that the fix deliberately changes and
which must be updated (details below). This ticket carries forward only the unfinished work and the
exact specs the original ticket spelled out, so nothing needs re-deriving.

Read the original ticket's prose (now captured here) for the full defect analysis; the one-paragraph
recap: in commit-phase consensus an unverified commit used to be stored in the authoritative `commits`
set while the promise phase was still incomplete (it can't be verified until the full promise set is
present). A forwarding node could inject a garbage commit for a referee **before** the promises
completed; it occupied that referee's slot, and the referee's genuine vote then collided with it
(`changed`/`equivocation`) and was silenced. Scope is **liveness/outcome, not safety** — a forged vote
never *counts* (never verifies), but genuine votes could be suppressed enough to block or wrongly void a
lift. Promises are unaffected (verified on arrival; a forged promise is dropped and never stored).

## What is ALREADY DONE (landed in the working tree, compiles clean)

- **`consensus/store.ts`** — added `getPendingCommits(transactionCode)` / `savePendingCommits(transactionCode, commits)`
  to the `TrxStore` interface (with doc), and implemented both in `MemoryTrxStore` via a
  `Map<string, Signature[]>`. `getPendingCommits` returns a **fresh copy** (`[...arr]`) so the
  participant can mutate its working pool without aliasing the store; `savePendingCommits` stores a copy.
  Imported `Signature` into the module.
- **`consensus/types.ts`** — added the `'pool-full'` member to `SignatureRejectReason` (with a doc
  comment). No exhaustive switch over that union exists anywhere else in the repo (verified — the
  `taleus-core` "equivocation" references are a separate single-referee concern in another package), so
  nothing else needed updating.
- **`consensus/participant.ts`** — reworked the merge:
  - Split the old `mergeSignature` into: a shared `checkMemberAndRole` gate; the **unchanged** promise
    branch (still dedupe-before-verify, which is safe for promises); and a new commit path.
  - `mergeCommit(merged, signature, pending)`: promise phase complete → `promoteCommit`; incomplete →
    `poolCommit`.
  - `promoteCommit(merged, signature)`: **verify FIRST**, then the dedupe/equivocation check against
    `merged.commits` (now a verified-only set), append on no collision. Used by both an incoming
    complete-phase commit and the drain.
  - `poolCommit(merged, signature, pending)`: idempotent on identical `(type,address,value)`; capped at
    `MAX_PENDING_COMMITS_PER_REFEREE` (**= 4**, a module const) **per signer** → overflow dropped as
    `pool-full`; else append to `pending` in place.
  - `drainPendingCommits(merged, pending)`: when promise phase complete and pool non-empty, `splice` the
    pool empty and run each through `promoteCommit` in insertion order (earliest genuine face stands).
  - `validateAndMerge`: after merging incoming promises, `getPendingCommits` → `drainPendingCommits` →
    merge incoming commits (passing `pending`) → `saveRecord` → `savePendingCommits` (only when the pool
    is or was non-empty, to avoid writing an empty pool on every promise-only update).
  - Removed the obsolete "liveness edge" `NOTE:` block.
  - Updated the `countVerifiedCommits` doc comment (re-verify is now purely defensive; unverified commits
    live in the pool, not in `commits`).

The invariants the code upholds: a genuinely-signed vote can never be suppressed by a signature that
does not verify; a referee that verifiably signs both faces is still caught as `equivocation` with the
first-arrived face standing; an honest early (out-of-order) commit is pooled, then drained+counted once
the promise set fills.

## What REMAINS (do these)

### 1. One pre-existing unit test MUST be updated (it intentionally changes behaviour)

`packages/tallynet/src/consensus/participant.test.ts`, the test **"retains an out-of-order commit
unverified, then counts it once the last promise lands"** (currently ~line 592). Under the fix, after
*delivery 1* (r2's commit arrives before bob promised) the commit is **pooled, not in `merged.commits`**.
So `expect(afterFirst.commits).toHaveLength(1)` is now wrong — it should be `toHaveLength(0)`, and the
test should additionally assert the pool holds it (read `store.getPendingCommits(base.transactionCode)`
→ length 1, or route the harness `store` out and check). Delivery 2 (bob's promise lands) must still end
in `settled: ['commit']` and `releaseSuccesses: [true]` — that part is unchanged. This is **not** a
pre-existing failure to triage; it is the fix changing the intermediate representation, so update the
test to match the new (correct) semantics. Do not skip it.

> Note: the harness in `participant.test.ts` returns `store` from `harness({...})`, so you can read
> `getPendingCommits` directly. The `MemoryTrxStore` now has those two methods.

### 2. `consensus/store.test.ts` — pending-commit pool coverage

Add a `describe('MemoryTrxStore — pending commits')` (or fold into the existing `MemoryTrxStore` block):
round-trip `savePendingCommits`/`getPendingCommits`; per-`transactionCode` keying (a different tx is

tests).

### 3. `participant.test.ts` — focused pool/drain unit tests (cheaper than the full network)

The single-participant harness can exercise the pool/drain transition directly. Add tests mirroring the
network cases where the harness supports it:
- Garbage `C` pooled pre-promise does not block the genuine `C` (deliver completing promises + genuine
  `C` → settles commit; `rejectReasons` contains `forged` from the drained garbage, never `changed`/
  `equivocation`).
- Garbage `NC` pooled pre-promise, same result.
- Pool cap: inject > 4 distinct pre-promise garbage commits for one referee → overflow rejected as
  `pool-full`; a genuine vote for that referee afterward still verifies and counts.
- Genuine equivocation still refused (both faces verify; first-arrived stands) — keep/extend the
  existing equivocation tests.

### 4. `testing/consensus.test.ts` — multi-node `describe` block

Follow the existing adversarial-signature pattern there (`makeSigner(seed, name)`, `corrupt`, an
observer/relay node `X`, two-phase `update()` delivery — see the existing
`'a forged referee commit is dropped'` test at ~line 504 for the exact idiom: build a `complete`
record with both participant promises, sign commits over it, deliver via `net.consensusNode('X').update(...)`
then `net.clock.runUntilIdle()`). Add:
- **Garbage `C` injected pre-promise does not silence the genuine vote.** Deliver `{ ...record,
  promises: [], commits: [corrupt(genuineC_for_R)] }` first (pooled), then `{ ...record, promises:
  [aliceP, bobP], commits: [genuineC_for_R] }`. Assert `X.outcome(tx) === 'commit'` (R sole referee or a
  majority needing R) and R's vote counted. **This is the headline regression test** — it failed under
  the old code (outcome `pending`, reject `changed`).
- **Garbage `NC` injected pre-promise** (collided as `equivocation` under old code): same, garbage `NC`
  first; genuine `C` still counts → commit.
- **Honest out-of-order early commit still counts.** Deliver R's **genuine** `C` before the promise phase
  completes (pooled), then a **separate** update carrying only the completing promise(s) and **not**
  re-carrying the commit; assert the pooled genuine commit drains, verifies, counts → commit. Guards the
  behaviour the pool must not regress.
- **Genuine equivocation still refused.** A referee signing two *verifying* opposite faces over the
  complete promise set is refused as `equivocation`; first (earlier) face stands; outcome matches it.
  (Keep the existing post-commit equivocation test too.)
- **Pool cap.** > `MAX_PENDING_COMMITS_PER_REFEREE` distinct pre-promise commits for one referee → the
  overflow drops with `pool-full`; a genuine vote for that referee afterward still verifies and counts
  (the cap must not lock out the real vote).

> Observer/relay `X`: a non-member node (so it only merges + classifies, never acts). Use a graph that
> includes an `X` node name but leave `X` out of the lift `members`, as the existing forged-commit test
> does.

### 5. `packages/tallynet/docs/design.md` — § Protocol design (Consensus)

Add the general rule, stated plainly: **no unverified input may change state that blocks a verified
one.** Concretely note: unverified commit-phase signatures are held in a durable side pool (keyed by
`transactionCode`, capped per referee, never digested/pushed) and are only promoted into the counted
`commits` set after they verify against the complete promise set; promise-phase signatures need no pool
because they are verified on arrival and an unverified promise is never stored (so a forged promise can
never become the `existing` that shadows a genuine one). The Consensus section is around lines 75–94
(the bulleted "Changes from ChipNet" list and the `*Implemented in ...*` footer); add the rule as a new
bullet or a short paragraph there.
