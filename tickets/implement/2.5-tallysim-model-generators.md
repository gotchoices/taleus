# tallysim — network model + generators

First of three chained implement tickets that stand up the `tallysim` package and answer the
network-shape half of Taleus's central research question: **how connected must a tally network be
before a payment can usually find a route through it?** This tier measures the *graph* alone, with an
**oracle** that sees the whole network and searches it directly — deliberately separate from the real
routing protocol (which the later `tallysim-discovery` tier runs on the same graphs). See the parent
plan's *Why* for the two-questions split.

The chain:
- **this ticket** — package scaffold + network data model + seeded generators (the networks).
- `tallysim-oracle` (next) — the whole-graph search: does a route exist, max-flow, clearing cycles.
- `tallysim-runner` — experiment runner + CLI + metrics + first checked-in experiment. This is the
  **tail** of the tier; `tallysim-discovery` and the trading-model backlog item depend on it.

This ticket delivers everything needed to *build* a network as plain serialisable data; it does **not**
search it (that is `tallysim-oracle`). Keep the package **platform-neutral** (runs in Node and the
browser — the viewer runs simulations live in a page), so no Node globals in the core.

## Package conventions

New Yarn-workspace package `packages/tallysim`, unscoped name `tallysim`, modelled on `packages/tallynet`
(copy its `package.json`, `tsconfig.json`, `tsconfig.build.json`, `jest.config.ts` shapes): ESM
(`"type": "module"`, `.js` import specifiers), TypeScript strict, tabs, single quotes, jest + ts-jest.
Root `yarn build` / `yarn test` / `yarn lint` pick it up automatically via `workspaces: ["packages/*"]`.

- **One dependency on a sibling: `tallynet`** (`"tallynet": "workspace:^"`). Never depend on
  `taleus-core`. Later tiers also use `tallynet`'s discovery engine and `tallynet/testing` harness; this
  tier uses only its PRNG and port.
- **Reuse `tallynet`'s seeded PRNG — do not inline a new one.** `tallynet/testing` exports
  `SeededRandom` (mulberry32; `packages/tallynet/src/testing/random.ts`) implementing the `RandomSource`
  port (`packages/tallynet/src/crypto.ts`). Use it everywhere randomness is drawn. (This supersedes the
  parent plan's "inline a small PRNG" bullet: the shared PRNG means one seed replays graph generation
  *and*, in later tiers, the protocol's own randomness — the whole run is reproducible from one seed.)
  `SeededRandom` already offers `nextFloat()`, `nextInt(maxExclusive)` and `randomBytes(n)`.
- **Platform neutrality enforced.** Copy `tallynet`'s `no-node-globals.test.ts` guard (greps every
  non-test, non-CLI source file for Node globals) and build the shipped artifact under a
  `tsconfig.build.json` with `types: []`. The CLI (a later ticket) is the sole Node-specific file and is
  excluded from this guard and build.
- **Determinism rule (load-bearing for the whole simulator).** No `Math.random`. No behaviour may depend
  on unordered-key iteration (`Object.keys`/`Map`/`Set` traversal order deciding a result): iterate
  arrays in a defined order, or sort first. Same seed ⇒ byte-identical network.

## Network data model

The model is plain JSON-serialisable data so a scenario can be saved, shared and replayed. **Entities**
are nodes, **tallies** are edges. Keep entities index-based (an integer id `0..n-1`) — no per-entity
payload is needed at this tier.

```ts
/** A credit relationship between two entities = one edge. Multiple tallies between the same pair are
 *  allowed (two tallies are two edges). No self-loops (stock !== foil) unless a generator is explicitly
 *  asked for them. */
interface Tally {
	stock: number   // entity id of the stock holder (conventionally the creditor side)
	foil: number    // entity id of the foil holder (conventionally the debtor side)
	balance: number           // b: units the foil currently owes the stock (signed; see Capacity model)
	stockCreditLimit: number  // L_stock: how far the stock lets the foil owe it (upper bound on b)
	foilCreditLimit: number   // L_foil: how far the foil lets the stock owe it (lower bound: b >= -L_foil)
}

interface Network {
	entityCount: number
	tallies: Tally[]
	meta: {
		generator: string            // generator id, e.g. 'uniform' | 'scale-free' | 'clustered' | 'small-world'
		params: Record<string, number>
		seed: number
		formatVersion: number        // bump when the shape changes; readers check it
	}
}
```

**Unlimited capacity.** A credit limit of `Infinity` means unbounded (the "unlimited capacity"
experiment variant). `Infinity` does not survive `JSON.stringify` (becomes `null`); the (de)serialiser
in this ticket must map `Infinity` ↔ a sentinel (e.g. the JSON value `null`, documented) so a saved
scenario round-trips. Provide `serialize(network): string` / `deserialize(string): Network` and test the
round-trip, including unlimited limits and an empty network.

### Capacity model (settles the parent plan's first design point)

A lift (or payment) moves value across a tally in one direction; how much it can move before hitting a
credit bound is that tally's **directed capacity**. Define the balance `b` from the foil's obligation:
`b` = units the foil owes the stock, so `b ∈ [-foilCreditLimit, +stockCreditLimit]` (the foil may owe
the stock up to `stockCreditLimit`; the stock may owe the foil up to `foilCreditLimit`, i.e. `b` as low
as `-foilCreditLimit`). "Value flows X→Y" means Y ends up better off (X takes on the obligation). Then,
per tally between stock `S` and foil `F`:

```
cap(F → S) = stockCreditLimit - b     // value flows foil→stock: b increases toward +stockCreditLimit
cap(S → F) = b + foilCreditLimit      // value flows stock→foil: b decreases toward -foilCreditLimit
```

Both are non-negative integers; `cap(F→S) + cap(S→F) = stockCreditLimit + foilCreditLimit` (the total
swing, independent of `b` — the current balance only sets the *split*). A zero-capacity direction
(`b` at a bound) is a valid, expected state.

This is the MyCHIPs lift-capacity idea reduced to what the **oracle** needs: raw credit-limit room,
answering *does capacity exist*. It deliberately **omits trading-variable fee structure**
(`target/bound/reward/clutch`, the `LiftLading` view in `docs/architecture.md`): those bound a lift's
*cost* and which routes an agent *prefers*, not whether a route physically exists. Fees and the balance
dynamics that consume capacity over time belong to the protocol tier and the trading-model backlog item,
not the oracle. Record this scoping decision in `docs/design.md`.

### Capacity / balance distributions

A generator assigns each tally its orientation (which endpoint is stock vs foil) and its
`(stockCreditLimit, foilCreditLimit, balance)` from a **parameterised distribution**, chosen per run:
- `unlimited` — both limits `Infinity`, `balance` 0 (the capacity-is-never-the-constraint baseline).
- `constant` — fixed limits, `balance` 0 (or a fixed start).
- `uniform` / `lognormal` — limits drawn from the distribution; `balance` drawn within
  `[-foilCreditLimit, +stockCreditLimit]` (or started at 0 — document the default).

Keep distributions as small, named, seeded functions over `SeededRandom`. Document each one's parameters
in `docs/design.md`.

## Generators

Four seeded generators, each a small function `(params, rng: RandomSource) => Network`, each with
**documented parameters** and a stable `meta.generator` id. Same seed ⇒ same network (test it).

- **`uniform`** — Erdős–Rényi style, parameterised by **mean tallies per entity** `k`. Create
  `m = round(n · k / 2)` edges between random distinct pairs; parallel edges allowed (two tallies between
  a pair are two edges), no self-loops. (At the extreme `k = 0` → no edges; document behaviour.)
- **`scale-free`** — Barabási–Albert preferential attachment, parameter `m` = edges each new entity
  brings; start from a small seed clique. Produces a few hubs and many small entities.
- **`clustered`** — communities (parameters: community count `c`, mean intra-community degree, and a
  tunable **number of bridge tallies** between communities). Dense within a community, sparse between.
- **`small-world`** — Watts–Strogatz: a ring lattice where each entity links `k` nearest neighbours,
  then each edge is rewired with probability `β`.

Orientation (stock vs foil per edge) is assigned by the generator deterministically from `rng`; document
the rule. Capacities/balances come from the chosen distribution (above).

## Structural utilities (needed by generator tests and, later, metrics)

Small pure graph utilities on a `Network`, used here for fidelity tests and reused by the runner's
metrics:
- **degree histogram / mean degree** (over the undirected multigraph).
- **connected components + largest-component fraction**, via union-find over the undirected edges.

Both must iterate deterministically. Place them where both the model and later the runner can import them
(e.g. `src/structure.ts`).

## Edge cases & interactions

- **Extreme parameters:** mean degree 0 (no edges → every entity isolated), a near-complete graph, a
  single community (`c = 1`), `β = 0` (pure lattice) and `β = 1` (fully rewired) for small-world. Each
  must produce a valid `Network` without throwing.
- **Multi-edges** between the same pair are allowed and counted as two tallies; **no self-loops**
  (`stock !== foil`) unless a generator explicitly offers them.
- **Zero-capacity directions** arise naturally when `balance` sits at a credit bound — valid data.
- **Disconnected graphs / isolated entities** are expected outputs, not errors.
- **Serialisation round-trip** must preserve `Infinity` limits and an empty network.
- **Determinism across platforms:** no `Math.random`; no result depending on unordered-key iteration.

## Tests to plan

- **Package builds, lints, tests green**, and the `no-node-globals` guard passes over the core.
- **Each generator — seeded reproducibility:** same seed ⇒ deep-equal `Network` (and a different seed ⇒
  different, to catch an ignored seed).
- **Parameter fidelity within tolerance:** measured mean degree ≈ `k` for `uniform`; `scale-free`
  degree distribution is heavy-tailed (a hub emerges); `clustered` has more intra- than inter-community
  edges and exactly the requested bridge count; `small-world` has the lattice's degree with the expected
  rewiring fraction.
- **No self-loops** in any generator's output (unless asked); multi-edges permitted.
- **Capacity model:** `cap(F→S) + cap(S→F) === stockCreditLimit + foilCreditLimit`; both non-negative;
  at a bound one direction is 0; `unlimited` yields `Infinity` capacities.
- **Serialisation round-trip** (incl. `Infinity`, empty network).
- **Structural utilities:** union-find largest-component fraction on hand-built graphs (fully connected
  = 1; two equal halves = 0.5; all isolated = 1/n).
