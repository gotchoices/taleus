This is the first of three tickets that split the original `5.5-tallysim-voter-model`. The original asked for the whole voter-model measurement step at once; it is too large for one pass. This ticket builds the **pure policy layer** — functions that take data and return a decision, with no network, clock, or harness wiring. Ticket `tallysim-voter-harness-drive` wires these into the running simulator; ticket `tallysim-voter-model` adds the sweep runner, metrics, CLI columns, and docs.

## Vocabulary (define once, used across all three tickets)

- **Voter / voter set.** A lift (payment) settles when a quorum of its *voters* sign commit. In `tallynet` a member's roles are `['P']` (participant, on the chain), `['V']` (voter), or `['P','V']`. A **referee** is a voter that is *not* also a participant (`V`-only) — someone vouching who isn't on the money path. The voter set of a plan is `plan.members.filter(m => m.types.includes(MemberTypes.voter))`.
- **Well-known node.** A node the rest of the network recognises — here made measurable as a **high-degree hub**. "Trusted voter" = a voter that is well-known; "obscure voter" = one that is not.
- **Stacked voter set.** A voter set padded with obscure `V`-only members (referees nobody knows) to dilute or game the quorum. The payer's policy should refuse these.

## What the tallynet prereqs already give you (do NOT rebuild)

The prereq tickets landed a rich API in `packages/tallynet/src/`. Read these before writing code:

- **`ScorePlan`** (`discovery/originator.ts`): `(plan, query) => number`, **higher is better**; `-Infinity`/`NaN` means "never pick / drop this plan". `defaultScorePlan` already prefers *fewer voters, then shorter path*: `-(voters + hops/(query.maxDepth+1))`. This ticket's voter-aware scorer should build on this shape (prefer fewer **and better-known** voters).
- **`TrxParticipantResource.acceptsProposal(ctx)`** (`consensus/resource.ts`): the promise-time gate. Returning `false` signs `NP` (no-promise) → the lift **voids**. `ctx.record.topology.members` is the full member list; the voter set and each member's `physical` contact point are readable there. The resource doc explicitly says *"Refuse a thin/stacked voter set lives HERE (the simulator's voter-model policy)"*.
- **`DiscoveryHooks.negotiatePlan(plan) => plan | undefined`** (`discovery/hooks.ts`): the discovery-time mirror — returning `undefined` drops a plan whose voter-set-so-far a node rejects. (Wiring `negotiatePlan` is the next ticket's job; this ticket only needs the **refusal predicate** that both `acceptsProposal` and `negotiatePlan` will call.)
- **`MemberTypes`** exported from `tallynet` — `participant` = `'P'`, `voter` = `'V'`.

## What to build in this ticket

### 1. Well-known derivation (`structure.ts` or a new tiny `sim/well-known.ts`)

A deterministic predicate over entity ids: the top-`k` highest-degree nodes are "well-known". Degree is already computable (`structure.ts` has `meanDegree`; count each entity's incident tallies). Signature sketch:

```ts
/** The `round(fraction · entityCount)` highest-degree entities (ties broken by lower id), as a Set. */
export function wellKnownEntities(network: Network, fraction: number): Set<number>
```

**Design note (a deliberate departure from the original ticket's TODO).** The original said "mark well-known nodes *in the generators*". The ticket's own `files:` list did **not** include `generators/`, and baking a flag into the `Network` model would ripple through serialization and the pinned byte-identical discovery sweep. Deriving well-known from **degree** instead keeps the model untouched, stays deterministic, and makes "trusted" measurable (a hub is well-known). Document this choice in the next ticket's doc update. If a future need arises for *explicit* marking, that is a separate model change.

### 2. Voter-aware plan score (`plan-select.ts`)

Add a `PlanPolicy` value (e.g. `'voter-aware'`) and a scorer that ranks a plan by its voter set: prefer **fewer** voters, and among those prefer **well-known** voters, then shorter path, then first-found. Reuse the `defaultScorePlan` idea but add an "obscure voter" penalty. Two shapes are needed and should share one core:

- a `PlanPolicy` branch in `selectPlan(plans, policy)` so the simulator's own pick (`selectPlan` over `outcome.plans`) is voter-aware; and
- an exported `tallynet`-shaped `ScorePlan` (so the next ticket can pass it to `buildSimNetwork` as the discovery originator's scorer, keeping discovery ordering and the final pick consistent).

`selectPlan` needs the well-known set to score, so its signature grows an optional argument (e.g. `selectPlan(plans, policy, wellKnown?)`). Keep `'shortest'` working unchanged (it ignores well-known).

### 3. `acceptsProposal` + non-relayer in the resource specs (`consensus-resource.ts`)

Extend `SimResourceSpec` and `makeSimResources`:

- Add an `acceptsProposal` option that **refuses a stacked voter set**: given the well-known set, refuse (return `false`) when the record's voter set contains more than a tolerated number of obscure (`V`-only, not-well-known) voters. The predicate must read the voter set from `ctx.record.topology.members`. Record each refusal on the `SimResourceHandle` (add a counter/flag) so a test and the later metrics layer can count "refused because of the voter set" distinctly from an ordinary `shouldPromise:false`.
- Add a `nonRelayer` flag to `SimResourceSpec` **as documentation only is wrong** — the non-relayer is NOT a resource-port behaviour; it is a `tallynet` harness config (`refuseRelay`). Do not add it here. (Called out because the original ticket mislabelled it: see `tallynet`'s `refuseRelay` config, wired in the next ticket.)

Keep the entity-id keying and the existing `shouldPromise` / `promiseThrows` / `shouldCommit` behaviour intact.

### 4. Nomination builder (`consensus-resource.ts` or the new `sim/well-known.ts`)

A helper that produces a `nomineesFor`-shaped function (entity id → referee nominations) for a **nomination policy**: `'self'` (a participant nominates itself as voter — the default voter-set-of-one behaviour) or `'well-known'` (nominate a well-known voter from the network). The output shape is `tallynet`'s `RefereeNomination[]` (`{ name, physical? }`) keyed by node **name**; the wiring that adapts entity-id → node-name lives in the next ticket. Keep it pure (network + well-known set + policy in, function out).

## Tests (this ticket)

- `wellKnownEntities`: exact top-`k` by degree on a hand-built network; ties broken by id; `fraction` 0 ⇒ empty.
- `selectPlan` voter-aware: given hand-built plans with differing voter sets, picks the lean/well-known one; `'shortest'` unchanged; the exported `ScorePlan` agrees with the `selectPlan` ranking.
- `acceptsProposal`: refuses a record whose voter set is padded with obscure `V`-only members; accepts a lean/well-known set; the refusal is recorded on the handle.
- nomination builder: `'self'` yields self-as-voter; `'well-known'` yields a well-known nominee.
