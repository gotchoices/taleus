## What's wrong (reproduced)

A lift whose promise phase never completes — a needed participant dies, crashes, or is unreachable before it promises — stays **permanently pending**, with every participant that *did* promise holding its credit forever. Nothing can close it: today a voter can only vote once the **complete** promise set is in hand, and that set never arrives.

Concrete reproduction already in the tree: `packages/tallysim/src/sim/consensus-timeout.test.ts` § *"a needed party that never returns abandons and stays pending"* — `line(2)`, route `0→1`, `voters: [0]`, the sole link drops. Node 0 originates (so it **holds** the record) and promises its own `P`, but node 1 never receives the push and never promises. Node 0 is the sole voter sitting on an incomplete promise set. Its recovery loop polls, backs off, and abandons → `pending`. The test's `expect(result.outcome).toBe('pending')` is the bug encoded as an assertion; after this ticket it reads `void`.

### Why the voter is stuck (the code path)

`TrxParticipant.getRecordState` (`packages/tallynet/src/consensus/participant.ts:660`) classifies the promise phase first. With an incomplete set and no `NP`, it returns `promising` (or `ourPromiseNeeded`) and **returns before the commit phase** (`:665-670`). So `advanceState` → `castCommit` is only ever reached once `promisePhaseComplete` is true. `castCommit` already votes `NC` on an expired code (`:842-844`), but it is never called for a voter whose set is incomplete. At the deadline, `onRecoveryTick` → `runAdvanceLoop` finds state `promising` and does nothing. The voter never votes; the lift cannot resolve.

This is distinct from the genuinely-stuck **dead-voters** case, which must stay `pending`: e.g. `packages/tallynet/src/testing/consensus.test.ts` § *"a dropped push on the only path stalls"* (`:400`), where the voter `T` is *beyond* the dropped link and never receives the record at all. A node that never holds the record cannot vote on it. That test's outcome is unchanged by this ticket (node `A` there is a non-voter participant).

## The rule (settled with the developer, 2026-11-27)

**At its deadline, a voter that has not voted commit votes void (`NC`), whether or not it holds every promise.** A deciding majority of `NC` votes proves the lift can never commit, so every member releases on that proof.

Safe because an honest voter votes `C` only *before* the deadline and only over the *complete* promise set, and never signs both faces. Equivocation rules are unchanged: a voter that already signed `C` keeps `C` (its later `NC` would be refused and its proof kept). The closing word stays with the voters — a participant with an incomplete set never voids on its own; it waits for and pulls the voters' decision.

## Design decisions to carry into the build

### 1. Void preimage binds the immutable core only (chosen)

**Decision: a void vote's (`NC`) preimage binds the immutable record core only — never the promise set — always.** A commit (`C`) must keep binding the complete promise set, because that set is the proof that everyone promised. A void needs no such proof: the whole point is that the set may be incomplete.

Chosen over the alternative (a separate "void-before-complete" face type) because it is strictly simpler and has a direct side benefit: **a void vote verifies the instant it arrives**, so `NC` needs no side pool at all (today both `C` and `NC` route through the pending-commit pool when the phase is incomplete). One `NC` face works identically with or without a complete set, so there is no second code path to keep consistent.

This preserves the invariant *"nothing unverified may block a verified vote"*: an `NC` is now always verifiable, so it is never pooled and never shadowed; a forged `NC` fails verification on arrival (its signer's core won't match ours) and is dropped `forged`, exactly as a forged promise is.

Concretely in `digest.ts` (`recordDigest`, `:85-90`): include the `pr` key for `kind === 'C'` **only**, not `'C' || 'NC'`. `signRecord`/`verifySignature` already pass `record.promises` through and need no change (`recordDigest` will simply ignore it for `NC`), but update their doc comments (they currently say "the commit preimage binds the promise set" — now only the *commit* face does).

### 2. Settlement counting

- A **void** majority settles (`rejected`) from the voter set in the topology, **regardless of whether the promise set is complete**. Because `NC` now verifies standalone, `countVerifiedCommits(record, 'NC', voters)` is valid at any time.
- A **commit** majority still requires the complete promise set (unchanged): `C` only verifies against the complete set, and `countVerifiedCommits(record, 'C', voters)` is only meaningful once `promisePhaseComplete`.
- Keep the existing `settles(count)` formula (strict-majority floor **and** method threshold) for both sides — unchanged. The void check simply moves earlier so it runs before the promise-phase gate.

### 3. Getting the record to voters

A voter can only vote `NC` on a lift it **knows about**. A node holding an incomplete record already force-re-pushes it (recovery loop, `:1079`) and serves pulls (`serveRecord`), so the record reaches every *reachable* voter through the existing push/pull/contact-point machinery — no new transport code. Requirement: **when a voter majority never hears of the lift, it stays `pending`** (the dead-voters case). This is unchanged behavior and must be preserved: the fix only lets a voter that *holds* the record decide; it never fabricates a decision at a node that cannot see the lift.

### 4. Clocks

Each voter acts at its **own** deadline. The autonomous trigger is its recovery timer, armed at `expiresAt(transactionCode) + skewGraceMs` (`SKEW_GRACE_MS`, per-node). The classification gate uses `anyCodeExpired` (raw expiry) to match the existing `castCommit` NC path — consistent with how a complete-set voter already votes `NC` on any post-expiry delivery. The skew grace continues to govern when the timer fires autonomously, not the classification itself.

## Edge cases & interactions (cover in tests)

- A voter that is also the dead participant (`P`+`V` that never promises): at its deadline its participant face signs `NP` first (via `ourPromiseNeeded` → `castPromise` expired path) → `rejected` globally. The voter-`NC` branch must sit *after* the participant-promise branch so this still voids as `NP`, not `NC`.
- A voter set of 1 (the reproduction): the sole voter's `NC` settles void.
- A threshold above ½: the no-settle band resolves to void once un-voted voters cast `NC` at the deadline (unchanged mechanism, now reachable on incomplete sets).
- A late promise arriving after some voters voided: their `NC` stands (verified over the core, independent of the set); the set completing later changes nothing.
- A voter that committed `C` before the deadline while others void at the deadline: settle by majority as today — add the **safety** scenario where the set completes just before the deadline at a remote node and a voter majority commits (`C`): **no member may release/void**. This guards against premature voiding.
- A forged `NC` (core mismatch) must never count: it fails verification on arrival and is dropped `forged`. Add/keep a test.
