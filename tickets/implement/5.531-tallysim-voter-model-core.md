First of **two** tickets splitting the original `5.53-tallysim-voter-model` (which was itself the third of the
three tickets splitting `5.5-tallysim-voter-model`). The split happened because the single ticket crossed the
token budget during investigation before any code landed. This ticket builds the **headline measured
experiment — the "principle 3" completion curve** on straight-line routes: how payment completion falls as more
nodes stop relaying, with and without published contact points. The sibling `tallysim-voter-model` (seq 5.532,
keeps the original slug so `tallysim-viewer-voter-model`'s `prereq` still resolves) adds circular routes, voter
nomination, stacked-voter plan-refusal, the consensus-threshold override, and the full doc subsection.

"Principle 3" is shorthand (from the two prereq handoffs) for: *a node that has promised but then goes dark
cannot be allowed to strand the payment; a member the commit push can't reach must be able to pull the settled
record from a reachable peer (a published contact point, or a link-neighbour).* The curve this ticket measures:
completion stays at 1.0 while ≤ 1 node on the route is dark **and** contact points are published; without contact
points a straight line shows a visible completion cliff (the dark node's far side can't reach the evidence).

  (`harness.ts`) already expose the ports `refuseRelayFor(entityId)` (non-relayer: promises then drops every
  commit-phase record, serves no pulls) and `silentAfterPromiseFor(entityId)` (offline-after-promise). Both are
  entity-id-keyed and adapted to node names at the harness boundary. **This ticket wires the scenario knobs into
  these ports in the runner** — the ports themselves need no change.
- **`compileConsensusConditions(network, spec, seed)`** (`conditions.ts`) today draws only `refusers`

  runner and the trace recorder deriving the same sets for a given `(scenario, runSeed)`.
- **`runConsensusQueries`** (`consensus-runner.ts`) calls `runLiftForOutcome(sim, network, outcome, query)` with
  **no options today**. This ticket passes the per-lift `RunLiftOptions` (`contactPoints`, `nonCooperating`).
- Metrics pipeline: `analyzeLift(events, result) → ConsensusLiftMetrics`, `summarizeConsensusMetrics(lifts,
  structural, queryCount) → ConsensusRunMetrics` (`consensus-metrics.ts`); CSV column order lives in

## Scope of THIS ticket

### Scenario knobs (`scenario.ts` `ConsensusSpec`)

Add, each JSON-serialisable (round-trips through the trace header) and cloned one level deep in
`cloneConsensus` (it already does `{ ...consensus }`, which covers flat scalars/booleans — **verify** that
suffices; the new knobs are all scalar/boolean, so it should):

- `contactPoints?: boolean` — threads to `RunLiftOptions.contactPoints` (stamps `physical` on originator + voters).
- `nonRelayerFraction?: number` — `round(fraction · entityCount)` nodes made **non-relayers** (`refuseRelay`).
  **Distinct** from the existing `refuserFraction` (a `shouldPromise:false` voider). Compiled on the dedicated
  consensus seed, same discipline as refusers.
- `silentAfterPromiseFraction?: number` — `round(fraction · entityCount)` nodes made silent-after-promise
  (`silentAfterPromiseFor`). (The original ticket floated `silentPayee?: boolean` as an alternative; a
  count-based fraction on the dedicated seed is cleaner and matches the refuser/non-relayer discipline — use the
  fraction and note in the doc that it subsumes the "payee goes silent after mint" edge case. The per-query payee
  isn't a fixed set, so a fraction over all entities is the right model here.)

### `conditions.ts`

Extend `ConsensusConditionsSpec` with `nonRelayerFraction?` + `silentAfterPromiseFraction?`, and
`CompiledConsensusConditions` with `nonRelayers: Set<number>` + `silent: Set<number>`. In
`compileConsensusConditions`, draw refusers (unchanged, FIRST), then nonRelayers, then silent — all from the one
`SeededRandom(seed)` via `pickFraction(range(entityCount), …, rng)`. Document the draw order in the JSDoc (so a
seed replays exactly), mirroring the existing comment style.

### `consensus-harness.ts` — `LiftResult` + `runLiftForOutcome`

Add two fields to `LiftResult`, computed at the END of `runLiftForOutcome` (after the pull pass, before return):

- `cooperatingMembers: number` — count of **distinct** route entities **not** in `options.nonCooperating`
  (the members that are allowed to reach commit — a non-relayer/silent node never recovers, so excluding it keeps
  the completion fraction honest, exactly as the pull pass already excludes them).
- `cooperatingCommitted: number` — how many of those cooperating members have `outcome(txCode) === 'commit'`
  after settlement + recovery.

`recoverStrandedByPull` already queries each cooperating member's outcome; factor out or reuse a small
`countCommitted(net, route, txCode, nonCooperating)` helper rather than re-deriving the member set three times.
Keep the circular-route single-originator case correct (`[...new Set(route)]` dedupes the repeated origin).

### `consensus-metrics.ts` — the completion + pull metrics

Add to `ConsensusLiftMetrics`: `cooperatingMembers`, `cooperatingCommitted`, `pullMessages` (= `result.pullCalls`),
`recovered` (= `result.recovered`). Carry them from the `LiftResult` in `analyzeLift` (these are already on the
result; no event scanning needed).

Add to `ConsensusRunMetrics` + aggregate in `summarizeConsensusMetrics`:

- `cooperatingMemberTotal` (Σ `cooperatingMembers`), `cooperatingCommittedTotal` (Σ `cooperatingCommitted`),
  `cooperatingCompletion` = committedTotal / memberTotal **guarded to 0 when memberTotal === 0 (never NaN)**. This
  is the principle-3 curve's y-axis — plotted against the swept `consensus.nonRelayerFraction`.
- `pullMessagesPerLift: DistributionSummary` (over all lifts, via `summarizeDistribution`) — the extra messages a
  pull costs. Call it out: pulls cost messages but buy completions.
- `recoveredTotal` (Σ `recovered`) — stranded-then-settled members across the run.

### CSV (`serialize-consensus-records.ts`)

Add the new scalar columns to `CONSENSUS_METRIC_COLUMNS` in canonical order (after the existing scalars, before or

`cooperatingCompletion`, `recoveredTotal`, then `...distributionColumns('pullMessagesPerLift')`. The generic CSV

## Tests (this ticket)

- **Principle-3 curve, linear, WITH contact points** (sweep): a materialised `line(N)` swept over
  `consensus.nonRelayerFraction` with `contactPoints: true` ⇒ `cooperatingCompletion` holds at `1.0` while the
  selected non-relayer count is ≤ 1. Re-derive the selected non-relayer via `compileConsensusConditions` in-test
  (the existing runner test does this for refusers — copy the pattern) so the pinned seed is transparent.
- **Principle-3 curve, linear, WITHOUT contact points** (sweep): same sweep, `contactPoints: false` ⇒ a visible
  cliff — members beyond the interior non-relayer stay `pending`, so `cooperatingCompletion < 1.0`. Assert it as
  the **expected gap**, not a failure (mirror the voter-harness test's "documented gap" framing).
- **Tie ⇒ unsettled** (harness-level, in `voter-harness.test.ts`): a `line(3)` (or larger), build with
  `resourceFor = makeSimResources({ 1: { shouldCommit: false } }).resourceFor`, drive
  `runLiftForOutcome(..., { voters: [0, 1] })`. With a 2-voter set the strict-majority floor needs `count*2 > W=2`
  ⇒ `count ≥ 2`; one commit + one `NC` reaches neither side ⇒ `outcome === 'pending'` (a clean third outcome, not
  a hang or crash). Assert `deliveryErrors === []` and `clock.pendingTimers === 0`.
- **Determinism** (extend `consensus-runner.test.ts`): two runs of the same spec (with the new knobs set) yield
  byte-identical records (`expect(a).toEqual(b)`).
- **CSV columns**: extend `serialize-consensus-records.test.ts` — the new columns appear in canonical order and
  only when present (mirror the existing `createConsensusCsvAccumulator` + header-order assertions).
