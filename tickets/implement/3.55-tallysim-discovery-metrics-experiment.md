## `experiments/found-vs-oracle/` — mirror `experiments/route-existence/`

Same shape as the sibling oracle experiment: committed `specs/*.json` (`SimSweepSpec` files), a `regenerate.sh` that rebuilds tallysim and runs each spec through `node dist/cli/simulate.js` (streaming output, so wrap long runs in `tee`), committed `out/*.{jsonl,csv}`, an optional combined `found-vs-oracle.jsonl`, and a `README.md`. **Byte-identical reproducibility** is required (builds on the trace tier's byte-identical guarantee + the shared seeded streams) — `regenerate.sh` must reproduce the committed `out/` exactly.

The question: **how close does the decentralised protocol get to the oracle, and what does it cost?** At a fixed mid-degree topology (scale-free and/or uniform), sweep three things (one spec each keeps each plot one- or two-dimensional):

1. **Depth limit `D` (and time budget `perHopBudgetMs`) vs `pFoundGivenExists`** — where does the protocol stop finding routes the oracle sees? **Critical framing (do not mislabel):** the sim runner runs the oracle at the *same* depth as the protocol, and the protocol's reach is only ≈ ⌊maxDepth/2⌋+1 hops (see `docs/design.md` § "Rounds ↔ hops"). So the gap a depth sweep shows is **expected protocol cadence (reach cost), not a connectivity failure.** Either budget the protocol's `maxDepth` at ≈ 2× the oracle hop distance being probed, or label the gap explicitly as the reach cost in the write-up. State which you did.
2. **Sleeping-node fraction (`conditions.sleepingFraction`) vs `pFoundGivenExists` and `messages`** — how fast does success fall as nodes go dark? Use a generous depth so the reach cadence is not the binding constraint.
3. **Latency (`conditions.latency`, e.g. a constant base) vs `timeToCompletionMs` and `roundsUsed`** — cost, not success (keep reliability ideal). For `vary` to reach a latency leaf, the base scenario must declare `conditions.latency` as a `{ kind:'constant', value:… }` object so `setByPath` can step `conditions.latency.value`.

**Keep the grid small and genuinely fast (route discovery is seconds but far costlier than the oracle's BFS).** Modest entity counts (`N ∈ {100, 1000}`, and prefer `N = 100` for the sleeping/latency sweeps), a few seeds (e.g. `[1, 2]`), ~50 queries per run. **Measure `regenerate.sh`'s wall-clock during implementation** and trim the grid so it stays well under ~10 minutes (agent-runnable); if `N = 1000` at high depth proves slow, cap it or drop it and note the deferral. The cost-ceiling concern is a tripwire, not a ticket — a `NOTE:` already lives at the sim-runner per-query loop (added by the core ticket); add a line to the experiment README about keeping grids modest.

## Guardrail

Every run must report `falseFoundCount === 0` (found ⊆ oracle). If any committed record shows `> 0`, that is a harness/terms bug — stop and file a `fix/` ticket rather than committing the data.
