Add the consensus **failure-injection** knobs to the scenario model, plus the one genuinely new selection
helper. The four failure modes the parent ticket names map onto the code like this — **only the refuser is
new**; the other three are the *existing* `ConditionsSpec` knobs, which already degrade the consensus phase
because the harness's `pushCondition` (tallynet `testing/network.ts`) reuses the very same per-link
conditions map that `compileConditions` produces:

| Failure mode | Where it lives | How it bites consensus |
|---|---|---|
| **A refuser** (signs `NP`) | **NEW**: `consensus.refuserFraction` → `resourceFor` with `{ shouldPromise: false }` | a refuser on a taken route voids that lift (`refused-promise`) |
| **A node that sleeps mid-transaction** | existing `conditions.sleepingFraction` | both its incident links `drop`; a consensus push to/from it never delivers → the lift **stalls** (`pending`) |
| **A dropped push** | existing `conditions.dropFraction` | those links `drop`; a push over a cut edge on the route stalls |
| **A slow voter / late fold** | existing `conditions.lateFraction` + `lateLatencyMs` | the late link delays the push; the record folds in late, so `timeToSettleMs` grows but the lift still settles |

**The key mechanism that makes `stalled` reachable with ONE network build** (write this into the design
doc, sibling `tallysim-consensus-docs-experiment`, but understand it here): a sleeping/dropped **target**
is still *found* by discovery (a neighbour resolves the peer-match terminus from its own adjacency without
delivering to the target), but consensus needs the target (a route participant) to promise — and the push
to it drops — so the lift stalls. Discovery succeeds, consensus stalls, on the same degraded network. This
is why no separate "clean discovery / dirty consensus" build is needed. Document honestly the v1 asymmetry
(a dropped push on a *needed* edge stalls; phase-2 "a refuser only hurts itself" is out of v1),
cross-referencing `feat-tallynet-propagation-timeouts`.

## scenario.ts additions

```ts
/** Consensus-phase failure injection + identity. Drawn from the dedicated consensus stream (SimScenario.consensusSeed). */
export interface ConsensusSpec {
  /** Fraction of entities made refusers (a refuser on a taken route signs NP → that lift voids). Count-based. */
  refuserFraction?: number
  /** Seed for every node's deterministic ed25519 identity; omitted ⇒ a fixed default (e.g. DEFAULT_CONSENSUS_IDENTITY_SEED = 1). */
  identitySeed?: number
}
```

Add to `SimScenario`:
- `consensus?: ConsensusSpec` — omitted ⇒ discovery-only (consensus not driven). Its presence is the
  "run consensus" switch for the runner and the trace.
- `consensusSeed?: number` — the **dedicated** seed stream for the refuser selection, independent of the
  network / workload / conditions / economy seeds (same discipline as `conditionsSeed`): "do not perturb
  the discovery streams" means the refuser draw must not shift which network / queries / link-conditions a
  run gets.

`SimScenario` is embedded verbatim in trace headers, so both fields are optional and absent on a
discovery-only scenario.

## conditions.ts addition

Add a count-based refuser selector reusing the existing private `range` + `pickFraction` +
`partialShuffle` (the `round(fraction · poolSize)` seeded-partial-shuffle machinery — do **not** inline a
second copy):

```ts
export interface ConsensusConditionsSpec { refuserFraction?: number }
export interface CompiledConsensusConditions { refusers: Set<number> }
/** Select exactly round(refuserFraction · entityCount) refuser entity ids from a dedicated SeededRandom(seed). */
export function compileConsensusConditions(network: Network, spec: ConsensusConditionsSpec, seed: number): CompiledConsensusConditions
```

(`ConsensusSpec` is structurally assignable to `ConsensusConditionsSpec`, so the runner calls
`compileConsensusConditions(network, scenario.consensus, consensusSeed)` directly.)

## How the runner will consume this (for context, not built here)

The runner turns `refusers` into a resource port with the **already-existing** `makeSimResources` from
`consensus-resource.ts`: `makeSimResources(Object.fromEntries([...refusers].map(id => [id, { shouldPromise:
false }])))` → `resourceFor`, handed to `buildSimNetwork(..., { identitySeed, resourceFor })`.

## Tests (conditions.test.ts, count-based)

- `compileConsensusConditions` selects **exactly** `round(fraction · entityCount)` refusers (assert the
  precise count at a couple of fractions, e.g. 0.3 of 10 ⇒ 3), deterministically for a given seed.
- `refuserFraction` 0 / undefined ⇒ empty set.
- A different `consensusSeed` ⇒ a (generally) different refuser set, but the SAME seed ⇒ identical set.
