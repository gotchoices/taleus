## Scenario: network split → `pending` while split, convergence after rejoin

**What it proves:** a lift partitioned so two cooperating halves can't reach each other stalls `pending`
(each half holds a minority of votes, no majority forms); when a single cross-partition link reopens, the
recovery loop pulls across it, a majority forms, and every member converges and releases. This mirrors
ChipNet § Network splits ("any single cross-island link restores the trend toward resolution").

**Exact reference construction (already passes at the protocol level — copy its shape):**
`packages/tallynet/src/testing/consensus.test.ts` ≈ line 1273, *"recovery loop heals a network split on
rejoin"*: `P0` (a `[P]`-only minter, `refuseRelay`) links to voters `A` and `B` via `p0a`/`p0b` (always
open); `A—B` link `ab` starts `{ drop: true }`. P0 carries the promise phase (all `P` complete at t≈0) but
forwards no vote; each voter casts its `C` at t≈0 yet sees only its own (1 of 2, no majority) → both stall
`pending`. P0, which merges both votes, reaches 2 of 2 and commits. Flipping `ab.drop = false` then
`runUntilIdle()` lets a live recovery tick pull the far island's `C` across the restored link → majority →
both voters converge and release. Assertions there: `['commit','pending','pending']` while split, then
`['commit','commit','commit']` after heal; each releases once; `pendingTimers === 0`; `deliveryErrors === []`.

**Why it needs a harness touch + a hand-driven lift (the open problem the original ticket flagged):**
- `runLiftForOutcome` does `start(record)` then one `runUntilIdle()` atomically — it can't interleave the
  mid-drive "flip the link open" step. So this scenario must drive the lift by hand in the test:
  `net.buildLift({...})`, `net.consensusNode(route[0]).start(record)`, `runUntilIdle()` (split → pending),
  mutate the link condition, `runUntilIdle()` (heal → converge), read outcomes. The P0/A/B triangle (route
  `['P0','A']` + extra links `['P0','B']`, `['A','B']`, voters `{A,B}`, P0 the non-voting minter) does NOT
  map onto `runLiftForOutcome`'s line/cycle route model anyway, so a hand-built `net.buildLift` is required.
  `sanitiseRecordIntents` is private to consensus-harness.ts but is only needed for `unlimited`-capacity
  tallies (it finite-ifies `Infinity`); a hand-built finite-limit network (like the `line`/`ring` helpers)
  needs no sanitising, so the test can skip it.
- The mutable-conditions handle: `InMemoryNetwork` reads its `conditions` PER DELIVERY via `resolveCondition`
  (`packages/tallynet/src/testing/network.ts` ≈ line 799) and accepts either a `Record<string, LinkCondition>`
  or a `(linkId) => LinkCondition | undefined` function — so mutating the object it holds (`conditions[id] =
  {drop:true}` / `delete conditions[id]`) takes effect on the next delivery. **But `buildSimNetwork`
  (`harness.ts:171-205`) compiles conditions internally (`compileConditions`, line 191) and does not expose
  the live object** it passes to `InMemoryNetwork` (line 198). The original ticket weighed (a) rebuild-sim-
  and-re-drive vs (b) a mutable conditions surface, preferring (a) "if it works without new harness
  plumbing". **(a) does NOT work cleanly**: `buildSimNetwork` creates fresh per-node consensus stores each
  call, so a rebuilt sim loses the in-flight record and re-driving `start(record)` just restarts the lift
  over a healthy network (no split to heal). So go with **(b), minimally**: make `buildSimNetwork` return the
  live compiled `conditions` object on its `SimNetwork` result (one additive field — backward-compatible,
  nothing reads `SimNetwork` positionally). Build the split scenario with an ideal `{}` `ConditionsSpec`
  (compiles to an empty object), then in the test add `conditions[linkIdForTally(k)] = { drop: true }` BEFORE
  the first drive to impose the split and `delete conditions[linkIdForTally(k)]` (or set `.drop = false`) to
  heal — exactly as the tallynet test mutates its object. `linkIdForTally` and `entityName` are importable
  from `sim/naming.js`.

**Assertions:** `pending` for the split-isolated voters while split; convergence (`commit`) for every
cooperating member after rejoin; balances move exactly once (only on the final commit) and are conserved
across the route; `net.deliveryErrors === []`; `net.clock.pendingTimers === 0` after convergence.

**Tripwire:** if the re-drive-the-whole-lift cost is a concern ("if routes get large, batching the re-drive

6.32 appended three CSV columns + JSONL keys, which makes
`packages/tallysim/experiments/commit-vs-found/out/*.{csv,jsonl}` stale and breaks `regenerate.sh`'s

**Idle-timeout caution:** the regenerate run is ~2 min but the runner kills on 10 min of SILENCE. STREAM the
output — `bash regenerate.sh 2>&1 | tee /tmp/tallysim-regen.log` — never a silent `> log 2>&1`. If the
wall-clock routinely exceeds ~10 min it is not agent-runnable; document the deferral and leave it for a human
/ CI rather than risk a lost run.
