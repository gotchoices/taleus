Second of three tickets splitting the original `5.5-tallysim-voter-model`. Ticket `tallysim-voter-policies` built the pure policy functions; this ticket **wires them into the running `tallynet` simulator** and adds the three behaviours the voter model turns on: nominated voters, contact points, and non-relayers — then drives a lift to settlement including the **pull recovery** that is the whole point of record availability. Ticket `tallysim-voter-model` (final) adds the sweep runner, metrics, CLI, and docs.

## The mechanism, confirmed from the tallynet source (read these first)

Everything needed already exists in `packages/tallynet/src/testing/network.ts` (the `InMemoryNetwork` the simulator wraps). The simulator's job is to *pass these config fields through* — none of it is a protocol change.

- **`hooks?: DiscoveryHooks | ((nodeId) => DiscoveryHooks)`** — per-node discovery-hook **factory** is supported. `DiscoveryHooks.negotiatePlan(plan) => plan | undefined` drops a plan whose voter-set-so-far a node rejects (the discovery-time refuse-stacked gate). The sim currently passes `hooks: makeCapacityHooks()` (one shared object, `sim/terms.ts`); extend to a factory so a node can add `negotiatePlan` (refuse stacked) on top of the capacity hooks.
- **`scorePlan?: ScorePlan`** — originator-only plan scorer (`(plan, query) => number`, higher better). Pass the voter-aware `ScorePlan` from `tallysim-voter-policies` so discovery *returns* plans ranked the same way `selectPlan` *picks* them.
- **`resourceFor?: (nodeId) => TrxParticipantResource`** — already wired through `ConsensusConfig.resourceFor` (entity-id keyed, adapted to node-name at the harness boundary). The `acceptsProposal` specs from the previous ticket flow through this unchanged.
- **`refuseRelay?: (nodeId) => boolean`** — the **non-relayer** the original ticket asked us to "add". It already exists: a node that promises normally (promise-phase pushes always deliver) but **drops every commit-phase record it would send or forward, and serves no pulls** (`makeUpdatePeer` suppresses the push when `record.commits.length > 0 && refuseRelay(from)`; `makeFetchRecord` returns `undefined` for it). This is a *node* fault, distinct from a dropped *link* (`conditions.dropFraction`).
- **`silentAfterPromise?: (nodeId) => boolean`** — a node offline after promising (neither sends nor receives commit-phase, serves no pulls). Models "the payee goes silent after the originator minted".
- **`nomineesFor?: (nodeId) => RefereeNomination[]`** — per-node referee (voter) nomination; folds voter-only members into `plan.members` during discovery (`prependMatch`), `physical` by default. Keyed by node **name**.
- **`LiftMemberSpec.physical?: boolean`** (on `buildLift`) — stamps `physical: 'dial:<name>'` on a member → a **contact point** reachable by any record-holder, not only link neighbours.

### The pull — the load-bearing detail

- **`ConsensusNode.fetchOutcome(transactionCode)`** (`consensus/participant.ts`) is the pull entry point: it reads the node's own stored record, pulls from every **reachable peer** (`reachablePeers(record)`), merges each reply, and returns the resulting outcome. A member cut off by an interior non-relayer **still has the record** (it promised in phase 1, which always delivers) — it is missing only the *commit* evidence — so `fetchOutcome` can recover it by pulling the committed signatures from a voter/originator.
- **Pulls are NOT auto-triggered.** The timer-driven recovery loop is explicitly deferred to `tallynet-propagation-timeouts` (a seam, not built). So to exercise and measure pull recovery, **the simulator must call `fetchOutcome` itself** on each still-pending cooperating member after `runUntilIdle`, then `runUntilIdle` again (settlement schedules fresh pushes). This is the "extra messages that *recover* otherwise-stuck members" the metrics ticket will count.
- **Contact points are the on/off pivot for principle 3** (the single-non-cooperating-member guarantee; `tallynet` docs § Contact points): on a *linear* lift, a cut-off member's `reachablePeers` can address the originator/voter **only if that member published `physical`** (a pull over a contact point has no direct edge → no `drop` → succeeds). With no contact point it can reach only link-neighbours — and the non-relayer between them serves no pulls — so it stays `pending`. A *circular* lift's ring already routes around one non-relayer without any contact point.
- **VERIFY while implementing:** read `reachablePeers` in `consensus/participant.ts` to confirm it addresses a `physical` member even with no shared tally link, and that a non-`physical` member's reachable set is link-neighbours only. The principle-3 test hinges on this; if it is not so, adjust the test expectation and flag it in the handoff rather than forcing it.

## What to build

### Extend `ConsensusConfig` (`sim/harness.ts`)

Add optional fields and pass them to `InMemoryNetwork`:

- `scorePlan?` — the voter-aware `ScorePlan`.
- `hooksFor?` / a per-node hooks factory that composes `makeCapacityHooks()` with `negotiatePlan` (refuse-stacked, using the well-known set) for nodes that should vet the voter set.
- `nomineesFor?` — adapt the entity-id-keyed nomination builder to the node-name-keyed `nomineesFor` (use `naming.ts` `entityId`/`entityName`).
- non-relayer and silent sets: `refuseRelayFor?: (entityId) => boolean` and `silentAfterPromiseFor?: (entityId) => boolean`, adapted to `refuseRelay` / `silentAfterPromise` (node-name keyed) exactly as `resourceFor` is adapted today.

Keep the "consensus omitted ⇒ discovery-only, byte-identical" guarantee: when none of the new fields are set, the harness config must be unchanged from today (the pinned discovery sweep must not move).

### Contact points + pull recovery (`sim/consensus-harness.ts`)

- `RunLiftOptions` grows `contactPoints?: boolean`. When true, `liftMembers` stamps `physical: true` on the originator and every voter (mirroring `tallynet`'s `mintFromPlan`, which already stamps the originator). When false/omitted, no member is `physical` (today's behaviour).
- After the initial `start` + `runUntilIdle`, add a **pull-recovery pass**: for each cooperating member (not a non-relayer / not silent) whose per-node `outcome(transactionCode)` is still `'pending'`, call `consensusNode(name).fetchOutcome(transactionCode)`, then `runUntilIdle` again; repeat to a fixed small bound or until no member advances (guard against infinite loops — it is deterministic and finite). The lift's reported `outcome` stays what the originator settles. Record how many pull calls happened and how many members recovered, on `LiftResult`, for the metrics ticket to read.
- Non-relayer placement: accept a non-relayer position/id in `RunLiftOptions` (e.g. an entity id, or "interior") so a test/the runner can put one at a chosen route position. The *selection* machinery (fraction → ids on a dedicated seed) belongs to the final ticket's scenario layer; here just accept explicit ids.

### Circular route driving (`sim/route.ts` / `sim/consensus-harness.ts`)

`runLiftForOutcome` already drives a circular `QueryOutcome` (the existing `consensus-harness.test.ts` "circular lift" case builds one by hand: `runQuery` to mint a session code, then synthesize `outcome.plans = [{ path: cycleTallies.map(i => ({ nonce: makeNonce(sessionCode, linkIdForTally(i)), intents: {} })), members: [] }]`). Add a reusable **circular-route constructor**: given the network + an originator entity, find a simple cycle through it (reuse `structure.ts` graph adjacency; `tallysim`'s oracle has cycle-finding for clearing queries — check `oracle.ts` before writing new graph code) and return the synthesized `QueryOutcome`. 

**Design note:** real *clearing discovery* (a circular route found by the protocol) is deferred to `feat-tallysim-clearing-discovery`. Constructing the ring directly from the known graph is the chosen stand-in so the circular *consensus* path (and its "ring routes around a non-relayer" property) can be exercised now. Document this in the final ticket's doc update.

## Tests (this ticket — end-to-end at the harness level, on hand-built line/ring networks)

- **Nomination + score:** a node nominates a well-known voter; discovery returns it in `plan.members`; `selectPlan` picks the lean/well-known plan.
- **Stacked refusal:** a plan padded with obscure `V`-only voters is refused — at discovery (`negotiatePlan` drops it) and/or at promise time (`acceptsProposal` → `NP` → void); assert the lift does not commit and the reason is the voter set.
- **Principle-3 curve (the headline):** linear line with one interior **non-relayer**. With `contactPoints: true`, every *cooperating* member reaches `commit` (via the pull-recovery pass). With `contactPoints: false`, members **beyond** the non-relayer stay `pending` — assert this gap as the **expected** outcome, not a failure.
- **Circular routes around:** ring with one non-relayer, `contactPoints: false` — the lift still settles for cooperating members (the ring routes around).
- **Edge cases:** non-relayer that is also a voter; non-relayer next to the payee; payee `silentAfterPromise` after mint (originator holds the plan ⇒ still settles); voter set of 2 that splits ⇒ `pending` (unsettled, does **not** hang — `runUntilIdle` terminates).
- **Determinism:** same `(network, seeds)` ⇒ identical `LiftResult`s and byte-identical networks (extend the existing determinism test).
- Keep `net.deliveryErrors === []` on clean runs.
