## Why this is split from `tallysim-timeout-harness-metrics`

The original `6.31-tallysim-timeout-harness-metrics` resolved its full design (twice) but hit the token budget
before any code landed. The work is cleanly two halves coupled through the `LiftResult` shape, so it is split
so each half builds + tests **green** on its own:

- **This ticket (Half A)** — remove the simulator's manual pull pass, add the `ttlMs` / `recoveryGiveupMs`
  knobs, thread them through. It **keeps** `LiftResult.pullCalls` / `LiftResult.recovered` as hard-coded `0`
  (the manual pass that computed them is gone, the protocol self-recovers), so `consensus-metrics.ts` and the
  existing `voter-harness.test.ts` assertions (`recovered === 0`, `pullCalls === 0`) keep compiling and passing
  untouched.
- **Half B (`tallysim-timeout-harness-metrics`, prereq on this ticket)** — re-homes those two counters onto the
  protocol's own trace events, removes the now-dead `LiftResult` fields, and adds the new measurements
  (credit-held duration, permanently-pending). Half B owns all `consensus-metrics.ts` / serializer / CSV work.

Keep the split boundary **exactly** here: this ticket must NOT touch `consensus-metrics.ts`,
`serialize-consensus-records.ts`, or their tests, and must leave `LiftResult.pullCalls` / `.recovered` in place
(returning `0`). That is what keeps the build green between the two halves.

## Verified facts (do NOT re-investigate — confirmed against source 2026-11-26)

- **The protocol already self-recovers inside the single `await net.clock.runUntilIdle()`** in
  `runLiftForOutcome` (`consensus-harness.ts:143`). `VirtualClock.runUntilIdle()` fires **every** live timer
  until the heap empties, so the 6.1 deadline one-shot (armed at `expiry + skewGrace`) and the 6.2 periodic
  recovery-loop ticks already fire there. The manual `recoverStrandedByPull` pass (`consensus-harness.ts:239`)
  therefore "legitimately finds nothing" today — the 6.2 review already flipped the tallysim tests'
  `recovered`/`pullCalls` expectations to `0`. It is dead weight kept in place expressly for this ticket to remove.
- **Removing the manual pass changes NO outcome.** After `runUntilIdle`, `recoverStrandedByPull` found nobody
  still pending (that is why `voter-harness.test.ts` asserts `recovered === 0`, `pullCalls === 0` in every
  recovery case). So reading `settled` and running `countCommitted` right after `runUntilIdle` (with the pass
  gone) yields identical outcomes. `voter-harness.test.ts` needs **no edit in this ticket** — its `=== 0`
  assertions still hold because we keep returning `0`.
- **`buildLift` takes `spec.ttlMs`** (`LiftSpec.ttlMs?`, `packages/tallynet/src/testing/network.ts:225`; default
  `600_000`, applied at the mint). It sets the session + transaction code expiry → the deadline. The current
  `net.buildLift(...)` call at `consensus-harness.ts:129-139` does NOT pass `ttlMs`, so every lift uses the
  600 000 ms default.
- **`InMemoryNetworkConfig.recoveryGiveupMs?`** exists (`network.ts:152`) and is already passed by the sim at
  `harness.ts:194` as the module constant `SIM_RECOVERY_GIVEUP_MS = 60_000` (`harness.ts:74`). Its NOTE at
  `harness.ts:72` explicitly hands "make this a per-scenario knob" to this work.
- **Recovery-loop timing (for the threading tests).** A stranded, no-path member arms a one-shot at absolute
  time `expiry + skewGraceMs`, then ticks with exponential backoff (`RECOVERY_BASE_MS = 5000`, doubling toward
  `recoveryMaxMs`) until `now > expiry + recoveryGiveupMs`, then emits `recovery-abandoned` and clears its timer
  (`participant.ts:scheduleRecoveryTick` / `onRecoveryTick`; proven by `participant.test.ts` cases (j),(l),(q)).
  The whole schedule is **anchored at `expiry`**, and `expiry = mintTime + ttlMs`. With ideal conditions
  (`conditions = {}` ⇒ links deliver instantly, `conditions.ts:45`) `mintTime` is identical across two runs of
  the same network+query, so shifting `ttlMs` by Δ shifts the final `clock.now()` at idle by **exactly** Δ.
  Holding `ttlMs` fixed and raising `recoveryGiveupMs` makes the loop run strictly longer (larger final
  `clock.now()`).
