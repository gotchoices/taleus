This is the first of five tickets that build `tallysim-viewer`, a browser app that *shows* a simulated
tally network: entities as nodes, tallies as edges, a payment search lighting up the graph as it spreads,
and the routes it finds. It is a development tool (not part of `web/`); it may be published to the web later,
so it stays a **static build with no server**.

This ticket creates the workspace package and its **platform-neutral, headlessly-testable core** — all the
pure logic that needs no browser, graph renderer, or canvas. The next tickets render it. Doing the logic
first (TDD) keeps the rendering tickets focused on rendering.

## The package

New unscoped Yarn-workspace package `packages/tallysim-viewer`, modelled on the sibling packages
(`packages/tallysim`): ESM (`"type": "module"`, `.js` import specifiers), TypeScript strict, tabs, single
quotes, jest + ts-jest for the core unit tests. It depends on **`tallysim` (`workspace:^`)** — and
transitively on `tallynet`, which `tallysim` re-exports what we need from, plus `tallynet`'s own
`makeNonce` (see below). Root `yarn build` / `yarn test` / `yarn lint` must pick it up (topological build
ensures `tallysim` builds first).

**Stack (settled — see "Stack decision" below for the full rationale):** Vite + TypeScript for the app and
static build; `graphology` + `sigma.js` (WebGL) for the graph; `uPlot` for sweep charts; **no heavy UI
framework** — plain TS modules and small hand-rolled controls. This ticket adds the Vite scaffold and the
dependencies but renders nothing yet; it only needs `vite build` (the package's `build` script) to succeed
on an empty-ish app shell and the jest core tests to pass.

### Scripts

- `build`: `tsc --noEmit -p tsconfig.json && vite build` — type-check then produce the static site in `dist/`.
- `dev`: `vite` — local dev server (developer convenience; not run in CI).

- `lint`: `eslint ./src`.

## Core modules to build (this ticket)

All under `packages/tallysim-viewer/src/core/`, **no browser imports** (no `window`, `document`, canvas,
sigma). Each is a plain TS module with a `.test.ts`, runnable under jest with no DOM.

### `trace-index.ts` — load and index a recorded run

Wrap `tallysim`'s `parseTrace` (do **not** re-implement NDJSON parsing). Build an index over one trace that
the playback tickets drive:

- Read the `header` (version is already checked by `parseTrace`; surface its rejection message unchanged)
  and the `network`.
- Materialise the event stream into a time-ordered array **grouped/joinable by `sessionCode`** (the header's
  `queries[]` tells you every session and its `{from, to, amount, depth}`). Provide: all sessions; events
  for one session in time order; the global min/max event `time`.
- Keep it incremental-friendly: expose a builder that can accept events in chunks (the live-run ticket
  streams them), not only a whole-file parse.

Expected test: a hand-built NDJSON trace (header + network + a few events across two sessions) indexes to the
right per-session event lists and time bounds; an unknown `traceFormatVersion` throws the version-named error.

### `deanonymise.ts` — map a nonce back to a tally edge (the load-bearing decoder)

Trace events carry an anonymised `nonce` (`tallynet`: `nonce = makeNonce(sessionCode, linkId)`), **not** a
link/edge id — the protocol hides a peer's link from relays by design. But the viewer sees the whole network,
so it can invert the hash: for a given `sessionCode`, compute `makeNonce(sessionCode, linkIdForTally(i))` for
every tally `i` and build the reverse map `nonce → tally index`. Then every nonce-bearing event
(`query-sent`, `query-received`, `candidate-pruned`, `plan-returned`, `late-answer-folded`) resolves to an
exact **edge**, and a found plan's `path` (a list of link nonces) resolves to an exact **edge sequence**,
which — walked from the known originator (`query.from`) across each tally's two endpoints — yields the exact
**node path**.

- Import `makeNonce` from `tallynet` and `linkIdForTally` from `tallysim` (exported via its `sim` barrel).
  Verify both are reachable from the viewer's dependency closure; if `linkIdForTally` is not surfaced far
  enough, re-export it (prefer importing from `tallysim`'s public entry).
- Build the per-session reverse map **lazily** and cache it (one map per session; sessions are few).
- Provide `tallyOfNonce(sessionCode, nonce) → number | undefined` and
  `nodePathOfPlanPath(sessionCode, from, linkNonces[]) → number[]` (the walked entity sequence; return a
  clear sentinel/throw if a nonce does not resolve or the walk is non-contiguous — that would signal a bug).

Expected test: build a tiny `Network`, pick a `sessionCode`, compute the nonces the real `makeNonce` would
produce for its tallies, and assert `tallyOfNonce` inverts them and `nodePathOfPlanPath` reconstructs a known
2–3 hop path's node sequence. Collision/!resolve path returns the sentinel.

> NOTE (tripwire): the reverse map is `O(tallies)` per session. Fine for planned viewer scales (few sessions,
> tallies in the thousands). If a trace ever has very many recorded sessions over a huge graph, build the map
> only for the session currently being viewed (already the lazy-per-session design) — do not precompute all.
> Record this as a `NOTE:` comment at the map-building site.

### `timeline.ts` — the playback state model

A pure state machine the replay UI binds to (no timers of its own — the UI ticket owns the clock; this module
is a pure reducer so it is unit-testable):

- State: `currentTime`, `playing`, `speed`, and a derived **active set** — which nodes and edges are "lit" at
  `currentTime`, each with its `round`/`depth` and (for edges) the last event kind touching it, plus which
  candidates are **pruned** (and the `PruneReason`) and which plans are **found** so far.
- Transitions: `seek(time)`, `play`/`pause`, `setSpeed`, `step(nextEventTime)`. Deriving the active set at an
  arbitrary `currentTime` must be correct whether you scrub forward or backward (recompute from events ≤ t, or
  maintain an incremental cursor that resets on backward seek — pick one and test both directions).
- It consumes the `trace-index` output and the `deanonymise` decoder; it emits plain data (node ids, edge =
  tally ids, round numbers, prune reasons), leaving all colour/rendering to the graph ticket.

Expected test: feed a scripted event list; assert the active node/edge sets, pruned set, and found-plan list
are correct at several scrub points, including a backward seek and a `late-answer-folded` event folding into a
later round (not dropped, not duplicated).

### `sweep-data.ts` — parse sweep output for the charts

Parse the `tallysim` CLI's sweep output (`cli/simulate.ts` / `cli/sweep.ts`) for the sweep-charts ticket:
**JSON-lines** (one `SimRunRecord`/`RunRecord` per line) and the **CSV** summary. Reuse `tallysim`'s
serialisation conventions (the `Infinity ↔ null` / empty-CSV-cell rule — see
`packages/tallysim/src/serialize-sim-records.ts`); do not invent a parser that diverges from how the CLI
writes. Produce tidy series: `{ seriesKey, points: {x, y}[] }` grouped by a chosen x-path (e.g.
`params["network.params.meanDegree"]`) and a chosen metric (e.g. `pFoundGivenExists`, `routeExistsCount`),
one series per other varied dimension / generator / capacity.

Expected test: a few hand-written JSONL records and the matching CSV parse to the same tidy series; a `null`
(non-finite) cell is read back as non-finite/absent, not `0`.

## Stack decision (document this in design.md)

Settled here so the rendering tickets don't re-litigate it:

- **Graph: `graphology` (data model) + `sigma.js` (WebGL renderer).** The target is "usable at thousands of
  nodes." `sigma.js` renders on WebGL and is purpose-built for large graphs; **cytoscape.js** (canvas) and
  **d3-force** (SVG/DOM) both bog down well before the thousands-of-nodes goal (DOM/canvas per-element cost),
  so they are rejected for the main graph. `graphology` gives a stable in-memory model and a worker-friendly
  ForceAtlas2 layout (`graphology-layout-forceatlas2/worker`).
- **Layout: ForceAtlas2 in a Web Worker, seeded.** Run layout off the main thread so the page stays
  responsive; seed the initial positions deterministically (e.g. seeded circular/random init) so replays of
  the *same* network are stable frame-to-frame. (Implemented in the graph-view ticket.)
- **Charts: `uPlot`.** Tiny, fast canvas line charts — right for sweep "metric vs. parameter, one line per
  series." (Implemented in the sweeps ticket.)
- **No heavy UI framework.** Controls are small; plain TS + minimal DOM helpers keep the bundle lean. Revisit
  only if the control surface outgrows hand-rolled widgets.
- **Accessibility:** colour-blind-safe categorical/sequential scales and light + dark themes (the dataviz
  skill's palette is a good starting point). Threaded through the rendering tickets.

## Edge cases & interactions

- **Version rejection** is `parseTrace`'s job — the index must *propagate* its clear message, not swallow it.
- **Empty / degenerate traces**: header + network with zero events; a session whose query found nothing; a
  network of < 2 entities. All must index without throwing and present as "no events" / "no route", distinct
  from "still loading".
- **Multiple sessions in one trace**: the index keys everything by `sessionCode`; the timeline model must
  render exactly one chosen session at a time (the replay ticket adds the picker / colour-by-session).
- **Nonce that does not resolve**: a defensive sentinel (should never happen for a well-formed trace of a
  network the viewer holds) — surfaced, not silently dropped.
- **Backward scrub**: deriving the active set must be correct scrubbing both directions (explicit test).
- **Non-finite metric values** in sweep data (`Infinity` max-flow → `null`): parsed as non-finite/absent.
