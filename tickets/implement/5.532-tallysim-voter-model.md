## Context already established (do not re-investigate — surface facts confirmed against source)

- **The nomination composition gap is real and load-bearing for the design here.**
  `runLiftForOutcome`'s `liftMembers(route, voters, contactPoints)` (`consensus-harness.ts`) builds the lift
  record's members **purely from the route entities + the `voters` option — it never reads `plan.members`**. So
  **referees nominated / stapled during discovery do NOT reach the consensus lift record.** This means:
  - `'self'` nomination needs **no** `nomineesFor` wiring at all: the default `voters: [route[0]]` already makes
    the originator a `[P,V]` member (voter-set-of-one). Just leave the default.
  - A stacked/obscure referee stapled at discovery lives ONLY in `plan.members`; it is visible to the
    **discovery-time** vetting (`negotiatePlan`, `scorePlan`, the originator's `refuseStackedPlanHook`) but is
    gone by promise time. So the stacked-voter **refusal must be measured at the discovery layer**, not via the
    promise-time `acceptsProposal` gate (which would never see it). (`debt-voter-nomination-on-path-composition`
    in `backlog/` owns the real `[P,V]` on-path marking fix; this ticket works WITHIN the gap, it does not fix it.)
- **`makeNomineesFor(network, wellKnown, policy)`** (`well-known.ts`) returns `nomineesFor(entityId) =>
  RefereeNomination[]`. `'well-known'` nominates the single highest-degree hub in `wellKnown`. Its own `NOTE:`
  warns it is sound only for an **off-route** nominee (an on-path hub's vote is silently dropped — the same gap).
  `wellKnownEntities(network, fraction)` returns the top `round(fraction·entityCount)` entities by degree
  (ties → lower id). The viewer-voter test and `voter-harness.test.ts` already exercise the off-route hub path.
- **Stacked-voter vetting primitives** (`consensus-resource.ts`): `refuseStackedPlanHook(policy)` is a
  discovery-time `negotiatePlan` hook that drops a plan whose `members` carry > `obscureTolerance` obscure
  referees (an obscure referee = a `[V]`-only member whose `Number(address.key)` is not in `policy.wellKnown`).
  `refusesStackedVoterSet(members, policy)` is the shared predicate. `voterAwareScorePlan(wellKnown)`
  (`plan-select.ts`) is the shared `ScorePlan` that ranks lean voter sets first (never drops — ranks only).
  The `voter-harness.test.ts` `stackingHook(extras)` helper shows how a node staples synthetic `[V]`-only
  members (`{ types:[VOTER], address:{ key:'bv0' } }`) via `negotiatePlanFor`.
- **Consensus method / threshold** (`tallynet`): `ConsensusMethod = { weighting:'distinct-voter', thresholdNum,
  thresholdDen }`; `DEFAULT_CONSENSUS_METHOD` is `1/2`. Validation requires `1/2 ≤ num/den ≤ 1` (a below-half
  threshold throws). It rides on **`LiftSpec.method`** (settlement — `net.buildLift({ … method })`) and on
  **`OriginatorOptions.method`** (discovery — stamped onto the `UniQuery` so a node can refuse one it dislikes).
  Settlement rule (`participant.ts`): a side settles when `count*2 > W` (strict-majority floor) **and**
  `count*thresholdDen ≥ thresholdNum*W`, where `W` = voter count. At `1/2` the two reduce to `count*2 > W`.
- **Circular routes**: `buildCircularOutcome(network, sessionCode, origin)` (`route.ts`) already builds a
  one-plan `QueryOutcome` from the shortest simple cycle through `origin` (the clearing-discovery stand-in). The
  `voter-harness.test.ts` ring test shows the pattern: mint a real `sessionCode` via a `runQuery(sim, { from:origin,
  to:origin, … })`, then `buildCircularOutcome(network, base.sessionCode, origin)`, then `runLiftForOutcome`. Its
  `plans[0].members` is `[]`, so `selectPlan('shortest')` returns it, `reconstructRoute` yields
  `[origin,…,origin]`, and the default `voters:[route[0]]` = origin.
- `drawPaymentQueries(workload, entityCount, rng)` draws distinct `(from,to)` pairs; **circular needs a separate
  single-origin draw** (`drawPaymentPair` requires a distinct pair).

## Scope of THIS ticket

### Scenario knobs (`scenario.ts` `ConsensusSpec`)

Add (JSON-serialisable; extend `cloneConsensus` only if any is non-scalar — all below are scalar/string):

- `routeShape?: 'linear' | 'circular'` (default `'linear'`).
- `voterNomination?: 'self' | 'well-known'` + `wellKnownFraction?: number`.
- `stackedVoters?: number` — pad plans with this many obscure `[V]`-only referees (discovery-time).
- `consensusMethod?: ConsensusMethod` — override to raise the threshold above `1/2` (e.g. `2/3`).

### `consensus-harness.ts`

- `RunLiftOptions.consensusMethod?: ConsensusMethod` → pass to `net.buildLift({ …, method })`. (Settlement side;
  the record carries the threshold. Threading it onto discovery options is optional — see below.)

### `consensus-runner.ts` — thread the remaining knobs + the circular path

- **Circular workload.** When `scenario.consensus?.routeShape === 'circular'`, draw a single-origin workload
  (add a small `drawCircularOrigins(workload, entityCount, rng): number[]`) instead of `drawPaymentQueries`; for
  each origin mint a session via a dummy `runQuery(sim, { from:origin, to:origin, amount, depth })` to get a real
  `sessionCode`, then `buildCircularOutcome(network, sessionCode, origin)` and drive `runLiftForOutcome`. A
  `undefined` outcome (origin on no cycle) contributes no lift (same as a not-found payment). Keep the sequential,
  rebuild-per-query, deterministic invariants.
- **Nomination.** When `voterNomination === 'well-known'`: build `wellKnown = wellKnownEntities(network,
  wellKnownFraction ?? 0)` once per run, wire `consensus.nomineesFor = makeNomineesFor(network, wellKnown,
  'well-known')` and `consensus.scorePlan = voterAwareScorePlan(wellKnown)`, and pass `wellKnown` into the
  per-lift `RunLiftOptions`. `'self'` needs no wiring (default voter-set-of-one). Document that an on-route hub's
  vote is silently dropped (the composition gap) — the sweep tolerates it.
- **Stacked voters (discovery-time).** When `stackedVoters > 0`: build a **shared counting refusal closure** in
  `consensusConfigFor` (it persists across the per-query rebuilds because the `ConsensusConfig` is built once per
  run):
  - `negotiatePlanFor(entityId)`: a deterministic subset of nodes staples `stackedVoters` synthetic obscure
    `[V]`-only members (non-numeric keys like `sv0…` ⇒ `Number(key)=NaN` ⇒ obscure) onto plans they fold.
  - `scorePlan`: a counting voter-aware scorer that returns `-Infinity` for a plan whose obscure-referee count
    exceeds tolerance (dropping it — the originator loop drops `-Infinity`/`NaN` plans) **and increments a
    shared `planRefusals` counter**; otherwise ranks voter-aware. This avoids the `negotiatePlan`
    staple-vs-refuse conflict (a node can only supply one `negotiatePlan`) and works for any random originator in
    the sweep. Expose the per-run `planRefusals` count to the runner (return it alongside the config, or read a
    mutable cell) so the metric can record it.
  - **Why the scorer, not the promise-time gate:** stacked referees live only in `plan.members` and never reach
    the lift record (the composition gap above), so `acceptsProposal`/`refuseStackedVoters` would never fire.
    Document this choice in the doc subsection.
- **Threshold.** Pass `scenario.consensus?.consensusMethod` into the per-lift `RunLiftOptions.consensusMethod`.
  (Optionally also thread it onto discovery options so a node could refuse it mid-search; not required for the
  measurement — note the deferral if skipped.)

### Metrics (`consensus-metrics.ts` + `serialize-consensus-records.ts`) — plan-refusal share

- Add `planRefusalCount` (Σ per-run `planRefusals` from the counting scorer) and `planRefusalShare` =
  `planRefusalCount / queryCount` **guarded 0/0 ⇒ 0** to `ConsensusRunMetrics`, carried through the runner (it is
  a run-level count, not a per-lift derivation — thread it into `summarizeConsensusMetrics` or set it on the
  record after summarise; pick the cleaner wiring and document). Add the two CSV columns in canonical order.
  - Scope note to put in the doc: this counts **discovery-time** voter-set refusals (plans the scorer dropped).
    The `scorePlan` *reordering* (lean ranked ahead of stacked without dropping) is a ranking, not a refusal, and
    is intentionally **not** separately counted; the promise-time path is unreachable here (composition gap).

### Tests (this ticket)

- **Circular has no cliff** (sweep): a materialised **ring** swept over `consensus.nonRelayerFraction` with
  `routeShape: 'circular'`, `contactPoints: false` ⇒ cooperating members still complete
  (`cooperatingCompletion` stays high; the ring routes around one non-relayer, as the existing `voter-harness.test.ts`
  ring test proves at the harness level). Contrast with the core ticket's linear cliff.
- **Stacked sets refused/passed over** (sweep or harness-level): a scenario with `stackedVoters > 0` ⇒
  `planRefusalShare > 0` (the scorer dropped ≥ 1 stacked plan) and those plans did not commit (a dropped plan
  forms no lift / commits nothing). Use a topology with an alternate lean route so *something* can still commit,
  or assert the refusal count directly.
- **Threshold `2/3`** (harness-level, `voter-harness.test.ts`): build a `line(5)` route `0→4`, drive
  `runLiftForOutcome(..., { voters: [0,1,2,3,4], consensusMethod })` with nodes 3 and 4 set `shouldCommit:false`
  (via `makeSimResources`). 3 commit, 2 `NC`, `W=5`: at `1/2` (`3*2=6>5`) ⇒ **commit**; at `2/3` (`3*3=9 ≥ 2*5=10`?
  no) ⇒ **pending** (the larger unsettled band). Assert the message count is ≥ the 1/2 case (more voting). This is
  the clean 1/2-vs-2/3 differentiator (a bare-majority-but-below-two-thirds count).
- **Determinism**: extend the runner determinism test to cover a circular + nomination + stacked spec
  (byte-identical records).
- **CSV**: `planRefusalCount`/`planRefusalShare` columns appear in canonical order, only when present.
