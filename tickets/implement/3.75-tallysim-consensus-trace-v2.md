A consensus `TraceEvent`'s `nodeId`/`to`/`from` are member **keys** (ed25519 pubkeys), not entity ids,
and the chosen route is **not** recoverable from the discovery event stream (the found-plan path gap). So
the *events* need no change (the union already spans both milestones), but the **header envelope** must
carry each lift's route + member map so the viewer can place consensus events. A header change **is** a
version bump.

## trace-format.ts

- `export const TRACE_FORMAT_VERSION = 2`.
- **Correct the module header**: it currently says consensus needs no bump. Fix it — *events* need no
  bump (true), but this *header* field does.
- New interface + optional header field:
  ```ts
  export interface TraceLiftEntry {
    sessionCode: string                  // joins to the TraceQueryEntry (discovery) this lift came from
    transactionCode: string              // joins consensus events (event.transactionCode)
    route: number[]                      // ordered entity ids [from, …, to] (originator first)
    tallyPath: number[]                  // ordered tally indices, one per hop — resolves edges exactly
    memberKeys: Record<string, number>   // member key (base64url) → entity id, to place consensus events
    amount: number
  }
  // TraceHeader gains:  lifts?: TraceLiftEntry[]
  ```
  Thread `lifts` through `TraceHeaderParts` / `buildTraceHeader` (optional; pass through when present).
- **`readHeader` accepts version ∈ {1, 2}** and treats `lifts` as optional (absent on a v1 file and on a
  discovery-only v2 run). Reject any other version with a message naming the found version AND the
  supported set (e.g. `unsupported traceFormatVersion 3 (this build reads 1, 2)`). A v1 reader rejecting a
  v2 file is correct; the new reader reads both.

## Populating lifts — cli/trace.ts `recordTrace`

When `scenario.consensus !== undefined`, drive the lift per query and record a `TraceLiftEntry`; when it's
absent, leave `recordTrace` **byte-identical** to today (branch on it; the discovery-only path must not
change — the pinned discovery trace tests depend on it).

**The consensus trace does NOT model capacity depletion** (deliberate, and the cleanest design — it
avoids the per-query-rebuild session-code reset that would duplicate codes in `queries[]`/`lifts[]` and
break the viewer's join). Instead:

- Build **ONE** consensus sim per pass (monotonic `VirtualClock`, session + transaction codes mint on one
  incrementing RNG ⇒ **unique** across all queries in the pass).
- For each lift's balance move, pass `runLiftForOutcome` a **fresh `cloneNetwork(initialNetwork)`** so the
  mutation is discarded and can't accumulate into an over-limit `settleRoute` assertion across lifts. (The
  recorded network snapshot stays the pristine initial network — the viewer replays from it.)
- Two passes, same as today:
  - **Pass 1** (learn): clone the sim build, run each query's discovery + lift, collect each query's
    `sessionCode` AND — for lifts that produced a `LiftResult` — a `TraceLiftEntry`:
    `{ sessionCode: outcome.sessionCode, transactionCode: result.transactionCode, route: result.route,
    tallyPath: result.tallyPath, amount: result.amount, memberKeys: Object.fromEntries(distinctEntities(
    result.route).map(id => [sim.net.memberKey(entityName(id)), id])) }`.
  - Build the header with `lifts` = the entries for the **recorded** query indices only (same `--query`
    filtering that already narrows `queries[]`); every recorded lift's `sessionCode` is in `queries[]`.
  - **Pass 2** (stream): rebuild an identical sim, rerun the same queries' discovery + lift, streaming
    events to the sink. Deterministic ⇒ pass-2 codes/events match pass-1's `lifts`.
- Consensus events carry `sessionCode` (reused from discovery), so the writer's `options.sessions` filter
  already records them for the selected queries — no writer change needed.
- `cli/simulate.ts`'s `--trace` already calls `recordTrace(spec.base, …)`, so it populates `lifts`
  automatically once `recordTrace` does — just verify (add a test), no new code there.
