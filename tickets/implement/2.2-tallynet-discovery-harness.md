## `src/testing/clock.ts` — `VirtualClock implements Clock`

Simulated time: `now()` advances **only** when timers fire. Deterministic; ties broken by insertion order.

- Internals: a **binary min-heap** of scheduled timers keyed by `(time asc, seq asc)` where `seq` is a monotonically increasing insertion counter (the tie-break). Use a real heap, not a linear scan — the 1,000-node scale test may queue thousands of timers and an O(n²) drain will blow the "few seconds" budget.
- `setTimer(fn, ms)` → push `{ time: now + Math.max(0, ms), seq, fn, cancelled: false }`, return that object as the handle. `clearTimer(handle)` → if it is one of ours and still live, mark `cancelled` (lazy deletion; pop skips cancelled). Guard against foreign/`undefined` handles (safe no-op, as `realClock` is).
- `now()` returns the current virtual time (origin 0 is fine; `Pending.duration` already tolerates a non-epoch origin — see `clock.test.ts` "measures duration from a clock origin other than the epoch").
- `advance(ms): Promise<void>` — fire every live timer with `time <= now + ms`, in `(time, seq)` order, advancing `now` to each as it fires, draining microtasks between fires; then set `now = now + ms` even if no timer sat at the end.
- `runUntilIdle(maxSteps?): Promise<void>` — drain microtasks, then repeatedly fire the earliest live timer (advancing `now`) until **no live timers remain**, draining microtasks between each. A `maxSteps` guard throws rather than looping forever.

### The microtask-drain problem (the crux — get this right)

The whole discovery run is async: firing a delivery timer runs a neighbour's `query`, which itself schedules more timers (sub-deliveries, its budget) **via promise continuations (microtasks)**. Between firing timer T and picking the next one, all consequent timers must already be scheduled, or you advance virtual time out of order.

**Decided approach (robust, platform-neutral):** drain microtasks between fires until timer **mutations quiesce**. Track a `mutations` counter that increments on every `setTimer`, every `clearTimer` of a live timer, and every timer fire. The drain loop:

```ts
// yield to the microtask queue until no timer was created/cleared/fired for N consecutive ticks
let quiet = 0
for (let pass = 0; pass < MAX_DRAIN && quiet < DRAIN_QUIET; pass++) {
	const mark = this.mutations
	await Promise.resolve()      // one microtask hop; no globals
	quiet = this.mutations === mark ? quiet + 1 : 0
}
```

Why mutation-tracking (not just "new timer scheduled"): when a subtree completes, a cascade of promise resolutions **clears** budget timers early (`budgetedStep` clears its timer when requests finish before the budget). That cascade produces no new timers but must fully unwind before the next fire, or a to-be-cleared timer fires prematurely and advances `now` wrongly. Counting clears (and fires) keeps the drain going through the cascade. The gap between a fire and its consequent mutations is ~2–5 microtask hops in this system (`getContext` is a resolved promise → `issueBatch` schedules delivery timers synchronously → `await budgetedStep` schedules the budget timer synchronously), so `DRAIN_QUIET ≈ 16` gives a wide margin; `MAX_DRAIN` large (e.g. 100_000) as a safety valve. Name the constants and comment why.

The run terminates because discovery schedules a bounded number of timers (deliveries fire once; budget timers fire or are cleared; rounds are bounded by `maxDepth`), so the heap strictly drains.

## `src/testing/random.ts` — `SeededRandom implements RandomSource`

A seeded PRNG producing `randomBytes(n)` reproducibly — **no `Math.random`**. Use **mulberry32** (tiny, good quality, uses `Math.imul` which the no-node-globals rule permits):

```ts
private nextUint32(): number {
	this.state = (this.state + 0x6d2b79f5) >>> 0
	let t = this.state
	t = Math.imul(t ^ (t >>> 15), t | 1)
	t ^= t + Math.imul(t ^ (t >>> 7), t | 61)
	return (t ^ (t >>> 14)) >>> 0
}
```

- `randomBytes(length)` — validate `length` is a non-negative integer (mirror `webRandomSource`'s guard), then fill a `Uint8Array` by consuming `nextUint32()` words. Deterministic for a given seed.
- Also expose helpers the graph generator needs: `nextFloat()` (`nextUint32() / 2**32`), `nextInt(maxExclusive)`. Avoid a zero initial state (seed to a non-zero constant if `seed === 0`).

## `src/testing/network.ts` — `InMemoryNetwork<TTerms,TPayload>` + findAddress builder + graph generator

Mirrors `../chipnet/test/{test-network,uni-scenario}.ts` on the virtual clock.

**Graph model (shared link ids — important):** a link is an **undirected** edge `{ id, node1, node2, intents: Record<string,TTerms> }` where `intents` are the terms as seen from `node1 → node2`. The **same link id** is used from both endpoints — this is correct, not a shortcut: `makeNonce(session, linkId)` is computed identically by both ends of a tally (see `src/nonce.ts` doc), so a neighbour reached over link L sees the same nonce the sender put on the plan tail, and the cycle check (`participant.ts` prunes a candidate whose nonce is already on the path) fires on the back-link automatically. Terms are **inverted** for the `node2 → node1` direction (a credit balance flips sign across the edge, as ChipNet's `TestLink.invertedLink()` does). Inversion is per-`TTerms`; take an `invertTerms?: (t: TTerms) => TTerms` config callback (default identity) and ship a `negateNumericTerms` helper for the `{ balance: number }` case.

**Precompute once (constructor), so per-query cost is local to a node's degree — never O(total nodes):**
- `adjacency: Map<nodeName, Array<{ id, neighbour, terms: Record<string,TTerms> }>>` — for each link, push `{id, neighbour: node2, terms}` to node1 and `{id, neighbour: node1, terms: invert(terms)}` to node2.
- a per-node `linkId → neighbour` lookup for `queryPeer`.

**findAddress builder** for node `name` (mirrors `uni-scenario.ts`, O(degree)):
```ts
(query, _inLinkId) => Promise.resolve({
	self: { member: { types: [MemberTypes.participant], address: { key: name } } },
	selfIsMatch: query.target.address.key === name,
	peerMatch: adj.filter(e => e.neighbour === query.target.address.key)
		.map(e => ({ match: { member: { types:[MemberTypes.participant], address:{key:e.neighbour} } }, link: { id: e.id, intents: e.terms } })),
	candidates: adj.map(e => ({ id: e.id, intents: e.terms })),
})
```

**`queryPeer` deliverer** for node `name` — resolve the linkId to its neighbour, schedule delivery on the `VirtualClock` after the link's latency, then call the **neighbour's** `query(request, linkId)` (same linkId), resolving with its response:
```ts
(request, linkId) => {
	const edge = linkLookup.get(name)?.get(linkId)
	if (!edge) return Promise.reject(new Error(`link ${linkId} has no neighbour at ${name}`)) // → pruned `failed`, never a crash
	const cond = resolveCondition(linkId)
	if (cond.drop) return new Promise(() => {})                 // never-resolving ("eternally sleeping") delivery; no timer armed
	return new Promise((resolve, reject) => {
		clock.setTimer(() => this.nodeByName.get(edge.neighbour)!.query(request, linkId).then(resolve, reject), cond.latencyMs ?? 0)
	})
}
```

**Link conditions (the three knobs), per-link, resolved per delivery:**
- `latencyMs` — virtual ms before the request reaches the neighbour (response returns in the same virtual instant the neighbour's `query` resolves). A latency **larger than a round's budget** models a node that answers late: the originator's round budget fires first, the candidate stays "sleeping" (outstanding), and the answer folds in a **later** round (the participant already handles this — `late-answer-folded`).
- `drop: true` — **decided manifestation: a never-resolving delivery** (no timer armed). The participant's budget skips it every round; it never yields a plan and is pruned `max-depth` when the ceiling is reached. (The other allowed manifestation was an error → pruned `failed`; we pick never-resolving and document it. A linkId with **no** neighbour is the error case → `failed`.)
- "sleeping node that wakes late" is just a finite `latencyMs` spanning one or more rounds — no separate knob needed.

Expose conditions as `Record<linkId, LinkCondition>` or a `(linkId) => LinkCondition | undefined` function in the config.

**Config / API sketch:**
```ts
interface NetworkLink<TTerms> { id: string; node1: string; node2: string; intents: Record<string,TTerms> }
interface NetworkGraph<TTerms> { nodes: string[]; links: NetworkLink<TTerms>[] }
interface LinkCondition { latencyMs?: number; drop?: boolean }
interface InMemoryNetworkConfig<TTerms,TPayload> {
	graph: NetworkGraph<TTerms>
	clock: VirtualClock
	random: SeededRandom
	hooks?: DiscoveryHooks<TTerms,TPayload> | ((nodeId:string)=>DiscoveryHooks<TTerms,TPayload>)   // default defaultHooks()
	invertTerms?: (t: TTerms) => TTerms                                                              // default identity
	conditions?: Record<string,LinkCondition> | ((linkId:string)=>LinkCondition|undefined)
	options?: Partial<OriginatorOptions & ParticipantOptions>
	sessionCodes?: SessionCodeValidators
	trace?: TraceSink | ((nodeId:string)=>TraceSink)
	sessionTtlMs?: number
}
class InMemoryNetwork<TTerms,TPayload> {
	constructor(config)                                    // builds one DiscoveryNode per node (own MemoryParticipantStore each)
	node(name: string): DiscoveryNode<TTerms,TPayload>
	discover(from, target, intents, options?): Promise<DiscoveryResult<TTerms,TPayload>>   // convenience → node(from).discover(...)
}
```
All nodes share one `VirtualClock` and one `SeededRandom` (session codes are drawn at `discover()` call time, synchronously, in call order → deterministic; concurrent originators keep independent stores/contexts, so they don't interfere). Document this.

**Basic seeded random-graph generator** (minimum for the scale test; anything fancier belongs in `tallysim`): `randomGraph(nodeCount, linkCount, random, makeTerms?): NetworkGraph<TTerms>` — node names `N0..N{n-1}`, `linkCount` edges between random node pairs (avoid self-loops), terms from a `makeTerms(random)` factory (default a `{ balance }` record).
