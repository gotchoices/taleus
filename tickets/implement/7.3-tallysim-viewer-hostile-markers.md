## Why

The parent plan asks that the viewer **mark hostile nodes and show where lifts break**. Much of the consensus-side scaffolding already exists: `consensusTimeline` in `packages/tallysim-viewer/src/core/timeline.ts` already derives an active set that carries `equivocators`, `contradictions`, `voters`, `pulled`, an `unresolved` list, and a `decision` (see `timeline.test.ts`). So "a voter equivocated" and "a member never resolved" are **already** computable from the trace; this ticket surfaces them in the rendering and adds the one thing the trace does not carry: **which nodes were configured as hostile** (refusers, no-commit voters, non-relayers, silent, stacked-voter padders), which is scenario metadata, not an emitted event.

## What to build

**1. Hostile-node markers.** The scenario's injected hostile sets are a property of the `SimScenario` in the **trace header** (`sim/trace-format.ts` line-1 `header.scenario.consensus` carries the fractions), but the header carries the *fractions*, not *which entity ids* were selected. Two routes — pick the one that keeps the trace format stable:
- derive the selected ids in the viewer by re-running the deterministic `compileConsensusConditions` / conditions compiler against the header's scenario + seed (the viewer already imports tallysim core for live sims), so no trace-format change is needed; or
- if that is impractical, add an **optional** `hostile?: { refusers, nonRelayers, silent, voteNo, … }` id-set block to the trace header (a header-only, backward-compatible addition — bump `traceFormatVersion` per the format's rule that a *header envelope* change bumps, and keep the reader accepting the older versions). Prefer route 1 if the compile is cheap and deterministic from the header alone.
- Render each hostile role with a distinct, colour-blind-safe marker/legend in the graph view, independent of the live active-set colouring (a node can be both hostile and currently active).

**2. "Where the lift breaks."** Using the consensus active set already derived, highlight the failure site when a lift does not commit everywhere:
- the **void reason** location — the refuser's node (the `NP`), or the voter(s) whose `NC` carried the void;
- the **stall** site — a `pending` lift's `unresolved` members and the dark edge/node the commit push could not cross (the sleeping/dropped-target asymmetry the design doc describes);
- the **equivocator / contradiction** — already tracked; make it visually prominent (it is the one genuinely dangerous case).

Keep the headless core (`src/core/`) unit-tested and the rendering (graph/replay/app) a thin consumer, matching the viewer's existing split (`docs/design.md`: headless core is unit-tested, rendering is Vite + graphology/sigma + uPlot).

## Edge cases & interactions

- **Trace-format stability.** If you add a header block, it must be **optional** and the reader must still accept current v1/v2 traces; a discovery-only trace has no hostile sets. Prefer re-deriving from the header to avoid any bump.
- **A hostile node that is also a voter / on the route.** A node can be hostile *and* a participant *and* a voter — markers must compose (role + hostility + current activity) without one hiding another.
- **Several colluding.** Multiple equivocators/refusers on one lift — the break-site highlight must handle more than one site, not assume a single failure point.
- **Linear vs circular routes.** The break-site logic must work for a circular (clearing) trace too, where the origin appears twice; reuse the viewer's existing `deanonymise.ts` route handling rather than re-inverting nonces.
- **Determinism of re-derivation.** If the viewer re-derives hostile ids from the header scenario+seed, it must use the **same** compiler and seed-offset the runner used, or the markers will point at the wrong nodes — pin it with a test that the re-derived set equals what the runner injected for a known scenario.
- **No hostile nodes.** An honest trace shows no hostile markers and no break site (every lift commits) — the common path must stay visually clean.
