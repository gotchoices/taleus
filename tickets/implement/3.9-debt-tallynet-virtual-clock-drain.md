## What's wrong (reproduced)

`VirtualClock` (`packages/tallynet/src/testing/clock.ts`) fires the next timer only after the work the previous fire triggered has "settled". It decides *settled* by draining the microtask queue and watching a `mutations` counter: when no timer is created / cleared / fired for `DRAIN_QUIET = 64` consecutive microtask hops (and no async callback is in flight), it calls the system idle and fires the next timer.

**64 is a guess about the longest promise-continuation chain between a fire and the point where its fallout schedules the next timer.** Any chain longer than the guess makes the drain quiesce *mid-chain*: the outer loop sees an empty heap, declares the run idle, returns — and the timer that the still-running chain schedules a moment later is orphaned and never fires. No throw. The result is just silently wrong (this is exactly how discovery once under-reported its reach — fixed by bumping 16 → 64 in `tallynet-discovery-depth-reach` and `tallysim-sim-runner-concurrent-divergence`, both now in `tickets/complete/`).

Reproduction (run during this ticket, confirms the failure mode before touching the fix): a timer whose callback schedules the *next* timer only after N detached `await Promise.resolve()` hops. At N ≤ 64 the second timer fires; at N = 120 and N = 200 it is silently dropped (`fired === ['first']`, `pendingTimers` stuck at 1, no error). The exact test is given under TODO below — it is the regression test this ticket must land.

## Root cause

`drainMicrotasks` (clock.ts:208) counts quiescence in **microtask hops**. The threshold is load-bearing and unknowable: it must exceed the longest microtask continuation chain any engine produces between a fire and its consequent timer mutations. Discovery's completion cascade is ~17–23 hops today; add hooks, async stores, more voter-model/timeout awaits, and a future chain exceeds 64 the same way it once exceeded 16 — and fails the same silent way.

## The fix — drain at macrotask granularity (recommended, prototyped)

Replace the microtask quiescence loop with a **macrotask** one. The JS event loop guarantees the microtask queue is drained *completely* before any macrotask runs — including microtasks enqueued while draining. So **one** real macrotask hop flushes an entire microtask continuation cascade of *any* length. Counting quiescence in macrotask hops (with a tiny threshold, e.g. 2) is therefore immune to microtask-chain length: the `DRAIN_QUIET=64` guess disappears.

Prototyped and validated during this ticket (scratch harness mirroring the drain/fire/runUntilIdle logic):
- Long chains of 8, 64, 200, **2000** hops all fire the next timer correctly at macrotask-quiet threshold 2.
- The **discovery-like** case does **not** deadlock: a callback that schedules a "budget" timer whose firing (in the outer loop, not the drain) is what completes the chain still resolves in correct order. This is the case the current class doc (clock.ts:65-70) warns the *pending-tracking* approach would deadlock on. The macrotask drain is safe because it **never awaits the callback promise** — it only flushes microtasks and re-checks whether the timer heap mutated. Mutations stabilise (the chain is parked awaiting a future fire), the drain quiesces, the outer loop fires the budget timer. Identical control flow to today, just macrotask-paced.

This also **subsumes the consensus `pending` case.** The async `update` chain (validate → merge → verify sigs → advance → sign → schedule onward pushes) arms no timer mid-flight (per the class doc), so it is pure microtasks and one macrotask flush drains it fully, including the onward pushes. The `pending` counter + `fire`'s promise-tracking can likely be **deleted**. **Do not delete blind:** remove it, run the consensus suites, and only keep it gone if they stay green. If any consensus/store step turns out to await a *real* macrotask (not just microtasks), keep `pending` — the macrotask-quiescence loop already tolerates it (a pending async callback is just another source of mutation that must settle).

### Two real constraints — read before coding

**1. `setTimeout` is forbidden in `testing/clock.ts`.** `no-node-globals.test.ts` (PORT_RULES, line 48-55) allowlists `setTimeout`/`clearTimeout` for **`clock.ts` only** — and that match is on the `src/`-relative path, which for the virtual clock is **`testing/clock.ts`**, *not* in the allowlist. The real-time clock at `src/clock.ts` is the allowlisted one. So a `setTimeout(resolve, 0)` macrotask in the virtual clock will fail the guard.
  - **Preferred: use `MessageChannel`** — a `postMessage` on a `MessageChannel` port schedules a macrotask, it is cross-platform (Node ≥15, browsers, Hermes/React Native), and the guard's grep does not forbid it. No allowlist change needed. This matches the fix ticket's own suggestion.
  - Alternative only if MessageChannel proves unworkable: add `'testing/clock.ts'` to the `setTimeout`/`clearTimeout` `allow` lists and declare the globals module-locally (as `src/clock.ts` does at its top). More blast radius on the neutrality guard — avoid unless needed.

**2. A `MessageChannel` keeps Node's event loop alive.** Observed in the prototype: the process would not exit until the ports were closed. In jest this surfaces as "a worker process has failed to exit gracefully" and can hang CI. Mitigate: create **one** module-level channel reused across drains and call `port.unref?.()` on it (Node `MessagePort` has `unref`; guard the call with `?.` since browsers/RN `MessagePort` does not), or close/recreate it when the clock goes idle. **Verify the full `tallynet` and `tallysim` suites exit cleanly** — not just pass.

### Performance — measure, it runs between every fire

The drain runs after **every** timer fire, and the 1000-node discovery scale sweep (`discovery.test.ts`, the `maxDepth boundary` describe and the 300-node/N299 graph) plus the `tallysim` sweeps (`sim-runner.ts:172/182`, `harness.ts:192`, `consensus-harness.ts:104`) fire thousands of timers per run. A macrotask hop is individually costlier than a microtask hop, but the macrotask loop needs ~2 hops per drain vs the current ≥64 microtask hops, so it is plausibly a wash or a win. **Measure wall-clock of the `tallynet` + `tallysim` suites before and after.** If macrotask-per-fire regresses materially, fall back to a **hybrid**: drain microtasks to quiescence as today, then do **one** macrotask confirmation hop; if that hop reveals a new mutation, loop. That keeps microtask speed while making correctness macrotask-bounded (the confirmation hop catches any cascade that outran the microtask threshold). The hybrid still removes the silent-failure mode; the plain macrotask loop is simpler — prefer it unless perf forces the hybrid.

## Option 2 (loud overrun guard) — do as cheap defense-in-depth, not instead

Independent of the drain rewrite, make an overrun *loud* instead of silent: after `runUntilIdle` / `advance` return, nothing should still be scheduling timers. The existing `expect(clock.pendingTimers).toBe(0)` assertions in `clock.test.ts` catch the orphaned-timer symptom in those cases; consider a built-in guard (e.g. after the loop exits, one more drain hop must produce no new timer, else throw). This is belt-and-suspenders — the macrotask drain is the actual fix.
