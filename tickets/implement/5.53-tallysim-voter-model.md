## Scenario knobs (`scenario.ts` `ConsensusSpec`, and `conditions.ts` if a compiler is needed)

Add to `ConsensusSpec` (presence of a `consensus` block already means "run consensus"), each on the same **dedicated-seed, count-based selection** discipline the existing `refuserFraction` uses (`compileConsensusConditions`, drawn from `consensusSeed` so it never perturbs the discovery streams):

- `contactPoints?: boolean` — stamp `physical` on originator + voters (threads to `RunLiftOptions.contactPoints`).
- `nonRelayerFraction?: number` — `round(fraction · entityCount)` nodes made **non-relayers** (`refuseRelay`). Distinct from the existing `refuserFraction` (a `shouldPromise:false` voider). Compile the selected ids the same way refusers are compiled; thread to the harness's `refuseRelayFor`.
- `routeShape?: 'linear' | 'circular'` — `'linear'` drives the payment query (today); `'circular'` drives the circular-route constructor from the previous ticket. Default `'linear'`.
- voter nomination: `voterNomination?: 'self' | 'well-known'` and `wellKnownFraction?: number` — thread to the nomination builder + well-known derivation.
- `stackedVoters?: number` — pad the voter set with this many obscure `V`-only members, to exercise the refuse-stacked path at scale.
- `silentPayee?: boolean` (or reuse a `silentAfterPromiseFraction`) — the "payee goes silent after mint" edge case.
- (optional) `consensusMethod?` override so a sweep can raise the threshold above `1/2` (e.g. `2/3`) and measure the extra messages + larger unsettled band. `tallynet`'s `ConsensusMethod = { weighting, thresholdNum, thresholdDen }` rides on the `LiftSpec.method` / query.

Clone these one level deep in `consensus-runner.ts`'s `cloneConsensus`, and allow `consensus.*` vary paths (already allowed for materialised networks). Keep everything JSON-serialisable (it round-trips through the trace header).

## Metrics (`consensus-metrics.ts` + `serialize-consensus-records.ts`)

Add per-lift fields (from the `LiftResult` the previous ticket enriched) and aggregate them into `ConsensusRunMetrics`, then add CSV columns to `CONSENSUS_METRIC_COLUMNS`:

- **Cooperating-members completion** — per lift: cooperating members total and how many reached `commit`; per run: the fraction, and enough to plot **completion vs. non-relayer count** (the principle-3 curve). Expect `1.0` with ≤ 1 non-relayer **and** contact points; a visible cliff without contact points on linear routes; no cliff on circular.
- **Time to settle** — already exists (`timeToSettleMs`); confirm it still reads correctly through the pull-recovery pass (the last event may now be a pull-driven push).
- **Messages per lift** — already exists (`messagesPerLift`, the `record-pushed` count). The **pull** messages from recovery must show up here (or as a separate `pullMessages` column) as the extra messages that *recover* otherwise-stuck members — call this out so a reader sees pulls costing messages but buying completions.
- **Plan-refusal share** — plans refused or passed over because of their voter set: `acceptsProposal` refusals (counted on the resource handles from `tallysim-voter-policies`) **plus** `scorePlan` non-selections (plans discovery returned but `selectPlan` passed over for voter-set reasons). Surface as counts/share. Note: an `acceptsProposal` refusal signs `NP`, so at the trace-event level it looks like `refused-promise`; distinguish it by counting at the policy layer, not by inventing a trace event — or add a dedicated `VoidReason` (`'refused-proposal'`) if the resource can tag it. Pick one, document it.

Guard every new fraction against 0/0 ⇒ 0 (never NaN), as the existing metrics do.

## Runner (`consensus-runner.ts`)

Thread the new scenario knobs into the per-run `ConsensusConfig` and `RunLiftOptions`: build the non-relayer / silent sets and the well-known set once per run (stateless gates, stable across the per-query rebuilds, same as refusers today); pass `contactPoints`, `routeShape`, nomination, and `stackedVoters` through. For `routeShape: 'circular'`, draw a circular workload (an originator per query) and drive the circular constructor instead of `runQuery`/payment. Keep the **sequential, rebuild-per-query, deterministic** invariants intact.

## Tests

- **Principle-3 curve** (sweep): `nonRelayerFraction` swept with `contactPoints: true` on a linear topology ⇒ completion holds at `1.0` for ≤ 1 non-relayer; with `contactPoints: false` ⇒ a visible cliff (members beyond the interior non-relayer stay `pending`), asserted as the **expected gap**, not a failure.
- **Circular has no cliff:** same non-relayer sweep with `routeShape: 'circular'`, `contactPoints: false` ⇒ cooperating members still complete.
- **Stacked sets refused/passed over:** a scenario with `stackedVoters > 0` ⇒ the plan-refusal metric is non-zero and those lifts do not commit.
- **Tie ⇒ unsettled:** a voter set of 2 that splits ⇒ the run records the lift as `pending`/unsettled (not a hang, not a crash).
- **Threshold `2/3`:** more voters must vote commit; measure the extra messages and the larger unsettled band vs `1/2`.
- **Determinism:** two runs of the same spec yield byte-identical records (extend the existing runner determinism test).
- CSV: the new columns appear with the canonical order and only when present in the data (mirror the existing `createConsensusCsvAccumulator` test).
