## Key mechanism findings from investigation (so you don't re-derive them)

**`runUntilIdle()` already fires the deadline + recovery timers — no new clock-driving is needed.**
`VirtualClock.runUntilIdle()` (`packages/tallynet/src/testing/clock.ts:188`) fires **every live timer until the
heap is empty**, regardless of the timer's scheduled time — it does *not* stop at message quiescence. The 6.1
deadline timer (armed at `expiresAt + grace`) and the 6.2 periodic recovery-loop backoff ticks are ordinary
`clock.setTimer` timers, so they already fire inside the single `await net.clock.runUntilIdle()` call in
`runLiftForOutcome` (`consensus-harness.ts:143`). Consequences, all confirmed against the 6.2 review
(`tickets/complete/6.2-tallynet-stalled-recovery.md`):

- The protocol **already self-resolves**: a silent-/sleeping-voter lift voids by its own deadline NC during the
  existing run loop (it no longer stays `pending`). A stranded member **already self-recovers** via the recovery
  loop's own pulls.
- The manual `recoverStrandedByPull` (`consensus-harness.ts:239`) therefore "legitimately finds nothing" today —
  the 6.2 review already flipped the tallysim tests' `recovered`/`pullCalls`/`recoveredTotal` expectations to 0.
  It is dead weight kept in place expressly for this ticket to remove.
- The **only** reason a timeout lift still reads `pending` after `runUntilIdle` is that the recovery loop hit its
  give-up ceiling and **abandoned** (resources held) — i.e. the permanently-stuck outcome. That ceiling is
  `SIM_RECOVERY_GIVEUP_MS = 60_000` in `harness.ts:74`, passed as `recoveryGiveupMs` to the `InMemoryNetwork`
  constructor (`harness.ts:194`). The NOTE at `harness.ts:72` explicitly hands "make this a per-scenario knob" to
  this ticket.

**`ttlMs` sets the deadline.** `buildLift`'s `ttlMs` (default `600_000`, `network.ts:454`) sets the transaction/
session code expiry → `expiresAt`. `runLiftForOutcome`'s `buildLift` call (`consensus-harness.ts:129`) does **not**
pass `ttlMs` today, so every lift uses the 600 000 ms default. Deadline-driven settlement still happens under
`runUntilIdle` regardless of `ttlMs` (the clock fast-forwards to the deadline), but the measured
time-to-resolution scales with `ttlMs`, and a scenario that wants the happy path to commit *before* the deadline
needs `ttlMs` large enough for that.

**Void-reason taxonomy — mostly already correct; one thing to VERIFY.** `analyzeLift`/`deriveVoidReason`
(`consensus-metrics.ts:164`) is already **outcome-driven**: `pending` ⇒ `'stalled'`; `void` ⇒ first of `expired`
(a `signature-rejected` with `reason === 'expired'`), then `refused-promise` (a `promise-signed` `NP`), then
`voted-no-commit` (a `voter-vote` `NC`). The ticket wants a deadline-driven void classified as `voted-no-commit`
and `stalled` to mean abandoned-pending (which it already does). **You must verify** in
`packages/tallynet/src/consensus/participant.ts` (`onDeadline` / `onRecoveryTick`, ~1416 lines) that a
deadline-driven void emits a `voter-vote` `NC` and **not** a `signature-rejected` `reason: 'expired'` — otherwise
it would be mis-counted as `'expired'`. (The 6.2 review describes "casting the deadline NC/NP through the
expired-code path", so this needs a concrete check; `'expired'` is meant for a record that arrives after its code
TTL, a different path — see design.md § Failure injection.) If a deadline void does emit an `expired`
`signature-rejected`, adjust the precedence (or the event the protocol emits — but prefer a tallysim-side fix) so
a resolved-by-timeout lift reads `voted-no-commit`. Add a unit test either way.
