## Key mechanism findings from investigation (so you don't re-derive them)

**`runUntilIdle()` already fires the deadline + recovery timers — no new clock-driving is needed.**
`VirtualClock.runUntilIdle()` (`packages/tallynet/src/testing/clock.ts:188`) fires **every live timer until the
heap is empty**, regardless of the timer's scheduled time — it does *not* stop at message quiescence. The 6.1
deadline timer (armed at `expiresAt + grace`) and the 6.2 periodic recovery-loop backoff ticks are ordinary
`clock.setTimer` timers, so they already fire inside the single `await net.clock.runUntilIdle()` call in
`runLiftForOutcome` (`consensus-harness.ts:143`). Consequences, all confirmed against the 6.2 review
(`tickets/complete/6.2-tallynet-stalled-recovery.md`):

- The protocol **already self-resolves**: a silent-/sleeping-voter lift voids by its own deadline NC during the
  existing run loop (it no longer stays `pending`). A stranded member **already self-recovers** via the recovery
  loop's own pulls.
- The manual `recoverStrandedByPull` (`consensus-harness.ts:239`) therefore "legitimately finds nothing" today —
  the 6.2 review already flipped the tallysim tests' `recovered`/`pullCalls`/`recoveredTotal` expectations to 0.
  It is dead weight kept in place expressly for this ticket to remove.
- The **only** reason a timeout lift still reads `pending` after `runUntilIdle` is that the recovery loop hit its
  give-up ceiling and **abandoned** (resources held) — i.e. the permanently-stuck outcome. That ceiling is
  `SIM_RECOVERY_GIVEUP_MS = 60_000` in `harness.ts:74`, passed as `recoveryGiveupMs` to the `InMemoryNetwork`
  constructor (`harness.ts:194`). The NOTE at `harness.ts:72` explicitly hands "make this a per-scenario knob" to
  this ticket.

**`ttlMs` sets the deadline.** `buildLift`'s `ttlMs` (default `600_000`, `network.ts:454`) sets the transaction/
session code expiry → `expiresAt`. `runLiftForOutcome`'s `buildLift` call (`consensus-harness.ts:129`) does **not**
pass `ttlMs` today, so every lift uses the 600 000 ms default. Deadline-driven settlement still happens under
`runUntilIdle` regardless of `ttlMs` (the clock fast-forwards to the deadline), but the measured
time-to-resolution scales with `ttlMs`, and a scenario that wants the happy path to commit *before* the deadline
needs `ttlMs` large enough for that.

**Void-reason taxonomy — mostly already correct; one thing to VERIFY.** `analyzeLift`/`deriveVoidReason`
(`consensus-metrics.ts:164`) is already **outcome-driven**: `pending` ⇒ `'stalled'`; `void` ⇒ first of `expired`
(a `signature-rejected` with `reason === 'expired'`), then `refused-promise` (a `promise-signed` `NP`), then
`voted-no-commit` (a `voter-vote` `NC`). The ticket wants a deadline-driven void classified as `voted-no-commit`
and `stalled` to mean abandoned-pending (which it already does). **You must verify** in
`packages/tallynet/src/consensus/participant.ts` (`onDeadline` / `onRecoveryTick`, ~1416 lines) that a
deadline-driven void emits a `voter-vote` `NC` and **not** a `signature-rejected` `reason: 'expired'` — otherwise
it would be mis-counted as `'expired'`. (The 6.2 review describes "casting the deadline NC/NP through the
expired-code path", so this needs a concrete check; `'expired'` is meant for a record that arrives after its code
TTL, a different path — see design.md § Failure injection.) If a deadline void does emit an `expired`
`signature-rejected`, adjust the precedence (or the event the protocol emits — but prefer a tallysim-side fix) so
a resolved-by-timeout lift reads `voted-no-commit`. Add a unit test either way.

## What this ticket does

**Remove `recoverStrandedByPull` as the primary mechanism** (keep it only as a documented fallback if a test
genuinely needs it — the 6.2 tripwire note says to retire it and re-home its counters). Re-home the two counters
onto the protocol's own trace events:

- `pullMessages` (was `LiftResult.pullCalls`): count the `record-pulled` trace events for this lift inside
  `analyzeLift` (they carry `transactionCode`; add a `case 'record-pulled'` to the event scan). These are the
  protocol's *own* recovery pulls now, not simulator-driven ones.
- `recovered` / `recoveredTotal`: decide a clean, honestly-derivable definition now that the loop does the
  recovery. Options to weigh (pick one, document it): (a) drop it in favour of `cooperatingCompletion`, which
  already measures "did the cooperating members reach commit"; (b) redefine as a run-level count of lifts that
  reached a terminal outcome *via a post-deadline recovery tick* (derivable from a `recovery-tick` with
  `changed: true` followed by `settled`). Do **not** keep a counter that is structurally always 0.

**Make `ttlMs` and `recoveryGiveupMs` per-scenario knobs** on `ConsensusSpec` (`scenario.ts:97`):

- `ConsensusSpec.ttlMs?` → thread through `RunLiftOptions` → `net.buildLift({ …, ttlMs })` in
  `consensus-harness.ts`. Document the default (600 000) and that it must exceed the happy-path settle time but
  stay inside the run budget for a stalled scenario. Remember to extend `cloneConsensus` in `consensus-runner.ts`
  (it clones the spec one level deep per cell) and the sweep validation if you let it be a `vary` path.
- `ConsensusSpec.recoveryGiveupMs?` → thread onto the `ConsensusConfig` and into `buildSimNetwork`'s
  `InMemoryNetwork({ …, recoveryGiveupMs })`, replacing the hard-coded `SIM_RECOVERY_GIVEUP_MS` module constant
  as the default (keep `60_000` as the default value and its rationale comment — the give-up window must stay
  small so a genuinely-stuck sim lift abandons quickly instead of polling a virtual hour). `recoveryBaseMs` /
  `recoveryMaxMs` are also available on the network config if a scenario needs them, but don't add knobs nothing
  uses — leave them to 6.35 if a scenario requires them.

**Add the measurements** to `consensus-metrics.ts` (keep the module pure — hand-built `LiftResult` + `TraceEvent`
in, metrics out):

- **Time-to-resolution.** Extend the existing `timeToSettleMs` to cover timeout-driven settlements. A deadline
  void is already a `void` outcome, so it already gets a `timeToSettleMs` (first push/promise → last consensus
  event, `consensus-metrics.ts:265`). The real change is that these voids now *occur*; confirm with a test that a
  deadline-void lift produces a finite `timeToSettleMs` spanning to the `settled`/`resources-released` event, and
  update the doc comments to say the distribution now includes timeout settlements. (Rename to
  `timeToResolutionMs` only if you also update the CSV column + design doc + experiment regenerate scripts; a
  doc-only clarification keeping the `timeToSettleMs` name is the lower-risk choice — your call, state it.)
- **Credit-held duration.** Per lift, derive from the trace: a participant holds its resource from its
  `promise-signed` (`signatureType === 'P'`) event until its `resources-released` event (both carry the emitting
  node id via `TraceBase.nodeId` and the `transactionCode`). Per-lift metric: e.g. the span from the first
  participant's promise to the last participant's release, or the max per-participant held interval — pick one,
  document it. Add `creditHeldMsPerLift: DistributionSummary` to `ConsensusRunMetrics`.
- **Permanently-held / never-resolved.** A `pending` lift whose participants' resources were never released
  (no `resources-released`, i.e. the loop abandoned) = credit never released. Add `permanentlyPendingCount` and
  `permanentlyPendingFraction` (= count / liftCount, **0 not NaN** when liftCount is 0) to `ConsensusRunMetrics`.
  (Today every `pending` lift is effectively this once the loop has run to idle, but keep the definition tied to
  "resources never released" so it stays correct if a future path releases on abandon.)

**CSV columns.** Add the new scalars/distribution to `serialize-consensus-records.ts` by **appending** to the
existing column order (do not reorder — the committed `experiments/commit-vs-found/out/*.csv` must not churn; a
`regenerate.sh` byte-identity check guards it). Expand each `DistributionSummary` to its
`count/mean/min/max/p50/p90/p99` columns as the existing ones do.

**Unit tests** (this ticket): `consensus-metrics.test.ts` for the credit-held-duration derivation, the
permanently-pending count/fraction (incl. the 0-lift NaN guard), the `record-pulled`-sourced `pullMessages`, the
deadline-void `voted-no-commit` classification, and the timeout-settled `timeToSettleMs`. `consensus-harness.test.ts`
for the `ttlMs` / `recoveryGiveupMs` threading and the removal of `recoverStrandedByPull` (a stranded-member
scenario still completes via the loop with the manual pass gone). The end-to-end scenario tests
(stalled/split/permanently-stuck) belong to 6.35.

## Edge cases & interactions

- **Determinism.** The deadline + recovery timers run on the same virtual clock but must not read the shared
  session-code random (`SeededRandom(SESSION_CODE_SEED)`). Two runs at one seed must still produce identical
  time-to-resolution and credit-held distributions — add/extend a seed-stability assertion (the full
  seed-stability test over the added timers is 6.35's, but keep this ticket's metrics deterministic).
- **Balance safety unchanged.** A timeout void moves no balances (only a commit does); `net.deliveryErrors === []`
  on clean runs. Removing the manual pull must not change any committed-lift balance outcome.
- **Pinned discovery sweep untouched.** Only the lift record / consensus config change; the shared discovery
  adjacency and the discovery-only wiring stay byte-identical (the existing finite-ification caveat).
- **Keep `analyzeLift` pure and O(events) per lift** (the existing NOTE at `consensus-metrics.ts:201`).
