## Key mechanism findings (from investigation — READ FIRST)

**The one subtlety that governs three of the scenarios: a lift voids by deadline ONLY if the promise phase
completes (late is fine). If a needed participant never promises, no vote is ever cast and recovery abandons
→ the lift stays `pending`, it does NOT void.** The gate is `getRecordState` (participant.ts:665-668):
`if (!this.promisePhaseComplete(record)) return 'promising'` — the commit/vote phase is never entered until
every participant holds a verified `P`. The deadline/expired path (`castCommit`) casts `NC` only for an
*un-voted voter that already has a complete promise set*. So:

- **Late voter (promises late) → VOID by deadline.** The promise set completes after the code expires; each
  voter then casts `NC` through the expired-code path → an `NC` majority → `void`. Deadline voids surface as
  a `voter-vote` `NC` and the 6.32 taxonomy maps them to `voidReason: 'voted-no-commit'` (NOT `'expired'` —
  consensus never emits `signature-rejected 'expired'`; see memory `tallynet-expired-reason-unemitted`).
- **Needed party never returns (sleeping / dropped) → PENDING.** Promise phase never completes, OR the
  commit evidence never reaches a member; the recovery loop backs off and, past `recoveryGiveupMs` beyond
  expiry, emits `recovery-abandoned`, stops re-arming, and leaves the record `pending` with resources held.

**Exact tallynet reference constructions to mirror (these already pass at the protocol level — copy their
shape):**
- Void-by-deadline: `packages/tallynet/src/testing/consensus.test.ts` ≈ line 1249, *"a promise phase that
  only completes after the code expires voids the whole route by deadline"*: `A—B` link latency `400_000`,
  `A—V` (sole voter) instant, default ttl `600_000`. B's promise lands at 400_000 (inside the window); the
  completed set cannot return over slow `ab` before the 600_000 expiry; A's recovery timer pulls B's set
  (pull ignores link latency, resolves immediately), re-pushes to V, and V's completing-promise update lands
  post-expiry → `castCommit` votes `NC` → sole voter → `['void','void','void']`.
- Permanently-stuck: same file, *"a dropped push on the only path stalls — no node settles"* (≈ line 400):
  `A—B—T`, `ab` link `{ drop: true }`, `recoveryGiveupMs: 60_000`. Only A holds a record; its pull + forced
  re-push both fall on the dropped link, so it makes no progress, backs off, and **abandons** at the ceiling
  — `['pending','pending','pending']`, `recovery-abandoned` present, `net.clock.pendingTimers === 0`.
- Dropped-commit-push recovers: this is ALREADY proven end-to-end by the existing tests — do not rebuild it
  from scratch, extend/point at them. `voter-harness.test.ts` § *record availability* (`contactPoints: true`,
  `nonCooperating: [2]` on `line(5)` with `refuseRelayFor: id===2` → every cut-off member pulls the record
  and commits), and `consensus-runner.test.ts` § *principle-3 completion curve* (the non-relayer heals via
  the loop; `recoveredTotal > 0`). With the manual pull gone (6.32) the protocol's own loop does the healing.

## Scenarios to add (this ticket)

Model these on `voter-harness.test.ts` (hand-built `line`/`ring` `Network`s, `buildSimNetwork` + `runQuery` +
`runLiftForOutcome`), not as new sweep cells — they are lift-shaped assertions.

- **Late voter → voids by the deadline.** A multi-voter (or sole-voter) lift where one voter answers only
  over a link whose latency exceeds a short `ttlMs`, so its promise completes the set only after expiry.
  Under `runUntilIdle` the lift **voids** by itself. Assert outcome `void`, `voidReason`
  `'voted-no-commit'`, balances unchanged, `net.deliveryErrors === []`, and `net.clock.pendingTimers === 0`.
  Mirror the tallynet `consensus.test.ts` ≈:1249 construction (slow link delays the completed set past
  expiry). Targeting a specific slow link from a `ConditionsSpec`: use `lateFraction` + `lateLatencyMs` and
  re-derive which node the seed picks (as the runner tests re-derive the refuser/non-relayer), OR pick a
  topology + fraction where the only late node is the voter you intend. `timeToSettleMs` for this lift
  should be a defined sample (it settled, via the deadline).

- **Dropped commit-push (interior non-relayer) → recovers by the loop.** A line/ring lift with a non-relayer
  cut off from the commit push; assert every cooperating member reaches `commit`
  (`cooperatingCommitted === cooperatingMembers`, i.e. completion 1.0) via the protocol's own recovery loop,
  with the manual pull gone. The existing `voter-harness.test.ts` § record-availability cases already prove
  this; add/confirm an assertion that the recovery loop (not a manual pull) did it — e.g. the per-lift
  `recovered === 1` from `analyzeLift`, and `net.clock.pendingTimers === 0`.

- **Permanently-stuck (needed party never returns) → stays `pending`, abandons, counted.** Use a SMALL
  `recoveryGiveupMs` so the loop abandons quickly. A dropped link on the only path to a member (mirror the
  tallynet dropped-push-stall test ≈:400), or a sleeping participant whose promise never completes the set.
  Assert outcome `pending`, `voidReason` `'stalled'`, a `recovery-abandoned` trace event is present, and
  (via `analyzeLift` / a tiny `summarizeConsensusMetrics` over the lifts) `permanentlyPendingCount >= 1`
  and `permanentlyPendingFraction > 0`. This closes 6.32's handoff gap §3 (no sweep yet produces a genuinely
  permanently-pending lift to assert the metric end-to-end).
