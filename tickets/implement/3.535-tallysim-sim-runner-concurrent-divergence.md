## Decision (made during fix-stage reproduction): KEEP `concurrent`, harden it

The discovery sweep runner (`sim/sim-runner.ts`) can run a run's queries two ways, chosen by
`SimRunnerDeps.concurrent`:

- **sequential** (default) — issue one query, drive the clock to idle, read its outcome, repeat;
- **concurrent** — issue every query, then drive the clock to idle once (one settle for the whole batch).

The original fix ticket was written when the two modes diverged on `roundsUsed` and the timing
distributions (`timeToFirstPlanMs`, `timeToCompletionMs`), and it listed three options: drop `concurrent`,
give each query its own clock, or keep-but-scope-honestly. **Reproduction during the fix stage shows the
divergence is already gone** and that equivalence is robust, not coincidental. So none of the three framings
is quite right anymore — the correct action is the lightest one: **keep `concurrent` (it is equivalent and a
touch faster), replace the now-overcautious "empirical / may re-diverge" caveats with the actual reason the
modes agree, and add a guard test so a future engine change that breaks the reason is caught.** No behaviour
change to the runner itself.

### What the fix stage actually found

The old divergence (the ticket's `line(5)`, 200ms, depth 8 table: 16500 run-alone vs 7100 run-alongside)
was a product of the **pre-fix `VirtualClock`**. `tallynet-discovery-depth-reach` (now in `complete/`) raised
`DRAIN_QUIET` from 16 to 64 so the drain no longer quiesces mid-cascade and fires an about-to-be-cleared
round-budget timer. That removed the folding that produced those inflated times. Re-running the ticket's own
scenario today (`line(5)`, constant 200ms, depth 8) gives identical records in both modes — completion times
of a few hundred ms, not 16500.

I then stress-tested the remaining theoretical risk — an *exact tie*, where a round's budget-expiry timer and
a delivery timer are scheduled for the **same** virtual instant and the clock's `seq` tie-break decides which
fires first. Budgets are `initialBudgetMs = 2000`, `perHopBudgetMs = 1500` (`discovery/originator.ts`), so a
constant latency of 2000 lands a round-0 delivery exactly on the round-0 budget boundary; 1750 and 2500 hit
the round-1/round-2 boundaries at 2 hops. Swept `{line5, line7, ring6} × {no-latency, 200, 1000, 2000, 1750,
2500, uniform 50–400, uniform 1000–3000} × seeds 1–5`, then again with `lateFraction 0.3 / lateLatencyMs 2600
/ dropFraction 0.1` layered on to force the late-answer **fold** path (the exact mechanism the old divergence
rode) under concurrency. **All 24 configs: concurrent record byte-identical to sequential.**

### Why they agree (the invariant that replaces the "empirical" hedge)

The clock breaks a same-instant tie by `seq`, a monotonic counter bumped on every `setTimer`
(`testing/clock.ts`). The key fact is about **two timers in the same session's causal chain**: their relative
arm order is identical in both modes.

- Within a round, `issueBatch` arms that round's outbound **delivery** timers *before* `budgetedStep` arms the
  round **budget** timer (`discovery/participant.ts` `reenter`). So at an exact tie, that round's own delivery
  has the lower `seq` and fires first; the completion cascade then clears the budget timer during the drain,
  so the budget never fires. Deterministic.
- An **answer-delivery** back to a node is armed by a downstream node reacting to a request, which was
  delivered *after* this node armed its budget — so the answer-delivery's `seq` is always greater than this
  node's budget `seq`. At an exact tie the budget fires first and the answer folds to the next round. Also
  deterministic, and the same in both modes.

Concurrent mode interleaves **other** sessions' timers into the global `seq` stream, but inserting a foreign
timer between a session's own two timers cannot invert their relative order. The simulation model has **no
per-node queueing or contention**, so each session's harvest depends only on its own timers' relative order —
which is mode-invariant. Hence `roundsUsed` and the timing distributions are identical across modes, for the
same structural reason the outcome metrics (found, `messages`, `nodesTouched`, `pruneReasons`,
`pFoundGivenExists`) always were.

This is a strong argument, but it rests on the *current* engine's arm-order discipline (delivery-before-budget
within a round; answer-delivery caused-after-budget) and on the model staying contention-free. That is exactly
what the guard test pins — so a future engine change that violates it fails loudly instead of silently
skewing a published sweep.

### CLI note

`cli/simulate.ts`'s `--concurrent` is a plain passthrough to `SimRunnerDeps.concurrent` (no refusal logic).
Because the modes are equivalent, **no refusal is needed** — the "make the CLI refuse `--concurrent` when
timing/round metrics are requested" option from the original ticket is explicitly *not* taken. The
`tallysim-discovery-metrics-io` and `tallysim-discovery-metrics-experiment` tickets are already in `complete/`
and the checked-in sweeps ran on default sequential, so no published number depends on the flag.

## What to change

The `sim-runner.ts` module header, the `runProtocolQueries` NOTE, the `sim-runner.test.ts` latency-equivalence
test comment, and `docs/design.md` § The discovery sweep runner currently hedge that byte-equality is
"empirical (this scenario + a broad sweep), not proven" and warn that an exact budget/delivery tie "could
still resolve the tie per-mode and re-diverge." That hedge is now **wrong** — the invariant above explains why
a tie resolves identically in both modes. Rewrite those spots to state the invariant (keep it concise; link to
the clock's `seq` tie-break and the participant arm order) and drop the "may re-diverge" language. Keep the
honest residual: the equivalence depends on the engine's arm-order discipline + a contention-free model, which
the guard test protects.
