## What to build

A new pure function `mintRecord` in **`src/consensus/mint.ts`**, re-exported from `consensus/index.ts`
(add `export * from './mint.js'` after the `./engine.js` line at `consensus/index.ts:14`).

```ts
import type { Plan, UniQuery } from '../discovery/types.js'
import type { TrxRecord } from './types.js'

export interface MintRecordArgs<TTerms, TPayload> {
	plan: Plan<TTerms, TPayload>     // the ONE chosen plan (design.md § "One plan per record (v1)")
	query: UniQuery<TTerms>          // carries method, liftContract, sessionCode (REUSE), intents, maxDepth
	payload: TPayload                // the opaque Taleus value the originator sets once
	transactionCode: string          // caller mints the self-expiring code; mintRecord stays pure (no clock/random)
}

export function mintRecord<TTerms, TPayload>(args: MintRecordArgs<TTerms, TPayload>): TrxRecord<TTerms, TPayload>
```

Keep it **pure**: the transaction code is passed in (Part 2's `proceed` mints it via the node's injected
clock+random). The **session code is reused from `query.sessionCode`** — never minted fresh — so the path
nonces (`makeNonce(sessionCode, linkId)`) still resolve at every node that took part in discovery.

### The member set (confirmed)

`plan.members` **IS already the folded member set** (discovery's return trip did the fold). Confirmed by
reading `prependMatch` (`discovery/participant.ts:714`) and the e2e invariant `assertValidPlan`
(`testing/discovery.test.ts:130-131`, asserts `members[0].address.key === originKey` and
`members[last].address.key === targetKey`):

- **Participants** = `plan.members.filter(m => m.types.includes('P'))` — already in **route order,
  origin-first, target-last**. `prependMatch` puts the prepending node (`asDependent`) FIRST and newly
  nominated voters (`missing`) LAST, and each node prepends on the way back (target prepends first,
  originator last), so by induction participants accumulate at the front in route order and voters at the
  tail. The `.filter` preserves that order.
- **Voters (`V` set)** = `plan.members.filter(m => m.types.includes('V'))` — the union of each
  participant's self-vote (a `[P,V]` member) and every `dependsOn` nominee (a voter-only member). **Already
  de-duplicated by key**: `prependMatch` folds a repeat nominee into `upgraded` (existing) rather than
  appending it again, so a voter nominated by several participants appears **once**.
- So `topology.members = plan.members` carried through essentially as-is (each is already a
  `DependentMember` with `types`, `address`, and optional `physical`/`secret`/`dependsOn`). A `[P,V]`
  member appears once with both roles. **A circular lift's originator appears once** though it rides two
  links (dedupe already done).

mintRecord does **not** invent voters. If `plan.members` carries **no `V` member**, the lift is voterless
and cannot settle — `mintRecord` must **throw** (the new-record rule `NonEmptyVoterSet`,
`participant.ts:805`, would reject it at first `update` anyway; fail early and explainably at mint). In the
default harness every node is `[P]` only, so a plain linear plan has no voter until some node is `[P,V]` or
nominates one — that is Part 3's concern, not this ticket's.

### The links (confirmed endpoint algorithm)

`plan.path` is `Link<TTerms>[]` where `Link = { nonce, intents }` — **no source/target** (anonymised). The
topology needs `links` keyed by nonce with **source/target member keys**. Algorithm (one modular formula
handles linear AND circular — confirmed against `buildLift`'s `source=route[i], target=route[i+1]`
convention at `network.ts:455` and the outward-built path direction):

```ts
const participants = plan.members.filter(m => m.types.includes('P'))  // route order, origin-first
const links: Record<string, TrxLink<TTerms>> = {}
for (let i = 0; i < plan.path.length; i++) {
	const link = plan.path[i]
	const source = participants[i].address.key
	const target = participants[(i + 1) % participants.length].address.key  // wraps only when it must
	links[link.nonce] = { source, target, intents: link.intents }
}
```

- **Linear lift**: `path.length === participants.length - 1`. The loop's `i+1` never wraps (it reaches at
  most `participants.length - 1`). source→target runs origin-ward→target-ward, matching the outward path.
- **Circular lift** (originator = payee, ring closes): `path.length === participants.length`. The last
  iteration's `(i+1) % n` wraps `participants[last] → participants[0]`, closing the ring. The originator
  rides two links (one out, one back) but is a single member entry — no duplicate (passes
  `NoDuplicateMembers`, `participant.ts:796`).
- Keying by `link.nonce` (the SAME nonce both endpoints derived, since `makeNonce` is endpoint-symmetric
  on the shared link id) keeps every participant node's `nonceToLinkId` resolving — **because the session
  code is reused**.

### Proposal parameters + codes

- `method` = `query.method`; `liftContract` = `query.liftContract` — **omit `liftContract` when absent**,
  never set it to `undefined` (DAG-CBOR rejects `undefined`-valued keys; see `types.ts:89` and the
  "omit, don't undefine" discipline throughout).
- `sessionCode` = `query.sessionCode` (reuse). `transactionCode` = the arg.
- `payload` = the arg. `promises: []`, `commits: []` (empty — all signing flows through the existing
  verified `update`/`sign` path; mint introduces no unverified-input path).

### Must satisfy the new-record rules (`participant.ts:787 buildNewRecordRules`)

The minted record is fed to `update`, which runs these on first sight. mintRecord must produce a record
that passes: valid tx+session codes (caller's responsibility for the codes); `NoDuplicateMembers`;
`LinksReferenceMembers` (every link source/target is a member key — guaranteed since endpoints come from
`participants`, which are members); `NonEmptyParticipantSet`; `NonEmptyVoterSet` (throw at mint if empty,
above); valid `ConsensusMethod`; `liftContract` non-empty-or-absent; `CoreEncodable`. (`SelfConsistent` is
per-node and not checked at mint — it runs at each node's own `update`.)
