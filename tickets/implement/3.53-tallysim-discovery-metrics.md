Third and final discovery ticket (after `tallysim-discovery-harness` runs a query on simulated time and `tallysim-discovery-trace` records a replayable, versioned trace). This ticket turns recorded runs into **protocol-level metrics**, wraps them in a sweep runner that mirrors the oracle runner, and checks in the first experiment that answers the tier's question: *does the decentralised protocol find the routes the oracle proves exist, and at what cost?*

## Per-query protocol result, derived from the trace + the oracle

For one query `{ from, to, amount, depth }` with session code `s`, combine two sources:

- **The oracle** (ground truth, on the *full, undegraded* network): `oracle.routeExistence(from, to, amount, depth).exists` → `routeExists`. This is the denominator of the headline metric.
- **The trace events for session `s`** (filtered by `event.sessionCode`) plus the `discover()` outcome:
  - `found` — the protocol returned ≥ 1 satisfying plan.
  - `plansFound` — number of plans returned.
  - `timeToFirstPlanMs` — first `plan-found` event time minus the query's start time (undefined if none).
  - `timeToCompletionMs` — last event time (or the clock time when `discover()` settled) minus start time.
  - `messages` — count of `query-sent` events for `s` (one per sub-request a node issues).
  - `nodesTouched` — distinct `nodeId` over `s`'s events.
  - `roundsUsed` — max `round` seen in `round-started` / `query-sent` events for `s`.
  - `pruneReasons` — a count per `PruneReason` (`cycle` / `failed` / `timed-out` / `max-depth` / `expired` / `no-reentrance`) from `candidate-pruned` events.

The query start time is `header.queries[s].start`? No — record it when issuing: the sim runner stamps `clock.now()` at `discover()` call time per session and keeps a `session → start` map. A **late answer** (`late-answer-folded`) must not be double-counted: count `query-sent`, not deliveries, for `messages`, and derive `roundsUsed` from the round counters, so a folded-in late answer contributes its one `query-sent` and nothing extra.

```ts
// sim/protocol-metrics.ts
export interface ProtocolQueryResult {
	routeExists: boolean
	found: boolean
	plansFound: number
	timeToFirstPlanMs?: number
	timeToCompletionMs: number
	messages: number
	nodesTouched: number
	roundsUsed: number
	pruneReasons: Record<PruneReason, number>
}
```

Aggregation is a **pure module** (like `metrics.ts`): a bag of `ProtocolQueryResult` in, a summary out, reusing `DistributionSummary` + `summarizeDistribution` from `src/metrics.ts`. Do **not** overload the oracle's `RunMetrics` — define a parallel `ProtocolRunMetrics`:

```ts
export interface ProtocolRunMetrics {
	queryCount: number
	meanDegree: number
	largestComponentFraction: number
	routeExistsCount: number            // oracle says a route exists (the denominator)
	foundCount: number                  // protocol found a route
	foundAndExistsCount: number         // found AND oracle-confirmed (the intersection)
	/** P(found | route exists) = foundAndExistsCount / routeExistsCount (0 if none exist, never NaN). */
	pFoundGivenExists: number
	/** Protocol "found" where the oracle says NO route exists — must be 0 if the harness is correct. A guardrail. */
	falseFoundCount: number
	timeToFirstPlanMs: DistributionSummary   // over found queries
	timeToCompletionMs: DistributionSummary  // over all queries
	messages: DistributionSummary
	nodesTouched: DistributionSummary
	roundsUsed: DistributionSummary
	plansFound: DistributionSummary
	pruneReasons: Record<PruneReason, number>  // summed over the run
}
```

`pFoundGivenExists` is the headline. `falseFoundCount` is a correctness guardrail, not a research metric: it must be 0 (the harness ticket proved *found ⊆ oracle*), and a run that reports > 0 is a bug — assert it zero in tests. All fractions guard the degenerate cases exactly as `metrics.ts` does (0 over 0, never `NaN`).

## The sim sweep runner (mirror the oracle runner)

Mirror `src/runner.ts`'s `runSweep` so a `SimSweepSpec` streams `SimRunRecord`s. Reuse the shared materialiser + amount-draw extracted into `src/workload.ts` by the harness ticket; reuse the same three-stream seed scheme (network / workload / economy) **plus** the conditions stream the harness ticket added. Extend the scenario model minimally:

```ts
// scenario.ts additions
export interface SimScenario {
	network: NetworkSource              // reuse the existing union (generator recipe | materialized)
	workload: WorkloadSpec              // reuse; kind must be 'payment' this tier
	conditions?: ConditionsSpec         // from sim/conditions.ts; omitted ⇒ ideal network
	/** Discovery tuning: depth rides on workload.depth; budgets map to OriginatorOptions. */
	budget?: { initialBudgetMs?: number; perHopBudgetMs?: number }
	/** Seed for the conditions stream (independent of network/workload/economy). */
	conditionsSeed?: number
	/** Record a trace file? Core yields events regardless; this gates the CLI's file output + the selected-query filter. */
}
export interface SimSweepSpec { base: SimScenario; vary: VarySpec[]; seeds: number[] }
```

`runSimSweep(spec)` is a generator: per cell × seed, materialise the network, build one `SimNetwork` (harness ticket), build the oracle on the full network, draw the payment queries (shared draw), run each query on the clock collecting its session's events (reuse the trace sink as an in-memory per-session collector, or the `makeTraceWriter` with an in-memory `LineSink`), compute `ProtocolQueryResult`s, aggregate to `ProtocolRunMetrics`, and yield a `SimRunRecord` `{ generator, capacity, params, seed, metrics }` (same provenance shape as `RunRecord`). Touches no filesystem; the CLI (`cli/simulate.ts`) drives it for file output (JSON-lines records + a CSV summary via the existing serialisers, extended for the protocol columns) and can additionally dump a full trace file for selected queries using the trace ticket's writer.

**Concurrency:** run a cell's queries **sequentially by default** on the one reused `SimNetwork` (clean per-query timing; the network is static in this tier so reuse is safe). Expose a documented `concurrent` option that issues all `discover()`s before one `runUntilIdle()` — this is the "several originators at once" path the parent ticket calls out; it must keep sessions separate (harness guarantee) and stay deterministic (session codes mint in call order). Default sequential; the concurrent mode is exercised by a test.

## The experiment

`experiments/found-vs-oracle/` — mirror `experiments/route-existence/` (committed specs + `regenerate.sh` that reproduces `out/*.{jsonl,csv}` byte-identically). Answer: **how close does the protocol get to the oracle, and what does it cost?** Sweep, at a fixed topology (one generator, e.g. `scale-free` and `uniform` at a mid mean degree):

- **Depth limit** `D` and **time budget** (`perHopBudgetMs`) vs. `pFoundGivenExists` — where does the protocol stop finding routes the oracle sees?
- **Sleeping-node fraction** vs. `pFoundGivenExists` and `messages` — how fast does success fall as nodes go dark?
- **Latency** (base distribution) vs. `timeToCompletionMs` and `roundsUsed` — cost, not success (ideal reliability).

Keep the grid small (route discovery on the harness is seconds, but far costlier than the oracle's BFS — keep entity counts modest, e.g. `N ∈ {100, 1000}`, a few seeds). Record the findings briefly in `design.md` § (new) *Found vs. oracle* — the shape of the gap, not a data dump.

## Edge cases & interactions

- **found ⊆ oracle ⇒ `falseFoundCount === 0`:** assert it across every seeded test and in the experiment runs. A non-zero count is a harness/terms bug surfacing through metrics — fail loudly, do not tolerate it.
- **"no route" vs "route exists but not found":** the two must be counted distinctly — `routeExists=false` queries are excluded from the `pFoundGivenExists` denominator; a `routeExists=true, found=false` query is the *gap* the experiment measures. Test both.
- **Depth-sweep budgeting (the protocol reaches ~half its `maxDepth`):** the protocol's reach is **not** the oracle's `maxDepth`. Measured empirically, an `L`-hop route is only found at `maxDepth ≥ 2(L − 1)` (reach ≈ `⌊maxDepth/2⌋ + 1` hops) — see `docs/design.md` § "Rounds ↔ hops". A depth sweep that compares the protocol at depth `D` against the oracle at the same `D` will therefore read a large "found vs oracle" gap that is **expected protocol cadence, not a network failure**, unless the sweep budgets the protocol's `maxDepth` at roughly **2× the oracle hop distance** being probed. Either budget the extra depth, or label the gap explicitly as the reach cost in the experiment write-up — do not present it as the connectivity gap.
- **Late answers:** `messages` counts `query-sent` (not deliveries) and `roundsUsed` reads round counters, so a `late-answer-folded` event adds no phantom message or round. Test a late-node scenario's counts against a hand-computed expectation.
- **Concurrent queries:** the `concurrent` mode keeps per-session metrics independent (no cross-session leakage in `nodesTouched` / `messages` / timing) and is deterministic across two runs. Test with ≥ 2 concurrent originators.
- **`entityCount < 2`:** no distinct pair; the query is counted as `routeExists=false, found=false` (contributes 0 to the headline, never `NaN`) — same guard as the oracle runner.
- **Unreachable target:** `found=false`, empty prune/plan metrics still well-formed; if the oracle also says no route, it is a "no route" (excluded from the denominator), not a miss.
- **Zero existing routes in a run:** `pFoundGivenExists = 0` by the guard (0/0 → 0), and the record is still valid.
- **Determinism:** two `runSimSweep` passes over the same spec yield byte-identical records (builds on the trace ticket's byte-identical guarantee + the shared seeded streams).
- **Cost ceiling (tripwire):** route discovery is much costlier than the oracle's BFS; a large-`N` sweep can be slow. Keep committed experiment grids modest and document the ceiling. Record a `NOTE:` at the sim-runner's per-query loop ("if a sweep ever needs large N, record only sampled queries' traces and/or cap concurrency") rather than filing a ticket.

## Tests to plan

- Hand-built graph with a known single route, ideal conditions: `pFoundGivenExists = 1`, `falseFoundCount = 0`, `messages`/`nodesTouched`/`roundsUsed` match a hand trace.
- Seeded random graphs: `foundAndExistsCount ≤ routeExistsCount`, `falseFoundCount = 0`, `found ≤ foundAndExists + (found where no route)` — and since found ⊆ oracle, `found === foundAndExists`.

- Concurrent vs sequential: same per-query results for independent queries; both deterministic.
- Degenerate guards: zero queries, zero existing routes, `entityCount < 2` — all `0`, no `NaN`, no throw.
