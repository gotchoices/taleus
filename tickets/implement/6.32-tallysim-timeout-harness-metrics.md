## Verified facts (do NOT re-investigate — confirmed against source 2026-11-26)

- **Trace event shapes** (`packages/tallynet/src/trace.ts:62-74`):
  - `record-pulled`: `{ type:'record-pulled', transactionCode, from, ok } & TraceBase(nodeId,time)` — one per
    reachable peer, emitted by the recovery loop's `fetchOutcome`. These are now the protocol's own recovery
    pulls (the simulator drives none).
  - `recovery-tick`: `{ type:'recovery-tick', transactionCode, attempt, changed }` — emitted **only on the
    force-repush path** of a tick that did NOT settle (a deadline-NC that settles in the tick returns before
    emitting one). So do NOT key "recovered" solely on `recovery-tick`.
  - `promise-signed`: `{ …, signatureType:'P'|'NP' }` — a `P` holds credit, an `NP` holds nothing.
  - `resources-released`: `{ type:'resources-released', transactionCode, success }`.
  - `signature-rejected` with `reason:'expired'` is **defined but never emitted** by the engine (memory
    `tallynet-expired-reason-unemitted`); a deadline-driven void emits `voter-vote` `NC`, which
    `deriveVoidReason` already maps to `'voted-no-commit'`. So the existing void-reason precedence is correct for
    timeout voids — **no `participant.ts` edit, no precedence change** — just prove it with a unit test.
- **Happy-path commits/voids emit NO `record-pulled` / `recovery-tick`.** A lift that settles before its deadline
  clears the recovery timer on settle (proven: the existing harness/voter tests assert `pendingTimers === 0`
  right after a clean commit — impossible if a ~600 s recovery timer were still armed). A lift whose member was
  stranded (dropped / forwarded-nothing) runs the loop ⇒ ≥1 `record-pulled` and/or `recovery-tick`.
- **CSV accumulator only emits listed columns.** `flattenMetrics` (`serialize-records.ts:72-88`) descends one
  level and emits every number / nested-number, but `createSweepCsvAccumulator` filters to the columns in
  `CONSENSUS_METRIC_COLUMNS` (`serialize-records.ts:143`). A new metric field **silently drops** from the CSV
  unless its column is appended to that list. So the three new fields MUST be appended (JSONL round-trip carries
  them regardless).
- **Consumers of the fields being removed** (`LiftResult.pullCalls` / `.recovered`): `consensus-metrics.ts`
  (reads `result.pullCalls` / `result.recovered` at `:252-253`); `consensus-metrics.test.ts`'s `lift()` helper
  (sets both to `0`); `voter-harness.test.ts` (asserts `result.recovered` / `result.pullCalls` at ~L97-98,
  ~L121, ~L144, comment ~L296). `consensus-harness.test.ts` does not reference the fields directly.

## Decision log (final — implement these; all resolved, no re-litigation)

1. **`pullMessages`** (`ConsensusLiftMetrics`): drop sourcing from `result.pullCalls`; in `analyzeLift` count
   `record-pulled` events for the tx (`case 'record-pulled': pullMessages++`).
2. **`recovered`** (`ConsensusLiftMetrics`, keep as a per-lift `number`, now 0/1): drop sourcing from
   `result.recovered`; set `1` iff the lift **settled** (`commit`|`void`) **and** emitted ≥1 `record-pulled`
   **or** `recovery-tick` for its tx, else `0`. `recoveredTotal = Σ recovered` stays "settled lifts that needed
   the recovery loop". Document it may now be **non-zero** in a drop-sweep (a drop that strands a member who
   self-heals) — that is the honest value; the committed CSVs go stale anyway (new columns, see §CSV), so 6.35
   regenerates/validates. Clean refuser-void / happy-commit runs stay `0`.
3. **`creditHeldMs?`** (new, per-lift, on `ConsensusLiftMetrics`): span from the **first** `promise-signed` with
   `signatureType === 'P'` (exclude `NP` — holds nothing) to the **last** `resources-released`, both for this tx.
   Omit when either is absent. Guard `last >= first` defensively (releases follow promises, so it holds; the
   guard documents intent). Add `creditHeldMsPerLift: DistributionSummary` to `ConsensusRunMetrics` (distribute
   the defined per-lift values only, like `timeToSettleMs`).
4. **`permanentlyPending`** (new, per-lift `boolean`): `outcome === 'pending' && no resources-released event seen`
   (tie it to "resources never released", not just "pending", so it stays correct if a future path releases on
   abandon). Add `permanentlyPendingCount` (Σ) and `permanentlyPendingFraction` (`count / liftCount`, **0 not
   NaN** when `liftCount === 0`) to `ConsensusRunMetrics`.
5. **`timeToSettleMs`**: NO logic change and KEEP the name (renaming churns CSV + docs + regenerate). A
   deadline-void is already a `void` ⇒ already gets a span to its last event (incl. `resources-released`). Just
   update the doc comment to say the distribution now includes timeout-driven settlements, and add a unit test
   proving a hand-built deadline-void trace yields a finite `timeToSettleMs`.
6. **Deadline-void classification**: NO `participant.ts` edit (see Verified facts). Add the unit test only.
