## Established facts (confirmed against source — do NOT re-investigate)

**Terminology correction:** the vote event is **`voter-vote`** (`{ type:'voter-vote'; transactionCode;
decision:'C'|'NC' }`), *not* `referee-vote` as the original ticket said. Use `voter-vote`.

**The real trace serializer is `serializeTraceLine`** (`packages/tallysim/src/sim/trace-format.ts`), not
`serialize-consensus-records.ts` (that is the CSV/JSON-lines **sweep-metrics** serializer — unrelated). A new
consensus event round-trips through `serializeTraceLine`/`parseTrace` with **no format-version bump** (documented
there). So `record-pulled` (5.6a) needs no viewer-only fields and no bump.

**Landed consensus trace events** (all in the `tallynet` `TraceEvent` union, `src/trace.ts`):
`record-pushed`, `record-received`, `promise-signed { signatureType:'P'|'NP' }`, `signature-rejected`,
`voter-vote { decision:'C'|'NC' }`, `settled { decision:'commit'|'void' }`, `resources-released`,
`equivocation-proof-kept { signer }`, `contradiction-detected { ourOutcome, peerOutcome }`, and (via 5.6a)
`record-pulled { from, ok }`. Every consensus event's `nodeId`/`to`/`from`/`signer` are member **keys**, not
entity ids.

**`TraceLiftEntry`** (tallysim `trace-format.ts`, carried in `header.lifts[]`) has exactly:
`sessionCode, transactionCode, route:number[], tallyPath:number[], memberKeys:Record<string,number>, amount`.
`memberKeys` maps only **distinct route entities** → entity id. The viewer's `createLiftResolver`
(`core/trace-index.ts`) turns it into `entityOfMember(key)` + `tallyOfEdge(fromEntity,toEntity)`.

**What the format does NOT carry (format gaps — document, do NOT fabricate):**
- **Off-route referee voters and nominator links.** Per `debt-voter-nomination-on-path-composition` (backlog),
  referees nominated at discovery do **not** reach the lift record, so in the current/near-term simulator ALL
  voters are route participants. An off-route referee voter's `voter-vote` key does **not** resolve via
  `memberKeys`. Show participant-voters precisely; **count** any unresolvable voter keys as "referee-only
  (stacked)" in the side panel (so "a stacked voter set looks stacked") but do not place them on the graph.
  Nominator links are not recorded — note the deferral.
- **Per-member contact points.** Not in the format (`header.scenario.consensus?.contactPoints` does NOT exist on
  the type yet — 5.53a adds it; do **not** reference it). Instead show the **observable consequence**: a member
  recovered via a successful `record-pulled` (settles) vs a member stuck in `promised` with no decision (stalls).
  That already makes "settles vs stalls on a linear lift with a refuser" visible without a contact-point flag.

## Current viewer consensus state (what already works — build on it)

`core/timeline.ts` `deriveConsensus` already recomputes a `ConsensusState` per `currentTime`:
`{ transactionCode, edges:[{tally,phase:'promised'|'committed'|'released'}], nodes:[{node,phase:'promised'|'voted'|'settled',vote?}], decision?, settledTime?, unresolved[] }`.
`paint.ts` `applyConsensus` paints promised/committed/void-flash over the discovery spread (suppressed in
isolate mode); `theme.ts` carries `promised`/`committed`/`voidFlash`. `routes.ts` has `liftRoute`/`liftOutcome`
(`committed`/`voided`/`stalled`)/`liftIsolate`; `controls.ts` `renderLiftRoute` shows the chosen route + badge.
A stalled lift (no `settled`) already leaves hops `promised` with `decision` undefined — the "unsettled/tie"
state is already non-spinning; keep it and label it clearly.

## Scope of THIS ticket

### `core/timeline.ts` — map the new events + classify voters

Extend `ConsensusState` with (all sorted/deduped, default `[]`):
- `voters: ConsensusVoter[]` where `ConsensusVoter = { key:string; node?:number; role:'participant'|'referee'; vote?:'C'|'NC' }`.
  Role = `participant` when the voter key resolves to a route entity (via `resolver.entityOfMember`), else
  `referee` (off-route, `node` undefined).
- `pulled: number[]` — entity ids that recovered via a successful pull (`record-pulled` with `ok:true`).
- `equivocators: number[]` — entity ids from `equivocation-proof-kept.signer`.
- `contradictions: number[]` — entity ids from `contradiction-detected.nodeId`.

In `deriveConsensus`'s event loop add cases:
- `voter-vote`: record a `voters` entry (classify role via `entityOfMember` directly — do **NOT** route an
  off-route voter key through the `resolveMember` helper, which pollutes `unresolved`; `unresolved` must stay
  for genuinely malformed non-voter events). When it resolves, keep the existing `bumpNode(voted)` + `nodeVote`.
- `record-pulled`: when `ok` and the puller key resolves, add its entity to `pulled`. (Phase is unchanged — the
  single `settled` event still settles the whole route; `pulled` is an orthogonal marker of *which* member
  needed a pull.)
- `equivocation-proof-kept`: resolve `signer` → `equivocators`.
- `contradiction-detected`: resolve `nodeId` → `contradictions`.

Keep `record-pushed`'s existing unresolved behaviour (the `badKey` test at timeline.test.ts:229–237 must stay green).

**Update the existing exact-shape consensus tests** (they use `.toEqual({...})` on `ConsensusState`, so new
fields break them): `timeline.test.ts` lines ~145–152 and ~229–234 (and any other `.toEqual` on a whole
`ConsensusState`) must gain `voters:[], pulled:[], equivocators:[], contradictions:[]`. The per-field assertions
(`c?.edges`, `c?.nodes`) are unaffected.

### Edge cases to cover (carry from the original ticket)

- Linear lift, interior non-relayer: **with** contact points → the far member recovers (a `record-pulled ok:true`
  → `pulled` mark); **without** → stays `promised`/stuck-pending (greyed, not errored). Both are the *observable
  consequence* framing, not a contact-point flag.
- Circular lift routing around a refuser via the ring: route `loop`, settles with no pull needed.
- Equivocating voter: `equivocation-proof-kept` marks it; the lift's settled `decision` shows which face won.
- Tie (no settlement): renders "unsettled" (stalled), does not spin.
