**Key design decision to know before reading/writing the abort tests** — `abort` signs our `NP` and then
calls `this.update(record)` (NOT a bare `push`). Why: in the pure-`NP` void nothing new propagates back to
the originator, and reachability's echo-suppression means the originator's own pushed `NP` never returns to
it — so a bare `push` would leave the **originator never releasing**. Routing the signed `NP` back through
`update` makes the originator release its own (empty) hold as a failure and diffuse the void **exactly as a
refusing participant does** (sign `NP` → classify `rejected` → `releaseOnce(false)` → push). So in the
seeded-abort test **every** node — including the originator — releases once as failure (`[false]`), which is
what the original ticket's test spec asked for. This is consistent with the existing refusal tests, where a
participant that signs `NP` releases `[false]` though it held nothing (`promiseCtxs === []`).

## Review/ handoff must flag

- `proceed` is deliberately thin (never ranks; caller passes a ranked plan). Full discovery→proceed e2e is
  **Part 3** (`tallynet-originator-proceed` Part 3 of 3).
- `abort`'s atomicity guard is **stricter** than principle 4's literal "abort before every participant has
  promised": because `proceed` auto-signs the originator's `P`, a `proceed`→`abort` is correctly refused,
  and `abort` is only effective on a seeded-but-unpromised record. Fully reconciling would need a
  seed-without-promise `proceed` variant **or** an "equivocation voids the lift" merge rule — **both out of
  scope** (merge rules belong to `tallynet-consensus-participant`, already landed).
- The `abort`→`update` decision above (originator releases its own empty hold as failure) — note it so the
  reviewer knows the seeded-abort test asserting `[false]` for the originator is intended, not incidental.
