## Why this exists (confirmed against source)

The original viewer ticket assumed `tallynet-record-availability` (now in `complete/`, seq 5.4) had added a
**pull** trace event. It did **not**. Record-availability shipped the pull *mechanism*
(`fetchOutcome`/`serveRecord` in `participant.ts`) plus two new trace events —
`equivocation-proof-kept { transactionCode, signer }` and
`contradiction-detected { transactionCode, ourOutcome, peerOutcome }` — but the pull itself emits **no trace
event**, so a recorded run cannot show "a silent node routed around by a pull." This ticket adds that event.

**No trace-format version bump is needed.** `packages/tallysim/src/sim/trace-format.ts` documents (lines ~16–21)
that `TRACE_FORMAT_VERSION` bumps only when a *line envelope* changes; a **new consensus event** needs no bump —
`serializeTraceLine`/`parseTrace` record and round-trip whatever `TraceEvent` the sink emits, verbatim, forking
nothing. So adding one variant to the `tallynet` union is purely additive and existing traces still parse.

## The event shape

Add to the `TraceEvent` union in `packages/tallynet/src/trace.ts`, mirroring `record-pushed`'s shape
(`{ type:'record-pushed'; transactionCode; to; promiseCount; commitCount; ok }`):

```ts
| (TraceBase & { type: 'record-pulled'; transactionCode: string; from: string; ok: boolean })
```

- `from` = the peer key we pulled **from** (the serving end), symmetric to push's `to`. It is a member
  **address key** — public in the route — so the disclosure invariant (see the `trace.ts` header) holds:
  `nodeId` (`TraceBase`) is the puller's own key, `from` is a public member address, no neighbour secret.
- `ok` = whether a usable reply came back and merged (true) vs the peer served nothing (false) — same
  true/false semantics as push's `ok`.

Keep the `// consensus events carry transactionCode` comment block above the union consistent (the new variant
carries `transactionCode`, so the viewer's `isConsensusEvent` (`'transactionCode' in event`) treats it as a
consensus event — intended).

## Emission site

`participant.ts` `fetchOutcome(transactionCode)` (~lines 241–253) already loops `reachablePeers(record)` and
calls `fetchRecord(transactionCode, peer)`, merging a reply via `update`. Emit one `record-pulled` **per peer**
after the fetch/merge, mirroring the existing `emitPushed` helper (~lines 874–884):

```ts
for (const peer of this.reachablePeers(record)) {
  const reply = await this.fetchRecord(transactionCode, peer)
  if (reply) {
    await this.update(reply, peer)
  }
  this.traceSink({ ...this.traceBase(record), type: 'record-pulled', transactionCode, from: peer.key, ok: reply !== undefined })
}
```

- `record` (the stored pre-merge record) is in scope and is a valid `traceBase` argument (the early `return
  'pending'` on no record guards it). Follow the existing `emitPushed`/`traceBase(record)` pattern exactly;
  consider factoring a small `emitPulled(record, from, ok)` for symmetry.
- Tracing is instrumentation only: `this.traceSink` is `safeTraceSink`-wrapped (a throw can never break the
  engine), and adding a sink call changes no control flow. Honour both engine invariants.
- `engine.ts`'s `fetchOutcome` just delegates to the participant; **no** new engine surface is needed.

## Non-issue to verify, not fix

`packages/tallysim/src/sim/consensus-metrics.ts` has a `switch (event.type)` (~line 181) over consensus events
with a `default` branch (no `never`-exhaustiveness assert), so `record-pulled` falls through harmlessly (it
only extends `maxTime`, i.e. time-to-completion — acceptable; a pull is part of settlement). Confirm no other
`tallynet`/`tallysim` consumer does an exhaustive `never` switch that the new variant would break
(`grep -rn "event.type" packages/tallynet/src packages/tallysim/src`).

## Test

There are existing pull e2e scenarios in `testing/consensus.test.ts` (interior refuser **with** contact points,
circular ring, silent originator/payee — per the record-availability handoff). Add a case that drives a pull
with a trace sink attached and asserts a `record-pulled` event with `ok:true` appears for the recovering member
(and, for the no-reply peers, `ok:false`). A focused `participant.test.ts` unit (a stub `fetchRecord` returning a
record for one peer, `undefined` for another) is the cheaper assertion of the per-peer `ok` semantics — prefer
that plus one e2e touch.
