Principle 0 (no global rules; each node decides) needs decision points. Some already exist — `DiscoveryHooks` (discovery) and `TrxParticipantResource.shouldPromise` (promise time). This ticket adds the voter-model-specific ones, with simple default policies the simulator (`tallysim-voter-model`) uses, and keeps TallyNet itself policy-free: the protocol enforces only verified signatures, the threshold invariant and (later) the deadline.

## What each decision point sees

The hooks already hand enough context; confirm and extend:

- **Promise-time (`shouldPromise`, `consensus/resource.ts`).** The `ResourceContext` already carries `member`, `inLinks`, `outLinks` and the full `record`. After `tallynet-terms-and-proposal-params`, the record core carries the full voter set (via `topology.members` with `V` roles), the consensus `method` + threshold, and the `liftContract` CID. So `shouldPromise` already sees everything principle 0 requires — **document that explicitly** in the hook doc (full voter set, threshold, deadline via `expiresAt(transactionCode)`, contract CID, every participant's terms on the links). Add the behaviour: when `shouldPromise` returns false (or a new `acceptsLiftContract`/`acceptsVoterSet` returns false), the node signs `NP` exactly as today — no new refusal path, just new reasons to refuse.
- **Discovery-time (`DiscoveryHooks`, `discovery/hooks.ts`).** During the search the final voter set is not yet assembled (voters are folded in on the return trip via `dependsOn`), but a returning plan carries the voters proposed **so far** in `plan.members`. Define precisely what the discovery hooks see of the proposed voters (the `plan.members` with their roles on `annotateReturn`/`negotiatePlan`), and let a node refuse a search whose query names a `method`/`liftContract` it rejects.

## New / extended hooks

- **Voter-set acceptance (promise time).** A host predicate over the record's voter set, so a participant can refuse a set it does not trust (too few voters, voters it does not recognise, a set stacked with obscure voters). Add to `TrxParticipantResource` (sits beside `shouldPromise`; a false result signs `NP`):

  ```ts
  /** Accept the record's voter set + consensus method + lift contract for OUR participation.
   *  Default when omitted: accept (today's behaviour). A false result signs NP. */
  acceptsProposal?(ctx: ResourceContext<TTerms, TPayload>): boolean | Promise<boolean>
  ```

  Keep it one hook (not three) so the host weighs voter set, method and contract together; the default accepts everything, preserving current behaviour. Wire it into `castPromise` **before** `shouldPromise`/`promise` (a refused proposal holds nothing), signing `NP` with a logged reason.

- **Originator plan scoring (`discovery/originator.ts`).** Discovery returns every satisfying plan; the originator drives one. Add a scoring hook so the originator ranks plans by voter set, not just hop count:

  ```ts
  /** Score a returned plan; the originator drives the highest score. Lower-is-worse; -Infinity ⇒ never pick.
   *  Default: prefer fewer voters, then shorter path, then first-found (deterministic). */
  scorePlan?(plan: Plan<TTerms, TPayload>, query: UniQuery<TTerms>): number
  ```

  The **default** policy: penalise a larger voter set and a longer path, so "a few well-known voters everyone trusts" outscores "a set stacked with obscure voters", and a stacked set is simply never chosen rather than refused by protocol. Expose which plan won so a sim/viewer can show plans passed over. The actual *selection* (pick the best, try another, keep searching) stays the originator's `discover` result plus the caller's loop — do not bake a retry policy into the protocol; just rank.

- **Voter-set acceptance (discovery time).** Extend `negotiatePlan` (or add a sibling) so a node on the return trip can refuse a plan whose voters-so-far it rejects, dropping that plan (returns `undefined`, as `annotateReturn`/`negotiatePlan` already do). Default identity (accept).

All defaults must leave every existing discovery/consensus test green.

## Edge cases & interactions

- `acceptsProposal` false on a middle participant → that participant signs `NP` → the lift voids in the promise phase (principle: any `NP` voids). Assert it.
- A voter set of 1 or 2 that the default `acceptsProposal` should arguably refuse: keep the **protocol** permissive (it settles a lone-voter set per the threshold) and put the "refuse a thin set" logic in the **default sim policy**, not the protocol. Document the split so a reviewer does not mistake policy for protocol.
- `scorePlan` returning `-Infinity` for every plan → the originator has nothing to drive → the caller treats it as "no acceptable route" (not a crash).
- A stacked voter set: a plan whose `members` include many `V`-only members a nominator added. The default `scorePlan` ranks it below a lean set; a test asserts the lean plan wins.
- Hook ordering at promise time: `acceptsProposal` → `shouldPromise` → `promise`; the first false/throw signs `NP` and holds nothing (the ChipNet ordering fix must not regress).
- Discovery hooks stay **synchronous** (as the others are); the promise-time hooks may be async (every call site already awaits).
- No hook may let unverified input change verified state — these hooks only gate *our own* signing and *our own* plan choice; they never admit a peer signature.
