The missing library step the regression check flagged (design.md § Lift proposal and settlement, and chipnet-review.md § Regression check): turning a discovered `Plan` into a `TrxRecord.topology` exists **nowhere** as protocol code — only the test harness `buildLift` hand-builds `topology.members` from a spec and never populates `dependsOn`. This ticket builds the real minting, the proceed/abort actions, contact-point stamping, and — critically — an end-to-end test that a `dependsOn`-nominated voter travels discovery → topology → vote count through a **real plan**, not a spec shortcut.

## Implementation blueprint (from completed investigation)

### Facts that save re-reading

- **`ConsensusNode` already has the entry points `proceed`/`abort` will build on.** `engine.ts:77`
  `start(record)` === `participant.update(record)` (originator seeds its own record; the state
  machine then classifies `ourPromiseNeeded`, signs the originator's `P`, pushes). `update(record,
  from?)` is the participant side. So `proceed` = `mintRecord(...)` then `start(record)`. No new
  push/plumbing needed — minting produces empty-signature records and all signing flows through the
  existing verified `update`/`sign` path (`participant.ts:627 sign`).
- **`promisePhaseComplete(record)` is `private` on `TrxParticipant`** (`participant.ts:467`): true iff
  every `P`-role member holds a verified `P`. `abort` must refuse once it holds. Options: (a) add a
  **public** `promisePhaseComplete(transactionCode)` reader on `TrxParticipant` + `ConsensusNode`
  that loads the stored record and calls the private predicate, and have `abort` use it; (b) make
  `abort` live on `TrxParticipant` where the predicate is in scope and expose a thin `ConsensusNode.abort`.
  Prefer (b): `abort` needs `store.getRecord`, `self`, `sign('NP')`, `push` — all private on
  `TrxParticipant`. Add `async abort(transactionCode)` to `TrxParticipant`, delegate from `ConsensusNode`.
  Abort logic: load record; if none or already released → no-op+log; if `promisePhaseComplete` → no-op+log
  (principle 3: originator has no special power after all promised); else sign our **`NP`** on our own
  participant member (reuse `castPromise`'s sign path or `sign(record,'NP','promises')`), save, then
  `push`. The existing `getRecordState` already maps any `NP` → `rejected` → void everywhere.
- **The record shape is fixed and well-understood** (`consensus/types.ts`): `TrxRecord` =
  `{ transactionCode, sessionCode, payload, topology:{members:DependentMember[], links:Record<nonce,TrxLink>},
  method, liftContract?, promises:[], commits:[] }`. `TrxLink = { source, target, intents }` where
  source/target are **member keys** (base64url). `topology.links` is **keyed by the edge's per-session
  nonce** (DAG-CBOR sorted keys ⇒ order-independent). Omit `liftContract` when absent (never
  `undefined` — DAG-CBOR rejects it); same "omit, don't undefine" discipline everywhere.
- **New-record validation the mint must satisfy** (`participant.ts:787 buildNewRecordRules`, runs on
  first `update`): valid tx+session codes; `NoDuplicateMembers` (**no repeated member key** — the
  circular trap); `LinksReferenceMembers` (every link source/target is a member key); ≥1 `P` member;
  **≥1 `V` member** (non-empty voter set); valid `ConsensusMethod`; `liftContract` non-empty string
  when present; `SelfConsistent` (a `P` member must ride ≥1 link; a `V`-only member rides none and is
  exempt); core canonically encodable. mintRecord must produce a record that passes all of these.
- **`plan.members` already IS the folded member set** (ticket's "inverse-free continuation"). Discovery's
  `prependMatch` (`discovery/participant.ts:714`) prepends each participant origin-first and appends its
  `dependsOn` voter nominees (`missing`), de-duping dependents and upgrading physical/secret. So
  `topology.members` ≈ `plan.members` carried forward — **with de-dup by key** (circular: originator
  appears once though it rides two links) and whatever role normalisation Taleus needs. `prependMatch`
  already enforces: a matched member must be `P`; a participant's `dependsOn` must **not** be a
  participant (voter-only nominees). mintRecord should surface the same voter-only-nominee invariant.
- **Link endpoint mapping is THE core algorithm + the main uncertainty.** `plan.path` is a list of
  anonymised `Link{nonce,intents}` (built outward, target-ward). `topology.links[nonce]` needs
  **source/target member KEYS**. Working hypothesis (verify with the e2e test, do not assume): filter
  `plan.members` to **participants** (`types∋'P'`) — they are in route order origin-first — then
  `path[i]` connects `participants[i] → participants[i+1]` (source=i, target=i+1, since path is
  target-ward). **Linear vs circular discriminator:** linear ⇒ `path.length === participants.length-1`;
  circular ⇒ `path.length === participants.length` (ring closes), where the last link wraps
  `participants[last] → participants[0]`. The nonce on `path[i]` is the SAME nonce both endpoints
  computed (`makeNonce(sessionCode, linkId)` is endpoint-symmetric via shared link id), so keying
  `topology.links` by `path[i].nonce` keeps every participant node's `nonceToLinkId` resolving — **reuse
  the discovery session code; do NOT mint a fresh one** (ticket requirement). ⚠️ The e2e test is what
  proves this correspondence holds with voter members interspersed and with peer-match termini; treat
  the hypothesis as unproven until that test is green.
- **Circular-lift discovery shape is an OPEN question to resolve first.** `discover` treats
  self-is-target as a **round-0 self-match** → `path:[] members:[O]` (`engine.ts` adapter note;
  `discovery.test.ts` "self is the target" → zero-hop plan). That degenerate plan has NO ring path, so
  it cannot mint the ticket's "single-member-entry/**two-link** topology". So either (a) the circular
  e2e case is built by a different discovery entry (target not literally self; search excludes the
  trivial self-match) — check whether such a path exists, or (b) the circular mint test seeds a
  hand-made two-link `Plan` (O↔X, both participants, O also voter) directly rather than via `discover`,
  and only the **referee/nominated-voter** e2e case goes through a real `discover`. The ticket's
  headline gap (a `dependsOn` nominee reaching topology+vote via a **real plan**) is satisfied by the
  linear-with-referee case; the circular case can be a mint-level unit test if real circular discovery
  isn't available. Decide this early — it gates the test design.
- **Contact points** (`Member.physical`): set on the originator's own member and on any voter whose
  plan member carries one. In the harness, `physical:true` ⇒ `dial:<name>` (`network.ts:408`); push
  reachability already fans out to every member with `physical` plus link neighbours
  (`participant.ts:685 reachablePeers`). For a **linear** lift, principle-3 reachability needs the
  originator AND every voter to publish a contact point (design.md § Contact points). mintRecord stamps
  what the plan carries; the harness mint path chooses whether to set them.

### Where code goes

- **`mintRecord`**: a pure function, best in a **new `src/consensus/mint.ts`**, re-exported from
  `consensus/index.ts` (barrel at `consensus/index.ts:8-14`). Signature per the ticket:
  `mintRecord({plan, query, payload, ttlMs?}) → TrxRecord`. It reads `query.sessionCode` (reuse!),
  `query.method`, `query.liftContract`, `query.maxDepth` (not needed for mint), and mints only the
  **transactionCode** (self-expiring, `session-code.ts generate(ttlMs,{now,random})` — needs clock+random
  injected, so either take them as args or make `mintRecord` a `ConsensusNode`/originator method that
  already holds `clock`). NOTE: `ConsensusNode` deps hold `clock` but not a `RandomSource` today — add
  one to `ConsensusNodeDeps` if the tx code is minted inside the node, or pass a pre-minted
  `transactionCode`. Session code is **reused from the plan/query**, never fresh.
- **`proceed`/`abort`**: methods on `TrxParticipant` (`consensus/participant.ts`) exposed via
  `ConsensusNode` (`consensus/engine.ts`). `proceed` also needs the `scorePlan`-ranked selection — but
  note `discover` **already returns plans best-first** (`originator.ts:207 rankPlans`), so "choose a
  plan" = take `plans[0]` (or let the caller pass the chosen plan). Keep `proceed` thin: it mints +
  `start`s. The taleus-core binding drives plan selection.
- **Harness mint-from-plan path**: add to `InMemoryNetwork` (`testing/network.ts`) a method like
  `mintFromPlan(originatorName, query, plan, payload, opts?)` that calls `mintRecord` and — crucially —
  **populates every involved node's `nonceToLinkIdByName` map** the way `buildLift`/`addLiftLink`
  (`network.ts:441`) does, so each participant's resource context resolves real link ids. Keep the
  spec-based `buildLift` unchanged. The discovery and consensus harnesses are the SAME
  `InMemoryNetwork` (it builds both `DiscoveryNode` and `ConsensusNode` per name when `signerFor`+
  `verifier` are passed) — but **discovery keys nodes by NAME while consensus keys by ed25519 KEY**
  (`network.ts:220-233`). A real `discover` returns plans whose member keys are NODE NAMES (the discovery
  `makeFindAddress` uses `name` as the address key, `network.ts:575`), but consensus members must be
  **ed25519 keys**. So the mint-from-plan harness path must **translate discovery name-keys → consensus
  member keys** (via `memberKeyByName`) when building the record, OR discovery's `findAddress` must be
  taught to use consensus keys. This name-vs-key seam is a real wiring task — budget for it.

### Known gaps / honesty for the reviewer

- The **path↔participant-order correspondence** for link endpoints is a *hypothesis*, proven only once
  the referee e2e passes. If it breaks with interspersed voters or peer-match termini, the fallback is
  to have discovery carry per-link endpoint keys explicitly (a `Link` field) — a larger change.
- The **circular-via-real-discovery** shape is unresolved (see above); the circular requirement may land
  as a mint unit test rather than a full `discover`→mint e2e.
- The **name-vs-key** translation in the harness mint path is new wiring not present in `buildLift`
  (which only ever deals in consensus keys). It is the most likely source of surprise.

## Plan → topology minting

Add to the consensus side (likely `ConsensusNode`/`engine.ts`, or a new `mint.ts` it calls) the originator's record-minting:

```ts
mintRecord(args: {
	plan: Plan<TTerms, TPayload>,     // the chosen plan (one plan per record — see design.md)
	query: UniQuery<TTerms>,          // carries target, intents, method, liftContract, maxDepth
	payload: TPayload,                // the opaque Taleus value the originator sets once
	ttlMs?: number,                   // for the self-expiring codes; default from options
}): TrxRecord<TTerms, TPayload>
```

It must:

- **Assemble the voter (`V`) member set** = the union of each participant's self-vote and its `dependsOn` nominees, exactly the fold `prependMatch` already performs on the return trip. The originator's own member is included; a circular lift's originator appears once in `members` even though it rides two links. De-duplicate members by key (a voter nominated by several members appears once). This is the step whose absence the regression check named — it is the inverse-free continuation of the `dependsOn`→`plan.members` fold already present in discovery.
- **Key the path links by nonce** into `topology.links` (source/target member keys, negotiated per-intent terms) — the same shape `buildLift` produces, but from the plan's `path`, not a spec.
- **Stamp the proposal parameters** from the query: `method`, `liftContract` (omit when absent), and mint the self-expiring `transactionCode`/`sessionCode` (reuse the session code the plan's nonces were salted with, so `nonceToLinkId` maps still resolve).
- **Stamp contact points**: set `Member.physical` on the originator's own member and on voters that published one (carried on the plan's members). Contact points are how a promised lift stays resolvable (design.md § Lift proposal and settlement); the originator and voters publishing one is what makes principle 3 hold for a linear lift.
- Produce a record with **empty** signature sets, ready to feed to the originator's own `TrxParticipant.update` (which then classifies `ourPromiseNeeded` and signs the originator's promise, exactly as today).

The harness `buildLift` stays as a test convenience, but add a path so tests can mint from a real discovered plan (below). The `taleus-core` binding (`feat-tallynet-bind-taleus-core`) calls `mintRecord` from its `DiscoveryResult.plans` → `ConsensusEngine` hand-off.

## Proceed / abort

- **Proceed** = choose a plan (via the caller's `scorePlan`-ranked selection from `tallynet-lift-policy-hooks`), `mintRecord`, and `update` the record into the originator's own participant. Phase 1 is then under way; the originator waits like any member.
- **Abort** = only valid **before every participant has promised**. The originator signs a **pre-promise void** — an `NP` on its own participant member — which voids the lift by the existing "any `NP` voids" rule, and pushes it. After every participant has promised the originator has no special power; `abort` must refuse (no-op + logged) once `promisePhaseComplete` holds. Add an `abort(transactionCode)` to the originator/ConsensusNode that checks this and signs `NP` only when still allowed.
- A **linear** lift needs no separate "word back from the payee": plans return to the originator along the path the query took (discovery already does this), so by the time the originator mints, it holds the full plan. Document this (principle 4) — do not build a payee callback.

## End-to-end test (the flagged gap)

Add a test in `testing/` that runs **discovery then consensus on one harness network**, with no `buildLift` spec shortcut for the voter set:

- Build a small graph where an interior participant **nominates a referee** (a `V`-only member) via its `findAddress` `dependsOn`.
- Run a real `discover`, take a returned `Plan`, `mintRecord` from it.
- Assert the nominated referee appears in `topology.members` as a `V` member, rides no tally link (referee-only), and — after the promise phase completes — its `C` vote is **counted** toward the majority (and a missing/`NC` vote from it changes the outcome per the threshold).
- Cover: a voter nominated by **two** participants appears once and counts once; a circular lift where originator = payee mints a valid single-member-entry/two-link topology.

This closes "untested end-to-end in TallyNet" from the regression check.

## Edge cases & interactions

- Voter sets of 1, 2 (tie under default threshold → no settlement), 3, many — assert each mints a valid topology and settles (or doesn't) per `tallynet-terms-and-proposal-params`.
- A participant that is also a voter (self-vote): appears once in `members` with both `P` and `V` roles.
- The same voter nominated by several members: one member entry, counted once (de-dupe by key at mint).
- Abort after one participant has promised but not all: still allowed (phase incomplete) → signs `NP` → voids. Abort after **all** promised: refused (the lift is now resolvable only by voters).
- A plan whose members include a `dependsOn` nominee that is itself a participant → `prependMatch` already rejects this; `mintRecord` must surface the same invariant (a voter-only nominee).
- Circular lift: originator rides two links; `mintRecord` must not create a duplicate member entry (the `hasDuplicateMemberKey` rule would reject it).
- Minting must set the session code so `nonceToLinkId` resolution still works at every node that took part in discovery (reuse the discovery session code; don't mint a fresh one).
- Deadline/timeout seams stay untouched (`tallynet-propagation-timeouts`); `mintRecord` sets the transaction-code TTL only.
- No unverified input path is introduced — minting produces a record with empty signatures; all signing goes through the existing verified `update`.
