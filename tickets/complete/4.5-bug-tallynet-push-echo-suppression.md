## What shipped

In `TrxParticipant.validateAndMerge` (`packages/tallynet/src/consensus/participant.ts:221`), after the existing `saveRecord`/`savePendingCommits` block and before the `record-received` trace, the participant now saves the **merged** record as the sender's last-known peer-record when `fromAddress` is present:

```ts
if (fromAddress) {
	await this.store.savePeerRecord(merged.transactionCode, fromAddress.key, snapshotRecord(merged))
}
```

This primes `push`'s skip-test (`push`, `:625`, `sameSignatureSets`): the peer we just received from already has a matching copy on file, so an unchanged record is not echoed back — but if our own state advances (promise/commit added via `advanceState`/`sign`, which run after `validateAndMerge`), the live record differs from the saved snapshot and the push correctly resumes. Saving the merged copy (not the raw incoming one, as ChipNet did) sidesteps ChipNet's own staleness `TODO`.

A regression test was added (`participant.test.ts`, `describe('TrxParticipant — reachability and push')`) driving a relay through receive-from-alice (pushes only to bob, no echo) then receive-from-bob (re-pushes to the now-stale alice, bob suppressed), covering both the no-echo and resumed-push halves.

## Review findings

Read the implement diff (`f7f6834`) first, then the code. Fix is correct, minimal, and idempotency-safe (an echo changes no outcome; this is a bandwidth/convergence optimisation). Checked across every angle:

- **Correctness / snapshot aliasing** — `snapshotRecord` copies the signature arrays, and `advanceState`/`sign` append via `record[bucket] = [...record[bucket], sig]` (new array, not in-place), so the saved snapshot stays frozen while `merged` advances. The store holds peer-records by reference (`store.ts:84`), so the snapshot is required, not optional — correctly used. `sameSignatureSets` ignores `attachment` and sorts, so ordering/opaque-data differences don't defeat suppression. ✅ No issue.
- **Resume-push ordering** — peer-record saved pre-`advanceState`; `push` compares against post-advance `merged`, so a member that advances still pushes its advancement to the sender. ✅ Verified by the new test's second assertion.
- **Settlement safety (circular / 2-cycle concern from the ticket)** — full package suite (`testing/consensus.test.ts`: linear, circular, diamond, sleeping, referee sets) passes unchanged with suppression active; lifts still settle everywhere. The implementer's noted absence of a *dedicated* 2-cycle-through-suppression test is acceptable — the existing circular-lift scenarios exercise the path and the convergence argument (content differs via own advancing state ⇒ re-push) holds. Not filed. ✅ Adequately covered.
