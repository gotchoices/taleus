## What shipped (engine half of the live-run feature)

The browser worker that generates a tally network and runs the real `tallynet` route-discovery search
in-page (no server, no Node), streaming the run's trace envelope back so it feeds the same replay view a
recorded trace does. The page half (form, click-to-pick, `new Worker(...)`, wiring the stream into replay)
is the sibling ticket **`tallysim-viewer-live-controls`** (seq 3.66, `prereq: tallysim-viewer-live-worker`).

Files after review:

- `build-scenario.ts` (pre-existing, unchanged) + `build-scenario.test.ts` — form values → `SimScenario` +
  `QuerySpec`; the pure translation helper, unit-tested.
- `sim-protocol.ts` — the type-only worker↔main `postMessage` union. Review added a contract note (below).
- `sim-worker.ts` — the worker: `generate` (materialise network, reply snapshot) and `run` (fresh
  `buildSimNetwork`, `runQuery`, stream `header` → `event`… → `done`). Refactored to delegate its two pure
  bits to `sim-run.ts`.
- `sim-run.ts` (**new, added by review**) — the worker's two pure, DOM-free functions, extracted so jest can
  cover them: `buildRunHeader` (mint the trace header for a known session code) and `plansToRoutes`
  (`QueryOutcome.plans` → `RouteInput[]`). Holds `VIEWER_VERSIONS`.
- `sim-run.test.ts` (**new, added by review**) — 9 tests over the two extracted functions.

## Review findings

Read the implement diff (`git show ebd2f10`) with fresh eyes first, then verified every `tallysim`/`tallynet`
API the worker calls against source, not the handoff's description.

**API correctness — checked, all correct.** Every call lines up with the current engine source:
- `buildSimNetwork(network, conditions, conditionsSeed, sink, scenario.budget)` matches `sim-runner.ts:160`
  and `cli/trace.ts:191` exactly (arg order, the `scenario.budget` → `OriginatorOptions` shape).
- `materializeNetwork(scenario.network, runSeed)`, `makeNetworkSnapshot`, `runQuery` → `{ sessionCode,
  found, plans }` all match `harness.ts` / `trace-format.ts`.
- `buildTraceHeader({ ...versions, scenario, runSeed, queries: [{ sessionCode, ...query }] })` — the query
  entry `{ sessionCode, from, to, amount, depth }` matches `TraceQueryEntry` field-for-field.
- `plan.path` is `Link<LiftTerms>[]` with `.nonce: string` and `.intents` — so `linkNonces`/`terms` map
  correctly and stay index-aligned (same `plan.path` order). `RouteInput` shape in `replay/routes.ts` matches.

**Control-flow (the handoff's "careful-read" list) — read and confirmed.** Header-from-first-event posts the
header before any `event` and once only; zero-event degenerate runs (`<2` entities, edge-less, `from===to`)
post a header from `outcome.sessionCode` after `runQuery` resolves, so a header **always** precedes `done`;
`runQuery` never throws for those cases (asserted in `harness.ts` docs + source); `run` before `generate`
throws → `error` phase `run`; both handlers catch internally and `handleRun` is `void`-ed, so the worker
cannot die silently.

**Determinism claim — plausible, confirmed by reading.** The worker's single `buildSimNetwork`+`runQuery` for
one query is behaviourally identical to the CLI's pass-2 (both fresh builds, fixed `SESSION_CODE_SEED=1`), so a
single-query live run's events + header byte-match a `tallysim trace` of the same seeds. Full byte-match is a
browser-only manual check that lands with the controls ticket.

**Test coverage — the honest gap, addressed (minor, fixed inline).** The implement stage left the worker's two
pure bits (header minting, plans→routes) with zero automated coverage — flagged by the implementer as the
biggest untested surface and offered as optional "cheap hardening." Done it: extracted both into a DOM-free
`sim-run.ts` and added `sim-run.test.ts` (9 tests: header stamping/provenance/seed/session-join; routes
multi-plan, index-alignment, self-payment loop, empty plans, empty path). This converts the largest untested
surface into a tested one without touching the worker's browser-only shell. Suite: 9→10 files, 69→78 tests.

**Worker↔controls contract gap — documented (minor, fixed inline).** The protocol carries no run-correlation
id and `run` re-supplies the scenario. Two real constraints the controls author must honour were implicit:
(1) **one run at a time** — overlapping runs would interleave two indistinguishable `header`/`event`/`done`
streams; (2) `run`'s `scenario` must equal the preceding `generate`'s, or the header's provenance won't match
the drawn network. Added a `NOTE` to `sim-protocol.ts`'s header spelling both out, with the fix (add a
session/run id) if concurrent runs are ever needed. Not a defect now (the natural controls design is
single-run), so documented at the contract, not filed.

**Source hygiene — good.** Small single-purpose functions, clear naming, no dead code beyond the
awaiting-consumer worker (expected). Comment density is high but purposeful. No `any`. Error paths logged, not
eaten.

**Tripwire re-homed.** The `VIEWER_VERSIONS`-are-hand-maintained-provenance tripwire moved verbatim with the
constant into `sim-run.ts` (still a `NOTE:` at its definition). Nothing reads those two version fields on load
(`parseTrace` validates only `traceFormatVersion`); if exact provenance is ever wanted, read real versions at
build time (Vite `define`).

**Still browser-only / deferred (unchanged from implement, correct to defer):** no headless-browser smoke test
instantiates the worker or drives the real `postMessage` stream — that and the manual use-cases (happy path,
determinism byte-match, self-payment, degenerate network, worker-failure surfacing) land with the controls
ticket. The worker's shell (`ctx` cast, `addEventListener`, the streaming wiring) is covered only by
type-check + `vite build`; its pure logic is now under jest.

**Major findings:** none — no new ticket filed.
