## Review findings

**Checked — no defect:**

- **Barrel correctness.** Confirmed `engine.ts` *imports* `DiscoveryResult` and never re-exports it, so the two new `export *`s in `discovery/index.ts` do not collide. Confirmed `src/index.ts` re-exports `discovery/index.js`, so the originator/engine symbols are genuinely on the package surface.
- **Harness helpers.** `storeOf`/`nonceToLinkMap` read the new `storeByName`, populated in `buildNode` where the store is now created once and shared with the `DiscoveryNode`. `nonceToLinkMap` is O(nodes), `async`, and — correctly documented and verified — used only in test assertions, never in discovery control flow. The per-node `getNonceToLinkMap` it builds on already merges a node's own contexts for a session; cross-node merge is safe because `makeNonce(session, linkId)` is identical at both ends of a link and distinct across links (no key conflict).
- **Design doc vs code.** Budget formula, constants (2000/1500 ms), `maxDepth` default (7), and "peer stats informational only" all match `originator.ts`. `sparstogram` confirmed absent from `package.json`. Backlog `feat-tallynet-adaptive-budget.md` exists and is referenced.
- **Tests are non-vacuous.** The 6-node happy path proves negotiation actually narrows every link to balance **100** (not the raw 500 the default pass-through hooks would carry) and that the originator resolves its own first-hop nonce back to `L1`. The maxDepth boundary is pinned in both directions; the slow-link case proves a late answer folds in exactly once; drop/not-found/disconnected/concurrent/scale all assert `pendingTimers === 0`. `yarn workspace tallynet build && test && lint` all green — **198 tests pass** (16 suites), suite ~1.8 s.

**Found — minor, fixed inline:**

- `packages/tallynet/src/index.ts` module doc called discovery part of "the discovery and consensus engines (later tickets)" while the same file now exports the discovery engine. Reworded: building blocks + the full discovery engine ship here; only consensus remains a later ticket.

**Observations recorded here (no ticket, no code change):**

- **`maxDepth` semantics are one step stricter than path length for a peer-match terminus.** A target reached as a neighbour of a relay (without entering that relay) at path length *n* needs `maxDepth >= n + 1` — empirically pinned by the `maxDepth boundary` describe (length-3 terminus missed at `maxDepth: 3`, found at `maxDepth: 4`). This is **not a bug**: the `path.length <= maxDepth` invariant always holds (asserted by `assertValidPlan`), nothing over-runs the ceiling, the behaviour is conservative (finds fewer, never more), and `OriginatorOptions.maxDepth`'s own doc describes it as "reentrance rounds," not path length — which is accurate. Now characterised by test. If a future reader wants the exact round→depth accounting pinned down *in the engine* rather than only by test, that is an optional follow-up on `originator.ts`, out of scope here.
- **`assertValidPlan` resolves nonces through the cross-node merged map**, so the "originator owns its own first edge" property is directly asserted only in the 6-node happy path (via `storeOf('N1')`), not in the random/scale/diamond cases, which check only chain connectivity. Acceptable — the key property has one strong witness — but a reviewer deepening these tests could add a per-originator first-hop check to the diamond/scale cases.

## Honest gaps carried forward (from implement, still true)

- **Budget constants (2000 / 1500 ms) are coarse guesses.** Adaptive tuning parked as `feat-tallynet-adaptive-budget` (local clock-measured quantile, never trust peer stats).
- **The harness drop/sleep model is deliberately simple** (`drop` = eternally-sleeping delivery, no timer; `latencyMs` = request leg only). Richer failure/timing models belong in `tallysim`.
- **The taleus-core adapter is only *described*** in `engine.ts` (a comment block mapping `LiftQuery`/`NegotiateCallbacks`/`CandidateRoute`). Implemented and verified against real taleus-core shapes by `tallynet-bind-taleus-core`.
