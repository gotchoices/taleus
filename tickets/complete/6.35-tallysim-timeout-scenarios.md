## What landed

A new test file **`packages/tallysim/src/sim/consensus-timeout.test.ts`** (266 lines) proving the three
self-resolving lift outcomes at the simulator level, the 6.32 consensus metrics read end-to-end over them,
and a determinism pass. **No production behaviour changed** — the only edits to `consensus-harness.ts` and
`consensus-metrics.ts` are doc-comment rewrites; `net.clock.runUntilIdle()` already fires the protocol's
deadline one-shot and recovery-loop ticks, so each lift settles itself inside the existing single drive.
Stale "v1 has no timeout" wording removed from the two module headers and `design.md`.

The three scenarios (each a hand-built `line` network read through `analyzeLift`):

1. **Late voter → voids by its own deadline.** `line(2)`, discovery on a fast sim, lift driven on a second sim
   over the same network at uniform 50 000 ms latency with a short `ttlMs` 80 000, so the completing promise
   reaches the sole voter post-expiry → `castCommit` votes `NC` → `void` (`voidReason` `voted-no-commit`).
2. **Dropped commit-push → recovers by the loop.** `line(5)`, node 2 a non-relayer, originator publishes a
   contact point; the stranded members pull the settled record on the protocol's own loop and commit
   (`recovered === 1`, completion 1.0).
3. **Needed party never returns → abandons, stays `pending`.** `line(2)` whose sole link drops
   (`dropFraction: 1`), small `recoveryGiveupMs`; the push never lands, the promise phase never completes, the
   loop abandons (`permanentlyPending === true`, `recovery-abandoned` event present).

Plus an aggregate metrics test (`timeToSettleMs.count === 2`, `permanentlyPendingFraction ≈ 1/3`, void-reason
tallies) and two determinism tests (deadline-void + permanently-stuck replay byte-identical `LiftResult`,
`ConsensusLiftMetrics`, and serialized network).

## Tripwires (parked in code, indexed here — not tickets)

- `consensus-timeout.test.ts:66` `NOTE:` at the deadline-void constants — the `L < ttl < 2L` ratio is tuned
  empirically against tallynet's recovery grace/backoff. Seed-independent (uniform constant latency) but
  schedule-fragile: a tallynet recovery-schedule change could flip the sole-voter vote to pre-expiry
  (→ commit) or make the loop abandon before voting (→ pending). The determinism tests catch a *value* drift,
  not a schedule change that stays deterministic but wrong-outcome — re-run this file after touching tallynet
  recovery timing. (Verified present and greppable.)
- The `line(3)`-stalls-to-pending finding is captured in `runLateVoterVoids`'s docstring
  (`consensus-timeout.test.ts:101-110`) so a future editor does not "simplify" the single-hop choice back into
  a multi-hop line and silently get `pending`.
