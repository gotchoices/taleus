## What shipped

A **lift** moves value around a chain/cycle of two-party credit relationships. Each party first
**promises** (reserves credit); then **voters** vote commit/void to settle atomically. Before this change,
if a party died *before* promising, the promise set never completed, no vote was ever cast, and every party
who had already promised held that credit forever (`pending`, no way out).

After this change: as long as a **voter is reachable**, that voter votes `NC` (no-commit) at its own
deadline **even on an incomplete promise set**, so a void majority settles the lift and everyone releases.
The only remaining stuck case is a **dead voter** — a voter majority that never hears the record, so no
reachable voter can ever produce a void vote. The pending-vs-void split moved from "did the promise phase
complete?" to "is a voter reachable?".

Mechanism: an `NC` preimage binds only the immutable transaction core (never the promise set, unlike a `C`),
so it verifies the instant it arrives — no side pool, no "void-before-complete" face. In `getRecordState`
the void-majority check now runs **before** the promise-phase gate; in the incomplete-set branch the
participant-promise check runs first (a `P`+`V` member that never promised signs `NP`, which voids via the
any-refusal rule), then the voter-void check (`weAre(voter) && !weHaveSigned(commits) && anyCodeExpired`).

## Review findings

Adversarial pass over the implement diff (`git diff 779c257 9e31506`), read before the handoff summary.
Scrutinized from every angle; the implementer's tests were treated as a floor.

**Correctness / protocol logic — checked, sound.**
- `getRecordState` reordering (void-majority check before the promise-phase gate) is safe: the `settles`
  strict-majority floor (`count*2 > W`) keeps commit and void mutually exclusive, so moving the void check
  ahead of the commit check cannot change which side wins.
- The incomplete-set branch ordering (participant-promise FIRST, then voter-void) is load-bearing and is
  explicitly tested (`participant.test.ts` § *a P+V member that never promised signs NP…*).
- `castCommit` casts `NC` **only** on `anyCodeExpired`; the voter-void branch is gated on the same, so a
  voter never signs a `C` over an incomplete promise set and never voids pre-deadline. Verified in source.
- `digest.ts`: an `NC` is byte-identical across any (even incomplete) promise set, so it verifies standalone.
  `promoteCommit`/`drainPendingCommits` still detect a C&NC equivocation (now with the `NC` holding the
  authoritative slot and the drained `C` colliding) — reversal is intentional and tested.

**Safety — checked, no premature void.** The `anyCodeExpired` pre-gate stops a merely-slow (not dead)
incomplete set from voiding early; guarded by the e2e safety counterpart (`consensus.test.ts` § *a voter on
a set that is merely slow … does NOT void prematurely*). Clock-skew sensitivity of the deadline is
pre-existing (documented `skewGrace` NOTE), unchanged by this work.

**Tests — checked, strong.** Unit (digest NC-invariance; participant incomplete-set void + ordering guard),
e2e (void-on-incomplete + safety counterpart + equivocation reversal + garbage-NC-rejected-on-arrival),
tallysim (harness dead-voter + incomplete-set-voids mirror + determinism + combined-metrics + runner
re-characterization). Happy path, edge, error, and regression all covered.

**Judgment call #3 (runner re-characterization) — reviewed and ACCEPTED.** The sim runner's voter model is
self-voting: `voters ?? [route[0]]` (`consensus-harness.ts:133`), the originator, confirmed always reachable
(`consensus-runner.ts:256`). The runner therefore *structurally cannot* produce a dead-voter pending — the
sleeping-target scenario now correctly voids by the reachable originator's deadline. Dropping runner-level
pending coverage is acceptable: dead-voter pending survives at the harness level (`runPermanentlyStuck`,
`voters:[1]`) and the summarizer level (combined-metrics test + `consensus-metrics` unit tests). This is the
honest reflection of the new protocol and a better end-to-end proof of the ticket's value.

**Docs — checked, accurate.** `tallynet/docs/design.md` (voter sets, deadline, principle 3, "Not in v1"),
`tallysim/docs/design.md` (pending=dead-voter, new incomplete-set-void bullet), and the downstream
`feat-lift-timeout-release.md` backlog ticket (common path is now a verified void; bilateral machinery
reserved for the dead-voter case) all reflect the new reality. No doc left stale.

**Cross-package ripple — checked, none.** `taleus-core` carries its own legacy single-referee lift state
machine (its `'pending'` is unrelated) and is not yet bound to tallynet (`feat-tallynet-bind-taleus-core`).
No other package consumes the consensus outcome semantics. No file that should have been touched was missed.

**Source hygiene — checked, fine.** Small single-purpose functions; comments verbose but purposeful given
the protocol subtlety. No new file-size concerns.

### Disposition

- **Minor (fixed inline):** added a tripwire `NOTE` at `participant.ts` `onRecoveryTick` (~:1088) documenting
  the load-bearing ordering — the advance loop (which casts the deadline `NC`) MUST run before the abandon
  check, or a reachable voter whose first post-expiry tick already sits past a small `recoveryGiveupMs` would
  abandon `pending` without ever voting. The dependency is pre-existing but now also carries the
  incomplete-set void; it was undocumented at the site. Covered by `consensus-timeout.test.ts`
  § incomplete-set-voids.
- **Major:** none — no new tickets filed.
- **Tripwire:** the ordering dependency above (parked as the `NOTE`, not a ticket — a future reorder is the
  only trip condition and the tests catch it).
