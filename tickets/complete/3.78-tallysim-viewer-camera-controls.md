## What shipped

Camera chrome for the tallysim-viewer graph, entirely inside `render.ts` (new functions) + `styles.ts` (new
CSS classes) + `docs/design.md` (new "Camera controls" subsection). `shell.ts` untouched.

- On-screen control cluster (bottom-right of the graph): zoom in/out, Fit, Reset, rotate left/right, each a
  `<button type="button">` with an `aria-label`.
- Keyboard shortcuts scoped to the graph by attaching the `keydown` listener to the graph container itself
  (`tabIndex = 0`) rather than `document`: `+`/`=` zoom in, `-`/`_` zoom out, `0` reset, arrows pan (step scaled
  by the camera's ratio), `[`/`]` rotate.
- Dismissible bottom-left hint ("Drag to pan. Scroll or pinch to zoom."), dismissal persisted in `localStorage`.
- Fit = `camera.animate({x:0.5,y:0.5,ratio:1})`, Reset = `camera.reset()` — both lean on sigma's own
  auto-rescale, no manual bounding-box math.

## Review findings

Reviewed the implement diff (commit `66934d5`) against the full `render.ts`, `shell.ts`, `styles.ts`, and the
sigma `Camera` type defs / drag source in `node_modules`.

**Correctness — no defects found.**
- Verified every camera method used exists with the signature called: `zoomIn`/`zoomOut` take
  `{factor?, ...AnimateOptions}`, `reset(options?)` and `animate(state, options?)` take `{duration}`
  (`sigma/dist/declarations/src/core/camera.d.ts`). `tsc --noEmit` passes.
- Arrow-key pan sign (flagged as unverified in the handoff): traced sigma's own drag-pan math
  (`sigma.esm.js:779-791`, `offsetY = lastMouse.y - mouse.y`). The keyboard camera-move model (ArrowUp →
  `camera.y - step` → camera moves up → reveals content above) is a defensible, self-consistent convention, not
  a bug. Left as-is; it was always a convention choice, not a correctness question.
- `reset()` restores `angle: 0` (DEFAULT_CAMERA_STATE); Fit keeps the current angle. Matches the documented
  Fit-vs-Reset split (`0` bound to Reset, Fit button-only).

**Resource cleanup — sound.** The container persists across loads (`shell.ts` `teardown()` only does
`graph.textContent = ''`), and the one listener attached directly to the container (`keydown`) is explicitly
`removeEventListener`'d in `destroy()`, which `renderNetwork` calls via `teardown()` before each re-render — so
no listener stacking (the handoff's "press `0` once, get one reset" gotcha). Button/hint click listeners are on
child elements removed on `destroy()` / cleared by `textContent = ''`, so they GC with their elements. The
WebGL-absent path returns `stubView()` before any camera code runs, so nothing to clean there.

**CSS / layout — correct.** `#tsv-graph` is `position: relative`, so the absolutely-positioned
`.tsv-camera-controls` / `.tsv-camera-hint` anchor to the graph box. `#tsv-graph:focus-visible` gives the
now-focusable container a visible focus ring. Buttons reuse the shared `#tsv-app button` chrome, so both themes
are covered without new per-theme rules.

**Docs — accurate.** The new design.md subsection matches the shipped key bindings, the Fit-clipping trade-off,
and the cleanup gotcha. No other doc references camera controls.

**Test coverage — gap, recorded as a tripwire (not a ticket).** `handleCameraKeydown` and `panCamera` are pure
(a `Camera` + a key in, camera calls out, no browser globals) and would be node-testable, but they live in
`render.ts`, whose top-level `import Sigma from 'sigma'` is exactly why the jest config defers this whole module
to a (deferred) headless-WebGL smoke test. Rather than fight that documented decision for marginal benefit, I
left a `NOTE:` at the `handleCameraKeydown` site saying the two functions are the piece worth extracting behind
a type-only `Camera` import (or folding into the smoke test) if the key map ever churns. No new test added; the
logic is verified correct by inspection + the sigma API/source check above.

**DRY (considered, not changed).** Zoom/reset/rotate actions appear in both `CAMERA_CONTROLS` and
`handleCameraKeydown`. The overlap is shallow one-liners, and the keys don't map 1:1 to the buttons (keys add
pan, buttons add Fit); an index-coupled lookup to dedupe would be more fragile than the explicit switch. Left
as-is deliberately.

**Not verifiable in this sandbox (inherent, no browser):** the manual click-through the ticket lists — each
button/shortcut doing what it says, shortcut inertness while the search box is focused, hint-dismiss persistence
across reload, Sweep-mode hide/show, tooltip-after-rotate, light/dark visuals, no-WebGL2 path. These rely on
behavior I could only confirm by code + API inspection, which I did; a human or the deferred smoke test should
do the live pass.
