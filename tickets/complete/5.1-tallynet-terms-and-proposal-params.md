## What shipped

The implementation landed as one atomic change (an exported wire-code + API rename plus two new required record/query fields that cannot split across commits without a broken intermediate build). Reviewed against the implement diff (commit `78bdf68`). Build, full test suite, and lint are green across the monorepo; after the two tests this review added, tallynet is 339 tests passing, lint exit 0.

### The three things that mattered most, and what I found

- **Digest binding (the high-risk part).** `recordDigest` builds its preimage from an explicit field list, so new `TrxRecord` fields do **not** auto-bind. Confirmed `mt: record.method` is always in the preimage and `lc: record.liftContract` is added **only when present** (never set to `undefined` — DAG-CBOR rejects it), matching the existing `pr` key's discipline. The `Pick<>` on the `record` param was correctly widened. The digest-vector tests (`digest.test.ts`) assert that two records differing only in `method`, or only in `liftContract`, hash differently — the tripwire that fails if this binding is ever removed. **Correct.**
- **Threshold math.** `getRecordState`'s `settles(count) = count*2 > totalWeight && count*thresholdDen >= thresholdNum*totalWeight`. Integer arithmetic only. The strict-majority floor (`count*2 > W`) keeps commit and void mutually exclusive at **any** threshold (two strict majorities over distinct voters sum to more than W); the threshold only raises the bar. At the default `1/2` the threshold test is implied by the floor, so the result is `> W/2` — byte-identical to before. Verified by hand across the cases (2-of-3 at 2/3, 3-of-4 at 3/4, the 2-of-4 no-settle band, unanimity, lone voter). **Correct and exact.**
- **Shared validator.** One `consensusMethodError` (`distinct-voter` only, positive-integer threshold, `1/2 ≤ t ≤ 1`) is wired into **both** the consensus new-record rules and the discovery query rules, so a node refuses a bad method during the search before it ever promises. **Correct.**

### Terms rename

`MemberType` `'R'` → `'V'`; `MemberTypes.referee` → `MemberTypes.voter`. A "referee" is now defined as a voter that is not also a participant — no distinct wire code. Trace event `'referee-vote'` → `'voter-vote'` renamed in lockstep with its `tallysim`/`tallysim-viewer` consumers. Verified no stray `referee-vote` trace strings remain anywhere (the only `referee` remnants are in `taleus-core`, an independent domain concept this ticket deliberately did not touch, and the intentional doc references to that schema).

## Review findings

- **Correctness (digest binding, threshold arithmetic, mutual exclusivity, validator bounds):** verified by code reading and by hand across the settlement cases. No defects. The default method reduces to the prior `> W/2` behaviour — every pre-existing consensus test passes with only `R`→`V` fixture edits.
- **Cross-package seam (trace event rename):** consistent across `tallynet`, `tallysim`, `tallysim-viewer`. No remnants. No defect.
- **Docs:** `packages/tallynet/docs/design.md` was read in full against the change. The voter terminology, threshold settlement, voter-set section, and the "Not in v1" note all reflect the new reality. The retained "legacy single referee per edge" references point at the `taleus-core` schema that `feat-tallynet-bind-taleus-core` replaces — correctly kept.
- **Test coverage — gaps closed in this pass (minor, fixed inline):**
  - Added `discovery/participant.test.ts` → "refuses a query whose consensus method we cannot honour, before promising (ConsensusMethod)": a reserved weighting and an out-of-range threshold are now directly asserted to be refused at discovery time (previously the discovery-side rule was only exercised indirectly). *(handoff gap #2)*
  - Added `consensus/participant.test.ts` → "rejects an empty-string lift contract but accepts a present, non-empty one (LiftContract)": the `LiftContract` rule had a shape check but no test. *(handoff gap #3)*
- **Doc hygiene (minor, fixed inline):** `outcome()`'s docstring in `consensus/participant.ts` still described settlement as a plain "strict commit/void majority"; reworded to name the method's threshold (it reuses `getRecordState`, so behaviour was already correct — only the comment was stale).
- **Query→record consistency (handoff gap #1) — confirmed acceptable scoping, not a defect.** `method`/`liftContract` ride on `UniQuery` and `TrxRecord` independently today; no production path folds a query's method into a minted record yet. That fold belongs to `tallynet-originator-proceed` (the plan→topology minting step), as `design.md` § Lift proposal and settlement states. Nothing to do here.
- **Overflow in `count * thresholdDen` / `thresholdNum * totalWeight`:** not a concern — voter counts and thresholds are tiny integers at lift scale. Noted and dismissed.
- **Resource cleanup / error handling / type safety:** no new resources, timers, or `any`. The new validator returns a typed `string | undefined`; rules thread it cleanly. No findings.
- **Major findings (new fix/plan/backlog tickets):** none.
- **Tripwires (conditional concerns parked, not ticketed):** none introduced. The pre-existing `NOTE:` tripwires in `countVerifiedCommits` (re-verifies every commit per pass; cache if voter sets grow large) and `canonicalPromiseSet` (re-maps/re-sorts per verify) are unchanged by this ticket and still accurate after the rename — the threshold comparison is O(1) integer arithmetic, adding no new cost.
