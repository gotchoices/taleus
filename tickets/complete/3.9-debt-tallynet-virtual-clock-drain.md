description: The test/simulator fake clock used to guess that pending async work had finished by counting a fixed number of idle steps; a longer-than-expected chain of work slipped past the guess and a timer got silently dropped. The guess is gone — the clock now lets the event loop turn a full macrotask at a time, which flushes an entire chain of any length in one step.

## What shipped

`VirtualClock` (`packages/tallynet/src/testing/clock.ts`) now drains the event loop **one macrotask at
a time** between timer fires instead of counting microtask hops against a guessed `DRAIN_QUIET = 64`
threshold. One macrotask hop flushes a microtask continuation cascade of any length, so the old guess —
and the silent timer-drop that happened whenever a real chain outran it — are gone. The macrotask is
scheduled with a lazily-created `MessageChannel` (`setTimeout` is forbidden in this platform-neutral
file), closed when the clock goes idle so no handle keeps a jest worker alive. The old async-callback
`pending` counter was deleted and a loud overrun guard (`assertDrained`) added. Implementation is sound
for all current usage; full detail in the git history (`ticket(implement): debt-tallynet-virtual-clock-drain`).

## Review findings

**Verdict: the landed fix is correct for its stated scope** (microtask-chain-length silent drop —
eliminated and regression-tested). Lint, build, and all tests pass. One real dormant defect was found
and filed; three doc/comment staleness items were fixed inline.

### Checked — build & test gates (all green)

- `tallynet`: lint ✓, `types: []` neutral build ✓, **324 tests pass**, suite exits clean (no
  "worker failed to exit gracefully", confirming the `closeChannel`-on-idle handling).
- `tallysim`: **381 tests pass** (including the concurrent-vs-sequential byte-identical invariant in
  `sim-runner.test.ts`, which this clock underpins). Re-ran after my doc edit; unaffected.
- Port-neutrality guard (`no-node-globals.test.ts`) still passes: confirmed `MessageChannel` is on
  neither the forbidden nor the port-rule list, and the `setTimeout` allowlist is `clock.ts` only
  (not `testing/clock.ts`), so the constraint that forced `MessageChannel` is real.

### Checked — correctness of the mechanism

- **Macrotask drain logic** (`drain`, `advance`, `runUntilIdle`, `fire`, `assertDrained`): verified the
  fire→drain→recheck loop fully flushes a callback's microtask cascade (including the onward timers it
  schedules at its end) before `earliest()` is re-read. The regression test
  (`long-continuation-chain drain`, N ∈ {8,64,200,2000}) directly covers this and is a genuine floor —
  N=200/2000 fail on the old clock.
- **`pending`-counter removal**: confirmed safe. Walked all three `setTimer` callers
  (`sequencing.ts:113` fires a synchronous `finish()`; both `network.ts` callbacks route rejections
  into caught handlers). None returns a rejecting promise to `fire`, so the new `void timer.fn()` (which
  matches `realClock` and lets rejections surface rather than swallowing them) introduces no unhandled
  rejection today. The implementer's `NOTE:` tripwire at the `fire` site is accurately dispositioned.
- **`advance` partial-window / `assertDrained` interaction**: the guard checks "no new mutation on one
  more hop", not "heap empty", so `advance(partialWindow)` that leaves out-of-window timers passes
  correctly. Confirmed by the slow-link tests.

### Found & FIXED INLINE (minor — doc/comment staleness the implement stage left behind)

- `packages/tallynet/src/testing/network.ts` (~line 465): the delivery-timer comment still described the
  deleted `pending` mechanism ("the VirtualClock tracks it in flight") and pointed at a removed class-doc
  note. Rewrote the comment and changed the callback to `void` its caught promise instead of returning a
  now-dead value. Behaviour identical; re-ran tallynet green.
- `packages/tallynet/docs/design.md` (reach paragraph) and `packages/tallysim/docs/design.md` (the depth-
  doubling blockquote): both still told the reader that discovery's reach is only correct *while*
  `VirtualClock`'s `DRAIN_QUIET` exceeds the per-level cascade, pointing at a `DRAIN_QUIET` NOTE that no
  longer exists — the exact dependency this fix removed. Updated both to state the macrotask drain flushes
  any cascade in one hop, so reach no longer depends on a tuned threshold.

### Found & FILED AS A NEW TICKET (major — real latent defect, dormant)

- **`tickets/backlog/debt-tallynet-macrotask-callback-drop.md`** — the macrotask drain's "one hop flushes
  everything" guarantee holds for **microtasks only**. A timer callback that awaits a *real macrotask*
  (a foreign `MessageChannel`/`setImmediate`/real I/O) before scheduling its next timer is **silently
  dropped**: the clock's own channel reaches quiescence while the callback's independent macrotask sits
  unserviced, the run returns, and the timer is orphaned with no error. `assertDrained`'s single extra hop
  shares the blind spot, so the "loud guard" does **not** catch it. Reproduced during review (standalone
  script in the ticket). **Dormant**: no current callback crosses a real macrotask boundary (consensus
  `update` is pure microtasks + sync crypto; discovery callbacks are void), so all suites are green — but
  it is the same silent-wrong-result class this ticket fixed, reachable the day a store does real async
  I/O behind a timer callback. The handoff's known-gap #3 claimed this case was "tolerated as long as the
  callback's macrotask work finishes within the drain's hops"; that reasoning is **wrong** — the issue is
  non-interleaving of channels, not hop count, so more `DRAIN_QUIET` does not help. Left a `NOTE:` at the
  test site pointing to the ticket; the fix lands the regression test.

### Tripwires (conditional — recorded, not ticketed)

- **Rejection surfacing at `fire`** (already a `NOTE:` at `clock.ts` `fire`): `void timer.fn()` lets a
  future async callback that rejects without catching surface as an unhandled rejection. None does today.
  Left as the implementer placed it — accurate.
- **`MAX_DRAIN = 100_000` is now macrotask hops**, a runaway backstop behind the `maxSteps` guard. Fine;
  noted in the code.
- **Reentrancy of the shared `MessageChannel` / single-slot `resolveMacrotask`**: correct only because
  `advance`/`runUntilIdle` are driven sequentially from outside (never re-entered by a timer callback on
  the same clock). Not a supported path; no code does it. Noted here, not ticketed — if nested clock
  driving is ever introduced, the single resolver slot and `closeChannel`-in-`finally` would need revisiting.

### Not changed (deliberately)

- `MAX_DRAIN`, `DEFAULT_MAX_STEPS`, the heap, and the macrotask primitive choice are all sound. The
  performance question the fix ticket raised was measured by the implementer (wall-clock wash on the real
  suites) and reconfirmed indirectly here (suite times unchanged); the hybrid fallback was correctly not
  needed.
