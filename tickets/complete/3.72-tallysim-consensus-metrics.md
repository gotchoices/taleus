## What shipped

A **pure** consensus-metrics module (`packages/tallysim/src/sim/consensus-metrics.ts`): recorded lift in,
metrics out — no network, clock, or filesystem. It is the consensus analogue of the already-landed
`sim/protocol-metrics.ts` (the discovery tier). Per lift and per run it answers: of the routes the protocol
found and took, how many committed vs. voided vs. stalled, how fast (ms), how many consensus messages, and —
for the non-commits — why.

Public surface (re-exported from `sim/index.ts`): `VoidReason`, `zeroVoidReasons()`, `ALL_VOID_REASONS`,
`ConsensusLiftMetrics`, `ConsensusRunMetrics`, `analyzeLift(events, result)`,
`summarizeConsensusMetrics(lifts, structural, queryCount)`. Headline metric: `pCommitGivenFound` =
`commitCount / liftCount` (0, never NaN, when no lift ran).

## Review findings

Adversarial pass over the implement diff (commit `84bcf46`), read before the handoff summary. Scrutinised for
correctness, type safety, DRY, source hygiene, error handling, resource cleanup, and test coverage.

**Correctness / type safety — checked, no defects.** Verified every trace-event type and field name the module
reads against the real `tallynet/src/trace.ts` `TraceEvent` union and `consensus/types.ts`: `signature-rejected`
carries `reason: SignatureRejectReason` (which includes `'expired'`), `promise-signed` carries
`signatureType: 'P' | 'NP'`, `referee-vote` carries `decision: 'C' | 'NC'`, `settled` carries
`decision: 'commit' | 'void'`. Confirmed `LiftResult` shape (`consensus-harness.ts`) and
`summarizeDistribution` / `StructuralMetrics` / `DistributionSummary` (`metrics.ts`). The `forTransaction`
type guard (`'transactionCode' in event && === result.transactionCode`) correctly excludes every discovery
event (none carry a `transactionCode`) and every other lift's events in a concurrent batch. Void-reason
precedence, the `0`-not-NaN fraction guard, and the zero-lift / empty-distribution degenerate paths are all
sound and mirror the landed `protocol-metrics.ts`.

**Test coverage — adequate as a floor.** The 11 tests cover the enumerated cases: reason-set shape; a commit
stream; NP→void (`refused-promise`); NC→void (`voted-no-commit`); pending-is-stalled with a stray NP that must
not override; `expired` beating a co-present NP; refuser-and-dropped-edge counting once; zero lifts; and an
end-to-end `analyzeLift`→`summarizeConsensusMetrics` over three hand traces. Happy path, the four void reasons,
the outcome-driven precedence, and the degenerate aggregate are all exercised.

**Minor findings — fixed inline (this pass):**

1. *Docs out of date.* The change added a whole measurement tier but `packages/tallysim/docs/design.md` had no
   `### Consensus metrics` subsection, although its sibling `protocol-metrics.ts` has a parallel `### Protocol
   metrics` one. **Fixed:** added the mirrored subsection under `## Consensus simulation` describing
   `analyzeLift`, `summarizeConsensusMetrics`, `pCommitGivenFound`, the void-reason precedence, and the
   compile-checked `zeroVoidReasons` source of truth.

2. *`timeToSettleMs` is really time-to-completion.* It spans to the **last** consensus event, which may be a
   post-`settled` `resources-released`, so it includes cleanup latency rather than ending at `settled`.
   **Not changed** — keying on the `settled` event would be fragile against a void path the real engine might
   emit without one (the very reality-gap the handoff flags), and the "last event" choice mirrors
   `protocol-metrics.ts`'s `timeToCompletionMs`. Recorded as a `NOTE:` at the computation site in `analyzeLift`
   so a future reader meets it when the consensus runner lands and the real event ordering is known.

**Tripwires (conditional — no ticket):**

- *Linear per-lift scan.* `analyzeLift` scans the whole `events` array per lift, so a caller passing a full
  concurrent batch to every lift is O(lifts × events). Already parked by the implementer as a `NOTE:` in
  `analyzeLift`; fine at current sim scale, pre-bucket by `transactionCode` if batch sizes grow. Mirrors
  `protocol-metrics.ts`'s `analyzeQuery`, so consistent, not a regression.
- *`timeToSettleMs` semantics* (above) — parked as a second `NOTE:` at the site.

**Major findings — none.** No new tickets filed.

**Known downstream gap (not this module's bug).** Every test feeds hand-built `TraceEvent`s; whether the real
`tallynet` consensus engine emits exactly these events in these orders for a commit / void / stall is validated
by the sibling `tallysim-consensus-runner-cli` ticket, which wires a recorded lift + trace through this module
against the real sign-and-settle harness. The module's contract with reality is confirmed there, not here —
the handoff is honest about this, and the `voidReason` precedence and `timeToSettleMs` NOTE both say to revisit
once that lands.
