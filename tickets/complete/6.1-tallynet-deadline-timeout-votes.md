prereq: tallynet-record-availability

TallyNet consensus had no timer: a fully-promised lift whose voters never finished (a silent voter, an
even-split tie, a dropped commit push) sat in `propagating` forever, every participant's reserved credit
held. This change gives each member node a one-shot deadline timer. The deadline is the transaction
code's own embedded expiry (a single lift-wide instant — no new record field); when it passes (plus a
small clock-skew grace, judged against the node's own clock), the node re-runs its state-advance loop so
an un-voted voter is driven to vote **void** (`NC`) through the engine's existing expired-code path. A
voter majority (commit *or* void) is therefore always eventually reached and every hold releases. A node
never concludes void from silence alone — only on evidence (an `NP` or an `NC` majority).

Also built: a **promise pre-gate** — a node signs `NP` when less than `minPromiseMarginMs` of the lift
window remains, so a slow promise phase that would leave the voters no time to vote voids cleanly instead
of stranding credit. `minPromiseMarginMs` (default 30_000) and `skewGraceMs` (default 5_000) are per-node
config (the protocol enforces the check; each node picks its own value), with `skewGraceMs <
minPromiseMarginMs` so a node that did promise still has margin to vote before its own void timer fires.
The originator may size the window via an optional `ttlMs` on `UniQuery` (`proceed` mints the code from
`args.ttlMs ?? args.query.ttlMs ?? DEFAULT_TTL`, clamped to the session-code TTL ceiling).

Design prose lives in `packages/tallynet/docs/design.md` § Lift proposal and settlement; `STATUS.md`
row 5 now marks void-on-timeout built and points to the two pending siblings.

## Review findings

Reviewed the four `ticket(implement)` commits as one diff (`740cb78^..619b916`) with fresh eyes before
reading the handoff. Build, lint, and the full suite were re-run after every edit.

**Checked (angles swept): SPP/DRY/modularity, scalability, maintainability, performance, resource
cleanup, error handling, type safety, source hygiene, and test coverage across happy path / edge / error
/ regression / interactions.**

- **The re-arm infinite-loop hazard — verified safe.** `scheduleDeadlineTick` does not arm when `now >=
  expiry`; the virtual clock advances `now` to each fire time, so a post-expiry `onDeadline` push
  delivers nothing new (push skip-test) and no node re-arms. The heap drains to 0 in every stall test.
- **Determinism — verified preserved.** Runs that settle before the deadline clear their timers in the
  same `update`, so no `deadline-reached` events fire; arm/clear emit no trace. The determinism test
  (linear-3, commits fast) is unchanged and green.
- **Pre-gate ordering invariant — verified.** `anyCodeExpired` catches a malformed code (`isExpired` →
  `expiresAt` → `decode` throws) and returns true, so once it returns false `expiresAt` cannot throw —
  the pre-gate's direct `expiresAt(record.transactionCode)` is safe.
- **`ttlMs` non-breaking — verified.** `mintRecord` never folds `ttlMs`; it is consumed only in
  `proceed` to size the minted code, so the immutable record core and its digests are untouched. The
  clamp to `DEFAULT_MAX_TTL_MS` keeps the minted code inside the node's own new-record validity ceiling.
- **Downstream trace consumers — verified.** The new `deadline-reached` `TraceEvent` variant lands in
  tallysim-viewer's `default` switch branch (no exhaustiveness guard anywhere), and `tallysim` +
  `tallysim-viewer` both build clean against it.

**Found and fixed inline (minor):**

1. **Fire-and-forget timer swallowed exceptions with no log.** The timer callback returned
   `this.onDeadline(...)` directly; `realClock.setTimer` does `void fn()`, so a throw inside `onDeadline`
   (a store read, a signature verify, a resource hook, a re-thrown release) would surface as a silent
   unhandled rejection — the one engine entry point with no caller to catch it, violating the project's
   "never eat an exception unlogged" rule. **Fixed:** the callback now `try/catch`-logs; direct callers
   of the public `onDeadline` still see the throw. (`participant.ts`, `scheduleDeadlineTick`.)
2. **The new per-node config knobs had no non-default test.** `minPromiseMarginMs` / `skewGraceMs`
   threading (`ConsensusNodeDeps` → `TrxParticipantConfig` → fields) was exercised only at its defaults;
   a broken pass-through would not have failed a test. **Fixed:** harness pass-through plus tests `(h)`
   (a custom `skewGraceMs` sets the armed delay) and `(i)` (a custom `minPromiseMarginMs` moves the
   pre-gate both ways). Suite is now 403 tests (was 401).

**Tripwires parked (code comments, not tickets):**

- `onDeadline` shares the read-merge-save non-atomicity the `engine.ts` re-entrancy NOTE describes — the
  timer fires on its own schedule and can interleave with an in-flight `update` of the same transaction
  at an await boundary. Harmless today (a lost vote is a liveness concern recovery already heals, and
  `onDeadline`'s own settling path is unreachable over the wire); `tallynet-stalled-recovery` (6.2) should
  serialize the two when it adds the retry. **NOTE added at `onDeadline`.**
- Pre-existing implementer NOTE in `updateDeadlineTimer` (one extra record classification per update) left
  in place — correct and already greppable.

**Known gap confirmed accurate, not re-filed.** `onDeadline`'s own voter-`NC` branch is unreachable via
normal network delivery (a voter holding a complete promise set always votes synchronously in the same
`update`), so it is covered only at the unit level (test `(a)`, by seeding the store). The end-to-end
"settling by deadline" test exercises deadline-*driven* void through `castCommit`'s expired path on a late
delivery — `onDeadline` fires a no-op first. Verified this claim by tracing the e2e scenario node by node.
A true `onDeadline`-drives-`NC` end-to-end test needs a harness knob to hold a voter back from voting;
that is already deferred to `tallysim-timeout-scenarios` (6.3). Because this branch is currently a no-op
over the wire, the deadline timer presently does no useful settling work on the network — its value is the
seam for 6.2's retry, the seeded-path coverage, and future-proofing. All of this is documented; not a
defect.

**Other limits confirmed documented, not re-filed:** in-memory-only timers (a restart re-arms only on the
next delivery — seam in `design.md`); an all-voted tie still cannot settle in-band (`tallynet-stalled-
recovery` owns periodic re-push/pull); `proceed`'s clamp hard-codes `DEFAULT_MAX_TTL_MS` rather than a
node's configured ceiling (a pre-existing coupling `DEFAULT_TTL` already had — acceptable).

**No major findings → no new `fix/`/`plan/`/`backlog/` tickets filed.** The pending downstream work
(`tallynet-stalled-recovery` 6.2, `tallysim-timeout-scenarios` 6.3) already exists as siblings.
