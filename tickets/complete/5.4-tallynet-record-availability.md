Shipped and reviewed the two record-availability mechanisms for `tallynet-record-availability`:

1. **Pull (principle 3, the hard linear case).** A cut-off member can `fetchOutcome(transactionCode)` to
   request the record from each reachable peer (a published contact point or a direct link neighbour) and
   merge every reply; `serveRecord` is the responder. A pull injects no unverified state — every reply
   goes through the same verify-on-merge union as a push.
2. **Equivocation proof kept (principle 2).** A voter signing both faces of a phase (`C`&`NC` or `P`&`NP`)
   now has both verified faces retained in a durable side store (`getProof`/`saveProof`, capped at 4/signer)
   instead of the second being silently dropped. Settlement is byte-for-byte unchanged (the authoritative
   sets still keep the first face). `detectContradiction` additionally flags — observation only, no remedy —
   when our own settled outcome contradicts an incoming copy that settled the opposite way.

### Checked, with disposition

- **Pull correctness (`fetchOutcome` / `serveRecord`)** — verified sound. The reachable set is read once
  from our own stored record (topology is immutable, so stable across the merges the pull triggers); each
  reply is merged via `update(reply, peer)`, which verifies on merge, so a forged reply is dropped (`forged`)
  and a stale/duplicate one is a harmless union no-op; with no stored record it returns `pending` and pulls
  nothing (no topology ⇒ no address). Idempotent on re-pull (release is gated by the release flag). Covered
  by 3 unit cases + 5 e2e scenarios (interior refuser with/without contact points, circular ring, silent
  originator, silent payee). **Found: nothing.**
- **Equivocation-proof retention** — verified. Both faces retained only when the incoming face itself
  verifies (`retainEquivocationProof` re-verifies; a forged opposite face is never stored, so `equivocators()`
  stays clean); authoritative sets unchanged; both `saveProof` calls target the same signer key (equivocation
  ⇒ same address); capped at `MAX_PROOF_FACES_PER_SIGNER = 4`, unreachable by honest paths (≤2 verified faces
  per phase). Covered for both phases and the forged-face case. **Found: nothing.**
- **Contradiction detection** — verified the flag can fire **only on genuine equivocation**: without a voter
  contributing two faces, each node's union is identical and only one side can reach a strict majority, so no
  two settled nodes disagree. Short-circuits before the second classification on the common `pending` path.
  Observation only — settlement untouched, flag has no consumer yet. **Found: nothing wrong.**

### Minor observation (deliberately NOT changed)

- In the **promise** phase, a *forged* opposite face (e.g. a forged `NP` arriving when a genuine `P` exists)
  is traced/logged with reject reason `'equivocation'`, whereas the **commit** phase labels the same situation
  `'forged'` (it verifies before the dedupe). This has **zero functional impact**: `retainEquivocationProof`
  verifies the incoming face, so the forgery is *not* retained as proof and `equivocators()` is not polluted;
  only the weaker `signature-rejected` trace reason is affected, and any real equivocation count should use the
  `equivocation-proof-kept` trace / `equivocators()` anyway. Correcting the label would require verifying every
  duplicate promise before the dedupe branch — undoing the deliberate, documented "dedupe-before-verify is safe
  for promises" fast path to fix a rare, impactless trace label. Net-negative; left as-is. (Pre-existing in
  spirit: the promise-phase reject-reason taxonomy already labelled this `'equivocation'` before this ticket.)

### Tripwire (conditional — recorded, not filed)

- `detectContradiction` classifies the **raw** incoming record; its commit/void-by-majority signal is verified

  `received.promises`) is **not** verified there, so a hostile peer could set the contradiction flag spuriously.
  Observation only today (settlement untouched; the flag has no consumer). A `// NOTE:` is already parked at the
  `theirs = …` site in `participant.ts`. If `feat-tallynet-hostile-peers` ever **acts** on the flag, it must
  verify `received`'s `NP` first. Not a ticket.
