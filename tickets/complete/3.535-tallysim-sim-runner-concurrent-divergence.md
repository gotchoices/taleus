## What this ticket resolved

`sim-runner.ts` can schedule a run's payment-discovery queries two ways, chosen by `SimRunnerDeps.concurrent`:
**sequential** (default: issue one query, drive the clock to idle, read its outcome, repeat) and **concurrent**
(issue every query, drive the clock to idle once). The two once diverged on `roundsUsed` and the timing
distributions; a prior `fix/`-stage investigation traced that to a since-fixed `tallynet` `VirtualClock` bug
(`DRAIN_QUIET` too small, resolved under `tallynet-discovery-depth-reach`) and found the modes now produce
byte-identical records.

The implement stage replaced the old "empirical / may re-diverge" hedging with the structural reason the
modes agree — an **arm-order invariant** — and added a parameterized guard test that sweeps networks ×
latencies (including exact budget/delivery tie instants) × fold-path configs, asserting
`JSON.stringify(concurrent) === JSON.stringify(sequential)` for each. It updated `docs/design.md` and the test
comments to match. No behavioural change to `sim-runner.ts`.

**The invariant, in brief:** the `VirtualClock` breaks a same-instant timer tie by insertion order (`seq`).
Within one search, a round's outbound delivery timers are armed (`issueBatch`) before that round's budget timer
(`budgetedStep`, `discovery/participant.ts` `reenter`); an answer-delivery back to a node is always caused
*after* that node armed its own budget. Concurrent mode interleaves other sessions' timers into the global
`seq` stream, but cannot invert one session's own two timers' relative order — and with no per-node
queueing/contention in the model, each session's outcome depends only on its own timers' order. So an exact
tie resolves identically in both modes.

## Review findings

Adversarial pass over the implement diff (commit `83b63ad`), plus the `tallynet` source the invariant rests on.

- **Invariant correctness — verified sound against source (checked, no defect).** Confirmed each mechanical
  fact the documented invariant depends on: `clock.ts` tie-breaks on `(time, seq)` with `seq` bumped on every
  `setTimer` (lines 107, 227); `originator.ts` budgets are `initialBudgetMs(2000) + round * perHopBudgetMs(1500)`
  (lines 56-57, 129); `participant.ts` `reenter` arms the delivery batch (`issueBatch`, line 348) before the
  budget timer (`budgetedStep`, line 349). Also confirmed the unstated premise — per-session isolation: both
  `inFlight` and the context store in `participant.ts` are session-keyed, so concurrent sessions cannot
  contend on shared node state. The "no per-node queueing or contention" claim holds for the current model.
  The tie-instant comments in the test (2000 → round-0 budget; 1750/2500 → round-1/round-2 budget at 2 hops)
  are arithmetically correct.

- **Stale CLI doc comment contradicting the invariant — MINOR, fixed inline.** `cli/simulate.ts` header still
  read "outcome metrics agree with sequential mode, but round/timing metrics do not" — the exact claim this
  ticket disproved. The implement handoff asserted the CLI "needed no change," but missed its own doc comment
  carrying the old divergence story. Rewrote it to state byte-identity across all metrics by the arm-order
  invariant. (This was the one spot the implement sweep for stale language overlooked.)

- **Guard test was vacuous-safe only by luck — MINOR, fixed inline.** The `it.each` guard sweep asserted
  byte-identity but never checked that a latency config actually spreads events over virtual time, so a future
  refactor that collapsed all timing to t=0 would make the "tie" configs pass trivially with zero coverage.
  Added a non-vacuity assertion (`timeToCompletionMs.max > 0`) gated to configs that carry latency (where
  non-zero completion for multi-hop found routes is deterministic; no-latency configs legitimately settle at
  t=0 and are excluded to avoid a flaky assertion).

- **Test coverage — adequate.** Happy path (equal metrics), the latency race window, and the late-answer-fold
  path are all exercised; the fold *mechanism* itself additionally has a dedicated direct test
  (`sim-runner.test.ts` "a folded late answer is not double-counted"). The `ring(6)` helper is correct (a
  `line(n)` plus one closing tally). No further tie-instant verification was added to the guard sweep — proving
  a tie landed exactly requires raw-event inspection the aggregated records don't expose, and the fix-stage
  sweep (commit `195318a`) already established the configs hit ties; reconstructing that in-test was judged
  disproportionate.

- **Source hygiene — clean.** `sim-runner.ts` diff is header-text only (confirmed no stray logic edit).
  Function decomposition, naming, and comment conciseness are fine.

- **No major findings, no new tickets, no tripwires.** The one residual caveat (the invariant depends on the
  engine's arm-order discipline and a contention-free model) is already documented in the module header and
  is exactly what the guard test protects, so it needs no separate tripwire.
