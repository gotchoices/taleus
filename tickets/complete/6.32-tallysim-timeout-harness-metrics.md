## What landed

The second half of the original 6.31. It re-homes two recovery counters onto the lift protocol's own trace
events and adds two new measurements, all computed by the pure `analyzeLift` / `summarizeConsensusMetrics`
functions from a lift's trace:

- **Removed** `pullCalls` / `recovered` from `LiftResult` (they were hard-coded `0` placeholders left by
  Half A). The simulator no longer sources recovery counts from its own bookkeeping.
- **`pullMessages`** now counts `record-pulled` trace events; **`recovered`** is a per-lift 0/1 flag — `1` iff
  the lift settled (`commit`|`void`) AND emitted a `record-pulled` or `recovery-tick` (the recovery loop ran).
  `recoveredTotal = Σ recovered` = settled lifts that needed the recovery loop.
- **`creditHeldMs`** (per lift) = first credit-holding (`P`) `promise-signed` → last `resources-released`;
  omitted when either endpoint absent. Aggregated as `creditHeldMsPerLift: DistributionSummary` over defined
  spans only.
- **`permanentlyPending`** (per lift boolean) = `outcome === 'pending'` AND no `resources-released` seen.
  Aggregated as `permanentlyPendingCount` (Σ) and `permanentlyPendingFraction` (`count / liftCount`, 0 not NaN
  at 0 lifts).
- **Three CSV columns** appended after `planRefusalShare`, no existing column moved.
- Verified (no code change) that a deadline-timeout void surfaces as a `voter-vote` `NC` and the existing
  precedence maps it to `'voted-no-commit'`, and that `timeToSettleMs` already spans deadline-voids.
- `docs/design.md` updated (serialiser column order, voter-model "New metrics" bullet, § *Consensus metrics*).

## Review findings

**Process:** read the implement diff (`ecae491`) with fresh eyes before the handoff, then every touched file and
the protocol trace/participant source the metrics depend on (`tallynet/src/trace.ts`,
`tallynet/src/consensus/participant.ts`). Confirmed each new counter keys on a real trace-event variant with the
fields the code reads (`record-pulled`, `recovery-tick`, `promise-signed.signatureType`, `resources-released`).
Ran `yarn workspace tallysim build && lint && test` — build + lint clean, **440/440 tests across 34 suites**.

**Correctness / semantics — checked, no defects.**
- `recovered` 0/1 keyed on `settled && (record-pulled | recovery-tick)`: verified `releaseOnce`
  (`participant.ts:859`) emits `resources-released` on both commit and void, and that `recovery-tick` fires on
  the non-settling force-repush path — so keying `recovered` on *either* a pull or a tick is right, and a
  pending lift correctly scores 0 (never settled).
- `creditHeldMs` endpoints: `firstCreditPromise` tracks only `signatureType === 'P'` (an `NP` holds nothing);
  `lastRelease` counts any `resources-released` (both commit and void free credit). `lastRelease >=
  firstCreditPromise` guard is defensive; correct.
- `permanentlyPending` keys on "resources never released", not merely "pending" — stays correct if a future
  abandon path ever releases. Per decision 4, intentionally lift-outcome-scoped (distinct from per-member
  stranding, which `cooperatingCompletion` captures).
- 0-lift / 0-member guards return 0 not NaN throughout; verified by the empty-run unit test.

**Minor — fixed inline in this pass.**
- *Stale doc comments on `recoveredTotal`.* The interface comment (`consensus-metrics.ts:153`) and the
  `summarizeConsensusMetrics` docstring still read "stranded-then-settled **members**" — the pre-change meaning.
  `recovered` is now a per-lift 0/1 flag, so `recoveredTotal` is a count of lifts, not members. Rewrote both to
  "the settled lifts whose recovery loop ran" (matches `design.md`). Comment-only.
- *Missing end-to-end lock on `creditHeldMs` (handoff gap §2).* The two new per-lift metrics were asserted only
  against hand-built traces; nothing locked their real-run values. Added one assertion to the committing sweep
  in `consensus-runner.test.ts` — `records[0].metrics.creditHeldMsPerLift.count > 0` — so a future engine change
  that stops emitting `resources-released` cannot silently zero the metric. Passes.

**Test coverage — happy/edge/error/regression.** The pure-function floor is thorough: deadline-void
classification, `pullMessages` count, all four `recovered` branches, `creditHeldMs` present/omitted (no-release,
NP-only), `permanentlyPending` true/false/settled, the summarize aggregates, and the CSV column-order +

**Forward note (not a ticket, not a tripwire — downstream owner exists).** No sweep currently produces a

experiment-CSV regeneration 6.35 already owns.

Regenerating (~2 min, idle-timeout-risky) is explicitly 6.35's responsibility; left untouched here. 6.35 should
also expect `recoveredTotal` to change *value* (not just gain columns) in drop-sweeps, since its semantic
changed from "members healed" to "lifts whose recovery loop ran".

**Guard branches / empty categories.** The `creditHeldMs` out-of-order guard branch is uncovered (no test
forces an out-of-order trace) — acceptable, it is defensive. No new tickets filed; no tripwires recorded in
