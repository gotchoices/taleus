Second of three tickets splitting the original `5.5-tallysim-voter-model`. The prereq
(`tallysim-voter-policies`) built the pure policy functions; this ticket **wired them into the running
`tallynet` simulator** and added the voter-model behaviours — nominated voters, contact points, non-relayers
(plus the silent-after-promise port) — then drove a lift to settlement including the **pull recovery** that is
the point of record availability. The final ticket (`tallysim-voter-model`, seq 5.53) adds the sweep runner,
metrics, CLI and docs.

## What landed (all in `packages/tallysim/src/sim/`)

- **`harness.ts`** — `ConsensusConfig` grew `scorePlan` (shared originator plan scorer) and four entity-id-keyed
  ports: `negotiatePlanFor` (per-node discovery voter-set gate), `nomineesFor` (referee nomination),
  `refuseRelayFor` (non-relayer), `silentAfterPromiseFor` (offline-after-promise). Discovery `hooks` now via
  `consensusHooks(consensus)`: with no gate it returns the single shared `makeCapacityHooks()` object so the
  pinned discovery sweep never moves; any gate turns it per-node. `consensusPorts` spreads each new port only
  when supplied.
- **`consensus-harness.ts`** — `RunLiftOptions` grew `contactPoints`, `nonCooperating`, `wellKnown`.
  `recoverStrandedByPull` runs after the initial push settles, calling `fetchOutcome` on each still-pending
  cooperating member. `LiftResult` grew `pullCalls` and `recovered`.
- **`route.ts`** — `buildCircularOutcome` + `findCycleThrough` (deterministic DFS shortest simple cycle,
  handling parallel-tally 2-cycles): the stand-in for real clearing discovery (`feat-tallysim-clearing-discovery`).
- **`consensus-resource.ts`** — `refuseStackedPlanHook`, the discovery-time twin of the promise-time
  `acceptsProposal` gate (both read `refusesStackedVoterSet`).
- **`index.ts`** — unchanged; both new symbols surface via existing `export *` barrels (verified).

Seven new tests in `voter-harness.test.ts` (contact-point recovery, the no-contact-point gap, circular
route-around, referee nomination fold, `scorePlan` ranking, `refuseStackedPlanHook` drop, determinism).

## Review findings

**Validation re-run (all green):** `cd packages/tallysim && yarn build` → clean; `yarn lint` → exit 0;
`yarn test` → **34 suites, 413 tests pass**. No changes were needed in this pass — the implementation is
correct as delivered and the handoff was honest and accurate.

**Checked, sound — no defect found:**

- **`recoverStrandedByPull` correctness & termination.** Members move pending→settled monotonically. Each
  round pulls every currently-stuck cooperating member once (skipping any that recovered mid-round); it breaks
  the instant a round advances nobody, with the `round <= members.length` bound as a redundant backstop. Chain
  pulls (a far member that can only recover once its neighbour has) are handled across rounds. Deterministic.
  Cannot hang even on caller misuse.
- **`findCycleThrough` / `buildCircularOutcome`.** DFS finds the globally shortest simple cycle (strict `<`
  keeps first-found on a tie), with correct pruning (`pathTallies.length + 2 >= best.length` cuts only branches
  that cannot beat the incumbent). Handles parallel-tally 2-cycles and never forms a cycle from a self-loop.
  `members: []` plans flow correctly through `selectPlan('shortest')` and `reconstructRoute`.
- **Hook / port adapters.** `consensusHooks` and `consensusPorts` are pure pass-throughs over the
  `entityName`/`entityId` bijection (`String(id)` ↔ `Number(name)`); the shared-object path is byte-for-byte
  the pre-consensus wiring, and each voter-model port is spread only when supplied.
- **Money-move semantics (handoff gap 1).** Money moves on the originator's own commit even when far members
  stay stranded — deliberate, matches the discovery-only settlement model, asserted as EXPECTED in test 2. Not
  an accounting bug for v1; the sweep (5.53) is where the semantics get measured.

**Tripwires (parked at the site, not ticketed) — confirmed present:**

- `findCycleThrough` is an exhaustive DFS, exponential on dense graphs → `NOTE:` at route.ts:120. Fine for the
  small hand-built rings it serves; real clearing discovery is `feat-tallysim-clearing-discovery`.
- The pull pass re-drives the clock per stuck member (O(members²) on large circular topologies) → already
  tracked in the 5.53 ticket's tripwires, so no duplicate NOTE added.

**Test-floor gaps (a floor, not a defect — all owned by a downstream ticket, nothing re-filed):**

- **`silentAfterPromiseFor` wiring is untested here.** It is a thin adapter *identical in shape* to the tested
  `refuseRelayFor` adapter, and the mechanism itself is proven at the tallynet level
  (`tallynet/src/testing/consensus.test.ts` §1187, §1200 — silent payee commits O+A, pends the payee). Low
  risk; 5.53's "nodes go silent" scenarios exercise it. No test added (the adapter symmetry makes it
  low-value).
- **Silent-originator-in-`nonCooperating`** (handoff's flagged corollary): a `silentAfterPromise` originator is
  excluded from the pull pass, so whether money moves vs. it stays `pending` is unexercised. Conditional on the
  sweep building that specific edge; 5.53 owns silent-node scenarios. Noted, not filed.
- **`scorePlan` ranking (test 5)** implicitly relies on the default discovery order differing from the scored
  order to prove the scorer reorders. Adequate (the stacking hook sits on the lower-indexed arm discovered
  first, so the lean-first assertion does distinguish a live scorer from a no-op), but it is an implicit
  dependency. Left as-is.

**Maintainability — the `nonCooperating` coupling (observed, not a defect):** the pull-exclusion set passed to
`runLiftForOutcome({ nonCooperating })` MUST be kept in sync by the caller with the network's
`refuseRelayFor`/`silentAfterPromiseFor`, because `buildSimNetwork` does not retain the consensus config on the
returned `SimNetwork`. Divergence can only miscount `recovered`/`pullCalls` (the termination guard prevents any
hang). It is already documented at the exact site (the `RunLiftOptions.nonCooperating` JSDoc, "MUST match the
network's injected set"). 5.53 wires both the network injection and this option from one fraction→ids
selection, so the two cannot diverge in the sweep. Flagged here; a cleaner design would retain the config on
`SimNetwork` and auto-derive the exclusion set — worth considering when 5.53 wires the sweep, but not changed
in a review pass before the consuming ticket's shape is settled.

**Docs:** `packages/tallysim/docs/design.md` § *Consensus simulation* does not yet mention pull recovery,
contact points, or `buildCircularOutcome`, and its "v1 has no recovery — a stalled push is a dead lift"
paragraph (≈ lines 801–806) is now partially superseded by the pull pass (the lift commits; stranded members
pull the evidence rather than staying dead). This is a **tracked, deliberate deferral**: ticket 5.53's Docs
section explicitly owns a *Voter model* subsection covering nomination, contact points + the completion curve,
the non-relayer-vs-refuser distinction, the explicit-pull design, and circular-route construction, and extends
exactly this § *Consensus simulation* range — so line 801 gets reconciled there. 5.53 should take care to
rewrite that "no recovery" paragraph, not just append the new subsection.

**Known composition gaps carried forward (above, already ticketed — not re-filed):** nominated referees fold
into the discovery plan but are not yet driven as consensus votes (`debt-voter-nomination-on-path-composition`,
backlog); the promise-time stacked-voter refusal is covered only via `consensus-resource.test.ts`, not
end-to-end through `runLiftForOutcome` (a consequence of the same composition gap); automatic retry/timeout
pulls are `tallynet-propagation-timeouts`.

**Dispositions:** minor inline fixes — none needed. Major/new tickets — none; every surviving concern is
already owned by a downstream ticket (5.53, `feat-tallysim-clearing-discovery`,
`debt-voter-nomination-on-path-composition`, `tallynet-propagation-timeouts`). Tripwires — the two above,
parked at their sites.
