The first of three split discovery-metrics tickets. Adds the pure protocol-metrics measurement layer
(`protocol-metrics.ts`), the discovery sweep runner (`sim-runner.ts`, mirroring the oracle `runner.ts`), the
`issueQuery`/`drawPaymentQueries` harness split, `SimSweepSpec`, and the shared `sweep-vary.ts` machinery.
Siblings `tallysim-discovery-metrics-io` and `tallysim-discovery-metrics-experiment` build on it.

Implementation detail is in the implement commit (`ticket(implement): tallysim-discovery-metrics-core`) and
the module/doc comments; this file records the review.

### Fixed in this pass (minor)

- **`ALL_PRUNE_REASONS` could silently drift.** Its comment claimed "a compile error here if the two ever
  drift," but `readonly PruneReason[]` accepts a *subset* — an added tallynet `PruneReason` would compile fine
  and later `pruneReasons[newReason]++` would yield NaN. Reworked so `zeroPruneReasons()` is a
  `Record<PruneReason, number>` object literal (compile-checked complete) and `ALL_PRUNE_REASONS` derives from
  its keys — the promised guarantee is now real. (`protocol-metrics.ts`)
- **Misleading `generator` doc comments.** Both `SimRunRecord` and `RunRecord` said generator is
  `'materialized'` for a pre-built network, but the code reports `network.meta.generator` (the `capacity`
  field is the one that reports `'materialized'`). Corrected both comments to match the tested behaviour.
  (`sim-runner.ts`, `runner.ts`)
- **Missing design-doc coverage.** `protocol-metrics.ts` and `sim-runner.ts` both cite "docs/design.md
  § Discovery simulation," but the measurement layer and sweep runner were undocumented. Added
  "### Protocol metrics" and "### The discovery sweep runner" subsections. (`docs/design.md`)
- **Added regression test** on a multi-hop line with real latency (see the major finding below).

### Major finding → filed `fix/tallysim-sim-runner-concurrent-divergence`

`SimRunnerDeps.concurrent` does **not** produce identical metrics to sequential mode, contrary to the
handoff's claim ("verified in tests and analytically"). Outcome metrics (found, `messages`, `nodesTouched`,
`pruneReasons`, `pFoundGivenExists`) agree, but **`roundsUsed` and the timing distributions diverge** under
real multi-hop latency: concurrent queries share one `VirtualClock`, so a round's budget-expiry races a
sub-request's delivery and the shared fire-order counter interleaves across sessions. The existing
equivalence test missed it by using only a zero-latency 1-hop network. Reproduced (`line(5)`, 200ms latency,
query 0→4: completion 16500ms sequential vs 7100ms concurrent). Not a measurement bug — the protocol genuinely
runs on a different schedule — so it is not fixable inline; the fix ticket lays out the options (drop
concurrent, per-query clocks, or scope the promise). Interim: corrected the false equivalence claims in
`sim-runner.ts` and `docs/design.md`, and the added test now asserts outcome-equality while characterizing the
round/timing divergence (to be tightened once the fix lands). `fix/` is top priority, so it resolves ahead of
the io/experiment siblings that expose/use `--concurrent`; those should stay on sequential for round/timing
output until then.

### Tripwires (parked, not ticketed)

- **Concurrent/sequential completion timing relies on every session emitting ≥ 1 trace event.** Today it
  always does (the originator's own participant emits `query-received` on entrance, even with no adjacency),
  so `analyzeQuery` reads each session's own last-event time and the shared `endMs` fallback is only for a
  zero-event session. Recorded as a NOTE at the concurrent branch in `sim-runner.ts`.
- **Pre-existing NOTEs kept** (from the implement): per-query discovery is ~O(network), far costlier than the
  oracle BFS (sample/cap for large N); and network/workload seed streams are independent only when base seeds
  differ (mirrors the oracle runner).
- **`SimScenario.workload.kind` is not validated to be `'payment'`** — `drawPaymentQueries` always draws
  payment pairs. Clearing discovery is explicitly deferred this tier; becomes real work only when a clearing
  workload is introduced (then the runner should branch on `kind`). Documented in the harness/scenario doc
  comments. Carried over from the implement handoff; still a valid tripwire.
