The 6.1 one-shot deadline timer was extended into a periodic recovery loop. While a node holds a
non-terminal (`pending`) record it re-arms a per-transaction timer; on fire, `onRecoveryTick` reloads,
pulls every reachable peer's merged copy, runs the advance loop (casting the deadline `NC`/`NP` through
the expired-code path), and — unless it settled or has passed the give-up ceiling — force re-pushes and
re-arms with exponential backoff. A give-up ceiling (`RECOVERY_GIVEUP_MS`, 1 h past expiry in production)
abandons a genuinely-stuck lift, leaving it `pending` with resources held. A post-deadline re-arm is gated
on progress (a merged new signature) so two fully-connected stuck nodes can't re-arm each other forever
(the timer-storm guard). The implementation shipped build+lint clean with 413 tallynet tests passing.

## Review findings

**Scope reviewed.** Read the full implement diff (`ba19fa1..acd23cc`, three commits) against
`participant.ts`, `engine.ts`, `trace.ts`, `network.ts`, both tallynet test files, the two tallysim test
files, and `design.md` — then re-read the handoff. Scrutinised the three invariants the handoff flagged
(the timer-storm guard, the clear-before-arm at the end of `onRecoveryTick`, and the give-up placement),
plus the tallysim deviation. Ran build + lint + full test suites for tallynet, tallysim, and tallysim-viewer.

**Correctness — the three load-bearing invariants hold.**
- *Timer-storm guard.* `update`'s `progressed` is a genuine-new-signature test (`recordSignatureKey` over
  both signature sets), and post-deadline `scheduleRecoveryTick` arms only on progress. I walked every
  state change that is NOT captured by `recordSignatureKey` (pooled commits, retained equivocation proof,
  the contradiction flag, peer-record skip-test priming) and confirmed none represents settlement progress
  that the loop needs to react to — so not re-arming on those re-deliveries is correct, not a stall. No
  re-delivery path that should keep the loop alive slips past the key. Two- and five-node fully-connected
  stuck lifts both drain their timer heaps (tallynet "set of two", tallysim 2/3-threshold).
- *Clear-before-arm.* The pull's inner `update` can arm a fresh base-delay timer mid-tick; step 10's
  `clearRecoveryTimer` then `armRecoveryTimer` guarantees exactly one live timer (unit (j) asserts
  `liveTimers()===1`; every E2E settle/abandon asserts `pendingTimers===0`). The mid-tick timer cannot
  fire before step 10 (virtual clock doesn't advance inside the tick; real delays are ≥ base). Sound.
- *Give-up placement.* The ceiling check sits after the settle attempt (pull + advance) and before the
  force-push, so a node that could still settle this tick settles first; an abandoning tick emits only
  `recovery-abandoned`, casts its deadline vote beforehand, and force-pushes nobody. Ordering is correct.

**Major finding — FIXED inline (regression this ticket introduced).** The tallysim test
*"an all-voter line commits at 1/2 but settles nowhere at 2/3 when two of five vote no-commit"*
(`voter-harness.test.ts:174`) **timed out (>30 s)** — it was red, despite the handoff's "tallysim 423 pass"
claim (the handoff's run was evidently on a faster machine; the failure is borderline and machine-sensitive).
Cause: the recovery loop fires inside the sim's `runUntilIdle`, and a genuinely-stuck lift (the 2/3
threshold band no side clears) polled through the full **1-hour** production give-up window — ~17
exponential-backoff ticks per node × 5 fully-connected voters, each tick pulling from and force-pushing to
every peer and re-verifying the whole voter set (thousands of Ed25519 verifications). The implementer added
`recoveryGiveupMs: 60_000` to the tallynet E2E stall tests but never threaded a small give-up through the
tallysim harness, so stuck sim lifts ground. Fix: `buildSimNetwork` now passes a sim-wide
`SIM_RECOVERY_GIVEUP_MS = 60_000` (`packages/tallysim/src/sim/harness.ts`). A healable lift settles on its
first post-deadline tick — well inside that window — so the only lifts shortened are the ones that must
abandon anyway, and their outcome is unchanged (`pending`, resources held). All 423 tallysim tests now pass
(suite 36 s, comfortable margin); tallynet 413 and tallysim-viewer build unaffected. The NOTE in the new
constant hands the per-scenario knob to 6.3 (`tallysim-timeout-scenarios`).

**Deviation audited — the two tallysim assertion flips are honest.** `voter-harness.test.ts` (:89 area)
and `consensus-runner.test.ts` (:145 area) flipped `recovered`/`pullCalls`/`recoveredTotal` from positive
to 0. Confirmed honest: the recovery loop fires during `runLiftForOutcome`'s `runUntilIdle` (`consensus-
harness.ts:143`) and self-heals the stranded members before the manual `recoverStrandedByPull`
(`consensus-harness.ts:149`) runs, so the manual pull legitimately finds nothing. Both tests still assert

===1`), unchanged. Not a papered-over regression. `recoverStrandedByPull` is left in place for 6.3 to remove.
