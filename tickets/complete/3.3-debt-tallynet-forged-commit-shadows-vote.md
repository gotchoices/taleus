## What shipped

In commit-phase consensus a commit signature binds the **complete** promise set, so it cannot be
verified until every participant has promised. Previously an out-of-order commit was stored in the
authoritative `commits` set **unverified** while the promise phase was still open — a forwarding node
could inject a garbage commit for a referee *before* the promises completed, occupy that referee's slot,
and the referee's genuine vote then collided with it (`changed`/`equivocation`) and was silenced. This is
a **liveness/outcome** hole (a forged vote never *counts* — it never verifies — but a suppressed genuine
vote could stall or wrongly void a lift that should have committed).

The fix: an unverifiable commit waits in a durable **side pool** (keyed by `transactionCode`, capped per
referee at `MAX_PENDING_COMMITS_PER_REFEREE = 4`, never digested / pushed / part of the wire record), and
is promoted into the counted `commits` set only after it verifies against the complete promise set. Two
drain sites cover the two ways the promise phase can complete: a **peer's** completing promise drains
inline in `validateAndMerge`; **our own** cast promise drains via `drainPendingFromStore` after
`castPromise` in the `ourPromiseNeeded` branch of `advanceState`. Promises are unaffected — a promise's
preimage never depends on the promise set, so each is verified on arrival and an unverified promise is
never stored.

## Review findings

Reviewed the full implement diff (`83ef3db..71f05ad`) from scratch before reading the handoff, from every
aspect angle. What was checked and found:

- **Core correctness of the pool / drain / promote path — CONFIRMED sound.** Traced every flow:
  merge-order (promises → drain → incoming commits) gives pooled commits the "first face stands" win over a
  same-update arrival; `promoteCommit` verifies *before* the dedupe check so an unverified commit can never
  occupy a referee's slot; the two drain sites (peer-promise inline, own-promise via
  `drainPendingFromStore`) are mutually exclusive per completing event (no double-drain); the
  `pending.length > 0 || hadPending` save guard correctly persists a filled pool and clears a drained one.
  No defect.

- **The own-promise drain path (the latent defect the implementer found & fixed) — CONFIRMED covered.**
  The restored sole-referee test (`participant.test.ts:716`) genuinely exercises it: `refCommit` is pooled
  during `validateAndMerge` (phase incomplete), then drained and counted only after `self`'s own promise
  completes the phase. Without `drainPendingFromStore` the lift would never settle in that update. Relays
  (non-members, never run `advanceState`) are covered by the inline `validateAndMerge` drain — exercised by
  the observer-node `X` e2e tests.

- **Pool-cap abuse — CONFIRMED safe, no new censorship power.** The cap is per-signer; only
  referee-member keys pass `checkMemberAndRole` before pooling, and membership is fixed in the immutable
  topology, so the pool is bounded by `4 × |referee members|`. A theoretical edge (attacker fills a
  referee's 4 slots with garbage, then a *genuine* commit arrives pre-promise and is dropped as
  `pool-full`) is self-healing: the genuine commit is signed over the complete promise set and travels with
  it, so a re-delivery once the phase is complete hits `promoteCommit` directly (bypassing the pool) and
  counts. A node that could withhold it entirely already has that power as a sole forwarder — the cap grants
  nothing new. Not a defect.

- **Test coverage — adequate as a floor.** Happy path, the headline attack (garbage C and garbage NC
  pre-promise), honest out-of-order early commit, genuine equivocation pre-promise (earliest face stands),
  pool-cap overflow, and store-level round-trip / copy-on-get / copy-on-save / DAG-CBOR-round-trippability
  are all covered at both the unit (`participant.test.ts`, `store.test.ts`) and e2e
  (`testing/consensus.test.ts`) levels. No gap worth a new ticket.

- **Docs — accurate.** `docs/design.md` § Consensus and the `store.ts` interface docs describe both drain
  sites and the promises-are-safe reasoning, and match the code.

- **Tripwire parked (1, new):** the side pool, like every map in `MemoryTrxStore`, is never pruned — a
  committed/voted lift drains its pool empty, but an **NP-voided** lift (promise phase never completes)
  leaves its pre-promise pool undrained. Bounded and tiny in memory; consistent with the store pruning
  *nothing* today (records, peer records, release flags all persist). Recorded as a `NOTE:` at the
  `pendingCommits` field in `store.ts` so whoever builds durable-store cleanup of terminal transactions
  prunes it alongside the records. **Not** a ticket (conditional, fine now).

- **Pre-existing tripwires — untouched, unchanged:** `countVerifiedCommits` re-verify-per-pass cost
  (`NOTE:` at that method) and the propagation-timeout seam (`NOTE:` in `getRecordState`). No new ones
  introduced beyond the store-pruning NOTE above.

- **Minor (not actioned):** `checkMemberAndRole` returns the matched `DependentMember` but both callers use
  it only as a boolean. Harmless and arguably future-useful; left as-is.

## Known gaps carried forward (from implement, still true)

- **No SQL/Quereus `TrxStore` implementation.** Only `MemoryTrxStore` implements the two new methods
  (copy-on-get / copy-on-save, per-`transactionCode` keying). A durable store must implement them; the
  interface + docs are in place. Lands with whatever ticket builds the durable consensus store.
- **Discovery audit (item 6 of the source ticket): confirmed out of model — no code.** Route-search state
  in `discovery/participant.ts` is not cryptographically authenticated in v1, so the
  "unverified-shadows-verified" shape does not apply there. Member-identity binding is a later feature.
