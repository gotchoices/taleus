First of two tickets that split `5.53-tallysim-voter-model`. This one built the **principle-3 completion
curve on straight-line routes**: measure how payment completion falls as more nodes stop relaying the commit
phase, with and without a published **contact point** (a dial address every record-holder can reach) to pull
the settled record from. The sibling `tallysim-voter-model` (seq 5.532) owns circular routes, voter nomination
driven as real votes, the stacked-voter plan-refusal end-to-end, the consensus-threshold override, and the
cohesive *Voter model* doc subsection.

"Principle 3": a node that promised then went dark must not strand the payment — a member the commit push
can't reach must be able to **pull** the settled record from a reachable peer (a contact point, or a
link-neighbour). The curve measured here: with contact points, completion holds at 1.0 while ≤ 1 node on a
route is a non-relayer; without them, a straight line shows a visible cliff (the dark node's far side has no
path to the evidence).

## What landed

Implement delivered the feature across `scenario.ts` (new `ConsensusSpec` knobs `nonRelayerFraction`,
`silentAfterPromiseFraction`, `contactPoints`), `conditions.ts` (compile non-relayer/silent sets on the
dedicated consensus seed, refusers drawn first so old seeds replay byte-identically), `consensus-harness.ts`
(the `cooperatingMembers`/`cooperatingCommitted` completion count + the pull-recovery pass), `consensus-metrics.ts`
(`cooperatingCompletion`, `pullMessagesPerLift`, `recoveredTotal` aggregates), `serialize-consensus-records.ts`
(five new CSV columns), and `consensus-runner.ts` (one compile feeds both the network ports and the per-lift
pull-exclusion, so injection and exclusion can't diverge). See commit `0448e38` for the full implement diff.

### What was checked and found

- **Tests — the "419 pass / all green" claim was machine-load-dependent and FAILED on re-run.** `yarn test`
  failed **3 of the new tests** (both principle-3 completion cases + the voter-model-knobs determinism case),
  all with *"Exceeded timeout of 5000 ms"* — consistently, across two full-suite runs. **Not a hang and not
  pre-existing:** each passes standalone in ~3 s; the whole `consensus-runner.test.ts` suite is ~14 s alone.
  Root cause: the consensus harness does ed25519 keygen **per query** (12 queries × `line(6)`), the new
  pull-recovery pass adds `runUntilIdle` clock drives, and the determinism case replays the whole sweep twice —
  so under the full 34-suite parallel load these heavy-but-correct tests blow Jest's 5 s default. **Fix:** a
  global `testTimeout: 30000` in `packages/tallysim/jest.config.ts` (short enough to still catch a genuine
  hang — the pull pass is bounded by `members.length` rounds; generous enough for parallel-load variance, and
  it protects the *existing* consensus tests from the same fragility on slower CI boxes). After the fix:
  **419/419 pass, twice, plus `yarn build` and `yarn lint` clean.**

- **Docs — two factual enumerations were left stale by this ticket's own code changes** (distinct from the
  voter-model narrative subsection 5.532 owns). Both **fixed** in `docs/design.md`:
  - The consensus-CSV column-order sentence (≈ line 377) ended at "the four `voidReasons.<reason>` tallies" —
    it now lists the five columns this ticket appended (`cooperatingMemberTotal`, `cooperatingCommittedTotal`,
    `cooperatingCompletion`, `recoveredTotal`, `pullMessagesPerLift.*`).
  - The `summarizeConsensusMetrics` aggregate description (≈ line 832) now names the record-availability
    aggregates (`cooperatingCompletion` guarded 0-not-NaN, `pullMessagesPerLift`, `recoveredTotal`).

- **Determinism / byte-identical old runs — verified, no issue.** Refusers drawn first from the dedicated
  stream (refuser-only specs replay unchanged); failure ports added only when their set is non-empty (the
  all-cooperative / one-refuser / stalled runs stay byte-identical); the knobs-set determinism test replays
  byte-for-byte. `nonCooperating = [...nonRelayers, ...silent]` order is deterministic and `cooperatingRoute`
  dedups it, so a node drawn into both sets is harmless.

- **Correctness of the completion count — verified.** `cooperatingRoute` is the single shared derivation for
  both the pull pass and the count, so they can't drift. `refuseRelayFor`/`silentAfterPromiseFor` take entity
  ids (number); the harness converts name→id, matching the injected sets. The pinned seed claims (non-relayer
  = interior node 3 on `line(6)`) are re-derived in-test and hold. `cooperatingCompletion` is guarded 0-not-NaN.
  All callers of `runLiftForOutcome`/`analyzeLift` typecheck (build clean); the trace recorder was deliberately
  left as-is (no trace scenario sets the new fractions, `TraceLiftEntry` captures no completion field) — flagged
  by the implementer, confirmed correct.

- **Source hygiene — clean.** Small single-purpose functions (`cooperatingRoute`, `countCommitted`), shared
  derivation over duplication, JSDoc concise and accurate. `countCommitted` is a cheap extra outcome-read pass
  (no clock drive) after recovery — minor redundancy, not worth refactoring.

### Tripwires (recorded, not filed)

- **O(members²) pull pass** — `recoverStrandedByPull` re-drives the clock to idle per stuck member; a topology
  that strands many members (a large circular route) costs O(members²) clock drains. The `// NOTE:` is landed
  at the site in `consensus-harness.ts`. Fine for the small lines/rings this tier runs.
- **`cooperatingCompletion` conflates refusal with stranding** *if* a sweep ever varies `refuserFraction` AND
  `nonRelayerFraction` together — a refuser-voided lift contributes 0/N exactly like a stranded one. Today only
  `nonRelayerFraction` is swept, so the number reads cleanly. Parked as a `// NOTE:` at the aggregation site in
  `consensus-metrics.ts` (split by void-reason if that changes).

### Honest gaps carried forward (not defects)

- **"Holds at 1.0" is seed-chosen for a real reason.** Contact points are stamped on the originator + voters
  only, and the sweep's sole voter IS the originator; a non-relayer that is itself a lift's originator serves
  no pull, so that lift's members can't recover. The WITH-contact test uses `workload.seed 1` specifically
  because its queries straddle node 3 but never originate AT it. A true model property — a design note for
  5.532/whoever sets the curve's y-axis (exclude non-cooperating originators, or publish contact points on
  non-originator members too), not a bug.
- **`silentAfterPromiseFraction` is wired but only exercised by the determinism test** — the port is shape-
  identical to the tested `refuseRelayFor` and proven at the tallynet level. A dedicated silent-node completion
  test would pin the semantics; low risk.
