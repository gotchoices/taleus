# Complete — tallysim oracle

Second of three chained network-model-tier tickets (`tallysim-model-generators` → **oracle** →
`tallysim-runner`). The oracle sees the whole compiled graph and searches it directly; it is the ground
truth the later discovery tier measures the real `tallynet` protocol against ("found vs. oracle").

## What shipped (unchanged from implement, plus review edits below)

- **`src/graph-view.ts`** — `buildGraphView(network)`: compiles a `Network` into a directed capacity graph
  in CSR form over typed arrays (`offsets`/`targets` `Int32Array`, `capacities` `Float64Array`). Two directed
  edges per tally; deterministic build.
- **`src/oracle.ts`** — `Oracle` wrapping one `GraphView`, reusing generation-stamped scratch buffers.
  Queries: `routeExistence` (bounded BFS), `selfPayment` (shortest directed cycle via BFS), `maxFlow`
  (Edmonds–Karp, not depth-bounded), `clearingCycles` (capped DFS count + exact BFS shortest).
- **Barrel** re-exports both; **`docs/design.md` § Oracle** fully written; README status updated.
- Verified by `src/oracle-brute-force.test.ts` (independent exhaustive enumeration + min-cut max-flow
  cross-check on small seeded graphs).

## Review findings

Reviewed the implement diff (`e88cba4`) with fresh eyes before the handoff, re-derived the capacity
formula and boundary conventions by hand, and scrutinised the brute-force harness as hard as the oracle.
Gates green throughout: **build + lint + test pass, 121 tests (9 suites)** — up from 120 (one test added
below). The `no-node-globals` platform-neutrality guard (17 tests) scans both new source files.

**Checked and correct (no change):**
- **Capacity formula anchor** — re-derived `graph-view.test.ts` by hand: balance 2, limits 10/5 ⇒
  `cap(S→F)=b+foilLimit=7`, `cap(F→S)=stockLimit−b=8`. Matches `capacity.ts`. The brute force reuses the
  same formula by design (it is the *definition*), so this hand check is the independent anchor — confirmed.
- **Depth/off-by-one** — `routeExistence` and `clearingCycles` count hops correctly: a cycle/path of length
  exactly `maxDepth` is included, `maxDepth + 1` excluded. Traced the `len + 1 <= maxDepth - 1` DFS guard
  and the BFS `lu === maxDepth` cutoff; both correct and covered by boundary tests.
- **Capacity filter `≥`** — `capacity === amount` qualifies, `amount − 1` does not; zero-capacity directions
  pruned. Covered.
- **`selfPayment` BFS argument** — the shortest `node→u` BFS-tree path plus a closing edge back to `node` is
  always a *simple* cycle (node has level 0 and is never re-enqueued); equals the shortest simple cycle the
  DFS counts. Consistent with the brute force (DFS cycle enumeration).
- **`clearingCycles` scratch reuse** — `onPath` is fully unwound even on the early `capped` return (each
  frame clears `onPath[v]` before propagating), so buffer reuse across queries is safe.
- **`maxFlow`** — Edmonds–Karp residual (XOR-1 partners, predecessor walk) is correct; terminates with
  `Infinity` capacities (saturating edge is always finite; an all-`Infinity` path short-circuits to
  `Infinity`). Diamond / bottleneck / parallel-edge / `maxFlow(X,X)=0` cases covered.

**Minor — fixed in this pass:**
- **Self-loop reported as a length-1 cycle.** `shortestCycleLength` (used by `selfPayment`) returned length
  **1** for a self-loop edge (`node → node`), contradicting the documented "min cycle is length 2" invariant
  and disagreeing with `clearingCycles` / the brute force (both require length ≥ 2). Self-loops are dormant
  today (no generator emits them) but the `Tally` model explicitly permits them, so this was a latent
  internal inconsistency. Added a `lu + 1 >= 2` guard (zero behaviour change on all current, self-loop-free
  graphs) plus a regression test asserting `selfPayment` and `clearingCycles` agree (both empty) on a
  self-loop network. `packages/tallysim/src/oracle.ts`, `packages/tallysim/src/oracle.test.ts`.

**Tripwire recorded (conditional — not a ticket):**
- **`clearingCycles` exploration cost is bounded by `maxDepth`, not `maxCount`.** The `maxCount` cap bounds
  the *count*; when qualifying cycles are sparse but the region is deep and high-branching (many simple
  paths, few closing back to `node`) the cap never trips and DFS cost is ~`O(degree^maxDepth)`. Added a
  `NOTE` at the DFS site in `oracle.ts`: the runner must keep `maxDepth` modest when sampling
  `clearingCycles` on dense graphs. (Joins the two existing tripwires — 2^53 capacity precision in
  `graph-view.ts`, and max-flow `O(V·E²)` cost on `Oracle.maxFlow` — both verified present and accurate.)

**Acknowledged gaps — left as-is (low risk, no ticket):**
- **Max-flow `Infinity` not cross-checked against brute min-cut** (seeded brute graphs use finite capacities
  0–4). The dedicated `returns Infinity when an all-unlimited path exists` and `maxFlow(X,X)=0` hand tests
  cover the special paths; the finite min-cut cross-check (40 seeds × 6 trials) anchors the general case.
  Adding an unlimited-graph min-cut cross-check is a possible future hardening, not a correctness gap.
- **No perf/scale test for `clearingCycles` or max-flow** — deliberate (both can be costly; guarded by the
  `maxCount` cap, the `maxDepth` bound, and the sampling guidance in design.md § Cost guidance). BFS route
  existence has a scale smoke test (10k entities, ~1,000 queries, sub-second).
- **`clearingCycles` counts degenerate same-tally 2-cycles** (a bidirectional tally's two directions). A
  valid graph cycle; whether the clearing *metric* should exclude it is a modelling decision for the
  runner/trading tiers, documented and deferred, not a defect here.

**Docs:** read every touched file. `docs/design.md` § Oracle and `README.md` accurately reflect the shipped
code (CSR layout, the four queries, conventions, cost guidance, tripwires). No doc drift found.
