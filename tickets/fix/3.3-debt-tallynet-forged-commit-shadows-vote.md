## What a reader needs to know first

In TallyNet's consensus a payment (a "lift") settles in two phases. First every **participant** on the route signs a **promise** (`P`) or refusal (`NP`). Once every participant has promised, the **referees** vote **commit** (`C`) or **no-commit / void** (`NC`); a strict majority of referees one way settles the whole lift.

Every vote is a signature over a canonical preimage. A referee's commit vote binds the *full promise set* into that preimage (see `digest.ts`) — so a commit vote can only be verified once a node holds the complete set of participant promises. Because promises and votes propagate hop-by-hop, a vote can legitimately arrive at a node **before** that node has received all the promises ("out-of-order delivery"). To tolerate that, the participant deliberately **stores an incoming commit vote without verifying it** while the promise phase is still incomplete, and verifies it later once the promise set fills (`participant.ts` `mergeSignature`, the `else if (this.promisePhaseComplete(...))` branch, and `countVerifiedCommits`).

## The defect

The signer address on a signature is just a referee's public key — which is public (it is listed in `topology.members`). The merge logic accepts **at most one** commit-phase signature per signer: the first one seen for a referee is kept, and any later signature from that same referee is refused as `changed` (same vote type, different bytes) or `equivocation` (opposite vote type). That "first one wins" rule runs **before** cryptographic verification.

Combine the two and a griefing attack falls out. While the promise phase is still incomplete, any node that forwards records (a relay, or any route member) can inject a commit-phase signature carrying a target referee's address, the referee's address, and **garbage signature bytes**. It passes the membership and role checks, no prior signature from that referee exists yet, and — because the promise phase is incomplete — it is **stored unverified**. When the referee's *genuine* vote later arrives, it collides with the stored fake and is refused as `changed`/`equivocation`. The fake never verifies either (it is garbage), so once the promise phase completes it is never counted. Net effect: **that referee's real vote is permanently silenced at the victim node.**

Do this for enough referees and no commit majority can ever form, so the lift cannot settle in-band and (once `feat-tallynet-propagation-timeouts` lands) is driven to void — a payment that every honest party wanted to commit is stalled or cancelled by a single misbehaving relay.

Scope of the damage:
- **Liveness / correctness of outcome, not safety.** A forged vote never *counts* toward a majority (it never verifies), so no false commit can be manufactured — but genuine votes can be suppressed, which is enough to block or wrongly void a lift.
- **Promises are not affected.** Promise-phase signatures are verified immediately on merge (their preimage does not depend on the promise set), so a forged promise is dropped as `forged` and never shadows a genuine one. Only the commit phase has the store-then-verify-later path, so only referee votes are exploitable.

## Why it is dormant today (and why it is still a real defect, not a tripwire)

The consensus module is not yet wired into production (the public barrel ships with the final `tallynet-consensus` ticket) and every current test is single-node with hand-built records, so nothing exercises a hostile peer. But this is **not** a "fine now, only matters if X grows" tripwire: the moment multi-node propagation runs against any adversarial or buggy peer, the fake-vote path is hit and a genuine vote is definitely lost. It is a latent defect waiting on a currently-dormant code path, hence `debt-` rather than `bug-`, and it belongs with the multi-node work (`tallynet-consensus`, 3.2) where it can be tested end-to-end.

## What a fix needs to do

The honest out-of-order case must keep working (an early genuine vote stored unverified, counted once promises complete). The fix is to stop letting an *unverified, non-verifying* stored vote block a genuine one. Options to weigh (design decision for the implementer):

- When a new commit-phase signature collides with an **existing stored-but-unverified** one for the same referee, do not blanket-refuse: if the stored one fails verification against the now-available promise set and the new one verifies, **replace** it. (A referee that genuinely signs two *verifying* opposite faces is still true equivocation and must still be refused — keep that.)
- Or: do not retain an unverified commit keyed in a way that can shadow a verified one — e.g. keep unverified arrivals in a side set that never blocks a later verified vote, and promote to the authoritative set only on successful verification.

Either way the invariant to preserve: **a referee's genuinely-signed vote can never be suppressed by a signature that does not verify**, while a referee that verifiably signs both faces is still caught as equivocation.

**Settled (2026-11-25): take the second option.** Unverified commit-phase arrivals go into a side pool that never blocks anything; a vote enters the authoritative set, and the changed/equivocation checks, only once it verifies. Cap the pool per referee per transaction (a small constant, e.g. 4 distinct signatures; drop and log beyond it) so a peer cannot grow it without bound. Record the general rule in `packages/tallynet/docs/design.md` § Protocol design: **no unverified input may change state that blocks a verified one.** Audit discovery and consensus for any other place that dedupes or rejects on an unauthenticated field, and fix any you find in this ticket.

Out of scope: detecting, attributing or punishing misbehaving peers (backlog `feat-tallynet-hostile-peers`).

## Tests to add (multi-node, in the 3.2 harness)

- A relay injects a garbage `C` for referee R during the promise phase; R's genuine `C` arrives after the promise set completes; R's vote is counted and the lift reaches commit consensus.
- Same with a garbage `NC` injected first (collides as `equivocation`); R's genuine vote still counts.
- Genuine equivocation unaffected: a referee that signs two *verifying* opposite faces is still refused, first face stands.
