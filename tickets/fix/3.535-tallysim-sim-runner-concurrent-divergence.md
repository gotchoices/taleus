## What's wrong

The discovery sweep runner (`sim/sim-runner.ts`) can run a run's queries two ways, selected by
`SimRunnerDeps.concurrent`:

- **sequential** (default) — issue one query, drive the clock to idle, read its outcome, repeat;
- **concurrent** — issue every query, then drive the clock to idle once (faster: one settle for the batch).

The implementer's handoff claimed the two modes "produce **identical** per-query metrics — verified in tests
and analytically." That is **false for `roundsUsed` and the timing distributions**
(`timeToFirstPlanMs`, `timeToCompletionMs`). The outcome metrics (found, `messages`, `nodesTouched`,
`pruneReasons`, `pFoundGivenExists`) *do* agree; only round count and timing diverge.

It went undetected because the only equivalence test used a complete, unlimited, 1-hop network with zero
latency — every query resolves at round 0 with nothing for the clock to reorder. A review test on a
multi-hop line with real latency (`sim-runner.test.ts`, "agrees on outcome metrics under real latency but
diverges on round/timing") reproduces the divergence; it currently *asserts* the divergence to pin the
behaviour.

### Reproduction (observed)

`line(5)` (0–1–2–3–4), constant 200ms link latency, depth 8, the single query **0→4**:

| | last round-started time | `timeToCompletionMs` |
|---|---|---|
| run alone (sequential) | 16500 | 16500 |
| run alongside query 1→4 (concurrent) | 7100 | 7100 |

Same network, same query, same latency — different clock schedule, different round count.

### Why

Concurrent queries share **one** `VirtualClock`. When a round's budget-expiry timer and a sub-request's
delivery timer fall at the same virtual time, which fires first decides whether the answer is harvested in
*this* round or folded into a *later* one — which changes `roundsUsed` and every event time after it. The
clock breaks same-time ties by a global monotonic fire-order counter (`seq`); in concurrent mode the sessions
arm timers interleaved, so a given session's timers get different `seq` values than when it runs alone, and
the tie resolves the other way. The messages issued and candidates pruned are the same either way, so those
metrics still match — only *when* answers land, and thus the round/time axes, shift.

This is **not** a measurement bug in `analyzeQuery`; it is the protocol genuinely running on a different clock
schedule. It cannot be fixed by changing how metrics are read.

## What a fix should decide

Two independent discovery searches should not perturb each other's round count or timing — the model has no
per-node queueing or contention, so the divergence is a simulation artefact, not a modelled effect. Pick one:

- **Drop `concurrent`.** It is currently unused except in tests (default is sequential; the CLI `--concurrent`
  flag lands in `tallysim-discovery-metrics-io`). Simplest; loses the batch-settle speedup.
- **Give each query its own clock even when batched** (e.g. build a fresh `SimNetwork` per query, or isolate
  per-session timer streams), preserving equivalence. Reconciles speed with correctness but is more work and
  may not actually be faster.
- **Keep it, but scope the promise honestly** — document (done in the interim) that concurrent is throughput-
  only and its round/timing metrics are not comparable to sequential, and make the CLI refuse `--concurrent`
  when timing/round metrics are requested.

Whichever is chosen: the interim caveat text in `sim-runner.ts` (module header + the `runProtocolQueries`
NOTE) and `docs/design.md` (§ Protocol metrics / discovery sweep runner) must be updated to match, and the
characterization test should be tightened to full equality (if the divergence is removed) or kept as a scoped
outcome-only check (if it is not).

## Ordering note

`tallysim-discovery-metrics-io` exposes a user-facing `--concurrent` CLI flag and
`tallysim-discovery-metrics-experiment` runs the checked-in sweeps. If either relies on concurrent mode for
round/timing metrics before this lands, the published numbers would depend on the flag. This ticket is in the
top-priority `fix/` stage so it resolves ahead of that feature work; if it cannot, those tickets should stay
on sequential mode for any round/timing-sensitive output.
