Implemented. Second of three tickets splitting the original `5.5-tallysim-voter-model`. The prereq
(`tallysim-voter-policies`) built the pure policy functions; this ticket **wired them into the running

## What a "non-relayer", "contact point" and "pull" mean here (plain language)

- **Non-relayer** — a node that promises normally during phase 1 of a payment but then drops every phase-2
  "it committed" record it would pass on, and answers no requests for that record. It models a node that
  goes dark mid-settlement. A node sitting between the voucher and the far end of a chain can strand everyone
  past it.
- **Contact point** — a directly-dial-able address a node publishes on the lift, so any other participant can
  reach it without sharing a tally with it. The originator and the voters get one when contact points are on.
- **Pull** — a stranded node asking a reachable peer (a contact point, or a tally-neighbour) for the settled
  record, instead of waiting for it to be pushed. It is how a node cut off from the push still learns the
  payment committed. v1 has no automatic retry timer, so the simulator triggers the pulls itself.

## What landed (all in `packages/tallysim/src/sim/`)

**`harness.ts` — five new `ConsensusConfig` ports + the hooks factory.** `ConsensusConfig` grew `scorePlan`
(the originator's shared plan scorer), and four entity-id-keyed ports: `negotiatePlanFor` (a per-node
discovery voter-set gate), `nomineesFor` (per-node referee nomination), `refuseRelayFor` (the non-relayer),
and `silentAfterPromiseFor` (offline-after-promise). The discovery `hooks` field is now computed by
`consensusHooks(consensus)`: **when no node supplies a `negotiatePlanFor` gate it returns the single shared
`makeCapacityHooks()` object — byte-for-byte what the harness passed before — so the pinned discovery sweep
never moves**; any gate turns it into a per-node factory. `consensusPorts` spreads each new port only when the
config supplies it, and is still `{}` when consensus is off.

**`consensus-harness.ts` — contact points, the pull-recovery pass, two new result fields.** `RunLiftOptions`
grew `contactPoints` (stamp the originator + voters `physical`), `nonCooperating` (entity ids excluded from
the pull pass — MUST match the network's `refuseRelayFor`/`silentAfterPromiseFor`), and `wellKnown` (passed to
`selectPlan`). After the initial push settles, `recoverStrandedByPull` calls `fetchOutcome` on each still-
pending cooperating member so it pulls the evidence from a reachable contact point or neighbour; the money-move
then reads the **originator's post-pull outcome**. `LiftResult` grew `pullCalls` and `recovered`.

**`route.ts` — `buildCircularOutcome` + `findCycleThrough`.** A deterministic DFS finds the shortest simple
cycle through an origin (handles parallel-tally 2-cycles) and `buildCircularOutcome` encodes it as a one-plan
`QueryOutcome` for `reconstructRoute`/`runLiftForOutcome`. This is the stand-in for real clearing discovery
(deferred to `feat-tallysim-clearing-discovery`) so the circular *consensus* path is exercisable now.

**`consensus-resource.ts` — `refuseStackedPlanHook`.** A discovery-time `negotiatePlan` that drops a plan
whose `members` are stacked (padded with obscure referees) under a `StackedVoterPolicy` — the discovery-time
twin of the existing promise-time `acceptsProposal` gate, both reading `refusesStackedVoterSet`.

**`index.ts` — no change needed:** `route.ts` and `consensus-resource.ts` are already barrelled via
`export *`, so the two new exported symbols surface automatically.

## The seven new tests (`voter-harness.test.ts`) — the use cases to scrutinise

1. **Contact points recover a stranded member (the headline).** `line(5)`, non-relayer at node 2, originator
   is sole voter and publishes a contact point. Push settles 0,1,2; nodes 3,4 are stranded, then pull node 0
   → `recovered === 2`, `pullCalls > 0`, every node commits, money moved the full line.
2. **No contact points → the documented gap.** Same chain, `contactPoints:false`: nodes 3,4 stay `pending`
   (`recovered === 0`) but the originator still commits and **money still moves**. This asserts the gap as
   EXPECTED, not a bug — settlement keys off the originator's own view (see Gap 1 below).
3. **Circular lift routes around a non-relayer with no contact points.** `ring(3)`, node 1 refuses; the
   originator pushes commit to both ring neighbours directly, so node 2 is reached around node 1. Built via
   `buildCircularOutcome`. Conservation holds around the loop.
4. **Referee nomination folds a well-known hub into the discovered plan.** A 7-node network with an off-route
   hub; `makeNomineesFor(..., 'well-known')` makes every participant nominate it; it surfaces once as a `[V]`
   member of the 0→2 plan.
5. **`scorePlan` ranks a lean voter set ahead of a stacked one.** Diamond; one arm stacks two obscure
   referees. `voterAwareScorePlan` puts the lean arm at `plans[0]`.
6. **`refuseStackedPlanHook` drops just the padded arm at discovery.** Diamond; the originator refuses the
   arm carrying an obscure referee, leaving the lean arm.
7. **Determinism.** The contact-point recovery scenario reproduces identical `LiftResult` (including
   `pullCalls`/`recovered`) and byte-identical serialized networks.

## Honest gaps & where a reviewer should push (my tests are a floor, not a ceiling)

1. **Money moves on the originator's commit even when far members are stranded (test 2).** Deliberate — it
   matches the existing discovery-only settlement model (settle off `route[0]`). Confirm this is the intended
   semantics for the sweep, not an accounting hazard. **Corollary, untested:** if the **originator itself** is
   in `nonCooperating` (a `silentAfterPromise` originator), it is excluded from the pull pass and stays
   `pending`, so money will NOT move even if a majority committed. The ticket's edge cases all keep the
   originator a committing voter, so this path is unexercised. A `silentAfterPromiseFor` originator case is the
   first thing I'd add.
2. **Nominated referees fold into the DISCOVERY plan but are NOT driven as consensus voters.** `liftMembers`
   marks voters only from the `voters` option over the route; it does not promote a plan's folded `[V]`
   referees into the consensus lift. So test 4's hub is a discovered voucher, not yet an actual vote in
   settlement. This is the known composition gap — see the NOTE in `well-known.ts` and the backlog ticket
   `debt-voter-nomination-on-path-composition`.
3. **Promise-time stacked refusal is not exercised end-to-end through `runLiftForOutcome`.** Because (2)
   means `runLiftForOutcome` never puts V-only referees into a consensus record, the promise-time
   `refuseStackedVoters` → `acceptsProposal` → `NP` → void path can only be built by hand (`net.buildLift`).
   It is unit-tested in `consensus-resource.test.ts`; the discovery-time refusal (test 6) is the integrated
   proof here. A reviewer who wants the promise-time gate covered through the harness would hand-build a lift
   with an obscure `[V]` member and a payer whose `resourceFor` carries `refuseStackedVoters` (build a
   `key→entity` map from `net.memberKey(name)` for the policy's `memberEntity`, since a consensus record keys
   members by ed25519 key, not node name).
