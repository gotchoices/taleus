## What was built

A **pure** consensus-metrics module (`packages/tallysim/src/sim/consensus-metrics.ts`): recorded lift in,
metrics out. No network, clock, or filesystem — testable entirely from hand-built `LiftResult`s plus
consensus `TraceEvent`s, built as a close mirror of the already-landed `sim/protocol-metrics.ts` (the
discovery-tier analogue). It answers, per lift and per run: **of the routes the protocol found and actually
took, how many committed vs. voided vs. stalled, how fast, how many consensus messages, and why the
non-commits failed.**

Public surface (all re-exported from `sim/index.ts`):

- `type VoidReason = 'refused-promise' | 'voted-no-commit' | 'stalled' | 'expired'`
- `zeroVoidReasons()` — the compile-checked source of truth for the reason set (the `zeroPruneReasons`
  pattern: a missing key is a compile error, a stray key is a compile error).
- `ALL_VOID_REASONS` — derived from the above so the two can't drift.
- `ConsensusLiftMetrics` / `ConsensusRunMetrics` — the per-lift and per-run shapes.
- `analyzeLift(events, result): ConsensusLiftMetrics` — one lift.
- `summarizeConsensusMetrics(lifts, structural, queryCount): ConsensusRunMetrics` — aggregate.

### Key design decisions (verify against the ticket)

- **Lift isolation by `transactionCode`.** Every consensus `TraceEvent` carries `transactionCode`; no
  discovery event does. `analyzeLift` filters on `event.transactionCode === result.transactionCode` via a
  typed guard (`forTransaction`, narrowing to `Extract<TraceEvent, { transactionCode: string }>`), so
  discovery noise and other lifts' events drop out. Tested with a co-present discovery `query-sent` and an
  `OTHER`-transaction `record-pushed` that must both be excluded.
- **`messages` = `record-pushed` count** (the push is the consensus message).
- **`timeToSettleMs`** = `max(time over all this lift's consensus events) − min(time over
  record-pushed|promise-signed events)`, **omitted for `pending`**. Also omitted (defensively) for a
  settled lift with no push/promise event at all — a degenerate case that shouldn't occur; see gaps below.
- **Outcome-driven void-reason precedence** (documented in the module header): `commit` → none;
  `pending` → always `'stalled'` (we do NOT infer a reason from stray `NP`/`NC` that never reached a
  decision); `void` → first of `expired` → `refused-promise` (`NP`) → `voted-no-commit` (`NC`) → a
  defensive, unreachable `voted-no-commit` fallback.
- **Degenerate guards:** zero lifts ⇒ `pCommitGivenFound = 0` (never NaN), all-zero void tally,
  distributions `count: 0`.

## How it was validated

- `corepack yarn workspace tallysim test --testPathPatterns consensus-metrics` → **11 passed**. (Note: the
  ticket wrote `--testPathPattern`; the installed Jest renamed it to `--testPathPatterns`. `yarn` is not on
  PATH in this environment — `corepack yarn …` works.)
- `corepack yarn workspace tallysim build` → exit 0 (tsc clean).
- `corepack yarn workspace tallysim lint` → exit 0.
- Full `corepack yarn workspace tallysim test` → **346 passed, 29 suites** (nothing else regressed).

Tests cover every case the ticket enumerated: the reason-set shape; a commit stream (`pCommitGivenFound=1`,
one settle sample = last−first, `messages` = push count); an `NP`→void (`refused-promise`); an `NC`→void
(`voted-no-commit`); a stall (pending ⇒ `stalled`, **no** settle sample, and a stray `NP` must not override
`stalled`); `expired` beating a co-present `NP`; a refuser-AND-dropped-edge void counting once as
`refused-promise`; zero lifts; plus an end-to-end `analyzeLift`→`summarizeConsensusMetrics` over three hand
traces.

## Known gaps / where a reviewer should push (tests are a floor, not a ceiling)

- **No end-to-end exercise against the real engine.** Every test feeds hand-built `TraceEvent`s. Whether
  the actual `tallynet` consensus engine emits exactly these events, in these orders, for a commit / void /
  stall is **not** proven here — that is the sibling `tallysim-consensus-runner-cli` ticket's job (it wires
  the recorded lift + trace into this module and runs the real sign-and-settle harness). The handoff is
  honest that this module's contract with reality is only validated once that lands. A reviewer worried
  about the trace vocabulary should spot-check the event field names against `tallynet/src/trace.ts`
  (done here) and, ideally, against one real recorded run under the runner ticket.
- **The defensive `voted-no-commit` fallback is intentionally unreachable** (a `void` with no `expired`,
  no `NP`, no `NC`). It is not — and cannot cleanly be — unit-tested as "unreachable". If a reviewer wants
  it observable, consider a one-line `log` there rather than a silent default; I left it silent to match
  protocol-metrics' style.
- **Settled-lift-with-no-events ⇒ no `timeToSettleMs` sample.** If a `commit`/`void` ever arrives with zero
  push/promise events, `timeToSettleMs` is silently omitted rather than throwing. That shouldn't happen
  (a settled lift pushed at least once), but it's a quiet path worth a glance.
- **`queryCount` is carried through unvalidated.** `summarizeConsensusMetrics` trusts the runner's
  `queryCount`; it does not assert `queryCount >= liftCount`. Deliberate (mirrors how structural metrics
  pass through), but flagged.

## Review findings (index — see tripwire and gaps above)

- **Tripwire (parked as a `NOTE:` code comment in `analyzeLift`):** the per-lift scan is linear in the
  whole `events` array, so a caller passing a full concurrent batch to every lift is O(lifts × events). Fine
  at current sim scale; if batch sizes grow, pre-bucket events by `transactionCode` once. This exactly
  mirrors `protocol-metrics.ts`'s `analyzeQuery`, so it is consistent, not a regression.
