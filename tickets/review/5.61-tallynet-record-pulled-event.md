## What changed

- `packages/tallynet/src/trace.ts`: added one variant to the `TraceEvent` union —
  `{ type: 'record-pulled'; transactionCode: string; from: string; ok: boolean }` — mirroring
  `record-pushed`'s shape. `from` is the peer's public member-address key (the serving end); `ok` is
  whether that peer actually served a usable reply. Purely additive: no `TRACE_FORMAT_VERSION` bump,
  nothing else in the union changed.
- `packages/tallynet/src/consensus/participant.ts`: `fetchOutcome` (the pull's requester side) now emits
  one `record-pulled` per reachable peer it asks, right after that peer's `fetchRecord` call resolves
  (whether or not a reply came back). Added a small `emitPulled` helper next to the existing `emitPushed`,
  same pattern. No control-flow change — `fetchOutcome`'s return value and the merge/update logic are
  untouched; this is pure instrumentation through the existing `safeTraceSink`-wrapped sink.

## Verified, not touched

Grepped every `switch (event.type)` in `tallynet`/`tallysim` (`protocol-metrics.ts`, `consensus-metrics.ts`).
Both have a tolerant `default` branch, not an exhaustive `never`-assert, so the new variant falls through
harmlessly in `consensus-metrics.ts` (contributes only to `maxTime`, i.e. pull activity extends the
time-to-completion window, which is correct — a pull is part of settlement). No consumer needed a change.

## Tests (both pass; `yarn workspace tallynet build / lint / test` all green, 393/393 tests)

- **Unit** (`participant.test.ts`, new test in the "record availability" describe block): a two-voter,
  one-self topology where `fetchRecord` serves `voter1` (returns the identical stored record back — a
  harmless no-op merge) and serves nothing for `voter2`. Asserts exactly one `record-pulled` per peer,
  `ok:true` for `voter1` and `ok:false` for `voter2` — the per-peer semantics the ticket called out as the
  cheap thing to assert directly, independent of overall settlement.
- **E2E** (`testing/consensus.test.ts`, extended the existing "interior refuser cuts the far member off"
  scenario rather than adding a new one — it already has the right topology: O—V—R—F linear chain, O and V
  publish contact points, R refuses to relay/serve). After F's `fetchOutcome` pull settles it, asserts the
  shared trace stream carries `record-pulled` events from F for all three of its reachable peers: `ok:true`
  from O and from V (both already committed, both reachable via contact point, no direct edge to F so the
  refuser R is not in the way), `ok:false` from R (R is F's only *linked* neighbour and refuses to serve
  pulls same as it refuses to relay pushes).
