## What the change does (one paragraph)

In commit-phase consensus a commit signature binds the **complete** promise set, so it cannot be
verified until every participant has promised. Previously an out-of-order commit was stored in the
authoritative `commits` set *unverified* while the promise phase was still open. A forwarding node could
exploit that window: inject a garbage commit for a referee **before** the promises completed; it occupied
that referee's slot, and the referee's genuine vote then collided with it (`changed`/`equivocation`) and
was silenced. Scope is **liveness/outcome, not safety** — a forged vote never *counts* (it never
verifies), but a suppressed genuine vote could stall or wrongly void a lift that should have committed.
The fix: unverifiable commits wait in a durable **side pool** (keyed by `transactionCode`, capped per
referee, never digested/pushed/part of the wire record) and are promoted into `commits` only after they
verify against the complete promise set. Promises are unaffected — a promise's preimage never depends on
the promise set, so each is verified on arrival and an unverified promise is never stored.

## ⚠️ IMPORTANT for the reviewer — a real defect in the "already-landed" code was found and fixed here

The source ticket stated the fix was "coded and compiles" and flagged **one** existing test to update.
Running the suite surfaced a **second, un-flagged** failure that was a genuine gap in the landed fix, not
a pre-existing/unrelated failure:

> `participant.test.ts › … › for a sole referee, the first face wins and a later opposite face cannot
> re-settle`

The pool was only drained inside `validateAndMerge` (which handles a **peer's** completing promise). When
**our own** cast promise completes the promise phase during `advanceState`, the pool was never drained, so
a commit that arrived before we promised sat in the pool forever and the lift never settled in that
update. Fix: a new `drainPendingFromStore(record)` helper called right after `castPromise` in the
`ourPromiseNeeded` branch (participant.ts). It no-ops unless the promise phase is now complete and the
pool is non-empty. This is the main new logic beyond the originally-landed diff — **review it closely.**
It restores the existing sole-referee test and is further covered by the new pre-promise-pool tests.

### Use cases / scenarios worth probing (reviewer starting points)

1. **The headline attack** — `consensus.test.ts`, "garbage C injected before the promises …". Before the
   fix this read `pending` with reject `changed`; now `commit`. This is the regression that must never come
   back.
2. **Our-own-promise drain path** (the fix above) — `participant.test.ts` sole-referee test + the
   pre-promise-pool `commit` cases where `self` is a participant. Consider: multi-participant lift where
   *our* promise is the last one; a lift where we are `[P,R]`; interleavings where a pooled commit and a
   same-update incoming commit for the same referee race (ordering: pooled drains first, "first face
   stands").
3. **Pool cap semantics** — cap is **per signer** (`MAX_PENDING_COMMITS_PER_REFEREE = 4`), so total pool
   size is bounded by `4 × |referee members|`. Only referee-member keys pass the `checkMemberAndRole` gate
   before pooling (a non-member/wrong-role commit is rejected, never pooled), and membership is fixed in
   the immutable topology — so the bound holds. Worth a second look that no pooling path skips that gate.
4. **Persistence correctness** — `validateAndMerge` only calls `savePendingCommits` when
   `pending.length > 0 || hadPending` (avoids writing an empty pool on every promise-only update);
   `drainPendingFromStore` always persists the emptied pool when it drained. Check no path leaves a stale
   non-empty pool persisted after a drain.
