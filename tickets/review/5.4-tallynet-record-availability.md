## What shipped (two mechanisms closing two gaps)

The ticket closes two holes the regression check named:

1. **Promised means resolvable (principle 3), the hard linear case.** Push-to-reachable was already
   built. On a *linear* chain with no contact points, an interior member that refuses to relay the
   commit blocks the commit evidence from everyone beyond it — nothing routes around it. The fix is a
   **pull**: a node can fetch the record for a `transactionCode` from any reachable peer (a published
   `physical` contact point, or a direct link neighbour) and merge each reply.
   - `serveRecord(transactionCode)` — the **responder**: returns our merged record (or `undefined`).
     Self-authenticating (every signature verifies on merge), so it is safe to serve anyone; union
     merge makes a stale/duplicate reply harmless.
   - `fetchOutcome(transactionCode)` — the **requester**: with no stored record returns `pending` and
     pulls nothing (no record ⇒ no topology ⇒ cannot even address a pull). Otherwise reads the
     reachable set **once** from our own stored record (topology is immutable), merges each peer's
     reply via `update(reply, peer)` (the peer as `fromAddress` primes the push skip-test so we do not
     echo straight back), and returns our resulting outcome.
   - `FetchRecordFunc<TTerms, TPayload>` is the new host port (`participant.ts`); `fetchRecord?` is an
     optional config/dep (default: a port that holds nothing, making `fetchOutcome` a no-op beyond
     reading our own outcome). Threaded through `ConsensusNodeDeps` and delegated on `engine.ts`.

2. **Proof kept (principle 2).** A voter signing both faces of a phase (`C`&`NC`, or `P`&`NP`)
   previously had its second face **dropped**. Now both verified faces are **retained as proof** in a
   durable side store, without changing settlement:
   - `store.ts` gained `getProof` / `saveProof` / `getProofSigners` (equivocation proof, keyed by
     `(transactionCode, signerKey)`, deduped by `(type,value)`, capped at `MAX_PROOF_FACES_PER_SIGNER`
     = 4 per signer) and `hasContradiction` / `setContradiction` (a settled-outcome contradiction flag).
   - `retainEquivocationProof(merged, existing, incoming)` (`participant.ts`) keeps both faces **only
     when `incoming` itself verifies** (a forged opposite face is not proof). Called from the
     `existing.type !== signature.type` branch of both `mergeSignature` (promise phase) and
     `promoteCommit` (commit phase), *in addition to* the existing `equivocation` reject. The
     authoritative `promises`/`commits` sets still keep only the first verified face — settlement is
     byte-for-byte unchanged.
   - `detectContradiction(received, merged)` surfaces when our own settled outcome (`commit`/`void`)
     contradicts an incoming copy that settled the opposite way (only reachable when voters
     equivocated). It sets the flag and emits a trace; **no remedy is built** (host policy, ChipNet
     § Lying referees). Read surface: `equivocationProof`, `equivocators`, `contradicts` on both
     `participant.ts` and `engine.ts`.
   - Two new trace variants in `trace.ts`: `equivocation-proof-kept` and `contradiction-detected`.

Harness (`testing/network.ts`): a pull channel (`makeFetchRecord`, resolves immediately on a
microtask — no clock timer — so `await fetchOutcome` settles the puller synchronously; its resulting
pushes still need `runUntilIdle`), plus two node conditions — `refuseRelay` (drops/serves no
**commit**-phase records it would send; still relays promise-phase, so the promise phase completes) and
`silentAfterPromise` (neither sends nor receives commit-phase records). Both already existed as
`InMemoryNetworkConfig` fields; this run threaded them through `consensus.test.ts`'s `NetOpts`/`makeNet`.

## Validation — tests added (the floor)

**Unit (`src/consensus/participant.test.ts`, +3 describe blocks, all green):**
- *Record availability* — (a) complete promise phase alone ⇒ `pending`, no release; `fetchOutcome`
  pulls the voter's settled commit ⇒ `commit`, exactly one release, stored `commits === [voterCommit]`;
  a 2nd `fetchOutcome` is idempotent (no 2nd release). (b) a pull reply carrying a **forged** commit is
  dropped by verify-on-merge (`forged`), puller stays `pending` — a pull cannot inject unverified
  state. (c) `fetchOutcome` on a never-seen tx returns `pending` and calls the stub **0** times.
- *Equivocation proof kept* — both commit faces (`C`,`NC`) retained while the authoritative set stays
  `[C]`; both promise faces (`P`,`NP`) retained; a **forged** opposite face is NOT retained (reject is
  `forged`, not `equivocation`, because `promoteCommit` verifies first).
- *Contradiction* — deliver all-commit (⇒ `commit`, release `[true]`, `contradicts` false), then the
  same voters' all-`NC` faces (they equivocated) ⇒ our outcome **stays** `commit`, `contradicts` true,
  exactly one `contradiction-detected` trace `{ourOutcome:'commit', peerOutcome:'void'}`, still one
  release, `equivocators` lists both voters, `equivocationProof` length 2.

**E2E (`src/testing/consensus.test.ts`, +1 describe block, 5 scenarios, all green):**
- *Interior refuser, linear, WITH contact points* — `O—V—R—F`, R refuses: push settles O,V,R;
  F stranded (`pending`); F `fetchOutcome` pulls O's settled record over O's contact point ⇒ `commit`,
  one release; 2nd pull idempotent; `deliveryErrors === []`.
- *Same WITHOUT contact points* — F's only reachable peer is R (serves no pull) ⇒ F stays `pending`
  even after `fetchOutcome`. (The linear-contrast / "k with no CP" gap.)
- *Circular ring, one refuser, no contact points* — `A—B—C—A`, B refuses: A pushes to both neighbours
  directly, so C is reached over `ca`; whole ring commits.
- *Originator silent post-promise* — `V1—O—V2`, O goes silent after promising: the two voters reach
  2-of-2 over their contact points and commit; O stays `pending`.
- *Payee silent after word reached originator* — `O—A—Z`, Z silent: minting already happened, so O and
  A commit, Z pends.

## Where to push adversarially (known boundaries, honest gaps)

- **The contradiction flag's promise-phase signal is unverified — tripwire, already parked in code.**
  `detectContradiction` classifies the RAW incoming record. Its commit/void-by-**majority** signal is
  verified (`countVerifiedCommits` re-verifies each commit), but a promise-phase void signal (an `NP`
  in `received.promises`) is NOT verified there, so a hostile peer could set the flag spuriously with a
  forged `NP`. This is observational only — settlement is untouched and the flag has no consumer yet
  (its consumer is the future `feat-tallynet-hostile-peers`). A `// NOTE:` is parked at the
  `theirs = …` site in `participant.ts`. **Do not file this as a ticket** — record it in the review's
  `## Review findings` index, and if `feat-tallynet-hostile-peers` ever *acts* on the flag it must
  verify `received`'s `NP` first.
- **The pull is on-demand, not timer-driven.** A node that never received the record cannot catch up by
  pull (no topology to address one). The periodic recovery loop that would call `fetchOutcome` on a
  timer is explicitly out of scope — `tallynet-propagation-timeouts` (a seam). Worth confirming the
  design doc's framing matches.
- **`k > 1` non-cooperating members** is not exercised end-to-end; the guarantee is stated in
  design.md § Contact points / § Record availability as holding only while a voter-majority stays
  assembled and reachable. Scrutinize whether the doc's claim and the single-refuser tests are
  consistent, and whether a 2-refuser cut deserves a `debt-` test later (not filed).
- **Proof cap (4/signer)** is unreachable by honest/verified faces (≤2 per phase) — a hostile-growth
  guard. The forged-face unit test shows a forged face is never stored, but the cap itself is not
  directly asserted at the boundary; a reviewer may want a cap-boundary test (low value — honest paths
  never approach it).
- **`detectContradiction` ordering.** It runs after the `advanceState` loop and before `push`, and
  reads `record` (the raw incoming) which `validateAndMerge` is documented not to mutate. Confirm that
  invariant still holds if `validateAndMerge` is ever changed.
