First of two tickets that split `5.53-tallysim-voter-model`. This one built the **headline "principle-3"
completion curve on straight-line routes**: measure how payment completion falls as more nodes stop relaying the
commit phase, with and without a published contact point to pull the settled record from. The sibling
`tallysim-voter-model` (seq 5.532, same slug) adds circular routes, voter nomination driven as real votes, the
stacked-voter plan-refusal end-to-end, the consensus-threshold override, and the cohesive doc subsection.

"Principle 3" (from the two prereq handoffs): a node that promised then went dark must not strand the payment — a
member the commit push can't reach must be able to **pull** the settled record from a reachable peer (a published
**contact point**, or a link-neighbour). The curve measured here: with contact points, completion stays at 1.0
while ≤ 1 node on a route is a non-relayer; without them, a straight line shows a visible cliff (the dark node's
far side has no path to the evidence).

## Use cases for the reviewer (testing / validation / usage)

The headline metric is `ConsensusRunMetrics.cooperatingCompletion` — of the members allowed to reach commit
(route entities minus non-relayers/silent), the fraction that actually committed — swept against
`consensus.nonRelayerFraction`. New behavioural tests to lean on and probe:

- **Principle-3, linear, WITH contact points** (`consensus-runner.test.ts`): a `line(6)` swept over
  `nonRelayerFraction {0, 1/6}`, `contactPoints: true`; completion holds at `1.0`, `recoveredTotal > 0` (recovery
  actually fired). The selected non-relayer is re-derived in-test (`compileConsensusConditions`) and pinned to
  node 3 (interior).
- **Principle-3, linear, WITHOUT contact points**: same shape, `contactPoints: false`; completion `< 1` (the
  expected gap, framed as documented, not a failure), `recoveredTotal === 0`.
- **Tie ⇒ unsettled** (`voter-harness.test.ts`): a `line(3)` with `{1:{shouldCommit:false}}` and `voters:[0,1]`;
  one commit + one NC reaches neither majority ⇒ `outcome === 'pending'`, no money moved, `deliveryErrors === []`,
  `pendingTimers === 0` (a clean third outcome, not a hang/crash).
- **Determinism**: two runs of a spec with all three new knobs set yield byte-identical records.
- **Metrics aggregation** (`consensus-metrics.test.ts`) + **CSV columns** (`serialize-consensus-records.test.ts`):
  completion/pull/recovered aggregation and the canonical column order are asserted directly.

## Honest gaps / where the reviewer should push (this is a floor, not a finish)

- **The "holds at 1.0" claim is seed-chosen, and for a real reason.** Contact points are stamped on the
  originator and voters only, and the sweep's sole voter IS the originator. If a non-relayer is itself the
  originator of a lift, it serves no pulls, so the members it starts cannot recover and completion dips. The WITH
  test uses `workload.seed 1` **specifically because its 12 queries straddle node 3 but never originate AT node 3**
  (verified by enumerating the drawn pairs); the comment at the test says so. With a seed that does originate at
  the non-relayer, completion lands slightly below 1.0 (observed 15/16 on the original seed 200). This is a true
  property of the model, not a test hack — but a reviewer should decide whether the sweep's y-axis ought to
  exclude lifts whose originator is non-cooperating, or whether contact points should also be published on
  non-originator members. Worth a design note; not filed as a ticket because it is arguably correct as-is.
- **`silentAfterPromiseFraction` is wired but only exercised by the determinism test**, not a dedicated
  silent-node completion test. The port is a thin adapter identical in shape to the tested `refuseRelayFor`, and
  the mechanism is proven at the tallynet level (`tallynet/src/testing/consensus.test.ts` §1187, §1200). Low risk;
  a reviewer could add a silent-originator-vs-silent-payee behaviour test to pin the completion semantics.
- **Trace recorder (`cli/trace.ts`) was deliberately left as-is.** It gets the network ports via the shared
  `consensusConfigFor`, but `recordLift` does not pass `nonCooperating`/`contactPoints` to `runLiftForOutcome`. No
  current trace scenario sets the new fractions, and `TraceLiftEntry` does not capture pull/completion fields, so
  recorded traces are unaffected. When the viewer ticket (`tallysim-viewer-voter-model`) wants these in a trace it
  must thread the per-lift options there too — flagged, not fixed here.
- **Scope deferred to the sibling 5.532 `tallysim-voter-model`** (do not re-review as missing): circular-route
  completion, voter nomination driven as real consensus votes (blocked on
  `debt-voter-nomination-on-path-composition`), the stacked-voter plan-refusal end-to-end through
  `runLiftForOutcome`, the consensus-threshold override, and the cohesive *Voter model* doc subsection —
  **including the still-present superseded "v1 has no recovery" paragraph ≈ `docs/design.md` lines 801–806**, which
  5.532 owns and must rewrite, not just append around.

  ticket's tripwire set). Fine for the small lines/rings this tier runs; batch one drain per round if circular
