`node dist/cli/simulate.js`, committed `out/*.{jsonl,csv}`, a combined `found-vs-oracle.jsonl`, and a

`serialize-sim-records.ts`) are the two prereq tickets' work, consumed as-is.

### The three sweeps

All at one fixed mid-degree topology — `scale-free`, `edgesPerNode = 3` (mean degree ≈ 6), **unlimited**
capacity, 50 queries, seeds `[1, 2]` — so each sweep isolates one variable from capacity gating:

| spec | varies | holds | headline |
|---|---|---|---|
| `depth-sweep` | `D ∈ {2,3,4,5,6}` × `N ∈ {100,1000}` | ideal conditions | `pFoundGivenExists` = 1 everywhere |
| `sleeping-sweep` | `sleepingFraction ∈ {0..0.5}` | `N=100`, `D=6` | pFound ≈ 1 → 0.4 |
| `latency-sweep` | `latency.value ∈ {0..200}` ms | `N=100`, `D=6`, reliability ideal | time grows linearly; pFound/rounds flat |

### The depth reframe (important — do not re-mislabel)

The implement ticket's "critical framing" told me the protocol's reach is ≈ `⌊maxDepth/2⌋+1` and to either
budget `maxDepth` at 2× or label the depth gap as "reach cost". **That framing is stale.** The prereq
`tallynet-discovery-depth-reach` landed first and fixed the simulator-clock bug (`VirtualClock` `DRAIN_QUIET`)
that caused the 2× undercount; `docs/design.md` § "Rounds ↔ hops" now states reach `= maxDepth = L`. The sim
runner already probes the oracle at the *same* depth as the protocol, so the comparison is apples-to-apples.
I therefore did **neither** of the ticket's two options — instead I compared at matched depth and the data
shows `pFoundGivenExists = 1` in every depth/`N` cell: **no reach gap at all**. That is the correct, honest
result and it directly confirms the depth-reach fix. The write-up states this explicitly. (This is consistent
with the recalled note: discovery reach = maxDepth = L; the half-the-ceiling claim was the clock artifact.)

## How to validate

From the repo root:

```
yarn workspace tallysim lint          # clean
yarn workspace tallysim build         # clean (tee'd)
yarn workspace tallysim test          # 273 pass / 23 suites
bash packages/tallysim/experiments/found-vs-oracle/regenerate.sh   # ~30s, rebuilds + regenerates out/
```

All four were run green during implement. The grid runs in ~30s wall-clock (well under the ~10-min
agent-runnable ceiling).

**Byte-identical reproducibility (required, verified):** I ran `regenerate.sh` twice and `diff -rq`'d both
`out/` and the combined file — identical. A reviewer should re-run it once and confirm `git status` shows the
committed `out/*.{jsonl,csv}` and `found-vs-oracle.jsonl` unchanged. If it diverges, that is a determinism
regression (most likely in the `tallynet` clock) and worth a `fix/`.

**Guardrail (required, verified):** every committed record must report `falseFoundCount === 0` (found ⊆
oracle). Quick check: `grep -o '"falseFoundCount":[0-9]*' found-vs-oracle.jsonl | sort | uniq -c` → all 42
records show `:0`. A non-zero count anywhere is a harness/terms bug — stop and file a `fix/`, don't accept the
data.

**Spot-check the shape** (the finding, not a data dump):
- `out/depth-sweep.csv` — `pFoundGivenExists` column is `1` in all 20 rows; `routeExistsCount` climbs with
  depth; `messages.mean` grows with depth and `N` then plateaus at `D ≈ 4–5`; `roundsUsed` stays 2–4.
- `out/sleeping-sweep.csv` — `pFoundGivenExists` falls ≈ 1.0 → 0.87 → 0.78 → 0.57 → 0.48 → 0.39 (seed-averaged)
  while `routeExistsCount` holds at 50 (oracle on the full network); `nodesTouched.mean` falls 22 → 5.
- `out/latency-sweep.csv` — `pFoundGivenExists` pinned at 1, `roundsUsed` flat (mean ≈ 1.5, max 3),
  `timeToCompletionMs.mean` ≈ 0 → 21 → 106 → 213 → 426 (linear in latency; max = latency × 6).

## Known gaps / honest flags (reviewer: treat as a floor)

- **Unlimited capacity only.** All three specs hold capacity unlimited to isolate the swept variable. A
  realistic-capacity discovery sweep is the natural next cut and is **not** done here. I did not empirically
  confirm whether greedy distributed search diverges from the oracle under finite capacity — my reasoning is
  that the per-hop `capFwd ≥ amount` check is identical on both sides so a full-budget BFS should still match
  (pFound ≈ 1), but that is an untested hypothesis. Candidate `feat-`/`debt-` follow-up, not filed (no
  evidence of a defect, and the ticket scoped this experiment to the clean-variable cut).
- **Depth sweep exhibits no gap by construction.** Because reach = maxDepth and capacity is unlimited,
  `pFoundGivenExists = 1` across the whole depth sweep. That is the intended demonstration (the reach fix), not
  a bug — but it means the only sweep that exercises a real found-vs-oracle *gap* is the sleeping sweep. If a
  reviewer wants the depth sweep to show a gap, that needs degradation or finite capacity, i.e. a different
  experiment.
- **`roundsUsed` is latency-*independent*, not "growing".** The ticket's phrasing anticipated rounds growing
  with latency; the data shows rounds are depth-bound and flat across latency. I reported the actual shape
  (flat) rather than the anticipated one. Worth a reviewer's eye to confirm that reading is right (it is:
  latency changes *when* a round's deliveries arrive, not *how many* rounds the search needs).
- **Short hub paths keep `roundsUsed` at 2–4** even at `D = 6` (scale-free). A `uniform` topology (longer
  paths) would exercise deeper rounds; not swept here. Topology is held fixed on purpose.
- **No unit test pins these committed specs.** The `falseFoundCount === 0` guardrail is asserted in
  `sim-runner.test.ts` on its own seeded runs, but nothing asserts it on *these* committed outputs — the
  experiment is checked-in data regenerated by a shell script, like `route-existence/`. A tiny smoke test
  (run one spec, assert guardrail) would be cheap hardening if the reviewer wants belt-and-suspenders; I
  followed the sibling experiment's precedent and did not add one.
- **Combined `found-vs-oracle.jsonl` is heterogeneous** — the three sweeps carry different `params` keys, so a
  reader keys on which coordinates a record has to tell them apart. Self-describing, but not a uniform table
  like `route-existence.jsonl`. Documented in the README.
