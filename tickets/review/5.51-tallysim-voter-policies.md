## What this ticket built (the pure voter-model policy layer)

Four small, independently-tested pure functions — data in, decision out, no clock/network/harness wiring. Wiring them into the running simulator is the **next** ticket (`tallysim-voter-harness-drive`); the sweep runner/metrics/CLI/docs are the one after (`tallysim-voter-model`).

Vocabulary (used throughout): a **voter** signs commit (`['V']` or `['P','V']`); a **referee** is a `V`-only voter (votes but rides no tally edge — vouches off the money path); a **well-known** node is one the network recognises, made measurable here as a **high-degree hub**; a **stacked** voter set is one padded with obscure (unrecognised) referees to game the quorum.

### 1. `wellKnownEntities(network, fraction)` → `Set<number>` (`well-known.ts`)
The `round(fraction · entityCount)` highest-degree entities, ties broken by lower id. `fraction ≤ 0` ⇒ empty; `≥ 1` ⇒ all. **Deliberate departure from the original ticket:** "well-known" is *derived from degree*, not marked in the `Network` model — a model flag would ripple through serialisation and perturb the pinned byte-identical discovery sweep. This keeps the model untouched and makes "trusted = a hub" observable. (The original ticket said "mark in the generators"; its own `files:` list excluded `generators/`. Document this choice in the `tallysim-voter-model` doc update.)

### 2. Voter-aware plan ranking (`plan-select.ts`)
- `PlanPolicy` gains `'voter-aware'` alongside `'shortest'` (unchanged).
- `selectPlan(plans, policy, wellKnown?)` — grew the optional `wellKnown` arg. `'voter-aware'` ranks by a single scalar penalty: **fewer voters ≫ fewer obscure voters ≫ shorter path ≫ first-found**. Omitted `wellKnown` ⇒ every voter obscure ⇒ degrades to fewer-voters-then-shorter.
- `voterAwareScorePlan(wellKnown)` — a `tallynet`-shaped `ScorePlan` (higher=better) the next ticket hands `buildSimNetwork` as the originator's scorer. Shares the one penalty core with `selectPlan`, so both order any plan set identically (the hop-bound differs — `selectPlan` uses max hops of the set, the scorer uses `query.maxDepth` — but the order is bound-independent).

### 3. Stacked-voter refusal (`consensus-resource.ts`)
- `StackedVoterPolicy` { `wellKnown`, `memberEntity`, `obscureTolerance?=0` } + the pure predicates `obscureRefereeCount(members, policy)` and `refusesStackedVoterSet(members, policy)`. Counts only **V-only referees** whose entity is not well-known; a `[P,V]` voter is on the money path, not padding, so it is never counted.
- `SimResourceSpec.refuseStackedVoters?: StackedVoterPolicy` installs an `acceptsProposal` gate that returns `false` (signs `NP` → voids the lift) when the record's `topology.members` is stacked. Each refusal increments the new `SimResourceHandle.voterSetRefusals`, distinct from an ordinary `shouldPromise:false`.
- The predicate is the single thing both enforcement points call: promise-time `acceptsProposal` (here) and discovery-time `negotiatePlan` (next ticket). The `nonRelayer` concern the original ticket mislabelled was **not** added — it is a `tallynet` harness config (`refuseRelay`), wired in the next ticket.

### 4. Referee nomination builder (`well-known.ts`)
`makeNomineesFor(network, wellKnown, policy)` → `(entityId) => RefereeNomination[]` (tallynet's `{ name, physical? }` shape, keyed by node **name**). `'self'` ⇒ each node nominates itself as voter; `'well-known'` ⇒ every node nominates the single highest-degree hub in `wellKnown` (empty set ⇒ nominates nobody).

All new symbols are exported via `sim/index.ts`.

## Known gaps / what a reviewer should probe

- **No end-to-end wiring exists yet** (by design). Nothing proves a stacked set *actually* voids a real lift in the harness, or that `voterAwareScorePlan` *actually* reorders discovery output — those are the next ticket's integration tests. Treat these as unit-verified building blocks only.
- **The `memberEntity` seam is the integration risk.** `acceptsProposal` runs on a **consensus record**, whose member keys are **ed25519 keys**, not entity ids — so the real gate needs the harness's key→entity bijection, which the next ticket must supply. These tests pass `Number(key)` as the mapper. If the next ticket forgets the real bijection, every voter resolves to `NaN` → "obscure" → the gate refuses *everything*. Verify the next ticket wires a real key→entity map.
- **`voterAwarePenalty` reads `Number(member.address.key)` inline** (no mapper). This is correct **only** because discovery-plan member keys ARE node names (the sim names a node `String(id)`). It would silently misclassify if ever pointed at a consensus record. Parked as a `NOTE:` in `plan-select.ts` at the function; it is a soft ranking (never a hard refusal), so a misread degrades ranking, it does not void anything.
- **Hop-bound assumption** (`hops ≤ hopBound`): both call sites satisfy it today; parked as a `NOTE:` at `voterAwarePenalty`. Not currently violatable (the originator caps `path.length ≤ maxDepth`).
- **`'well-known'` nomination is "one global hub for everyone."** Deliberate (a single trusted third-party voter), but a reviewer may want to confirm that is the intended model vs. e.g. nearest-hub-per-node (which would need graph distance). Easy to change in isolation if not.
