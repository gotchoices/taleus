## What changed (Half A of the split from `tallysim-timeout-harness-metrics`)

The lift simulator used to drive a **manual pull pass** (`recoverStrandedByPull`) after the single
`net.clock.runUntilIdle()` in `runLiftForOutcome`, pulling the settled record onto any member an interior
non-relayer had cut off from the commit push. The prereq `tallynet-stalled-recovery` moved recovery *into the
protocol*: `VirtualClock.runUntilIdle()` fires every live timer until the heap empties, so the protocol's own
deadline one-shot and periodic recovery-loop ticks already fire inside that one drain. The manual pass therefore
"legitimately found nothing" (the 6.2 review had already flipped the tallysim tests' `recovered`/`pullCalls`
expectations to `0`). This ticket **removes** the manual pass and adds two per-experiment knobs.

### The actual diff

- **`consensus-harness.ts`** — deleted `recoverStrandedByPull` + its call site. `runLiftForOutcome` now reads the
  settlement off the originator straight after `runUntilIdle`, with no pull pass. Added `RunLiftOptions.ttlMs?`
  (threaded into `net.buildLift` as `...(options?.ttlMs !== undefined ? { ttlMs: options.ttlMs } : {})`, so the
  no-ttl path is byte-identical). Module header + the `LiftResult.pullCalls`/`.recovered` field docs updated.
- **Deliberately left in place:** `LiftResult.pullCalls` / `.recovered` still exist and are hard-coded to `0`.
  This is the split boundary — it keeps `consensus-metrics.ts` (reads `result.pullCalls`, `result.recovered`,
  `lift.recovered`) and the existing `voter-harness.test.ts` assertions (`recovered === 0`, `pullCalls === 0`)
  compiling and green with **no edit**. **This ticket did NOT touch** `consensus-metrics.ts`,
  `serialize-consensus-records.ts`, or their tests.
- **`harness.ts`** — added `ConsensusConfig.recoveryGiveupMs?`; `buildSimNetwork` now passes
  `recoveryGiveupMs: consensus?.recoveryGiveupMs ?? SIM_RECOVERY_GIVEUP_MS` (the 60_000 ms constant is kept as
  the default).
- **`scenario.ts`** — added `ConsensusSpec.ttlMs?` and `ConsensusSpec.recoveryGiveupMs?`.
- **`consensus-runner.ts`** — `runConsensusQueries` spreads `ttlMs` into the hoisted `liftOptions`
  (spread-only-when-set); `consensusConfigFromCompiled` sets `config.recoveryGiveupMs` only when the scenario
  supplies it. `cloneConsensus`'s `{ ...consensus }` already deep-copies these scalars (no new clone line), and
  `validateConsensusSweep` already permits `consensus.*` vary paths (both knobs are varyable with no change).

## How it was validated (tests are a floor, not a ceiling)

`yarn workspace tallysim build && lint && test` all green — **426 tests, 34 suites**. Three new tests in
`consensus-harness.test.ts` (`runLiftForOutcome — protocol self-recovery and the ttl / give-up knobs`):

- **Stranded members self-heal (manual pull gone).** `line(5)`, `refuseRelayFor: id === 2`,
  `{ contactPoints: true, nonCooperating: [2] }` ⇒ `commit`, every node `0..4` reads `commit` (the protocol loop
  heals 3 and 4 over node 0's contact point, all inside `runUntilIdle`), every tally `-5`, `deliveryErrors === []`,
  `pendingTimers === 0`, and `pullCalls === recovered === 0`.
- **`ttlMs` threads to the mint (exact-delta).** No contact points ⇒ 3,4 run recovery to abandonment. The whole
  tick schedule anchors on the **transaction code's** expiry (`safeExpiry` → `sessionCodes.expiresAt(transactionCode)`),
  and the sim mints that code fresh with `ttlMs` while *reusing* the discovery session code — so
  `finalClock(700_000) - finalClock(100_000) === 600_000` exactly (mintTime is ttl-independent under ideal
  conditions). This is the one latency-free proof `ttlMs` reached `buildLift`.
- **`recoveryGiveupMs` threads to the loop (monotonic).** Same stranded line; a larger give-up window runs
  strictly more backoff ticks: `finalClock(500_000) > finalClock(50_000)`, with the originator committing and
  3,4 staying `pending` in both.

### Reviewer's eye — where to look hard

- **The exact-delta claim (test 2)** rests on: (a) the deadline anchoring on the transaction code, not the reused
  session code — verified against `participant.ts:scheduleRecoveryTick`/`safeExpiry`; (b) `mintTime` being
  identical across the two `ttlMs` runs because `ttlMs` never touches discovery. If either were false the delta
  would not be exactly 600_000. Worth a sanity re-read.
- **No behavioural change from removing the pass.** The claim is that after `runUntilIdle` nobody the manual pass
  would have recovered is still pending, so reading `settled` with the pass gone is identical. The green
  `voter-harness.test.ts` (unedited) is the existing evidence; confirm nothing else depended on the pass's clock
  side-effects.
- **Spread-only-when-set byte-identity.** `ttlMs`/`recoveryGiveupMs` are each threaded only when defined, so a run
  that sets neither should produce exactly the pre-existing calls. Confirm the `!== undefined` guards (not truthy
  checks) so a deliberate `0` would still thread — though `0` is nonsensical for either knob.
