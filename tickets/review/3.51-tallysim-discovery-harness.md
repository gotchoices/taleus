## What was built

The discovery-simulation **wiring** that joins tallysim's two tiers — the all-seeing **oracle** (ground
truth: *does a route exist*) and the real decentralised route-discovery protocol (`tallynet`) — so an
experiment can measure whether the protocol finds the routes the oracle proves exist. It turns a tallysim
`Network` into a running `tallynet` discovery network on compressed, deterministic time, gives each node a
local-only capacity view equal to the oracle's directed-edge capacity, imposes network conditions, and runs
one payment query to completion.

The discrete-event scheduler was **not** rebuilt — this consumes `tallynet/testing`'s `VirtualClock` +
`InMemoryNetwork`. Everything simulator-specific lives in `tallysim/src/sim/`.

New/changed code:
- `sim/naming.ts` — the one node↔entity bijection (`entityName`/`entityId`) + `linkIdForTally`.
- `sim/terms.ts` — `LiftTerms`, `invertLiftTerms`, and `makeCapacityHooks()` (overrides only the two
  capacity checks of `tallynet`'s default hooks).
- `sim/conditions.ts` — `compileConditions(network, spec, seed)`: count-based (not Bernoulli) selection via
  seeded partial Fisher–Yates; precedence sleeping(drop) > late(lateLatencyMs) > dropFraction(drop) > base
  latency; drawn from a dedicated seed stream so session codes stay stable.
- `sim/harness.ts` — `buildSimNetwork` + `runQuery` (discover-then-drain) + `SimNetwork`/`QuerySpec`/`QueryOutcome`.
- `sim/index.ts` — barrel.
- `workload.ts` (new) — `materializeNetwork`/`drawAmount`/`drawPaymentPair` extracted verbatim from
  `runner.ts` so both tiers share one materialiser/draw; `runner.ts` rewired to import them.
- `distributions.ts` — `uniformInt`/`lognormalSample` now exported (DRY; additive, no behaviour change).
- `index.ts` — exports `./workload.js` and `./sim/index.js`.
- `docs/design.md` — new `## Discovery simulation` section (left the `## Trace & replay format` stub for
  the trace ticket).

## Validation performed

`yarn workspace tallysim build` + `test` + `lint` all pass. **199 tests, 16 suites, 0 failures.** Lint
clean. Tests added: `sim/terms.test.ts`, `sim/conditions.test.ts`, `sim/harness.test.ts`.

The correctness anchor — **found ⊆ oracle** — is tested on seeded `uniform` graphs with no conditions: for
every plan the protocol returns, the oracle confirms the route exists within the matched depth, every hop's
forward capacity ≥ amount, and `path.length ≤ depth`. Hand-built graphs (line, diamond, unreachable/isolated
target, zero-capacity gate) assert exact `found`/plans. Reuse + per-query-amount is tested on one network.
Conditions tests assert determinism, exact counts, incidence, and precedence.

## The headline finding the reviewer MUST weigh (and the metrics ticket depends on)

**The protocol's effective reach is ~half its `maxDepth`, not `maxDepth − 1`.** The earlier investigation
(and a prior memory note) claimed peer-match reach = `maxDepth − 1`. That is **wrong** — I verified it
empirically against several chain lengths:

| hops L | 1 | 2 | 3 | 4 | 5 |
|--------|---|---|---|---|---|
| min `maxDepth` that finds an L-hop route | 1 | 2 | 4 | 6 | 8 |

So `maxDepth ≥ 2(L − 1)` for `L ≥ 2`, i.e. reach at ceiling `D` is `⌊D/2⌋ + 1` hops. `tallynet`'s own
`maxDepth boundary` test only checks one data point (L=3, depth 3 vs 4), which cannot distinguish `2(L−1)`
from `maxDepth − 1`; the longer chains do.

This is **intrinsic `tallynet` behaviour** (it reproduces with the default hooks, ample capacity, zero
latency — nothing my capacity hooks or harness add), parked in `docs/design.md` § Discovery simulation
(architectural, no single code site). The `found ⊆ oracle` guarantee holds regardless — the protocol simply
*undercounts* oracle-reachable routes, more than previously believed.

**For the reviewer:** decide whether this ~2× cost is expected `tallynet` reentrance cadence or a latent
inefficiency worth a `tallynet` ticket. It is out of scope to fix here, but it is a real, measured
characteristic. **For the metrics ticket (`tallysim-discovery-metrics`):** a depth sweep expecting the
protocol to match the oracle's depth must budget `maxDepth ≈ 2 × hop distance`, or the "found vs oracle"
gap will read as far worse than the network actually is.

## Known gaps / things to probe harder (your tests are a floor, not a ceiling)

- **A sleeping *target* does NOT block a route** — a neighbour resolves the peer-match from its own
  adjacency without ever delivering to the target; only a sleeping non-target **relay** blocks. The
  degradation-gap test therefore pins a seed (line(4), seed 0) that sleeps the relay node 1, and asserts the
  sleeping set is `{1}` so it fails loudly if the RNG/selection changes. Worth a harder look: is this
  peer-match-escape the right model for "a payee that is offline"? (Arguably a real offline payee *should*
  make the payment unfindable — but that is a protocol-semantics question, not this wiring's bug.)
- **The late-node test numbers were tuned empirically** (`lateFraction: 1`, `lateLatencyMs: 3000`,
  `maxDepth: 8`, default `sessionTtlMs`), not analytically derived. It asserts only that a route *is still
  found* when a large latency exceeds a round budget; it does not characterise the latency ceiling beyond
  which the session expires. Push on the budget/TTL interaction.
- **Sleeping/late is an undirected approximation** (both incident links carry the condition). Documented;
  acceptable for a per-link surface, but confirm it matches how the metrics ticket wants to attribute a
  degraded node.
- **Byte-identical oracle-runner output after the `workload.ts` extraction** rests on the `runner.test.ts`
  determinism tests (they pass) and the draw-order being preserved (`from`, `to`-loop, `amount`). I did
  **not** separately diff the committed `experiments/route-existence/out/*` fixtures — the determinism tests
  are the proxy. Worth a direct check if you want certainty.
- **Session-code seed** is a fixed module constant (`SESSION_CODE_SEED = 1`) in `harness.ts`; outcomes don't
  depend on session-code values (only nonces do), so this is safe, but it means every `SimNetwork` shares
  the same session-code stream — fine for this tier, flagged in case a future multi-run harness wants it
  parameterised.
