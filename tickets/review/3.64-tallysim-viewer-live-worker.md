## What this ticket built

The **engine half** of the viewer's live-run feature: generate a tally network and run the real `tallynet`
route-discovery search *in the browser* (no server, no Node), streaming the run's trace envelope back to the
page so it feeds the same replay view a recorded trace file does. The **page half** (the form, click-to-pick,
`new Worker(...)`, wiring the stream into the replay) is the sibling ticket **`tallysim-viewer-live-controls`**
(seq 3.66, `prereq: tallysim-viewer-live-worker` → this slug). Read that ticket too — together they are the
original "live run" feature.

Three files, all under `packages/tallysim-viewer/src/live/`:

- **`build-scenario.test.ts`** (new) — the ticket's one real headless test; jest. Covers the pre-existing
  `build-scenario.ts` (form values → `SimScenario` + `QuerySpec`).
- **`sim-protocol.ts`** (new) — the **type-only** worker↔main `postMessage` union (`MainToWorker` /
  `WorkerToMain`). No runtime code; shared source of truth for both sides.
- **`sim-worker.ts`** (new) — the worker: `generate` (materialise the network, reply with its snapshot) and
  `run` (build a fresh `buildSimNetwork`, `runQuery`, stream `header` → `event`… → `done`).

`build-scenario.ts` was already written and type-checked before this ticket; it was **not** rewritten — only
tested. (If a reviewer edits it, re-confirm `buildLiveRun`'s `runSeed === 0` invariant, which the worker's
header stamping assumes.)

## ⚠️ The honest gap — the worker has NO runtime test

`build-scenario.test.ts` is the floor, and it only exercises the **pure translation helper**. The worker
(`sim-worker.ts`) and the `postMessage` streaming are **browser-only**: the sole automated coverage they have
is that they **type-check and vite-build**. No test instantiates the worker, drives a `generate`/`run`, or
asserts the message stream — and nothing *imports* the worker yet (the sibling controls ticket wires
`new Worker(...)`), so even at runtime it is currently dead code awaiting its consumer. **Treat the worker body
as a careful-read target, not a tested surface.** Reviewer attention is best spent confirming the control flow
below by reading, since no assertion guards it:

- **Header-from-first-event.** A session code is minted *inside* `discover()` and is not knowable
  synchronously. The sink builds + posts the `header` on the **first** event (then that event and all later
  ones). Confirm: header is posted **before** any `event` message; the header's single query entry is
  `{ sessionCode, ...query }` with the event's `sessionCode`.
- **Zero-event degenerate runs.** `< 2 entities`, an edge-less generator, or `from === to` can emit **zero**
  events → the sink never fires. After `runQuery` resolves, if no header was posted, it is posted from
  `outcome.sessionCode`. Confirm a header is *always* posted before `done`, so the page can build an index.
- **Routes for the found list.** `done.routes = outcome.plans.map(p => ({ from, to, linkNonces: path nonces,
  terms: path intents }))`. This is how the live source lights the **full** found-routes list with exact-path
  isolate (a recorded trace can't — `plan-found` is path-less). Confirm `linkNonces`/`terms` are index-aligned
  (same `plan.path` order) and that a self-payment loop's path nonces ride through.
- **Error isolation.** `generate`/`run` are each wrapped; a throw posts `{ type:'error', phase, message }` and
  the promise from `handleRun` is `void`-ed so it never rejects unhandled. Confirm the worker cannot die
  silently (the controls surface `error` as a message).
- **`run` before `generate`** (no kept network) throws → posts `error` phase `run`. Confirm.

## Design decisions made during implementation (review these)

- **Fresh `buildSimNetwork` per Run, kept `network` across runs** (a slight departure from the original
  single-ticket's "one `InMemoryNetwork` serves many queries" phrasing). Rationale: a fresh `buildSimNetwork`
  restarts the session-code RNG at its fixed seed, so **each** live run byte-matches a `tallysim trace`
  single-query trace of the same seeds — the cleanest reading of "same params + seed ⇒ byte-identical trace".
  The expensive, user-visible reuse (rendered graph + settled layout) is preserved on the main-thread side.
  The generated `network` is read-only this tier (no balances move), so keeping it is safe. If a future
  reviewer prefers literal one-`InMemoryNetwork`-per-many-queries reuse, swap the per-run `buildSimNetwork` for
  a mutable trace-sink indirection into a single long-lived network.
- **Worker-scope typing without the `WebWorker` lib.** The viewer's tsconfig uses `lib: [ES2022, DOM,
  DOM.Iterable]` (no `WebWorker` — it conflicts with DOM), so `DedicatedWorkerGlobalScope` is out of scope.
  `self` is cast to a minimal `{ postMessage; addEventListener }` shape (all from the DOM lib). This
  type-checks with no lib change; verify the cast is still the lightest option if the reviewer dislikes it.
- **`VIEWER_VERSIONS` = `{ tallysimVersion:'0.1.0', tallynetVersion:'0.1.0' }`** — stamped into the header's
  two version fields. See the tripwire below: these are provenance only.

## Tripwires noted (knowledge, not queued work)

- **`VIEWER_VERSIONS` are hand-maintained provenance strings** that do not auto-track the bundled
  `tallysim`/`tallynet` package versions. Fine now: `parseTrace` validates only `traceFormatVersion`, never
  these two — they record which viewer build produced a live run, nothing reads them on load. Parked as a
  `NOTE:` at the constant in `sim-worker.ts`. *If* exact provenance is ever wanted in downloaded traces, read
  the real versions at build time (Vite `define`) instead of the literal.

## Use cases to validate (manual, in the sibling controls ticket)

These are browser-only and land with `tallysim-viewer-live-controls`; listed here so the reviewer knows what
"working" means for this engine:

- **Happy path.** Pick a generator + params + seed → Run → graph animates the search spreading → a found route
  (if any) appears in the found-routes list and isolates its exact path on select.
- **Determinism.** Same params + seed in the viewer vs. `yarn workspace tallysim trace <scenario.json>` → the
  streamed events byte-match the recorded single-query trace.
- **Self-payment** (`from === to`): the closed loop draws from its path nonces; no throw.
- **Degenerate network** (`< 2 entities` / edge-less generator): `found:false`, empty routes, no throw, a
  header still arrives so the page builds an index.
- **Worker failure**: an error in generate/run surfaces as a clear message in the controls, never a hang.
- A **headless-browser smoke test** of the worker + streaming stays deferred (per the original ticket).
