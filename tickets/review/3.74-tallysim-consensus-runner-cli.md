## What was built (implement summary, verified against the diff)

The **sequential consensus sweep runner** — the consensus counterpart to the existing discovery
`sim-runner.ts` — plus its serialiser and a Node CLI. All four new modules were created and wired; build,
lint, and the full tallysim test suite pass (368 tests, 32 suites).

- **`sim/consensus-runner.ts`** — `runConsensusSweep(spec)` (async generator, one `ConsensusRunRecord` per
  `cell × seed`), `runConsensusSweepToArray`, and the `ConsensusRunRecord` type (same provenance shape as
  `SimRunRecord`; `metrics` is `ConsensusRunMetrics`). For each run it **clones** the materialised network
  (`cloneNetwork(materializeNetwork(...))`), draws the payment workload, then drives each query to a settled
  lift: `buildSimNetwork` → `runQuery` (discovery) → `runLiftForOutcome` (sign-and-settle, mutates balances
  on commit) → `analyzeLift`, finally `summarizeConsensusMetrics`.
- **`serialize-consensus-records.ts`** — `consensusRecordToJsonLine` / `…ToJsonLines` / `parseConsensusJsonLine`
  / `createConsensusCsvAccumulator` / `consensusRecordsToCsv`, reusing the generic machinery in
  `serialize-records.ts`; the only new thing is the consensus CSV column order.
- **`cli/consensus.ts`** — `parseArgs` / `runToOutputs` / `ConsensusSinks` / `fileSinks` / `main`, modelled
  on `cli/simulate.ts` **minus `--concurrent` and `--trace`**. Flags: `<spec.json> [--jsonl <out>] [--csv <out>]`.
- **Wiring** — `src/index.ts` (+`serialize-consensus-records`), `src/sim/index.ts` (+`consensus-runner`),
  `package.json` (+`"consensus": "node dist/cli/consensus.js"`).

## The three load-bearing design decisions (confirm these in review)

1. **Sequential only — no concurrent mode.** A committed lift moves `tally.balance` on the ONE kept network,
   and the next query must see that; so lifts form an ordered sequence and balances between two lifts are
   defined only under a fixed order. The discovery runner's `concurrent` dep is deliberately absent here
   (offering it would make balances order-dependent). Documented at length in the module header.

2. **Deliberate duplication of the sweep-plumbing helpers.** `cloneSimScenario`, `cloneConditions`,
   `cloneCapacity`, `applyVary`, `validateConsensusSweep` are **copied** from `sim-runner.ts` (where they are
   private) rather than extracted to a shared module — per the implement ticket's instruction, to keep the
   pinned byte-identical discovery sweep untouched. **A reviewer may legitimately prefer extracting a shared
   `sweep-clone.ts`.** This is the single biggest "confirm the call" item. If extraction is wanted, it is a
   mechanical refactor touching both runners + their determinism tests — better as its own `fix/` ticket than
   inline, since it re-touches the pinned discovery path.

3. **`validateConsensusSweep` prefix widening.** `sim-runner`'s guard allows only `workload.*` vary paths for
   a *materialised* network. This runner widens that to accept `workload.` / `conditions.` / `consensus.`
   prefixes, because a materialised consensus scenario legitimately varies `conditions.dropFraction` /
   `consensus.refuserFraction` (both are cloned one level deep so the vary is isolated). Structural
   network params still can't be varied on a materialised network (it's shared by reference, exactly as
   discovery does). **Confirm this is the behaviour the CSV x-axis wants.** (For a *generated* network there
   is no restriction at all — the end-to-end CLI check below varies `consensus.refuserFraction` over a
   generated network and it works.)

### Why those seeds (so a reviewer can re-derive them)

Seed selection was done with a throwaway sweep over `conditionsSeed` / `consensusSeed` / run-seed that printed
`pendingCount` / `voidReasons`, then the first satisfying combo was hardcoded and the scratch deleted. The
committed tests are therefore deterministic and fast. To re-verify a seed, run the spec and read
`records[0].metrics` — the refuser/sleeping node is a pure function of the seed via `compileConsensusConditions`
/ `compileConditions`.

**The stall mechanism (the subtle part):** a route to a *sleeping* target is **findable but un-pushable**.
Discovery forms a plan to node T when T's awake neighbour reports `peerMatch` (without T responding), so a
sleeping T (both its links `drop`) is still discovered. But the consensus push to T is dropped, so T — a
participant — never promises ⇒ not-all-promised ⇒ the lift stays `pending` (`voidReason 'stalled'`). A sleeping
node also cuts the line, so queries straddling it simply don't route (no lift). The test needs ≥ 1 query that
*targets* the sleeping node; the pinned `workload.seed 200` + run seed 1 supplies that.

## Known gaps / things the reviewer should probe (your tests are a floor)

- **Only line topologies are tested.** The behavioural tests use hand-built lines for predictable routes.
  Real sweeps run generated networks (uniform/scale-free/clustered/small-world); the end-to-end CLI check
  above exercises a generated uniform network, but there is **no checked-in test over a generated network in
  the runner suite**. A reviewer wanting more confidence could add a generated-network determinism case.
- **No `queryCount === 0` / sub-two-entity runner test.** The degenerate guard (`entityCount < 2` ⇒ fully
  zeroed `ConsensusRunMetrics` via `summarizeConsensusMetrics([], structural, 0)`) is implemented and mirrors
  the discovery runner, but is not directly unit-tested at the runner level (it is covered indirectly by the
  metrics module's own zero-lift tests). Cheap to add if wanted.
- **Keygen-per-query cost.** The runner rebuilds `buildSimNetwork` (and thus re-derives consensus identities)
  once *per query*, because an already-built `InMemoryNetwork` freezes link capacity and can't see a committed
  balance change. This is fine for the small grids this tier runs (~tens of queries). Recorded as a `NOTE:`
  tripwire at the rebuild loop in `consensus-runner.ts` (`runConsensusQueries`): if a grid grows large, cache
  the consensus identities / nodes across rebuilds. **Not a ticket** — conditional on grid size.
- **`timeToSettleMs` spans to the last consensus event**, which may be a post-`settled`
  `resources-released` (so it's really time-to-completion, cleanup included). That is a property of the
  prereq `analyzeLift`, carried through unchanged here — flagged in `consensus-metrics.ts`'s own comment; not
  this ticket's to change.
