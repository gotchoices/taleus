Second of three `tallynet-consensus` tickets (`tallynet-consensus-core` → **this** → `tallynet-consensus`). The core (record model, canonical signed preimage, sign/verify, store, trace events) is already reviewed and in `complete/`. This ticket added the **state machine** — the per-node logic that ingests a record, merges it by signature union, advances our own state (promise / vote / release), and pushes it onward — plus its unit tests. The network harness and end-to-end multi-node scenarios are the final ticket (`implement/3.2-tallynet-consensus`), which depends on this slug.

Treat the tests as a **floor, not a finish line.** They are pure single-node unit tests; the whole multi-node propagation dimension is deliberately untested here (see *Gaps* below).

## What was built

- **`src/consensus/resource.ts`** — the host resource port (`OurLink`, `ResourceContext`, `TrxParticipantResource` with `shouldPromise?` / `promise` / `release` / `shouldCommit?` / `resolveAttachment?`). ChipNet's ordering bug is fixed: the gate (`shouldPromise`) runs **before** the hold (`promise`), so a declined promise holds nothing. `resolveAttachment` is where the Taleus referee's opaque per-edge signatures ride on the vote.
- **`src/consensus/participant.ts`** — the `TrxParticipant<TTerms, TPayload>` class: `update` → `validateAndMerge` → `advanceState` loop → `push`. New-record validation via an explainable `RuleSet`; the per-signer phase rules; `getRecordState` (two phases, strict majority both ways, tie handling); promise/vote/release with the fixed ordering; membership/link resolution (circular-lift safe); reachability + push with a per-peer unchanged-copy skip. All time flows through an injected `Clock`; all events through a wrapped `TraceSink`.
- **`src/consensus/index.ts`** — re-exports `resource.ts` and `participant.ts` (still internal; the public `src/index.ts` barrel ships with the final ticket).
- **`src/consensus/participant.test.ts`** — new, **39 tests** (the single new suite; the prior implement run wrote the source and left tests as the remaining work).
- Two trivial lint-only fixes to the prior run's source that had never been linted: dropped an unnecessary `as 'P' | 'NP'` assertion in `participant.ts` (control-flow already narrows it) and a redundant `unknown | Promise<unknown>` → `unknown` return type in `resource.ts`. No behaviour change.

## How it was validated

`yarn workspace tallynet build && yarn workspace tallynet test && yarn workspace tallynet lint` — **all three green.** 282 tests / 20 suites total (243 → 282; the +39 are all in `participant.test.ts`). The platform-neutrality guard (`no-node-globals.test.ts`) scans the new source and passes — the engine uses no `Date.now`/`setTimeout`/`Math.random`/`Buffer`/node imports (time via the injected `Clock`).

### Test harness (what a reviewer is building on)

Pure single-node tests. Real `@noble/curves` ed25519 signer/verifier (copied from `signature.test.ts`), a `MemoryTrxStore`, an **injected mutable clock** (`makeClock` — no fake timers, since the engine owns no timer; its `setTimer`/`clearTimer` are wired to throw so any accidental timer use fails loudly), a recording trace sink + logger + `updatePeer` stub, and a configurable `TrxParticipantResource` double (cooperative holder, `shouldPromise:false` refuser, throwing `promise`, `always-throw`/`throw-once` release, `shouldCommit` gate, `resolveAttachment`). Records are hand-built per test; `generate()` mints real session codes valid at a fixed `NOW`.

### Use cases exercised (one test each unless noted)

- **Construction** — rejects a signer whose key ≠ `self.key`.
- **First-sight validation (the new-record `RuleSet`, all throw):** expired transaction code; expired session code; empty referee set; empty participant set; duplicate member entry; a link referencing a non-member; our own participant member riding no link (self-inconsistent).
- **Signature-merge rejections (record otherwise unharmed):** forged promise; non-member signer; promise from a referee-only member (wrong-role); commit from a non-referee (wrong-role); type-substitution P→NP arriving fresh (→ `forged`); replay from another transaction with the same topology (→ `forged`); a changed value for the same phase (→ `changed`, first kept); identical re-delivery deduped silently; a differing immutable core (→ `core-mismatch`, whole update throws, stored copy unharmed).
- **Promise phase:** cooperative → signs `P` then waits; declined gate → `NP`, nothing held; throwing hold → `NP` + log; expired-at-promise-time → `NP` without attempting the hold (seeded by first sight, then clock advanced past expiry).
- **Commit phase / settlement:** solo [P,R] node cascades promise → commit (carrying its `attachment`) → release(true) in one update; solo `shouldCommit:false` → `NC` → release(false); expired-at-commit-time → `NC` without consulting the gate; **out-of-order commit** retained unverified across delivery 1, then verified-and-counted once the last promise lands in delivery 2.
- **Referee set sizes:** set of 2 on one vote → no settle; set of 2 split 1C/1NC → settles **neither** way (the even-split fix); set of 3 → settles on the second concurring vote. (Set of 1 is the solo test.)
- **Equivocation:** a referee signing a genuine second opposite face is refused on merge (`equivocation`), the first face stands, logged; for a sole referee the first face wins and a later opposite face cannot re-settle.
- **Lifecycle / release-once:** re-delivery after settlement does not re-release; a fresh participant over the same store (restart **after** release) does not re-release; a restart **before** release (settled record persisted, flag unset) releases exactly once on recovery; a `throw-once` release re-throws (the update rejects), leaves the flag unset, and on retry releases exactly once — never twice.
- **Reachability / push:** pushes to reachable peers, suppresses an unchanged re-push, re-pushes once the signature set changes; a failing push logs and emits `record-pushed` `ok:false` and is not retried in-band.
- **Topology:** a circular 3-ring puts our member on two links (our in/out edges both resolved in the resource context) and pushes to both neighbours; a pure relay (self not a member) merges + pushes but never promises, votes, or releases.

Every `chipnet-review.md` § Transaction-module-defects row this chain owns is now exercised: the gate-before-hold ordering (`:75-77`), precedence/expiry always refusing (`:151-153,169-171`), no "majority of zero" (`:285-287`), strict-majority-both-ways / even-split (`:285-287`), the circular-lift `:105` case being valid, push-logs-once (`:133-134`), and terms-at-transaction-time handed to the host (`:210-212`). The two preimage/verify defects (`:224,255` and `:159,173` vs `:222,253`) were closed and tested in the core ticket.

## Things to scrutinise (honest gaps & caveats)

- **Multi-node propagation is entirely untested here.** Every test is one node seeing hand-built records. Convergence across a real route — ring/star order, a commit genuinely racing promises between distinct nodes, push fan-out actually reaching quorum — is the next ticket (`3.2-tallynet-consensus`). The out-of-order and push tests simulate *delivery order* at one node; they do not prove graph-wide convergence.
- **Merge order deviates from the ticket prose, on purpose.** The implementation checks **membership → role → already-have-one-from-this-signer → crypto-verify → store**, *not* verify-first. Consequence for the adversarial labels: a type-substituted/forged signature is `forged` **only when it arrives with no prior genuine signature from that member** (fresh → verify runs → fails). A forged relabel arriving *after* the member's genuine signature is reported as `equivocation`/`changed`, not `forged` — the outcome (refuse the second, keep the first, log once) is identical, but the reject *reason* differs. The tests assert the fresh-arrival case; a reviewer may want to confirm the after-genuine case is acceptable as `equivocation`/`changed`. Rationale is in the `mergeSignature` doc comment.
- **Commits are verified lazily and re-verified per classification pass.** `countVerifiedCommits` re-verifies every retained commit on each `getRecordState` call, and `getRecordState` runs in a loop. This is the mechanism that makes out-of-order delivery work (a commit arriving before promises is retained, not rejected, and counted once the promise set fills). It is parked as a **tripwire** `NOTE:` at `countVerifiedCommits` (and a matching one on `canonicalPromiseSet` in `digest.ts`): fine at lift scale (a handful of referees); if referee sets ever grow large, cache verification per `(promise-set, signature)`. Not a defect today.
- **The propagation-timeout seam is a `NOTE:` only.** A stuck commit phase (a tie, or referees yet to vote) stays `propagating` and does **not** settle in-band — v1 has no timer. The seam for a timeout-triggered referee `NC` (void-on-timeout) is marked in `getRecordState`'s `propagating`/tie branch, keyed off `expiresAt(transactionCode)` (no new field). Out of scope here; owned by `feat-tallynet-propagation-timeouts`. The tests assert ties simply do not settle — they do **not** test any eventual timeout resolution (there is none to test yet).
- **`MemoryTrxStore` holds records by reference.** The participant guards this by pushing a frozen per-peer snapshot (`snapshotRecord`) so the unchanged-copy skip compares against a frozen copy, not a live alias — exercised by the suppress/re-push test. A durable store backing this must preserve the same "the participant saves a distinct object per push" contract (documented in `store.ts`).
- **Terms are not interpreted by TallyNet.** `shouldPromise`/`shouldCommit` are the host's hooks; the tests drive them as booleans and never assert on edge terms. Actual terms-matching logic lives in the Taleus host (`taleus-core`), out of scope.
