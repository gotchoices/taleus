half and this test-writing half). The originator `proceed`/`abort` actions themselves were already

## What this ticket added

Six new `it(...)` cases in a new `describe('consensus end to end — originator proceed / abort', ...)`
block in `packages/tallynet/src/testing/consensus.test.ts` (inserted between the existing `buildLift —
routeLinkIds` block and the `determinism` block), plus one new test helper:

- **`handPlan(net, randomSeed)`** — a small helper that hand-builds a `Plan`/`UniQuery` pair over
  `linear(3)`'s P0—P1—P2 graph (edge ids `e0`, `e1`; P2 is `[P,V]`), bypassing discovery entirely. This
  is deliberate: `proceed` never ranks or searches — it only mints the transaction code and folds
  whatever plan it is handed — so a hand-built plan exercises it exactly as a caller handing it
  `discover`'s `plans[0]` would. The full discovery→proceed path is a separate, not-yet-written "Part
  3" of the three-part `tallynet-originator-proceed` work (see below).

The six cases:

1. **`proceed` happy path** — `net.consensusNode('P0').proceed({ plan, query, payload })` on a
   hand-built plan. Asserts the returned record already carries the originator's own `P` signature,
   then drives the clock to idle and asserts every node (`P0`, `P1`, `P2`) settles `commit` and
   releases exactly once (`[true]`), with no pending timers and no delivery errors.
2. **`abort` voids a seeded-but-unpromised record** — builds a record via `net.buildLift(...)` (so its
   `promises` array is empty, as a freshly-discovered-but-not-yet-started lift would be), seeds it
   directly into the originator's store (`net.consensusStoreOf('P0').saveRecord(record)`, bypassing
   `start`/`update`), then calls `abort(tx)`. Asserts every node — **including the originator** — settles
   `void` and releases once as failure (`[false]`), and that the originator's stored record carries its
   own signed `NP`.
3. **`abort` refused once every participant has promised** — runs a normal lift to settlement via
   `runLift`, then calls `abort(tx)` afterward. Asserts it is a true no-op: the stored record's
   `promises` array is byte-for-byte unchanged (no `NP` appended), the outcome is still `commit`, and
   there is no second release.
4. **`abort` refused after our own `P` (atomicity guard)** — `proceed(...)` on a hand-built plan (so the
   originator signs its own `P` immediately), drives to commit, then calls `abort(tx)`. Asserts no-op:
   still `commit`, release count unchanged.
5. **`abort` no-ops on an unknown transaction code** — calls `abort` on a code that was never seeded.
   Asserts nothing was ever released.
6. **`abort` no-ops on an already-settled transaction** — runs a lift to commit, then `abort(tx)`.
   Asserts no second release.

## Why case 2 asserts `[false]` for every node, including the originator (read this before touching `abort`)

`abort`'s implementation (`participant.ts` `TrxParticipant.abort`) signs the originator's own `NP` and
then calls `this.update(record)` — **not** a bare `push`. This was a deliberate design choice already
made in the implement half, not something introduced by these tests, but it is the reason case 2's
assertion looks initially surprising: in the pure-`NP` void case nothing new ever propagates back to the
originator (reachability's echo-suppression means a node's own pushed record never returns to it), so a
bare `push` would leave the **originator never releasing at all**. Routing the signed `NP` through
`update` instead makes the originator release its own (empty) hold as a failure and diffuse the void
**exactly as a refusing participant does** (sign `NP` → classify `rejected` → `releaseOnce(false)` →
push). So in case 2 **every** node — including the one that initiated the abort — releases once as
failure, consistent with the existing refusal tests elsewhere in the same file (a participant that signs
`NP` releases `[false]` even though it held nothing).

## Known gaps / things the reviewer should know

- **No discovery→proceed end-to-end test exists yet.** Every `proceed` test here hands it a
  hand-built `Plan`, never one returned by `discover(...)`. The full "search for a route, then proceed
  with the winning plan" path is explicitly **out of scope** for this ticket and is tracked as "Part 3"
  of the three-part `tallynet-originator-proceed` work (parts 1–2 landed in the two implement halves;
  Part 3 was never filed as its own ticket in this run — a human should decide whether to file it now or
  fold it into whatever picks up ChipNet-style multi-hop discovery testing next).
- **`abort`'s atomicity guard is stricter than the design principle's literal wording.** The design
  principle (docs/design.md § Protocol design) says an abort is valid "before every participant has
  promised." The actual guard is tighter: because `proceed` auto-signs the originator's own `P`
  immediately, a `proceed`-then-`abort` sequence is refused (case 4) even though not every participant
  has promised yet — only the originator has. `abort` is therefore only ever effective on a record that
  was seeded (e.g. via discovery) but never run through `proceed`/`update` for this node. Fully
  reconciling the literal principle with the auto-sign behavior would need either a seed-without-promise
  variant of `proceed`, or an "equivocation voids the lift" merge rule that lets a later `NP` override an
  earlier `P` from the same signer — **both are out of scope here**; the latter would be a
  `tallynet-consensus-participant` change (that ticket's merge rules already landed and were not
  reopened). This is a real, intentional behavior gap versus the principle's wording, not a bug — flagged
  here as a tripwire for anyone later implementing a "cancel this lift" UX on top of `abort` and finding
  it refuses more often than principle 3 alone would suggest.
- **Test coverage floor, not ceiling.** The six cases cover the originator-action surface the ticket
  asked for (`proceed` happy path; `abort`'s four no-op/refusal branches; `abort`'s void-everywhere
  success path). They do not cover `proceed` racing with an incoming peer push for the same
  (not-yet-existing) transaction code, nor `abort` called concurrently with an in-flight `update` for the
  same code — both are covered by the existing module-level re-entrancy caveat already documented on
  `ConsensusNode.update` (`engine.ts`, the "NOTE: `update` is not re-entrancy-safe per node" comment),
  which predates this ticket and was not re-verified here.
