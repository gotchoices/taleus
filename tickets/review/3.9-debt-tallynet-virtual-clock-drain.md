## What changed (and why)

`VirtualClock` (`packages/tallynet/src/testing/clock.ts`) fires simulated timers in `(time, seq)` order and, between fires, waits for the async fallout of the previous fire (a neighbour's `query`, a pushed record's `update`) to finish scheduling its own timers — otherwise virtual time advances out of order.

**Before:** it waited by counting *microtask* hops — it declared the system settled after `DRAIN_QUIET = 64` consecutive microtask hops with no timer activity. 64 was a guess about the longest promise-continuation chain between a fire and the timer that chain schedules. Any chain longer than the guess made the drain quiesce *mid-chain*; the outer loop saw an empty-looking heap, declared the run idle, and the timer the still-running chain was about to schedule was orphaned and never fired — a wrong result with **no error**. (This exact failure bit discovery once before, fixed by bumping 16 → 64; a future longer chain would reintroduce it.)

**After:** the drain turns the event loop one **macrotask** at a time. The JS event loop fully drains the microtask queue before any macrotask runs, so **one** macrotask hop flushes a microtask continuation cascade of *any* length. Counting quiescence in macrotask hops (`DRAIN_QUIET = 2`, a true constant now) is immune to chain length — the guess, and the silent-drop with it, are gone.

Key implementation points a reviewer should check:

- **Macrotask primitive = `MessageChannel.postMessage`.** `setTimeout` is forbidden in `testing/clock.ts` (the port-neutrality guard `no-node-globals.test.ts` allowlists timer globals only for the real-time `src/clock.ts`). `MessageChannel` is cross-platform (Node ≥15, browsers, Hermes/RN) and not on the guard's forbidden list. It is declared module-locally (`declare const MessageChannel`), mirroring how `src/clock.ts` declares `setTimeout`, so the neutral `types: []` build (which has neither DOM nor Node libs) still compiles. The guard test still passes unchanged.
- **No `unref()` — close-on-idle instead.** The fix ticket suggested `unref()` *or* close. `unref` was tried and is **wrong here**: while a drain's macrotask is the only pending work, an unref'd port lets Node's event loop go empty and exit *before* the macrotask runs, leaving the awaited promise forever unsettled (reproduced in a standalone prototype — the run aborted with "unsettled top-level await"). Instead the channel is created lazily and **closed when the clock goes idle** (`closeChannel`, in a `finally` around both `advance` and `runUntilIdle`). Verified: all three suites exit cleanly with `--detectOpenHandles`, no "worker failed to exit gracefully".
- **`pending` counter deleted.** The old code tracked async timer-callback promises (the consensus `update` case) so the drain wouldn't quiesce mid-`update`. With macrotask draining this is unnecessary: `update` arms no timer mid-flight (it's pure microtasks + synchronous ed25519), so one macrotask flush drains the whole chain including the onward pushes it schedules at its very end. `fire` is now just `this.mutations++; void timer.fn()`. **Confirmed safe by running the full consensus suite green** (including the slow-link "sleeping node" and pre-promise-pool cases, which are the ones that stress async-callback settling). `network.ts:makeUpdatePeer` still *returns* the `update` promise with its old comment referencing the removed mechanism — the return is now harmless (ignored), but see Known gaps.
- **Loud overrun guard added (Option 2 defense-in-depth).** After the fire loop goes idle, `assertDrained` does one more macrotask hop and throws if any timer was scheduled by a late continuation. With the macrotask drain this never trips; it converts the old *silent* drop into a loud throw if the invariant were ever violated. All 822 tests across the three packages pass without tripping it.

## How to validate / exercise

Run from the package dir with the ESM flag jest needs: `NODE_OPTIONS=--experimental-vm-modules npx jest` (or `yarn test`).

- **Regression test (the headline):** `src/testing/clock.test.ts` → `describe('VirtualClock long-continuation-chain drain')`. A timer whose callback schedules the *next* timer only after N detached `await Promise.resolve()` hops, parametrized N ∈ {8, 64, 200, 2000}. **All four pass now; N=200 and N=2000 fail on the old clock** (second timer silently dropped, `pendingTimers` stuck at 1). This is the floor — a reviewer could add N=10000, or a cascade that mixes `setTimer` + `clearTimer`, or a callback that awaits a real macrotask (see gaps).
- **Consensus (the `pending`-removal proof):** `src/testing/consensus.test.ts` — 26 end-to-end cases (linear/ring/diamond routes, refusals, slow links, adversarial signatures, pre-promise pool). Determinism case asserts byte-identical trace streams across two runs.
- **Discovery + scale:** `src/testing/discovery.test.ts` (maxDepth-boundary and multi-hundred-node graphs) — the subsystem the original silent bug under-reported reach in.
- **Concurrent == sequential byte-identical invariant:** `packages/tallysim/src/sim/sim-runner.test.ts` — "stays byte-identical under concurrency" guard sweep + the real-latency case. Both pass (the drain change doesn't affect fire ordering, which is heap-determined).
- **Port-neutrality guard:** `src/no-node-globals.test.ts` — confirms the new `MessageChannel` use isn't a neutrality violation.

### Performance — measured, no material regression

The drain runs after every fire. An isolated micro-benchmark (20k fires, 20-hop cascade each) shows the macrotask drain ~43% slower than the old 64-microtask drain in isolation (221 vs 154 ms) — but that isolates the bare drain. On the **real** clock-heavy suite (discovery + consensus + network, 46 tests), warm-run wall-clock is a wash: new ~4.29 s vs old ~4.31 s (same tests, old clock swapped in from HEAD via read-only `git show`, restored after). Real fires do far more work (ed25519, validation, large-heap ops) than the micro-benchmark's bare cascade, so the drain is a small slice. **Conclusion: plain macrotask drain kept; the hybrid fallback the fix ticket described was not needed.**

## Known gaps / what to scrutinize (reviewer: treat tests as a floor)

- **`network.ts:makeUpdatePeer` stale comment.** The delivery-timer callback (`network.ts` ~line 465-480) still *returns* `update(...).then(...)` and its comment still says "The callback RETURNS the receiver's `update` promise so the VirtualClock tracks it in flight". That tracking (`pending`) is **gone**; the returned promise is now ignored by `fire`. Behaviour is correct (the `.then(ok, err→deliveryErrors)` still runs as a microtask the drain flushes), but the comment is now misleading and the explicit `return` is dead. I left the code untouched to keep the diff to clock.ts; a reviewer may want to simplify the callback to `void` and fix the comment. Low risk, cosmetic.
- **Rejection handling changed (tripwire, tagged `NOTE:` at `fire`).** The old `pending` path swallowed a rejecting async callback (`.then(settle, settle)`); the new `void timer.fn()` matches `realClock` and lets a rejection surface as an unhandled rejection. No callback rejects uncaught today (the network push catches into `deliveryErrors`; discovery callbacks return void), so no test observes it. If a future async timer callback can reject without catching, add a `.catch` at the `fire` site. Parked as a code `NOTE:`, not a ticket.
- **The "pure microtasks" assumption for async callbacks is load-bearing but untested in isolation.** The whole `pending`-removal rests on consensus `update` never awaiting a *real* macrotask (only microtasks). It's true today (in-memory store, synchronous crypto) and the consensus suite passes, but there's no *direct* test of "async timer callback that awaits a macrotask still settles before the next fire." The macrotask drain tolerates such a callback (it's just another mutation source that must quiesce) **as long as** the callback's macrotask work finishes within the drain's hops — `DRAIN_QUIET=2` plus `MAX_DRAIN` give slack, but a callback chaining many real-macrotask awaits is unexercised. If a future store/port does real-macrotask I/O behind a timer callback, add a test like the long-chain one but with `await macrotaskHop()` in place of `await Promise.resolve()`.
- **`MAX_DRAIN = 100_000` is now macrotask hops, not microtask hops.** Kept as the runaway valve. It should never trip (normal drains finish in ~3 hops), but if it ever did, 100k real event-loop turns is slow — the outer `maxSteps` guard catches the common runaway (self-rescheduling timer) first, so this is a backstop only.
- **`advance`'s overrun guard vs intentionally-pending timers.** `assertDrained` checks "no *new* mutation on one more hop", not "heap empty" — so `advance(partialWindow)` that deliberately leaves out-of-window timers (e.g. the "sleeping node" test's `advance(SLOW_MS/5)`) passes it correctly. Confirmed by those tests, but it's the subtle case to re-check if the guard is ever tightened.
