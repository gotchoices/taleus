## What this change did

Half A (`tallysim-harness-knobs`) had removed the simulator's manual `recoverStrandedByPull` pass and left
`LiftResult.pullCalls` / `LiftResult.recovered` returning hard-coded `0` so the build stayed green. This change:

- **Removed** `pullCalls` and `recovered` from the `LiftResult` interface and the `runLiftForOutcome` return
  object (`consensus-harness.ts`). They are no longer sourced from simulator bookkeeping.
- **Re-homed** the two counters onto the protocol's own trace events in `analyzeLift` (`consensus-metrics.ts`):
  - `pullMessages` now counts `record-pulled` events (the protocol's recovery-loop pulls).
  - `recovered` is now a per-lift **0/1** flag: `1` iff the lift **settled** (`commit`|`void`) **and** emitted
    ≥1 `record-pulled` **or** `recovery-tick`. `recoveredTotal = Σ recovered` = "settled lifts that needed the
    recovery loop".
- **Added two new measurements:**
  - `creditHeldMs?` (per lift) = span from the **first** `promise-signed` carrying a `P` signature (an `NP`
    holds nothing) to the **last** `resources-released`; omitted when either endpoint is absent. Aggregated as
    `creditHeldMsPerLift: DistributionSummary` over the defined values only.
  - `permanentlyPending` (per lift `boolean`) = `outcome === 'pending'` **and** no `resources-released` seen.
    Aggregated as `permanentlyPendingCount` (Σ) and `permanentlyPendingFraction` (`count / liftCount`, **0 not
    NaN** at 0 lifts).
- **Appended** three CSV columns after `planRefusalShare`, in order: `...creditHeldMsPerLift.*`,
  `permanentlyPendingCount`, `permanentlyPendingFraction` (`serialize-consensus-records.ts`). No existing column
  moved.
- **Did NOT touch** `participant.ts` / the void-reason precedence: a deadline timeout void surfaces as a
  `voter-vote` `NC` (the engine never emits `signature-rejected` `expired`), which the existing precedence
  already maps to `'voted-no-commit'`. Proved with a unit test, not a code change.
- **Did NOT change** `timeToSettleMs` logic or name (a deadline-void is already a `void` ⇒ already gets a span).
  Doc comment updated to say the distribution now includes timeout-driven settlements; proved with a hand trace.
- Updated `packages/tallysim/docs/design.md` (the serialiser column-order list, the voter-model "New metrics"
  bullet, and the § *Consensus metrics* descriptions of `analyzeLift` / `summarizeConsensusMetrics`).

## Test cases a reviewer should exercise / scrutinise

**Pure-function tests (the floor — all hand-built traces) in `consensus-metrics.test.ts`:**
- Deadline-void trace (`record-pushed` → `promise-signed P` → `voter-vote NC` → `settled void` →
  `resources-released`) ⇒ `voidReason === 'voted-no-commit'` and a **finite** `timeToSettleMs` (not Infinity).
- `record-pulled` count ⇒ `pullMessages`.
- `recovered` 0/1: settled + `record-pulled` ⇒ 1; settled + `recovery-tick`-only ⇒ 1 (tick is not a pull, so
  `pullMessages` stays 0); settled + no activity ⇒ 0; pending + activity ⇒ 0 (never settled).
- `creditHeldMs`: first-`P`-promise → last-release span; omitted when no release; omitted when only `NP`.
- `permanentlyPending`: pending + no release ⇒ true; pending + release ⇒ false; any settled ⇒ false.
- `summarizeConsensusMetrics`: `creditHeldMsPerLift` distributes defined spans only; `permanentlyPendingCount`
  sums; `permanentlyPendingFraction` is `count/liftCount`; the **0-lift guard** gives 0 (not NaN) for the
  fraction and `count: 0` for the distribution.

**Serialiser tests in `serialize-consensus-records.test.ts`:** JSONL round-trip carries the three new fields;
CSV emits the three new columns in appended order after `planRefusalShare`; a new column-order test asserts
`planRefusalShare < creditHeldMsPerLift.count < permanentlyPendingCount < permanentlyPendingFraction`.

**Real-engine tests that now exercise the re-homed counters:**
- `consensus-runner.test.ts` principle-3 completion curve — **two assertions changed** (see "Known gaps" §1).
- `voter-harness.test.ts` / `consensus-harness.test.ts` — the `result.recovered` / `result.pullCalls`

## Known gaps / things to scrutinise (handoff is honest — treat tests as a floor)

1. **`recovered` semantics changed meaning, and `recoveredTotal` no longer separates "healed" from "failed".**
   Old (manual pull): "members moved off `pending`". New (decision 2): **"the recovery loop ran"** — keyed on a
   `record-pulled`/`recovery-tick`, regardless of whether it actually healed anyone. Consequence: in
   `consensus-runner.test.ts`, **both** the with-contact-points and without-contact-points drop-sweeps now
   report `recoveredTotal > 0` (the loop runs in both; it only *succeeds* with a contact point). I changed those
   two assertions from `=== 0` to: with-contact cell-0 `=== 0` (no non-relayer ⇒ clean commits, loop never
   runs) and cell-1/6 `> 0`; without-contact `> 0`. **The real success differentiator is now
   `cooperatingCompletion` (1.0 healed vs. <1.0 failed), which both tests already assert.** A reviewer should
   confirm this 0/1 "loop ran" semantic is what decision 2 intended (it matches the ticket's decision log
   verbatim) and that leaning on `cooperatingCompletion` for success is acceptable. I used `toBeGreaterThan(0)`
   rather than hard-coding the empirical `7` because the exact count is a workload-seed detail, not the property
   under test — a reviewer who prefers the pinned exact value can tighten it (it is deterministic at 7).

2. **The two NEW per-lift metrics (`creditHeldMs`, `permanentlyPending`) are ASSERTED only against hand-built
   traces, never against a real runner sweep.** They *are* computed on every lift in the real
   `consensus-runner.test.ts` runs (so they can't throw), but nothing asserts their values there. The engine
   genuinely emits `resources-released` after `settled` for every settling node
   (`tallynet/src/consensus/participant.ts:872`, `releaseOnce`, once-per-node, both commit and void), so
   `creditHeldMs` **will** populate on real runs — but there is no end-to-end assertion locking that in. Highest
   value add for a reviewer: a runner-level assertion that `creditHeldMsPerLift.count > 0` on a committing sweep,
   so a future engine change that stops emitting `resources-released` can't silently zero the metric.

3. **`permanentlyPending` is keyed on the LIFT's outcome, not on stranded members.** In the
   no-contact-point drop-sweep the lift *outcome* is `commit` (the sole-voter originator commits) even though
   members 3 and 4 stay stuck — so `permanentlyPending` is **false** there. It captures "the whole lift never
   resolved", which is distinct from "some member was stranded" (that is `cooperatingCompletion`). This is per
   decision 4 and is intentional, but a reviewer expecting `permanentlyPendingCount > 0` in that sweep would be
   surprised. A scenario that produces a genuinely `pending` lift (e.g. the voter-set-tie or raised-threshold
   cases in `voter-harness.test.ts`) is where `permanentlyPending` would light up — none of those currently
   assert it.

4. **`creditHeldMs` guard `lastRelease >= firstCreditPromise`** is defensive (releases follow promises, so it
   holds in practice); it documents intent and avoids a negative span on an out-of-order trace. No test forces
   an out-of-order trace, so that guard branch is uncovered — acceptable, but noted.
