## What changed

In `TrxParticipant.validateAndMerge` (`packages/tallynet/src/consensus/participant.ts`), right after the existing `saveRecord`/`savePendingCommits` persistence block and before the `record-received` trace emit, added:

```ts
if (fromAddress) {
	await this.store.savePeerRecord(merged.transactionCode, fromAddress.key, snapshotRecord(merged))
}
```

This primes the push skip-test (`push`, same file) with the **merged** record (what we now hold), not the raw incoming one — ChipNet primed with the raw incoming record and even left itself a `TODO` worrying about staleness; saving the merged snapshot avoids that problem entirely. `snapshotRecord` is the existing module-local helper already used by `push` to freeze a copy before `savePeerRecord`.

Effect: when `push` later walks reachable peers for this transaction, the peer we just received from already has a matching peer-record on file, so the content-equality check skips pushing back to them — unless our own state has since advanced (promise/commit added), in which case the live record differs from the saved snapshot and the push correctly goes out.

`packages/tallynet/src/consensus/store.ts` was not touched — `savePeerRecord`'s existing shape was already correct for this call; it was only in the ticket's `files:` list for docstring cross-reference.

Doc update: `packages/tallynet/docs/chipnet-review.md`, the "Inbound peer-record save" row in the § Regression check consensus table, verdict changed from `**regression** (minor; bug-tallynet-push-echo-suppression)` to `kept`. (Left the adjacent "Invalid-record logging" row's regression note untouched — it references the same ticket slug but covers a separate, still-unaddressed logging gap not in this ticket's scope.)

## Test coverage added

New test in `packages/tallynet/src/consensus/participant.test.ts`, in the `describe('TrxParticipant — reachability and push', ...)` block, right before the "logs once and emits ok:false when a push fails" test:

`'suppresses the echo back to the peer we just received from, but still forwards onward and re-pushes once content changes'`

Drives a relay node (alice ↔ bob tally link, relay not a member) through two `update` calls:
1. `update(record+aliceP, fromAddress: alice)` → asserts pushes go only to `[bob.key]` (no echo to alice).
2. `update(record+aliceP+bobP, fromAddress: bob)` → asserts pushes become `[bob.key, alice.key]` (bob's own content stays suppressed since we just got it from bob; alice's stored copy is now stale from step 1, so she gets re-pushed).

This exercises both the no-echo case and the correctly-resumed-push case in one flow, confirming the fix doesn't just go silent permanently.

I manually verified (before adding the real test) that with only the test added and the fix *not yet* applied, the first assertion fails — `pushes` after the first `update` is `[alice.key, bob.key]` (echo present) — confirming the test actually reproduces the bug. After the fix, it passes.
