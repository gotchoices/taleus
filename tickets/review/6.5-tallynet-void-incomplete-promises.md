## What this change does (plain language)

A **lift** moves value around a chain/cycle of two-party credit relationships (tallies). Each party on the
route first **promises** (reserves credit), then **voters** vote commit/void to settle it atomically. Before
this change, if a party died *before* promising, the promise set never completed, no vote was ever cast, and
**every party who already promised held that credit forever** — the lift sat `pending` with no way out.

After this change: as long as a **voter is reachable**, that voter votes `NC` (no-commit) at its own deadline
**even on an incomplete promise set**, so a void majority settles the lift and everyone releases. The *only*
case that still stays stuck `pending` is a **dead voter** — a voter majority that never hears the record (so no
reachable voter can ever produce a void vote).

The pending-vs-void split therefore moved from *"did the promise phase complete?"* to *"is a voter reachable?"*.

### Judgment call for fix #3 (reviewer: please sanity-check this reasoning)

The sim runner's voter model is **self-voting**: every lift's voter set defaults to `[route[0]]` (the
originator), and there is **no runner knob to make a different node the voter**. The originator is always
reachable, so under the new protocol a sleeping-*target* lift's incomplete set is **always voided** by the
originator at its deadline — the runner **structurally cannot** produce a dead-voter pending. I confirmed this
empirically with a throwaway probe: the scenario now yields `liftCount 9, commitCount 6, voidCount 3,
voidReasons['voted-no-commit'] 3, pendingCount 0`.

So I re-characterized the test from "stays pending (stalled)" to "voids by the reachable voter deadline
(voted-no-commit)". This is the honest reflection of the new protocol *and* arguably the better end-to-end proof
of this ticket's value (the runner demonstrating the self-void is exactly the improvement). The alternative —
adding a `voter = payee` knob to the runner to keep a pending scenario — is real scope creep for a test fixture;
I did not do it. **Dead-voter pending is still covered** at the harness level (`runPermanentlyStuck`, now
`voters:[1]`) and the summarizer level (the combined-metrics test + `consensus-metrics` unit tests). The
reviewer should confirm they agree losing *runner-level* pending coverage is acceptable (see review findings).
