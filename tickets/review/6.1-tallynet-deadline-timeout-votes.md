## What was built (in one breath)

TallyNet consensus had **no timer**: a fully-promised lift whose voters never finished (a silent voter,
an even-split tie, a dropped commit push) sat in the `propagating` state forever, every participant's
reserved credit held. This change gives each node a **one-shot deadline timer**. When the lift's
transaction code expires (it already self-expires — no new field on the record), an un-voted voter is
driven to vote **void** (`NC`) through the engine's existing expired-code path, so a voter majority
(commit *or* void) is always eventually reached and every hold releases.

Seven planning decisions, now built (full prose in `docs/design.md` § Lift proposal and settlement):

1. **The deadline is the transaction code's own expiry** — a single lift-wide instant, no new field.
   The originator may size it via an optional `ttlMs` on `UniQuery` (and `proceed` mints from
   `args.ttlMs ?? args.query.ttlMs ?? DEFAULT_TTL`, clamped to the session-code TTL ceiling).
2. **One deadline, not per-phase.** What a node does at the deadline is structural, not temporal.
3. **Void-on-timeout is a *voter* `NC`, commit-phase only** — reuses `castCommit`'s `anyCodeExpired → NC`.
4. **No pre-promise-void timer** — a participant promises synchronously on first sight; the
   `anyCodeExpired → NP` path already covers an expired record held at wake-from-sleep.
5. **No unilateral void from silence** — a node concludes void only on evidence (`NP` or `NC` majority);
   a participant waiting past the deadline stays `pending`, it does not self-void.
6. **Trust only our own clock** — the timer fires at `expiresAt + SKEW_GRACE_MS` judged against our clock.
7. **Ring/star convergence not adopted** — push-to-reachable + contact points + the pull already suffice.

Plus a **promise pre-gate** (decision 1's node-side check): a node signs `NP` when
`expiresAt(transactionCode) - now < minPromiseMarginMs`, so a slow promise phase that would leave the
voters no time to vote voids cleanly instead of stranding credit. `minPromiseMarginMs` (default 30_000)
and `skewGraceMs` (default 5_000) are per-node config on `TrxParticipantConfig` / `ConsensusNodeDeps`
(principle 0: the protocol enforces the check; each node picks its own value). `SKEW_GRACE_MS <
MIN_PROMISE_MARGIN_MS` by design, so a node that *did* promise still has margin to vote before its own
void timer fires.

## The two subtle points the reviewer should kick hardest

1. **The re-arm infinite-loop hazard (and why it can't trip).** The virtual clock advances `now` to each
   timer's fire time, so a deadline timer firing at `expiresAt + grace` makes the code expired *at fire
   time*. If `onDeadline → push → neighbour update` then re-armed a timer while `now >= expiry`, the delay
   would be 0 and it would fire again immediately → push → … → `runUntilIdle` throws at MAX_STEPS. The
   guard is in `scheduleDeadlineTick`: **it does not arm when `now >= expiry`.** Combined with `push`'s
   existing skip-test (an unchanged record is never re-pushed to a peer whose last-acked copy matches), a
   post-expiry `onDeadline` push delivers nothing new, no node re-arms, and the heap drains. **Verify
   this holds** against every stall test — the end-to-end suite asserts `pendingTimers === 0` everywhere.
2. **Determinism is preserved.** Commit/void runs settle *before* the deadline instant, so every node
   clears its timer before it could fire — no `deadline-reached` events, no extra fires, byte-identical
   trace streams across seeded runs (the determinism test still passes). Arm/clear emit no trace.

## Use cases to validate (the tests, as a floor)

Unit (`participant.test.ts`, `describe('TrxParticipant — deadline timer')`):
- (a) **core new behaviour** — an un-voted voter over a complete-promise set is driven to `NC` on the
  deadline → void (seeded store; see "Known gaps" for why seeded).
- (b) a voter that already voted `C` **no-ops** on the deadline (no equivocation, no second face).
- (c) a promised-and-waiting participant arms a timer (delay = `LONG_TTL + SKEW_GRACE_MS`) and no-ops when
  it fires (can't `NP` over its own `P`).
- (d) arms on a non-terminal record, clears on a terminal one in a single update.
- (e) leaks no timer across settle or abort.
- (f) `onDeadline` is a safe no-op on an unknown / released / non-member transaction.
- (g) the promise pre-gate signs `NP` when too little of the window remains (short `ttlMs`, still valid).

End-to-end (`testing/consensus.test.ts`, `describe('consensus end to end — settling by deadline')`):
- A promise phase that only completes **after** the code expires voids the whole route. Graph `A—B` (ab
  latency 400_000) and `A—V` (instant, V the sole voter). A promises@0, B's promise lands@400_000, the
  completed set returns to A@800_000 (past the 600_000 expiry), A re-pushes to V, and V's
  completing-promise update at 800_000 casts `NC` via `castCommit`'s expired path → whole route voids.
  (Keep the ab latency 400_000 **exactly**: 2× = 800_000 > 600_000 so the set lands post-expiry, yet a
  single 400_000 hop leaves B's promise margin 200_000 ≥ 30_000.)

Also updated the stale comment on the dropped-push stall test (the deadline timer now *does* arm and

## Known gaps — a real coverage seam, stated honestly

**`onDeadline`'s own voter-`NC` branch is unreachable through normal network delivery**, so it is covered
**only at the unit level** (test (a), by seeding the store). Reason: `advanceState`'s `ourCommitNeeded`
case votes *synchronously* inside the same `update` that completes the promise phase, so a voter is never
left holding a complete promise set un-voted when a delivery arrives. The end-to-end "settling by
deadline" test therefore exercises **deadline-driven void**, but the `NC` is cast through `castCommit`'s
expired path on a late delivery — `onDeadline` fires a no-op first. A true `onDeadline`-drives-`NC`
end-to-end test needs a new harness knob (a voter held back from voting until the deadline); that is
**deferred to `tallysim-timeout-scenarios` (6.3)**. Do not read the e2e test as proving the
`onDeadline`-`NC` path over the wire — it does not, by construction.

Other things a reviewer might probe:
- Timers are **in-memory only**. A node that restarts mid-lift re-arms only when the next delivery
  re-adopts the record. Documented as a seam in `design.md`; durable-timer recovery is out of scope here.
- The pre-gate reads `expiresAt(record.transactionCode)` directly; it is reached only after
  `anyCodeExpired` returned false, so the code is well-formed and `expiresAt` cannot throw. Confirm that
  ordering invariant still holds if `promiseDecision` is ever refactored.
- A tie of voters that have **all** already voted still cannot settle (an even split satisfies neither
  side) — unchanged, documented limit; `tallynet-stalled-recovery` (6.2) owns the periodic re-push/pull
  retry that a genuinely stalled transaction needs.
