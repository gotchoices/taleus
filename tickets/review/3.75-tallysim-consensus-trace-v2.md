## What this ticket built

A simulated payment run can now be recorded with its **consensus phase**, not just its route-discovery
phase, and replayed byte-for-byte. The on-disk trace format went from version 1 to version 2.

Why a version bump was needed: a consensus trace event names its nodes by **member key** (an ed25519
public key), not by the simulator's integer entity id, and the route a payment actually took is **not**
reconstructable from the discovery event stream. So each settled lift's route + a member-key→entity-id map
must travel in the trace **header** (one new optional field, `lifts`). A new header field is a format
envelope change, hence the bump. Events themselves did not change (the event type union already covered
consensus), so only the header moved.

### The changes, concretely

- **`trace-format.ts`** — `TRACE_FORMAT_VERSION = 2`; new `TraceLiftEntry` interface
  (`sessionCode`, `transactionCode`, `route`, `tallyPath`, `memberKeys`, `amount`); `TraceHeader` gains an
  optional `lifts?: TraceLiftEntry[]`; `buildTraceHeader` stamps `lifts` **only when present** (so a
  discovery-only header stays byte-identical to a v1 header but for the version field); `parseTrace` now
  accepts versions `{1, 2}` and rejects anything else naming found-vs-supported. The module header's
  versioning note was corrected (it previously said consensus needs no bump — true for events, false for
  this header field).
- **`cli/trace.ts` `recordTrace`** — when `scenario.consensus` is present, each query's **lift** is driven
  to settlement in both recording passes and a `TraceLiftEntry` is recorded per found/recorded query. When
  `scenario.consensus` is absent the path is unchanged (byte-identical to before, bar the version field).
  The sibling `cli/simulate.ts --trace` reuses `recordTrace`, so it picks this up for free (covered by a
  test; no code change there).
- **`consensus-runner.ts`** — extracted `consensusConfigFor(scenario, network, runSeed)` (identity seed +
  refuser resource port) and had the metrics runner call it, so the runner and the trace recorder derive
  the **same** identities + refusers for a given `(scenario, runSeed)`. Pure refactor; the runner's output
  is identical (its pinned tests still pass).

### The deliberate design choice to scrutinise

The consensus trace **does not model capacity depletion**, on purpose, and this is the crux of the design
— verify the reasoning holds:

- It builds **one** consensus sim per recording pass (not one per query like the metrics sweep). That keeps
  session + transaction codes minting on a single incrementing RNG, so they stay **unique across the whole
  pass** — which the viewer relies on to join events to queries by code. Rebuilding per query (as the
  metrics sweep does) would reset the session-code RNG and mint duplicate codes, breaking that join.
- Because the sim is built once, its link capacities are frozen at the initial network; each lift's balance
  move is therefore discarded against a fresh `cloneNetwork` copy, and the recorded network snapshot stays
  the pristine initial network (the viewer replays from it).
- This means the trace (no depletion, one sim) and the consensus **metrics** sweep
  (`sim/consensus-runner.ts` — depletion, rebuild per query) are each internally deterministic but need
  **not** agree with each other. That is the same situation the existing discovery trace already has versus
  the discovery sweep (they seed differently). Both are correct; they answer different questions.

### Test coverage added (treat as a floor)

- **`trace-format.test.ts`** — a v2 header with `lifts` round-trips (deep-equal); a v2 discovery-only header
  omits the `lifts` key entirely (not an empty array); a hand-made v1 file still parses with `lifts`
  absent; an unsupported version (3) is rejected naming found-vs-supported (`(this build reads 1, 2)`).
- **`cli/trace.test.ts`** — a `consensus: {}` scenario records one `lifts` entry per found recorded query
  with `route`/`tallyPath`/`memberKeys` populated and each lift joining back to a header query + its
  consensus events (by `transactionCode`); the whole trace is **byte-identical across two runs**; with
  `--query 0`, both the recorded lifts and every recorded event belong to the one selected session; a
  discovery-only scenario records **no** `lifts` and the header omits the field.

### Things a reviewer should poke at (honest gaps)

- **Determinism across the two passes rests on the shared resource port being behaviourally stateless.**
  `consensusConfigFor` is called once and its `resourceFor` port is reused across pass 1 and pass 2; its
  handles accumulate observations but the promise/commit **gates** are pure functions of the spec. I argue
  this makes the two passes identical — confirm there is no path where accumulated handle state changes a
  decision (if there were, the byte-identical test would already fail, but the invariant is worth an eye).
- **Byte-identity is only asserted on the small 3-entity line scenario.** The two-run determinism test is
  the real guard; a larger/failure-injected scenario (e.g. `consensus: { refuserFraction: ... }`) is not
  exercised by a trace test. The consensus harness/runner tests cover refuser/pending/circular outcomes
  directly, but driving a *trace* through a void/pending lift is untested here — a lift that voids or stalls
  still records a `TraceLiftEntry` (it found a route; `outcome` is not stored on the entry), which is the
  intended behaviour but worth a confirming read.
- **Docs not updated.** `docs/design.md § Trace & replay format` still describes the v1 shape; I updated the
  authoritative module-header doc in `trace-format.ts` but did not touch `docs/design.md`. A one-line doc
  sync (v2 adds the header `lifts` field) is a reasonable inline fix for the reviewer, or a small follow-up.
- **Viewer not run (out of scope).** `tallysim-viewer` consumes `TraceHeader`; the new `lifts` field is
  additive and the viewer currently ignores it (it does not yet *place* consensus events using `lifts` —
  that is future viewer work, consuming the field). The viewer's tests reference `TRACE_FORMAT_VERSION`
  symbolically, so they should be unaffected, but I did not run `yarn workspace tallysim-viewer test` /
  `build`; CI or the reviewer should confirm the sibling workspace still builds against the bumped format.

### Tripwire recorded (not a ticket)

- `NOTE:` in `cli/trace.ts` `recordLift` — it clones the whole network per lift so the throwaway balance
  move never touches the snapshot. Fine for planned trace sizes; if a traced scenario ever has very many
  queries over a huge network, reuse one scratch clone across lifts (reset balances per lift) instead of
  one clone each.
