## What this ticket resolved

The prior `fix/`-stage investigation (see git history on `tallysim-sim-runner-concurrent-divergence`) found
that `sim-runner.ts`'s two query-scheduling modes — `sequential` (default: one query at a time) and
`concurrent` (`SimRunnerDeps.concurrent: true`: issue every query, settle once) — no longer diverge on
`roundsUsed`/timing the way they once did. That divergence was traced to a since-fixed `tallynet`
`VirtualClock` bug (`DRAIN_QUIET` too small), already resolved by the separate `tallynet-discovery-depth-reach`
ticket. This implement-stage pass:

- Replaced the "empirical / may re-diverge" hedging language in `sim-runner.ts` (module header + the
  `runProtocolQueries` NOTE) with the actual reason the two modes agree: an **arm-order invariant**. Within
  one search, a round's outbound delivery timers are armed (`issueBatch`) before that round's budget timer
  (`budgetedStep`, in `tallynet`'s `discovery/participant.ts` `reenter`); an answer-delivery back to a node is
  always caused *after* that node armed its own budget. The `VirtualClock`'s tie-break is insertion-order
  `seq` (`tallynet/src/testing/clock.ts`), and inserting other sessions' timers into the global `seq` stream
  in concurrent mode cannot invert the relative order of one session's own two timers — so an exact
  budget/delivery tie resolves identically in both modes. No per-node queueing/contention in the model means
  this is sufficient, not just necessary.
- Updated the matching test comments in `sim-runner.test.ts`.
- Added a new parameterized guard test (`it.each`, in the `'runSimSweep — concurrent and sequential agree,
  both deterministic'` describe block) that sweeps 12 configs — `line(5)`, `line(7)`, a new `ring(6)` helper,
  crossed with no-latency / exact budget-tie latencies (`2000`, `1750`, `2500` ms — chosen to land exactly on
  the round-0 budget and the 2-hop round-1/round-2 budget boundaries) / two uniform latency ranges, several
  with `lateFraction`/`lateLatencyMs`/`dropFraction` layered on to exercise the late-answer-fold path — and
  asserts `JSON.stringify(concurrent) === JSON.stringify(sequential)` for each. Runs in ~1s; a failure names
  the diverging config via the `%s` test-name interpolation.
- Updated `docs/design.md` § *The discovery sweep runner* to state the invariant and drop the "open call"
  framing — `concurrent` is explicitly kept (equivalent, and a touch faster).
- Confirmed `cli/simulate.ts --concurrent` needed no change: it's a plain passthrough to
  `SimRunnerDeps.concurrent` with no refusal logic, and none of the checked-in sweeps
  (`tallysim-discovery-metrics-io`, `tallysim-discovery-metrics-experiment`, both already in `complete/`) use
  `--concurrent` — they ran on default sequential, so no published number was ever at risk.

**No behavioural change** to `sim-runner.ts` itself — this ticket is documentation + a regression guard, not
a code fix.

## For the reviewer

- **Check the invariant argument, not just that tests pass.** The claim in the module header (and repeated in
  `docs/design.md`) is a structural argument about arm order, not an empirical "we swept N configs and they
  matched." If you can think of an engine change that would violate "round's own delivery timer armed before
  that round's own budget timer" or "an answer-delivery is always caused-after the receiving node's own
  budget arm," that is exactly the kind of change the guard test is meant to catch — worth trying to construct
  a counterexample.
- **The guard test's config list is representative, not exhaustive.** It was scaled down from a ~24-config
  sweep used during the fix-stage investigation (which included seeds 1–5) to keep runtime to ~1s per the
  ticket's "dozen-ish configs" guidance. If you want more confidence, the fix-stage sweep description (now
  only in git history / the deleted ticket body) listed the fuller cross-product — can be resurrected from
  commit `195318a` (`ticket(fix): tallysim-sim-runner-concurrent-divergence`) if ever needed.
- **No code path changed in `sim-runner.ts` beyond comments** — `git diff` on that file is header-text only;
  worth a quick visual confirmation that no stray logic edit snuck in alongside the doc rewrite.
- `cli/simulate.ts`, `harness.ts`, and the `tallynet` files (`testing/clock.ts`, `discovery/participant.ts`,
  `discovery/originator.ts`) were read for verification only — no edits, by design (the fix is documentation
  + a test, the production code already behaves per the invariant).
