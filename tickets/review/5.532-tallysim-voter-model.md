# What landed

Second (final) ticket of the `tallysim-voter-model` split. The sibling `tallysim-voter-model-core` had already
landed the straight-line completion curve (non-relayers, contact points, cooperating-member completion + pull
metrics, CSV, linear runner threading). **This ticket added the remaining voter-model dimensions** to the
sequential consensus sweep runner and documented the whole model. All work is **implemented, built, and
tested** — `yarn build`, `yarn test` (423 passing across 34 suites), and root `yarn lint` are all green, and
the full-repo `yarn build` (incl. tallysim-viewer) passes.

## The four dimensions (what each does, where it lives)

1. **Loop-route (circular) payments** — `ConsensusSpec.routeShape: 'linear' | 'circular'` (default `'linear'`).
   A circular run draws **one origin per query** (`drawCircularOrigins`, origin-then-amount, mirroring the
   linear pair-then-amount draw), mints a real session code via a self-query, then builds the **shortest
   simple cycle** through the origin straight from the graph (`buildCircularOutcome`, pre-existing) and lifts
   that. This is the **clearing-discovery stand-in** (real clearing discovery is `feat-tallysim-clearing-discovery`).
   Runner path: `runOne` picks the draw by shape; `resolveOutcome(sim, network, query, routeShape)` dispatches
   linear discovery vs. circular self-query + ring build; a circular origin on no cycle yields no lift.

2. **Nominated vouchers** — `voterNomination: 'self' | 'well-known'` + `wellKnownFraction`. `'self'` is the
   implicit default (voter-set-of-one, no wiring). `'well-known'` derives the top-degree hub set
   (`wellKnownEntities`), nominates the one hub as an off-route `[V]` referee (`makeNomineesFor`), and scores
   plans voter-aware (`voterAwareScorePlan`). **Well-known is measured from graph degree, not a model flag** —
   the deliberate departure from the original `5.5` sketch (a flag would perturb the pinned discovery sweep).

3. **Padded-voter (stacked) rejection** — `stackedVoters: number`. When `> 0`, every node staples that many
   obscure referees onto every plan it folds into (`stackingNegotiateFor` → `stackedVoterMembers`), and the
   originator's scorer (`countingRefusalScorer`) **drops** any stacked plan (`-Infinity`, which the originator's
   `rankPlans` filters) and counts it. Measured at the **discovery scorer**, not the promise-time
   `acceptsProposal` gate — see the composition-gap gotcha below.

4. **Raised agreement threshold** — `consensusMethod?: ConsensusMethod` threaded onto `buildLift` via a new
   `RunLiftOptions.consensusMethod` (omitted ⇒ `buildLift`'s own `1/2` default, byte-identical). A raised
   threshold (e.g. `2/3`) can leave a split voter set settling **nowhere** (`pending`).

New metrics: `ConsensusRunMetrics.planRefusalCount` + `planRefusalShare` (`= count / queryCount`, 0-guarded),
emitted as the last two CSV columns after `pullMessagesPerLift.*`. `summarizeConsensusMetrics` gained an
optional 4th arg (`planRefusalCount = 0`). `cloneConsensus` now deep-clones the one nested knob (`consensusMethod`).

## Use cases to test / validate / exercise

- **Circular no-cliff** (`consensus-runner.test.ts`): `ring(6)`, `routeShape:'circular'`, `contactPoints:false`,
  sweep `nonRelayerFraction ∈ {0, 1/6}` ⇒ `cooperatingCompletion === 1` in both cells (the ring pushes both
  ways around the interior non-relayer; nobody stranded, `recoveredTotal === 0`). The test **re-derives** the
  pinned non-relayer (node 3) and the drawn origins in-test and asserts they are disjoint, because a
  non-relayer that is itself the sole-voter originator serves no pushes/pulls and would strand its own ring
  (outside the claim). **The workload seed (20) was tuned so origins {1,2,4,5} avoid node 3** — if the
  conditions compiler's pick ever moves, the in-test disjointness assertion fails loudly (tune the seed).
- **Stacked refused** (`consensus-runner.test.ts`): `line(5)`, `stackedVoters:2` ⇒ `planRefusalCount > 0`,
  `planRefusalShare > 0`, `liftCount === 0`, `commitCount === 0` (every route's only plan is refused).
- **Threshold 2/3** (`voter-harness.test.ts`): `line(5)`, `q {0→4}`, voters `[0,1,2,3,4]`, nodes 3+4 vote NC.
  At `1/2` ⇒ `commit` (3 votes, 3·2=6>5); at `2/3` ⇒ `pending` (3·3=9 ≥ 2·5=10 false; void side 2·2=4>5 false).
  Also asserts the 2/3 run's push count `>=` the 1/2 run's (held).
- **Determinism** (`consensus-runner.test.ts`): a `ring(6)` run with **every** knob set at once
  (`circular` + `well-known` nomination + `wellKnownFraction 0.3` + `stackedVoters 2` + `consensusMethod 2/3`)
  replays byte-for-byte (`expect(a).toEqual(b)`), exercising `cloneConsensus`'s method deep-clone and all wiring.
- **CSV columns** (`serialize-consensus-records.test.ts`): `planRefusalCount`/`planRefusalShare` appear last,
  after `pullMessagesPerLift.*`, in canonical order.

## Known gaps / honest caveats (please scrutinise)

- **On-route silent-drop (the composition gap).** Nominated/stapled referees reach the **discovery** layer only
  — `liftMembers` builds the lift record's members purely from route + voters and never reads `plan.members`.
  So: (a) `well-known` nomination of a node **on the money path** silently drops that referee vote (the hub is
  often on-path); (b) stacked-voter refusal **must** be measured at the discovery scorer (done), because the
  promise-time gate never sees the padding. Both are documented inline (`well-known.ts`, `consensus-runner.ts`)
  and in the doc's *Voter model* subsection. The clean fix (mark on-path participants `[P,V]` directly) is
  `backlog/debt-voter-nomination-on-path-composition` — **not** in scope here; this ticket works within the gap.

- **DEVIATION from the ticket plan: the staple is applied on ALL nodes, not even-id only.** The ticket specified
  an even-id staple with the rationale "every line route spans consecutive integers so always contains an even
  node ⇒ every route stapled." **That premise is wrong for single-hop routes from an odd origin to an even
  payee**: the payee is reached by peer-match and never runs its `negotiatePlan`, so such a route's only even
  node (the payee) never staples and the lift escapes refusal (observed: `liftCount` was 2, not 0). Stapling on
  every node closes the hole deterministically (the originator always processes its own plan). This is a
  **maximal-padding** model (a length-L route accrues L·count referees) — documented in a block comment on
  `stackingNegotiateFor`. Worth a reviewer's eye: confirm you agree all-nodes is the right call vs. a narrower
  subset that still covers single-hop origins.

- **Trace CLI does not drive circular route shape.** `cli/trace.ts` always `drawPaymentQueries` (linear only);
  `routeShape:'circular'` is sweep-only this ticket. The stacked/nomination/method wiring still rides through
  `consensusConfigFor`, so a *linear* consensus trace replays its discovery identically. Deferred alongside
  real clearing discovery. Noted in the doc's Trace & replay section.

- **Circular test seed fragility.** The no-cliff test's green depends on `workload.seed 20` keeping node 3 out
  of the drawn origins. The in-test disjointness assertion guards this (it fails loudly, not silently), but a
  reviewer re-tuning network/conditions seeds should expect to re-pick it.

- **Threshold message-count assertion direction.** The `2/3 messages >= 1/2 messages` assertion was unverified
  in the plan; it **held** empirically. If a future engine change flips it, relax to `> 0` on both — the
  load-bearing assertions are the `commit` vs `pending` outcomes.
