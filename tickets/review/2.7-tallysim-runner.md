# Review: tallysim experiment runner + CLI + first experiment

Final ticket of the tallysim **network-model tier** (after `tallysim-model-generators` and `tallysim-oracle`).
It turned the seeded generators + whole-graph oracle into a usable experiment harness and produced the tier's
first checked-in result. The downstream plan ticket `tallysim-discovery` and the backlog item
`feat-tallysim-trading-model` build on the sweep runner and the "step the economy" seam delivered here.

**This review is a code-review pass over already-written, already-green code.** Build, lint, and the full test
suite pass; the experiment data is committed and reproduces byte-identically. Treat the tests as a *floor*,
not a finish line — see **Known gaps** below for where to push.

## What was built (and what the reviewer is checking)

The runner platform core, metrics, serialisers, scenario/sweep model, economy seam, and the Node-only CLI were
built and verified by a prior run (Phases 1–2). **This run added the CLI smoke test, the first experiment, and
the docs (Phases 3–4).** The whole thing now hangs together end to end.

Pipeline, in one breath: a `SweepSpec` (JSON) describes a base scenario + the parameter(s) to vary + the seeds
to repeat over → `runSweep` (a streaming generator, `src/runner.ts`) materialises each network, draws a seeded
workload, runs the oracle per query, aggregates pure metrics (`src/metrics.ts`), and yields one `RunRecord` per
cell × seed → serialisers (`src/serialize-records.ts`) turn records into JSON-lines + a CSV summary → the
Node-only CLI (`src/cli/sweep.ts`) streams them to files.

### Core design points to verify

- **Three independent seed streams** per run (network / workload / economy), each offset by the run seed.
  Determinism is load-bearing and tested: a sweep run twice is byte-identical (`runner.test.ts`,
  `serialize-records.test.ts`, and the CLI smoke test).
- **Browser-safety of the core.** Only `src/cli/**` may touch `node:*`; the `no-node-globals` guard
  (`src/no-node-globals.test.ts`) scans the core and passes. The viewer tier (`tallysim-viewer`) depends on
  this staying true. The CLI is kept off the neutral `tsconfig.build.json` and compiled with node types by
  `tsconfig.cli.json`.
- **Max-flow is opt-in and sampled** (`workload.metrics` must list `'max-flow'`), because Edmonds–Karp is
  costly; default off. Route-existence (BFS) runs on every query.
- **Degenerate inputs guarded**: P over zero trials is 0, never NaN; a distribution over zero samples reports
  `count: 0`. Tested on empty/isolated/single-entity networks.
- **The economy seam** (`EconomyStep` + `noOpEconomyStep`) is a documented no-op hook for
  `feat-tallysim-trading-model`; a materialised network is returned **by reference** today (NOTE in
  `runner.ts`) — fine while the step never mutates, but a future mutating trading model must clone per run.

## How to validate (concrete)

- **Gates**: `yarn workspace tallysim build && yarn workspace tallysim lint && yarn workspace tallysim test`
  (162 tests, all pass). Root `yarn build` is clean (topological).
- **Run a sweep by hand**:
  `yarn workspace tallysim sweep packages/tallysim/experiments/route-existence/specs/uniform-unlimited.json --jsonl /tmp/x.jsonl --csv /tmp/x.csv`
  — JSON-lines stream (one record per `(cell × seed)`), CSV summary one row per run.
- **Reproduce the experiment**: `packages/tallysim/experiments/route-existence/regenerate.sh` rebuilds and
  regenerates `out/*.{jsonl,csv}` + the combined `route-existence.jsonl` (594 records) **byte-identically**.
  Confirmed in this run via a copy-then-diff after a fresh build.
- **Sanity-check the finding against the data**: the finding recorded in `docs/design.md` § Runner /
  experiments → *First experiment* is derived from the committed CSVs. Key claims to spot-check against
  `out/*.csv`:
  - uniform `largestComponentFraction` turns up at mean degree ≈ 1 (0.05→0.57→0.80→0.94 at degree 1→1.5→2→3);
  - depth-bounded `pRouteExists` turns up along `degree^D ≈ N` (e.g. N=10000: D=4 at degree≈10, D=6 near 4–6,
    D=8 near 3–4);
  - realistic (lognormal) capacity shifts the route curve up vs unlimited at matched (N,D,degree) while leaving
    `largestComponentFraction` unchanged;
  - scale-free is always one component (`largestComponentFraction`=1) and routes at far lower mean degree than
    uniform because hubs keep paths short (~4 hops at N=10000 vs ~5.4 for uniform).

## Known gaps (push here — tests are a floor)

- **Metric cross-checks lean on pair-independent topologies.** `runner.test.ts` cross-checks metrics against
  the oracle mostly on networks where every pair behaves the same (complete / isolated), because the runner
  draws *random* `(X, Y)` pairs. A stronger check would pin a non-trivial materialised topology and assert the
  runner's aggregated `pRouteExists` / path-length matches an independent per-pair oracle computation over the
  *same* drawn pairs. Worth adding if the reviewer wants confidence beyond the degenerate cases.
- **Experiment is route-existence (payment) only.** The clearing workload and max-flow sampling are implemented
  and unit-tested, but no checked-in *experiment* exercises them. A clearing-availability experiment is natural
  follow-on work (belongs to a future ticket, not this review).
- **Spec files carry a `_note` human-comment field** that the runner silently ignores (lenient JSON parsing —
  `runSweep` reads only `base`/`vary`/`seeds`). Intentional and harmless, but flagged so it isn't mistaken for
  a parsed field.
- **Cross-engine determinism of lognormal capacity.** The realistic specs use `lognormal` (Box–Muller →
  `Math.exp/log/cos`), whose last-ULP results are not guaranteed bit-identical across JS engines (pre-existing
  NOTE in `distributions.ts`). The committed artifact was generated under Node; `regenerate.sh` reproduces it
  byte-identically *within one engine*. If the browser viewer ever regenerates these specs and must match the
  committed bytes, prefer an integer capacity distribution or pin the generating platform. Not a defect — a
  documented tripwire.
