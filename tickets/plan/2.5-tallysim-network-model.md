## Why

The central research question for Taleus: **how complex must a tally network become before lift payments become statistically likely?** Two separate questions hide inside it:

1. **Does a route exist?** A question about the graph: its size, how many tallies each entity holds, how they cluster, and how much credit capacity each tally has in each direction.
2. **Does TallyNet find it?** A question about the protocol: depth limit, time budget, latency, sleeping nodes.

This ticket answers (1) with an **oracle**: code that sees the whole graph and searches it directly. Ticket `tallysim-discovery` then runs the real protocol on the same graphs and measures (2) as "found vs. oracle". Keeping the two apart is the point: when a lift fails, it tells you whether the network or the protocol was the cause.

Prior art: MyCHIPs ran a full-stack simulation (databases, docker, servers; `../../mc/mychips/doc/sim-*.md`, `test/sim/`). It worked, but was heavy and slow to iterate. `tallysim` runs in one process, seeded and deterministic, with no I/O in the core, so it runs in Node and in the browser (the viewer, `tallysim-viewer`, will run simulations live in a page).

## Scope

New workspace package `packages/tallysim` (unscoped name `tallysim`, conventions as `packages/tallynet`: ESM, strict TS, tabs, jest, platform-neutral, no Node globals in `src/`). Depends on `tallynet` only (for its `RandomSource` port and, later, its engines and `tallynet/testing` harness); never on `taleus-core`.

- **Network model.** Entities (nodes) and tallies (edges). A tally joins two entities and has, per direction, the credit capacity a lift can use (derived from a balance and the two sides' credit limits, as MyCHIPs' lift capacity is; see `docs/architecture.md` on tallies and lifts). Keep the model plain serialisable data (JSON), so a scenario can be saved, shared and replayed.
- **Seeded generators**, each with documented parameters:
  - uniform random (Erdős–Rényi style, by mean tallies per entity);
  - scale-free (preferential attachment: a few hubs, many small entities);
  - clustered communities with a tunable number of bridge tallies between them (geography, industries);
  - small-world (ring lattice + rewiring).
  Plus capacity / balance distributions per tally. One seeded PRNG module (small, inlined, documented algorithm) used everywhere; same seed, same network.
- **Oracle.** For a payment of amount A from X to Y with max depth D: does a path exist with capacity ≥ A in the lift direction (bounded-depth search), and its shortest length. Also max-flow X→Y (useful to see how much is payable, not just whether), and for clearing: how many directed cycles with spare capacity pass through a node, up to depth D. Name the algorithms in the design doc; keep each one a small, tested function.
- **Experiment runner.** A scenario = generator + parameters + seed + a query workload (random pairs, amounts). A sweep varies one or two parameters over ranges and repeats over seeds. Output: one JSON-lines record per run (parameters, seed, metrics) plus a CSV summary. A small CLI (`yarn workspace tallysim sweep <spec.json>`) drives it; the CLI is the only Node-specific file and lives outside the platform-neutral `src/` core (or behind a separate entry), so the core still runs in a browser.
- **Metrics (oracle level):** P(route exists) vs. parameters, path length distribution, max-flow distribution, fraction of entities in the largest connected component, cycle availability for clearing.
- **First experiment, checked in** (`packages/tallysim/experiments/`): P(route exists) against mean tallies per entity, for N ∈ {100, 1,000, 10,000}, D ∈ {4, 6, 8}, uniform and scale-free, unlimited capacity and then realistic capacity. Record the result briefly in the design doc (not a summary doc): where the curve turns up, and how capacity limits move it. Rough expectation to check against: route existence takes off once the mean degree passes ~1 (giant component); with depth limit D you need roughly degree^D ≳ N; capacity limits push both up.
- **Docs.** `packages/tallysim/README.md` and `packages/tallysim/docs/design.md` (the canonical simulator design: tiers, model, generators, oracle, metrics, trace and replay format to come). Add the package to `docs/index.md` and the package list in `AGENTS.md`.

## Design points to settle in this plan

- Capacity model: exactly how per-direction capacity derives from balance and limits, and which way a lift moves it. Keep it close to MyCHIPs; write it down.
- Whether scenarios store the materialised graph or only (generator, params, seed). Recommend: both are valid inputs; the runner materialises.
- Performance target: 10,000 entities × mean degree 10, 1,000 oracle queries in seconds, not minutes. Pick data structures accordingly (adjacency arrays, typed arrays if needed).
- How a later trading model (backlog `feat-tallysim-trading-model`) plugs in: it will evolve balances between lift attempts. Leave the seam (a "step the economy" hook) without building it.

## Edge cases & interactions

- Self-payment (X = Y) is a circular lift: the oracle looks for a cycle, not a zero-length path.
- Disconnected graphs, isolated entities, duplicate tallies between the same pair (allowed: two tallies are two edges), zero-capacity directions.
- Generators at extreme parameters (mean degree 0, complete graph, one community).
- Determinism across platforms: no `Math.random`, no iteration over unordered keys deciding results.

## Tests to plan

- Each generator: seeded reproducibility, parameter fidelity within tolerance (measured mean degree, community structure), no self-loops unless asked for.
- Oracle against brute force on small graphs (exhaustive enumeration ≤ 10 nodes); capacity respected; depth respected.
- Runner: a tiny sweep produces the expected record shape and is identical across two runs with the same seed.
