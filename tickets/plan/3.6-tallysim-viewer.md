The developer wants to *see* a test network: entities as nodes, tallies as edges, a lift query lighting up the graph as it propagates, and a found lift circuit shown clearly. `tallysim` (core) produces networks, runs the real TallyNet engine on simulated time and records versioned traces (`packages/tallysim/docs/design.md` § trace format). This package is the visual front end. It is a development tool, not part of `web/`; it may be published to the web later, so keep it a static build with no server.

## Scope

New workspace package `packages/tallysim-viewer`, depending on `tallysim`. A static single-page app.

- **Graph view.** Force-directed layout of entities and tallies that stays usable at thousands of nodes. Edge styling shows capacity per direction (thickness / colour, arrowheads for the lift direction). Zoom, pan, hover for an entity's or tally's details, search for an entity.
- **Query animation.** Replay a trace on a timeline: play / pause / speed / scrub. Nodes and edges light up as a query reaches them, round by round (colour by depth or round), pruned branches fade with the prune reason on hover, sleeping / late nodes are visibly distinct.
- **Found routes.** Each plan found is shown as a highlighted path (a circular lift as a closed loop); list the plans with their length and terms; selecting one isolates it in the graph.
- **Two sources.** Load a trace file, or run a simulation live in the page (tallysim's core is platform-neutral): pick a generator, parameters and seed, a payer and payee (click two nodes), and run.
- **Sweeps.** Load a sweep's output (JSON lines / CSV from the tallysim CLI) and plot metric vs. parameter, one line per series (e.g. P(found) and P(exists) vs. mean tallies per entity).

## Design points to settle in this plan

- **Stack.** Recommended default: Vite + TypeScript, rendering with sigma.js on graphology (WebGL, built for large graphs), a lightweight chart library for sweeps. Evaluate cytoscape.js and d3-force against the thousands-of-nodes target; pick one, document why. Avoid a heavy UI framework unless the controls need it; if one is used, keep it small.
- Layout for large graphs: run it in a worker or precompute it, so the page stays responsive; keep the layout stable across replays of the same network (seeded).
- Running a live simulation off the main thread (web worker), streaming trace events to the view.
- Accessibility basics: colour scales that work for colour-blind viewers, light and dark themes.

## Edge cases & interactions

- A trace with an unknown or newer format version is rejected with a clear message.
- Very large traces: load and index incrementally; scrubbing stays responsive.
- Multiple concurrent queries in one trace: choose one to show, or colour by session.
- Empty result (no route) is shown as such, distinct from "still searching".

## Tests to plan

- Trace loading / indexing and the timeline state model are plain TS modules with unit tests (no browser needed).
- A build check in `yarn build`; a smoke test that renders a small trace headlessly if the stack allows it cheaply.
