After `tallynet-consensus`, TallyNet can drive a found route to commit or void, emitting consensus `TraceEvent`s through the same `TraceSink` and pushing records over the `tallynet/testing` harness (see `tallynet-consensus` § Simulation readiness). This ticket adds that phase to the simulator and viewer.

## Scope

- **Simulator.** After discovery, the originator picks a plan (simple, documented policy: shortest, or first found) and runs consensus over it on simulated time. Referee: the originator's own referee by default (one referee), with a scenario option for referee sets. A successful lift moves each tally's balance along the route in the network model, so the next query sees the changed capacity.
- **Failure injection:** a participant that refuses to promise, a node that sleeps mid-transaction, a dropped push, a slow referee. Each shows up in the trace and metrics.
- **Metrics:** P(commit | route found), time to settle, messages per lift, void reasons.
- **Viewer.** The chosen route animates through its phases: promises arriving per edge, the referee's vote, then commit (route turns solid) or void (route flashes and clears). The trace format gets the new events; bump its version and keep reading older traces.

## Edge cases & interactions

- Circular lift (originator on two links) animates as a closed loop and settles once.
- A void after some promises: every held resource is released, and the trace shows it.
- A run with several lifts in sequence: balances change between them, deterministically under the seed.

## Tests to plan

- Seeded scenarios with known outcomes (all-cooperative commits; one refuser voids); conservation: every committed lift leaves each intermediary's net position unchanged (what it gains on one tally it gives on the other).
- Determinism of the full discovery + consensus trace.
